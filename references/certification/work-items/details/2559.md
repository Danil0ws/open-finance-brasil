#### Current Behavior:

---

In the test scenario `payroll-credit-portability_api_invalid-consent_test-module_v1`, the client is sending the `loans` and `payroll-credit-portability` scopes to the `/par` endpoint. Because of that, we end up returning `200` instead of `403`.

#### Expected Behavior:

---

The those scopes are **not** sent in this scenario, so the request would be correctly blocked and we would return `403`.

Olá @WandembegSilvaOpf. Respondendo aos pontos levantados:

**1 e 2 - É correto enviar scope no /par? Ele deve ser ignorado?**

Sim, enviar o scope no /par é correto. O /par carrega os mesmos parâmetros de uma authorization request, incluindo scope (RFC 9126 e RFC 6749). O scope também não é "ignorado": ele é processado pelo Authorization Server, que pode conceder ou reduzir conforme sua política. O perfil de segurança do Open Finance Brasil também esclarece que o AS não deve rejeitar um pedido apenas por conter scopes além do necessário, podendo reduzir o escopo concedido ao suficiente (OFB Financial-grade API Security Profile v2.1.0).

No caso da Payroll Credit Portability, os endpoints que envolvem consentimento do usuário utilizam `OAuth2AuthorizationCodeLoans` (`loans`, `openId`, `consent:consentId`), enquanto endpoints como GET /portabilities/{portabilityId} utilizam `OAuth2ClientCredentials` com o scope `payroll-credit-portability`. São fluxos distintos, com tokens obtidos de forma separada.

A presença de `payroll-credit-portability` no /par deste cenário não é um erro e também não bloqueia o sucesso no teste: como mencionado acima, espera-se que o AS reduza o escopo concedido ao suficiente, desde que haja os escopos mínimos na requisição.

---

**3 - Quais permissions estão associadas aos scopes credit-portability e payroll-credit-portability?**

Este é o ponto central. O endpoint GET /credit-operations/{contractId}/portability-eligibility deve ser autorizado com base nos escopos mínimos descritos no item 2 e também nas **permissions de LOANS presentes no consentimento**. A spec de Payroll Credit Portability define:

> "Os endpoints \[GET\] /credit-operations/{contractId}/portability-eligibility e \[POST\] /portabilities devem utilizar o escopo authorization_code para validar a permissions de LOANS" (Payroll Credit Portability v1.0.0-beta.2)

Por isso o Resource Server deve validar as permissions de LOANS no `consentId` referenciado de forma independente.

Isso é consistente com a Loans API: _"as permissions necessárias deverão ter sido solicitadas quando da criação do consentimento relacionado (consentId)"_ (Loans API v2.5.0).

---

**Conclusão**

Se o token contém corretamente os scopes mínimos, mas o consentimento referenciado não contém permissions de LOANS, a chamada para `/portability-eligibility` deve retornar 403, independentemente de haver scopes adicionais no access token. Esse é o ajuste necessário para passar nesta etapa do teste.

Hello, @matheus-mantovani,

We understand that the consent does not include the permissions related to portability, and therefore a 403 should have been returned. However, the scope associated with the permission was sent in the **/par** endpoint during the authorization process, which caused the consent to receive authorization to execute the operation.

Our question is whether this scope being sent in **/par** is correct, and if so, whether we should consider only the permissions explicitly included in the consent.
We would also like to know which permissions are associated with **payroll-credit-portability** and **credit-portability**, as this is not clearly documented — the documentation lists the scopes, but not the permissions themselves.

From our understanding, including the scope in the **/par** request is incorrect for the **payroll-credit-portability** test scenario, as the scope should not be present.
For example, the test credit-portability_api_invalid-consent_test-module_v1 (https://web.conformance.directory.openbankingbrasil.org.br/log-detail.html?log=htB9xUlOUkjG8cr&public=true) does not send any portability-related scope when generating the authorization token, as shown in the screenshot below:

![image](/uploads/27f5bef7884efbe902b4ce25098fc963/image.png){width=900 height=466}

However, the test payroll-credit-portability_api_invalid-consent_test-module_v1, which should behave equivalently, does send the scope:

![image](/uploads/ec44b8540fa0e5ecf416d7bee30d0927/image.png){width=900 height=462}

To summarize our questions:

Is it correct to send the scope in the **/par** endpoint during the authorization step? If so, should the requested scope be ignored?
What are the permissions associated with the **credit-portability** and **payroll-credit-portability** scopes?

The test summary says:

• Call GET /credit-operations/{contractId}/portability-eligibility endpoint sending:\
• Authorization = token linked to the consent with customer permissions\
• Expect a 403 - Validate error message

Using your log as reference, that's why the test, in this step, calls the GET /portability-eligibility using a token with:

`"scope": "payroll-credit-portability loans openid resources openid consent:urn:bancodobrasil:9FD12A2211044D7EA29D9615EB20E5F0"`

This consentId is linked to a previous consent that has customer permissions. 

![image.png](/uploads/fdb27247f19397067a1c17185d227b5b/image.png){width=285 height=455}

You can confirm the correct permissions by checking the first consent: `urn:bancodobrasil:FDE5E246D1334BF7923754450C011084` .

To pass this step, your implementation should validate the permissions granted to the referenced consentId and reject the request accordingly (returning 403, as expected by the test).
