## 1. What Happened and what were you expecting?
According to [Swagger spec](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/18055346/Informa+es+T+cnicas+-+Pagamentos+-+v2.0.0), date validations should be threat as below:

**1.3.2.2 Data de pagamento: Valida se a data de pagamento enviada é válida para a forma de pagamento selecionada (DATA_PAGAMENTO_INVALIDA);**

As the parameters payment.schedule and payment.date are *mutually exclusive* they should not exist in the request (business rule here).
Once they exist mutually, the validation code returned should be DATA_PAGAMENTO_INVALIDA as we are validating dates into the payment payload. 
Besides, the **schedule** and **date** attributes are not part of the **details** object.

According to Swagger specification the only two possible error codes for date validations and HTTP 422 are:

**1.3.1.1 Envio de campos obrigatórios: Valida se todos os campos obrigatórios são informados(PARAMETRO_NAO_INFORMADO)**
This should happen when date attributes are not sent on the payment payload. Date assume a mandatory role in certain scenarios.

or either

**1.3.2.2 Data de pagamento: Valida se a data de pagamento enviada é válida para a forma de pagamento selecionada (DATA_PAGAMENTO_INVALIDA)**
This should happen when business rules based on dates are validated.

Both messages should be valid.

If the date attributes were within the details object, it would make sense to have DETALHE_PAGAMENTO_INVALIDO as error message, but as it is a **date business rule validation** it should follow date specific messages like 'DATA_PAGAMENTO_INVALIDA' to make it easier to understand the behavior of the API or yet the 'PARAMETRO_NAO_INFORMADO' message because the behavior of the attribute assuming a mandatory role in the test being executed..
