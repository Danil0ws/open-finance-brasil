## 📝 Descrição

Prezados, boa tarde,

Durante a execução do cenário "enrollments_api_rejected-postauthorisation-enrollment_test-module_v2", o fluxo da Jornada sem redirecionamento segue até que o enrollment atinja o status "AWAITING_ENROLLMENT" (com token de authorization_code emitido). Em seguida, esse enrollment é cancelado/rejeitado manualmente, e, ao prosseguir com o fluxo, enviando a requisição de fido-registration-options, é esperado o retorno 422 com o código de erro "STATUS_VINCULO_INVALIDO".

Entendemos que este comportamento é baseado no trecho da especificação de segurança que menciona: “Para tokens gerados com o scope: payments ou recurring-payments, o status do consentimento não será validado”; porém, o trecho refere-se especificamente ao status do consentimento e não ao status do enrollment. Poderiam nos indicar onde, na documentação regulatória, há orientação de que o status do enrollment deva ser desconsiderado pela camada de segurança?

Além disso, no caso de considerarmos o trecho citado como aplicável tanto para consents quanto para enrollments, não deveríamos também aplicar o seguinte requisito: “deve revogar os refresh tokens e, quando aplicável, os access tokens quando o Consentimento (Consent Resource) relacionado for apagado”, nos casos de rejeição e revogação de consentimentos e enrollments? 

Nesse caso, sempre teríamos o retorno 401, para situações de rejeição/revogação, barrando o processo ainda na camada de segurança.

### Comentário 9
**Autor**: Christian Eloysio (@christianraidiam)
**Criado em**: 01/11/2024, 19:23:50
**Atualizado em**: 07/11/2024, 14:02:19

Hi Rafael, thanks for the ticket!

We understand that this part of the [security specification](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/245760001/EN+Open+Finance+Brasil+Financial-grade+API+Security+Profile+1.0+Implementers+Draft+3#7.2.2.-Authorization-server) is unclear:

> "Access to resources shall only be shared when presented with an access_token linked to an active consent with the status 'AUTHORISED.' For tokens generated with the scope: payments or recurring-payments, the consent status will not be validated."

In our understanding, the phrase "share access to resources" refers only to granting access to endpoints that transition the object consent to the AUTHORISED state or beyond within the API flow. Before this point, no user-related data—whether for payments or data sharing—should be accessible. By all means, in indeed only mentions consents, and not enrollments, which would not be covered by this claim.

Consequently, we understand that this test, which involves a request to the `POST fido-registration-options` endpoint, should not fall under this rule and would therefore not require validation in the security layer. As such, a 422 response would be expected from the test.

This part of specification was initially added to cover idempotency scenarios for the Payments API, where consent is moved to REVOKED after the POST Payment Call. In this context, any idempotent calls are blocked at the security layer, preventing the expected response. However, for enrollment endpoints, idempotency is already supported by design. This is because enrollment status only changes after authorization via a `PATCH Enrollments` call. Outside of this, the enrollment remains in the AUTHORISED state, so idempotent calls are not blocked by the security layer.

Regarding the following specification:

> "Shall revoke refresh tokens and access tokens where applicable when the linked Consent Resource is deleted;"

We also interpret this as applying to Consents only—not Enrollments—as is stated in the specification. Consequently, when a request is made to `POST fido-registration-options` after a `PATCH Enrollments` action, the access token linked to the consent should still be valid, with a 422 expected from the business layer as per the test module’s requirements.

That said, we believe there may be a security gap in the specification, which currently reference only the consent object, without addressing enrollment-specific distinctions. Since the access tokens and refresh tokens are not revoked after the enrollment in which they are linked is revoked, It does not clearly state that Enrollments with REVOKED status should be restricted from accessing the `POST fido-sign-options` and `POST Consents AUTHORISED` endpoints, even though this is being tested in the `enrollments_api_revoked-enrollment_test-module_v2` of API Certification. While the Enrollments API mentions a `STATUS_CONSENTIMENTO_INVALIDO` status for cases where “status do consentimento não permite autorização,” it is not specified which status permits access to these endpoints. We understand that this is partially addressed in the sequence diagram but not explicitly clarified in the specification.

To clarify, we would like the **working group’s feedback on the following questions**:

1. Is our understanding as outlined above correct?
2. Would refresh_tokens issue from the Enrollments Authorization Code flow not be revoked after an enrollment is also revoked, meaning that everything would be blocked at the business layer?
3. Given this, should we document that `POST fido-sign-options` and `POST Consents AUTHORISED` endpoints are only accessible with a an Enrollment in AUTHORISED status?

For this case in specific, our view is that this is not a huge concern, but we do strongly recommend a review of the security specifications, which currently reference only the consent object, without addressing enrollment-specific distinctions, which could bring technical and legal implications. 

One example where this applies is that, given that enrollments and consents are objects apart, any claim stated at [7.2.2. Authorization server](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/245760001/EN+Open+Finance+Brasil+Financial-grade+API+Security+Profile+1.0+Implementers+Draft+3#7.2.2.-Authorization-server) would not be required by the Auth Server, for example:

* shall retain a complete audit history of the **_consent_ resource** in accordance with current Central Bank brazilian regulation;
* shall return authentication failure and return code \_accessdenied in the error parameter (as specified in section 4.1.2.1 of [RFC6749](https://tools.ietf.org/html/rfc6749 "https://tools.ietf.org/html/rfc6749")) if the CPF of the authenticated user is not the same as indicated in the loggedUser element of the **_Consent Resource Object_;**
* shall return authentication failure and return code \_accessdenied in the error parameter (as specified in section 4.1.2.1 of [RFC6749](https://tools.ietf.org/html/rfc6749 "https://tools.ietf.org/html/rfc6749")) if the businessEntity element has not been populated in the related **Consent Resource Object** and the user has selected or authenticated by using a credential related to a business account;
* an autenticated or selected business account's CNPJ must match the value present in the businessEntity element of the **Consent Resource Object**. In case of divergence authorization server shall return authentication failure and return code _access_denied_ in the error parameter (as specified in section 4.1.2.1 of [RFC6749](https://tools.ietf.org/html/rfc6749 "https://tools.ietf.org/html/rfc6749"));
* shall ensure _refresh_token_ expiration time is at least equal to the linked **consent resource** expiration time.

The _consent_ word is mentioned 34 times in the security documentation, and the _enrollments_ is not mentioned once - even with them having a pretty similar structure. We understand that the specification should be reviewer and clarified where consent is interchangeble with enrollments, and where is not. We are at the disposal to help the Working Group in solving this problem in the best solution.
