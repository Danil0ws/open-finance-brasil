## 📝 Descrição

## 1. What Happened and what were you expecting?
The engine is requiring ASPSP (Detentoras de Contas) to perform webhook retry attempts for errors that return 503 from PISP's (ITP's).

There is no mention of HTTP Status 503 code return in the Webhook API Swagger (https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/125370456/Informa+es+T+techniques+-+Webhook+-+v1.0.0-beta.3) and nothing in this swagger describing that the ASPSP's must implement the retry mechanism (And it doesn't even make sense... Webhook availability is an PISP obligation, not the ASPSP's).

There is also no such requirement for a replay mechanism in the Webhook Convention documentation (https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/105021661/Conven+the+of+Webhook).

In the General Information documentation, in the topic "In case of notification failure" (https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/125370456/Informa+es+T+T+techniques+-+Webhook+-+v1.0.0-beta.3), there is a mention that ITP may perform pooling if it has not received notification via webhook, and since the unavailability came from PISP, it should perform pooling.

We need to ensure that tests for undefined requirements are not implemented in the compliance engine, as this impacts implementations across the ecosystem, even more so with such tight deadlines to adjust. We cannot let requirements be defined by tests, they have to be defined as a specification (by going back to specification, with proper communications to the ecosystem and rephrasing of deadlines).

If this unspecified requirement for playback mechanisms is in fact mandatory, we will have an impact that will not allow us to meet the regulatory dates.

The right thing to do is for the engine to observe the returns provided for in Swagger (which is what serves as a guide for the ecosystem), eliminating the 503 code response, as well as removing the retry test in the scenario "dcr_api_dcm-pagto-remove-webhook_test-module": 
      •Return a 503 - Validate the contents of the incoming message, including the presence of the x-webhook-interaction-id header and that the timestamp value is within now and the start of the test
      •Expect an incoming message, for at most 60 seconds, which must be mtls protected, to be received on the webhook endpoint set for this test

Hi Rogerio! We totally agree that any behavior should be defined by the Conformance Suite, but this behavior is actually defined at https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/146669587/Informa+es+Gerais+-+Webhook+-+v1.0.0-rc.2#Em-caso-de-falha-de-notifica%C3%A7%C3%A3o, which specified that:

**Detentora**

A detentora de conta fará no máximo 3 tentativas de notificação:

* A primeira tentativa de notificação do evento, pela detentora de conta, deverá ocorrer em até 1,5 segundo após o evento;
* A segunda e a terceira tentativas só ocorrerão em caso de falha;

Therefore, the conformance suite is compliant to specifications. We are happy to help with any additional needs!
