@alinnezanin and @marcelino.junior thanks for raising this issue.

Per the test module summary, this is an **auxiliary** flow that: (1) approves a consent and (2) **makes two payments with the information specified in the configuration.**

Given that behavior, the configuration sets the same date for “payment 1” and “payment 2”, and the module will **intentionally create two payments on the same date**. This does not represent two different cycles, it’s executing the two configured payment calls for data/validation purposes.

On the other hand, as mentioned in #2350, the current behavior does not align with the expected rule for the paymentReference generation in the first cycle of recurring payments. Action we’re taking: we’ll adjust the second payment’s paymentReference to point to the **current cycle’s start** (not the next cycle), while keeping the auxiliary module behavior (two payments as configured) unchanged.

This, however, is **not blocking for the retry test executions**, since the auxiliary test plan is not mandatory. You may also generate the payloads independently, as shown in the [Wiki](https://gitlab.com/raidiam-conformance/open-finance/certification/-/wikis/Phase-3-Automatic-Payments-Tests).
