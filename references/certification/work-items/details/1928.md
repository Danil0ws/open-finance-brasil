## 📝 Descrição

The `automatic-payments_api_automatic-pix-wrong-creditor_test-module` currently assumes that after a failed `firstPayment`, the consent should transition to the `CONSUMED` state. However, as defined in the [Open Finance Brasildocumentation](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/718405726/M+quina+de+Estados+-+v2.0.0-beta.2+-+SV+Pagamentos+Autom+ticos), consent should only transition to `CONSUMED` when either the `expirationDateTime` is reached or the `totalAllowedAmount` is fully utilized.

Therefore, the behavior of the test should be updated as follows:

<table>
<tr>
<td>

Ensure the first payment cannot be executed if the creditorAccount is not for the informed creditor<br><br>· Call the POST recurring-consents endpoint with automatic pix fields, with startDateTime as D+1, period as SEMANAL, a fixed Amount 1 BRL, and sending firstPayment information with amount as 1 BRL, date as D+0, and creditorAccount account number as a random number<br>· Expect 201 - Validate Response and ensure status as AWAITING_AUTHORISATION<br>· Redirect the user to authorize consent<br>· Call the GET recurring-consents endpoint<br>· Expect 201 - Validate Response and ensure status is AUTHORISED<br>· Call the POST recurring-payments endpoint with the amount as 1 BRL, and creditorAccount number as a defined at the consent<br>· Expect 422 DETALHE_PAGAMENTO_INVALIDO or 201 - Validate Response<br>If a 201 is returned:<br>· Poll the GET recurring-payments {recurringPaymentId} while the Status is RCVD, ACCP or ACPD<br>· Call the GET recurring-payments {recurringPaymentId}<br>· Expect 200 - Validate Response and ensure status is RJCT, ensure that rejectionReason.code is DETALHE_PAGAMENTO_INVALIDO<br>· Call the GET recurring-consents endpoint<br>· Expect 201 - Validate Response and ensure status is **AUTHORISED**
</td>
</tr>
