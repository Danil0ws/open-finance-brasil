## 📝 Descrição

When POST /enrollments/{enrollmentId}/fido-registration is called by the certification platform, it sends a FIDO2 payload to finish the registration flow. Inside this payload, the field data.response.attestationObject is a CBOR object encoded with base64. According to the WebAuthn specification, all CBOR encoded values must follow the CTAP2 canonical CBOR form [1] but the certification platform does not follow this requirement. Specifically, it generates indefinite-length maps which is explicitly forbidden by the specification [2]:

`Indefinite-length items must be made into definite-length items.`

This non-conformity is causing test failures because WebAuthn servers should reject CBOR values that are not encoded in the canonical form.

[1] https://www.w3.org/TR/webauthn-2/#sctn-conforming-all-classes
[2] https://fidoalliance.org/specs/fido-v2.0-ps-20190130/fido-client-to-authenticator-protocol-v2.0-ps-20190130.html#ctap2-canonical-cbor-encoding-form

In WebAuthn, indefinite-length items are not allowed, so any CBOR-encoded data must use definite-length encoding.

Example of Indefinite Length in CBOR:
```
0x5F: Indicates the start of a byte string with an indefinite length.
0x7F: Indicates the start of a text string with an indefinite length.
0x9F: Indicates the start of an array with an indefinite length.
0xBF: Indicates the start of a map with an indefinite length.
```

You can check the CBOR-encoded AttestationObject for any of these markers (0x5F, 0x7F, 0x9F, or 0xBF) to determine if the object contains items of indefinite length.
