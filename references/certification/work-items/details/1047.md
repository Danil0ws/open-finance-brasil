## 📝 Descrição

## 1. What happened and what were you expecting?
I am experiencing a failure when trying to execute the test suites `consents_api_extension-security_test-module_v2` and `consents_api_invalid-logged-user-extension_test-module_v2`. I believe the issue lies with the test plan:

* consents_api_extension-security_test-module_v2: According to the test plan, the request `POST /open-banking/consents/v2/consents/:consent-id/extends` should be sent without the header `x-fapi-customer-ip-address`, but this is not happening, altering the test scenario.

* consents_api_invalid-logged-user-extension_test-module_v2: In the request `POST /open-banking/consents/v2/consents/:consent-id/extends`, an incorrect CPF document is being sent, resulting in an invalid document that fails the 11-digit CPF validation rule (01010101014). This causes the API to return a 400: Bad request error instead of the expected error. A valid CPF should be used, even in the case of an incorrect CPF.[Screenshot_2023-10-19_at_10.26.08](/uploads/2be6b61498285b72a91e7b59551b2a24/Screenshot_2023-10-19_at_10.26.08.png)

Hi Ian! in this specific case, we will change the a random cpf, but that follows the regex rules for cpf.

The validation that its being teste here, is as defined at the swagger:

* A renovação de consentimento ativo do cliente somente poderá ser aceita pela transmissora para um usuário logado na receptora, identificado por seu documento (**`loggedUser`**; **`businessEntity`** quando aplicável) e permitido a partir de token de acesso (informado no cabeçalho **`Authorization`**) conseguido anteriormente durante a criação e confirmação do consentimento vigente. A transmissora deve validar documento fornecido (**`loggedUser`**; **`businessEntity`** quando aplicável) e token de acesso para executar a renovação de consentimento. Caso a transmissora detecte que trata-se de acesso inválido por questões de segurança, é esperado status de erro 401 ou 403.

In that sense, a random cpf should not be able to execute a consent extension for a consent ID which is not bounded to that cpf, and does have an account at the account holder.

HI Leonardo! Thanks for the ticket!

Regarding the issues raised:

* On the consents_api_extension-security_test-module_v2 test plan, there's actually two calls, as described at the summary:
  * • Call the POST Extends Endpoint with expirationDateTime as D+365, and do not send the x-fapi-customer-ip-address header\
    • Expects 401 - Validate Error Message

    • Call the POST Extends Endpoint a Client Credentials Token\
    • **Expects 401 - Validate Error Message**
  * The erro you are receiving its because a message because you are retuning a 422-**DEPENDE_MULTIPLA_ALCADA at a client credential token, where it should be 401.**
  * In that sense, for this specific test, you need to return a 401 if a client credentials token is used on a POST Extends call. Therefore, there is no correction on the conformance suite for this.

     
* On the consents_api_invalid-logged-user-extension_test-module_v2, 401 should be a valid behavior in this case. We will change the cpf value being sent for  a valid but not registered cpf.
