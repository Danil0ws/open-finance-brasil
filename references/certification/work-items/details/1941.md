Hi, @ivanzb 

Thanks for the ticket! 

We understand your concern; however, the point you raised is exactly what this test is designed to validate: that payments can only be scheduled after the first payment is set.

The field `referenceStartDateTime` is intentionally set to a date earlier than the `firstPayment.date`. Note that this should not be validated during the consent creation, as the `referenceStartDateTime` only represents the reference start date for the payment series, not the actual payment date. Observe that in the specification, there is no restriction mentioned for the field `referenceStartDateTime` in the POST recurring-consents:

![image](/uploads/7529c24f0f6f6ff4f98a5bd9faec8770/image.png){width=700}

This scenario is validated in the test steps outlined below, where a payment attempt from the series is made for a date earlier than the first payment:
> ...  
> • Call the POST recurring-payments endpoint with the an amount of 0.5 BRL, and date ad D+8  
> • Expect 422 PAGAMENTO_DIVERGENTE_CONSENTIMENTO or 201 - Validate Response  
> If a 201 is returned:  
> • Poll the GET recurring-payments {recurringPaymentId} while the Status is RCVD, ACCP or ACPD  
> • Call the GET recurring-payments {recurringPaymentId}  
> • Expect 200 - Validate Response and ensure status is RJCT, ensure that rejectionReason.code is PAGAMENTO_DIVERGENTE_CONSENTIMENTO  
> ...

Therefore, there is no corrections on the CS side. To a successful execution, the implementation needs to be adapted so that it aligns with the test summary.

Feel free to open another ticket if you get any other issue! Happy to help!
