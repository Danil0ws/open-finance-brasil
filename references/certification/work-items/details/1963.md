#### Current Behavior:
---
The test expects:

• Call the POST recurring-payments endpoint with the amount as 300.00, but with a different creditor proxy, but the correct creditorAccount information

• Expect 422 PAGAMENTO_DIVERGENTE_CONSENTIMENTO - Validate Error Message

• Call the POST recurring-payments endpoint with the amount as 300.00, but with a different creditorAccount information, but the correct proxy

• Expect 422 PAGAMENTO_DIVERGENTE_CONSENTIMENTO - Validate Error Message
![Captura_de_Tela_2025-01-08_às_16.26.51](/uploads/6fb000eaed19098af473ca6c4475f80d/Captura_de_Tela_2025-01-08_às_16.26.51.png)

#### Expected Behavior:
---
These validations could be performed asynchronously, and if they fail, the payment could be rejected. Additionally, the `PAGAMENTO_DIVERGENTE_CONSENTIMENTO` enum does not seem appropriate for this validation, as neither the `creditorAccount` nor the `proxy` are included in the consent.

In my view, these validations could be handled asynchronously, rejecting the payment with the `PAGAMENTO_RECUSADO_DETENTORA` enum, similar to how payments are processed in [v4](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/347079010/Informa+es+T+cnicas+-+SV+Pagamentos+-+v4.0.0) today. Do you have a different perspective on this?

Furthermore, the regulation does not seen specify that these validations must be performed synchronously.

Hi,

Thanks for raising this issue!

Regarding the steps outlined:

> • Call the POST recurring-payments endpoint with the amount as 300.00, but with a different creditor proxy, but the correct creditorAccount information\
> • Expect 422 PAGAMENTO_DIVERGENTE_CONSENTIMENTO - Validate Error Message

and

> \
> • Call the POST recurring-payments endpoint with the amount as 300.00, but with a different creditorAccount information, but the correct proxy\
> • Expect 422 PAGAMENTO_DIVERGENTE_CONSENTIMENTO - Validate Error Message

The reasoning behind these validations is as follows:

* Even though the proxy is not explicitly included in the consent, it must match the document and creditor information associated with it during consent creation.
* If any field, whether it pertains to creditorAccount information, CNPJ, or proxy, differs from the information provided in consent, this discrepancy must be validated.

This approach was approved by the working group, ensuring that the error message "PAGAMENTO_DIVERGENTE_CONSENTIMENTO" correctly reflects the issue when there is a mismatch between information. We will conduct future revisions of this behavior upon release of new versions of this specification, for now, this behavior is as expected.

In regards to this type of failure being returned synchronously or asynchronously we have the following definition on the available specification:

> **Validações na criação do pagamento - Síncrono (_POST /pix/recurring-payments_)**\
> 4.2 **Casos de erro sintáticos e semânticos, previstos com retorno HTTP Code 422 - Unprocessable Entity (detalhamento adicional na documentação técnica da API):**\
>  4.2.2 Semânticos\
>  4.2.2.6 Divergência entre pagamento e consentimento: Valida se dados do pagamento são diferentes dos dados do consentimento (PAGAMENTO_DIVERGENTE_CONSENTIMENTO)\
>  4.2.2.7 Recusado pela detentora: Valida se pagamento foi recusado pela detentora (PAGAMENTO_RECUSADO_DETENTORA), com a descrição do motivo de recusa;

Therefore conformance suit is correctly expecting this errors to happen synchronously.

Feel free to add comments to this issue in case further assistance is required.
