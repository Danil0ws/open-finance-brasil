Hello @ofb-conformance. Thanks for raising this.

By design, the test is intentionally re-signing the JWS (and changing iat and jti) on the second HTTP call because the **API **[**documentation**](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/728301590/SV+Idempot+ncia)** requires every new request to be re-signed with a new jti and iat**.

At the same time, the idempotency rules state that when the same x-idempotency-key is used and the data claim is identical to the original request, the AS must return the same result as the first call (or reject with 422 ERRO_IDEMPOTENCIA when the data differs, for example).

In short: different iat/jti does not mean different operation, but a new request. Idempotency is anchored by x-idempotency-key + equality of the data claim.

About the test log: on the second POST /enrollments/{enrollmentId}/fido-registration-options, the test failed because the AS returned **HTTP 201** but the body **omitted data.challenge**. For this endpoint, a successful 201 response must include the challenge, as documented.

Please feel free to reopen the issue if you have further questions.

Best regards
