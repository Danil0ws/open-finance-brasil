O teste enrollments_api_automatic_payments-unmatching-fields_test-module_v2-2 está esperando **PARAMETRO_INVALIDO** quando deveria esperar **PARAMETRO_NAO_INFORMADO** visto que não foi enviado o **recurringConsentId.**

Conforme documentação ([Informações Técnicas - [SV] Pagamentos Automáticos - v2.2.0 - Área do Desenvolvedor - Open Finance …](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1178042617/Informa+es+T+cnicas+-+SV+Pagamentos+Autom+ticos+-+v2.2.0)) PARAMETRO_INVALIDO é retornado quando o parâmetro informado não obedece a formatação específica e PARAMETRO_NAO_INFORMADO quando algum parâmetro obrigatório não é informado.

![image.png](/uploads/6e755688f40bba81d340c5c268f423cb/image.png){width=900 height=61}

Conforme restrição do campo **recurringConsentId,** este campo é obrigatório quando o authorisationFlow for igual a FIDO_FLOW.

![image.png](/uploads/45bfbcaacc545564c69b69e91c74cc65/image.png){width=900 height=201}

Desta forma, solicito correção desse teste.

If I understood your point correctly, this is a business-rule restriction, not a technical/formatting issue with the parameter itself.

![image.png](/uploads/3d181dd503c10136b752bc644c9d3d12/image.png){width=900 height=358}

In the Automatic Payments v2.2 specification, the API clearly separates:

* Syntactic validations (422) such as:
  * missing mandatory fields (PARAMETRO_NAO_INFORMADO)
  * invalid formatting (PARAMETRO_INVALIDO)
* Semantic/business validations (422) such as:
  * business rules for payment details (DETALHE_PAGAMENTO_INVALIDO)

So in this case, the expected outcome is not tied to “parameter formatting”, but to whether the institution enforces a business rule for this scenario, which is why the DTO asked the test to accept the following behavior:

> Calls the POST recurring payments Endpoint, using the access token with the nrp-consents, authorisationFlow as FIDO_FLOW and without sending the recurringConsentId field
>
> * Expects 201 or 422 ~~PARAMETRO_NAO_INFORMADO~~ **DETALHE_PAGAMENTO_INVALIDO** - Validate Error Response

Hi @marciojas. After Open Finance Structure Technical Team (DTO) evaluation, this test summary and behavior will be changed to:

* \[...\]
* Calls the POST recurring payments Endpoint, using the access token with the nrp-consents, authorisationFlow as HYBRID_FLOW and recurringConsentId with the corresponding recurringConsentId
  * Expects 201 or 422 ~~PARAMETRO_INVALIDO~~ **DETALHE_PAGAMENTO_INVALIDO** - Validate Error Response
* \[...\]
* Calls the POST recurring payments Endpoint, using the access token with the nrp-consents, authorisationFlow as FIDO_FLOW and without sending the recurringConsentId field
  * Expects 201 or 422 ~~PARAMETRO_NAO_INFORMADO~~ **DETALHE_PAGAMENTO_INVALIDO** - Validate Error Response
* \[...\]

As previously highligted by @danielamllr, regarding the error code, in Automatic Payments v2.2.0, `recurringConsentId` is part of the payment details and it becomes mandatory only under a specific business condition: when authorisationFlow = FIDO_FLOW. Since this is a **conditional rule** (i.e., not a generic “missing request parameter”), the appropriate response is the **business validation** error 422 DETALHE_PAGAMENTO_INVALIDO.

PARAMETRO_NAO_INFORMADO / PARAMETRO_INVALIDO are intended for generic parameter presence/format issues, but in this scenario the failure is that the payment request **does not comply with the business restriction defined for the FIDO flow**.

The test was originally developed as requested by the Open Finance Structure. However, after this change request, an update is in progress on our side.

Thanks for your contribution, we'll keep you posted on the updates.

Prezados,

Analisamos o cenário **enrollments_api_automatic_payments-unmatching-fields_test-module_v2-2** e a expectativa do teste em relação ao código de erro retornado.

De acordo com a documentação técnica de **Pagamentos Automáticos v2.2.0**:

* **PARAMETRO_NAO_INFORMADO** deve ser retornado quando um **campo obrigatório não é enviado**
* **PARAMETRO_INVALIDO** deve ser retornado quando um **parâmetro é enviado, porém não obedece à formatação especificada**

O campo **recurringConsentId** possui a seguinte restrição explícita:

> Este campo é de preenchimento **obrigatório apenas quando o authorisationFlow for igual a FIDO_FLOW**.

Ao analisar a execução do teste, identificamos que, no momento da chamada:

• Calls the POST Recurring Payments Endpoint, using the access token with the nrp-consents, authorisationFlow as HYBRID_FLOW and recurringConsentId with the corresponding recurringConsentId

O teste **não está enviando o authorisationFlow como FIDO_FLOW**, mas sim como **HYBRID_FLOW**. Nesse contexto, o campo **recurringConsentId não é obrigatório**, conforme a própria especificação.

Portanto:

* Não se caracteriza ausência de campo obrigatório (**PARAMETRO_NAO_INFORMADO**)
* Tampouco há envio de parâmetro com formatação inválida (**PARAMETRO_INVALIDO**) relacionado ao recurringConsentId

Dessa forma, a expectativa do teste para retorno de erro **está alinhada com o comportamento esperado pela regulamentação**, uma vez que a obrigatoriedade do campo recurringConsentId está condicionada exclusivamente ao uso do **FIDO_FLOW**, o que não ocorre neste cenário.
