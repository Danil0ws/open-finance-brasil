Hi Bruno! Sorry for the delay!

In this case, the test expects a failure at the at the authorization endpoint because of some changes made specifically for the Phase 3v3, as clarified at[ Informa 461](https://mailchi.mp/832639a81181/open-banking-informa-9403876?e=2eb7798bd9).

In a nutshell, the main ideia for the Phase 3v3 was to have an enhanced User Experience, ensuring the user cannot consent to a payment that will be denied at. In that sense, a lot of validations should take place either on the POST Consents or the Authorization endpoint, with the results being retrieved at the GET Consents Endpoint.

For this specific case, the user should be able to reject the consent at the authorization endpoint, by clicking the "Cancel" button. When this happens, an error message should be returned from the authorization endpoint, as specified at [RFC 6479](https://www.rfc-editor.org/rfc/rfc6749#section-4.1.2.1):

"If the request fails due to a missing, invalid, or mismatching redirection URI, or if the client identifier is missing or invalid, the authorization server SHOULD inform the resource owner of the error and MUST NOT automatically redirect the user-agent to the invalid redirection URI. **If the resource owner denies the access request or if the request fails for reasons other than a missing or invalid redirection URI,** the authorization server informs the client by adding the following parameters to the query component of the redirection URI using the "application/x-www-form-urlencoded" format, per [Appendix B](https://www.rfc-editor.org/rfc/rfc6749#appendix-B): "

Here, the most important thing is that the authorization_code cannot be sent back when the user is redirected, and that error field is sent back. Besides that in the GET Consents endpoint, the status  should be 'REJECTED' and the rejectionReason 'REJEITADO_USUARIO'

I hope that helps, and we are happy to help with any additional needs!
