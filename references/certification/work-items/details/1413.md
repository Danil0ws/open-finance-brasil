## 1. What happened and what were you expecting?

It seems that there are two problems regarding this test.

![image](/uploads/aed7ed0854c3eeecf982c047f665717b/image.png)

2. After some steps the test tries to make a call to GET /v4/pix/payments/consents/{consentId}, however this endpoint does not exist according to the official specification.

Hello Everyone,

After a thorough analysis of the issue, we will ask for additional guidance from the Working Group (WG) regarding the **expected behavior of the self-link for the PATCH {ConsentID} Endpoint.** 

Specifically, the endpoint PATCH /pix/payments/consents/{consentId} mandates a self-link in its response. Despite this endpoint typically being associated with a batch of payments, there's an absence of an endpoint to query all payments associated with a consentID, leading to a scenario where **no link at this endpoint could direct to the status of all payments under a ConsentId**. Additionally, the URL path for this endpoint is unique, rendering it **invalid for any subsequent requests that might utilize the self-link**.

A similar issue arises with the POST Payments Endpoint, where a batch of payments is executed, and a unique self-link is provided in the response. We have already received guidance from the WG for the POST Payment Endpoint, stating that the self-link should direct to the first payment.

Taking into account the issues raised, we would like further clarification of the Working Group (WG) on the appropriate behavior of the self-link in the PATCH /pix/payments/consents/{consentId} Endpoint, particularly regarding the following scenarios:

1. **If the self-link is identical to the URL of the PATCH Endpoint:** In this situation, the URL is not valid for any subsequent requests. Should we then remove the self-link from this endpoint altogether?
2. **If the self-link should direct to the status of the first payment, similar to the POST Payments Endpoint:** Would this necessitate a revision of the field's description at the endpoint, which is currently labeled as "URI completo que gerou a resposta atual"?

We are happy to discuss this as needed.

Hi everyone,

From what was described in this issue, and from what we could gather from the provided test logs, there are two different topics at hand:

1. Conformance suit expects consent ID field in the PATCH /payments/v4/pix/payments/consents/{consentID} → This is indeed a unexpected behavior and we are working on a fix.
2. Conformance suit calling nonexistent GET /v4/pix/payments/consents/{consentId} endpoint → At the GET endpoint being called during **Validate Consent Self link** step, which happens right after the PATCH endpoint is called, the request_uri used is not set by the conformance suit. Rather it uses the one provided in the self link contained within the response_body for PATCH /payments/v4/pix/payments/consents/{consentID} sent by the AS. Therefore this specific Item does not present an unexpected behavior from the conformance suit. To avoid Failure during the **Validate Consent Self link** step, please make sure the correct self link is provided in the response_body for the PATCH endpoint.
