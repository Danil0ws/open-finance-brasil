## 📝 Descrição

**Observed behavior**

* Scenario: Automatic FVP Credit Portability (CPC) tests.
* During Dynamic Client Registration for the FVP **client** used in this journey, the scopes sent in the registration **do not include** `credit-portability`.
* A participant has recently shared an [issue](https://gitlab.com/raidiam-conformance/open-finance/certification/-/issues/2432) in which the problem cause was this validation, ensuring that any scope used later in PAR / authorization flows must be part of the scopes registered in the DCR for that `client_id`.
* In the same environment, the FVP later sends a PAR / authorization request including the `credit-portability` scope, and the AS responds with:
  * { "error_description": "The requested scope is invalid, unknown, malformed, or exceeds that which the client is permitted to request.", "error": "invalid_scope" }
* The list of scopes [currently](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/246054957/PT+Open+Finance+Brasil+Financial-grade+API+Dynamic+Client+Registration+2.0+RC1+Implementers+Draft+3) requested in DCR for the role DADOS is:
  * invoice-financings, resources, exchanges, financings, consents, funds, loans, treasure-titles, bank-fixed-incomes, accounts, customers, openid, unarranged-accounts-overdraft, variable-incomes, credit-cards-accounts, consent:\*

    → credit-portability is **missing** here.

---

**Expected behavior**

* When FVP performs DCR for the client used in Credit Portability journeys, the registration should:
  * include the `credit-portability` scope
  * ensure that the set of scopes registered in DCR is consistent with the scopes later used in PAR / authorization requests for CPC flows

---

**Notes (DTO & DCR documentation)**

* The Credit Portability API [specification](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1141637284/Informa+es+T+cnicas+-+PC+Portabilidade+de+Cr+dito+-+CPC+-+v1.0.0) already defines the use of the `credit-portability `scope for the CPC flows at resource-server level.
* However, the **DCR behavior for this scope still needs to be validated with DTO**, specifically against the DCR [specification](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/246054957/PT+Open+Finance+Brasil+Financial-grade+API+Dynamic+Client+Registration+2.0+RC1+Implementers+Draft+3):
  * _“PT Open Finance Brasil Financial-grade API Dynamic Client Registration 2.0 RC1 – Implementers Draft 3”_ (section that lists allowed scopes per role).
* We need DTO to confirm whether this document should explicitly include the `credit-portability` scope for the role/profile used by the Automatic FVP client in CPC journeys.
* This ticket tracks the FVP side (DCR/PAR behavior). In parallel, this question will be raised with DTO so they can confirm the expected configuration and, if needed, update the official DCR documentation.

---

**Proposed next steps**

1. Update FVP DCR for the CPC client to include credit-portability, assuming DTO confirms that this is the expected behavior.
2. Adjust FVP DCR implementation accordingly

Hi @iago.rampazzo.magalhaes, @emersonnow and @reginalb.

After analysing this behavior together with the DTO team, we confirmed that the error was **not caused by the FVP omitting credit-portability in the DCR body**, but by how the AS was deriving the allowed scopes from the Directory metadata.

**Root cause and fix**

* In the current FVP behaviour, **no scopes are sent in the DCR body** for the DADOS role.
* The AS derives the allowed scopes from the **software statement assertion (SSA)** issued by the Directory, based on the regulatory roles and metadata configured for that software.
* At the time of the error, the **Directory metadata for the DADOS role did not yet include the credit-portability scope**, so the SSA also did not list this scope.
* When the FVP later sent a PAR / authorization request including credit-portability, the AS correctly rejected it with invalid_scope, because that scope was not present in the SSA / client configuration.

The DCR specification was updated on December 02. We have also updated the Directory metadata for the DADOS role to include credit-portability. New SSAs now expose this scope, the client is created with credit-portability allowed, and the original issue #2432 has been fixed.

---

**Alignment with DCR specification**

This behavior is aligned with the “PT Open Finance Brasil Dynamic Client Registration – v2.1.0” profile, which states the AS:

 9. _"deve validar se os escopos solicitados são adequados para as permissões regulatórias autorizadas da instituição e contidas no \_software_statement. A relação de permissões regulatórias e os escopos correspondentes está descrita nas seções a seguir._
10. _deve, sempre que possível, validar os metadados declarados pelo cliente em relação aos metadados fornecidos no software_statement, **adotando os valores presentes no SSA com precedência**."_

Section 7.2 – “Funções regulatórias para mapeamentos OpenID e OAuth 2.0” also clarifies that, if scopes are omitted during DCR, **the AS must grant the full set of potential scopes based on the regulatory roles registered for the institution (Server Defaults).**

Reference:

* DCR profile v2.1.0: https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1334116369/PT+Open+Finance+Brasil+Dynamic+Client+Registration+-+v2.1.0

Given this model, the FVP behavior (omitting scopes in DCR and relying on Directory / SSA) is consistent. The issue was specifically that both the DCR specifications and the Directory metadata for DADOS had not yet been updated to include credit-portability.

---

**Open Finance structure follow-up**

DTO is aware of this scenario and will evaluate whether this expected behaviour (AS deriving scopes from SSA and regulatory roles) should be further reinforced with the ecosystem.

Additionally, they have added to their backlog the creation of an Automatic FVP test to validate that AS implementations correctly align scopes used in PAR /authorization with the scopes derived from the SSA and the regulatory roles.

---

**Impact on FVP**

Given the above, we are not planning changes to the FVP DCR behaviour for CPC journeys. With the Directory metadata updated and the participant’s AS validating scopes from the SSA, the current behaviour is now as expected.

We will therefore close this issue. If similar behaviour is observed again after these updates, please let us know so we can review.
