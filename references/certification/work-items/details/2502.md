## 📝 Descrição

**Current Behavior:**\
When running the test **`payments_api_scheduled-key-divergence_test-module_v5`** from the test plan **`payments_test-plan_v5`**, the following scenario occurs:

The test attempts to create a payment via **`POST /pix/payments`** using a valid payload but with a proxy key different from the one in the original consent. The API performs this validation synchronously and returns a 422 error code, which is compliant with the API documentation. However, the test currently expects the API to return a 201 status and subsequently allows a **`GET`** operation to identify the payment status as REJECTED.

---

**Expected Behavior:**\
The test should accept the synchronous 422 Unprocessable Entity response when there is a divergence between the payment data and the consent data, as specified in the API documentation. The error response should be validated to ensure the correct error message is returned.

Hi @danielamllr ,
Thank you for your answer.
However, I agree with what @arthurkaizer pointed out and bring some more considerations about this test behavior and about the process of scheduling and settlement of a Pix payment.

I couldn't find in the specifications a rule or something like that specifying that for **scheduled payments** I can't use the synchronous validations, as you stated in your answer. Since we have the possibility of validating some scenarios sinchronously or assynchronously, the Conformance Suit should accept both. So, when you create a consent using proxy **"X"**, and after that you want to create a Payment with proxy **"Y"**, we are in compliance with the specification when we reject this payment with the code PAGAMENTO_DIVERGENTE_CONSENTIMENTO.
**2.2.2.6 Divergência entre pagamento e consentimento: Valida se dados do pagamento são diferentes dos dados do consentimento (PAGAMENTO_DIVERGENTE_CONSENTIMENTO)**

Going a little further, let's say now the test creates both the consent and the payment using the same proxy, and **the POST/payments returns Http status 201 and payment status as RCVD.** Here we can have two possibilities:
1. proxy doesn't exists on DICT;
2. proxy exists on DICT and is valid.

In **scenario 1**, when we try to schedule the payment and move it from RCVD to SCHD, we perform a validation of the proxy on DICT, and if it doesn't exists or isn't valid, we reject the payment with error code PAGAMENTO_RECUSADO_DETENTORA, as specified in the documentation:
4.1.6 Recusado pela detentora: Valida se pagamento foi recusado pela detentora (**PAGAMENTO_RECUSADO_DETENTORA**), com a descrição do motivo de recusa (ex. **chave Pix inválida**, QRCode inválido, conta bloqueada);
In **scenario 2**, since the proxy is valid, the payment status is changed to SCHD and the **scheduling** step in finished.

After the scheduling process, there is the settlement process of the payment. In this step, before sending the payment to SPI, we perform another validation of the proxy on DICT because it could have been modified since the payment was scheduled. If the proxy stays the same, the payment is finished and then can move to ACSC. However, if there is a divergence in the data retrieved from DICT in the settlement process, we RJCT the payment using the error code CHAVE_PIX_DIVERGENTE_AGENDAMENTO_LIQUIDACAO.
According to the specifications, this error code should be used only during the settlement process, not during the scheduling process.

> Durante a **liquidação** de pagamentos agendados, seguindo a resolução BCB n402, de 22/07/2024, previamente ao envio de um pagamento à liquidação, o detentor deve consultar a chave utilizada para o agendamento no DICT. Se a consulta retornar que a chave Pix não está registrada ou que os dados da chave divergem dos dados durante o agendamento, o detentor não deve enviar o Pix para Liquidação. Todos os pagamentos associados a esse consentimento devem ser rejeitados com o motivo CHAVE_PIX_DIVERGENTE_AGENDAMENTO_LIQUIDACAO, e o usuário pagador deve ser notificado

>  4.1.11 Divergências entre dados das chaves pix para **agendamento** e **liquidação**: O pagamento agendado não pode ser enviado para liquidação devido a divergências entre dados da chave recebedora utilizada para criação do agendamento com a chave recebedora em momento de liquidação (CHAVE_PIX_DIVERGENTE_AGENDAMENTO_LIQUIDACAO);

So, in the specific scenario of this test, we are only talking about the **scheduling process**, and therefore it is not compliant with the current specification if we reject a payment here using the code CHAVE_PIX_DIVERGENTE_AGENDAMENTO_LIQUIDACAO.

If there is another place explicity saying that for scheduled payments we can't perform some of the synchronous validations (like comparing the proxy between consent and payment), please share with us.

**Autor**: Daniela Muller (@danielamllr)

Hi,

Thank you for your analysis.

After reviewing the scenario and the applicable specification, the current test behavior is correct and aligned with the Payments API requirements.

For **scheduled Pix payments**, divergences between the payment data and the consent data (such as a different proxy key) **do not need to be rejected synchronously at the POST /pix/payments step**. Although the specification lists **PAGAMENTO_DIVERGENTE_CONSENTIMENTO** under the 422 validation scenarios, this does not mandate that all such validations must occur synchronously during payment creation.

In the context of **scheduled payments**, the API may:

* Accept the payment creation request with **HTTP 201**, and
* Perform the divergence validation later in the payment lifecycle, resulting in a final status of **RJCT** with the appropriate `rejectionReason.code`, such as `CHAVE_PIX_DIVERGENTE_AGENDAMENTO_LIQUIDACAO`.

This is exactly what the test `payments_api_scheduled-key-divergence_test-module_v5` is validating: that a scheduled payment with a divergent Pix key is ultimately rejected with the correct final status and rejection reason.

Returning a synchronous **422 Unprocessable Entity** at the payment creation step prevents the payment lifecycle from progressing and does not meet the expected behavior for this scenario.

Please let us know if you need any further clarification.
