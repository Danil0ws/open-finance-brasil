## 📝 Descrição

**Conflicting tests in the plan "no-redirect-automatic-payments_api_test-plan_v2-2"**

There is a conflict between tests in the plan **"no-redirect-automatic-payments_api_test-plan_v2-2"**.

In the test **"enrollments_api_automatic-payment_enrollment-limits_negative_test-module_v2-2"**, the description states:

> *"Ensure that an Automatic Pix first payment will fail if it is above the enrollment limits".*

However, in the test **"enrollments_api_automatic-payments_enrollment-limits_v2-2"**, the description states:

> *"Ensure that an Automatic Pix recurring payment can be executed if it is above the enrollment limits, provided it respects consent limits".*

These tests conflict with each other, since both refer to **Automatic Pix payments**. The only difference mentioned in the test descriptions is the product being **"AUTOMATIC PAYMENTS"** versus **"AUTOMATIC_PIX"**. However, as the payloads are identical, I am unable to distinguish between these two scenarios based on the request data.

### Comentário 2
**Autor**: Matheus Mantovani (@matheus-mantovani)
**Criado em**: 26/12/2025, 19:27:22

Hello @lucassmonn00, thanks for raising this.

These two tests are not intended to conflict. The key distinction is **`firstPayment`** vs **`recurring payments`**, not “AUTOMATIC PAYMENTS vs AUTOMATIC_PIX”.

According to the Enrollments API [specification](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1217626343/Informa+es+T+cnicas+-+SV+V+nculo+de+dispositivo+-+v2.2.0-rc.3), the device/enrollment limits (daily limit and per-transaction limit of the linked device) must be enforced only for the `firstPayment` and must not be enforced for Automatic Pix `recurring payments`. For `recurring payments`, the limits to be considered are the ones defined in the Automatic Pix consent.  

![image.png](/uploads/354d2ddfa833de3865eaea058df6de0d/image.png){width=900 height=159}

Additionally, in the Automatic Payments API [specification](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1178042617/Informa+es+T+cnicas+-+SV+Pagamentos+Autom+ticos+-+v2.2.0), the consent includes a dedicated `firstPayment` object, described as the “service enrollment/adhesion payment”, and it is treated separately from the recurring cycle (e.g., not linked to `referenceStartDate`).  

![image.png](/uploads/d79f442b736f6f7dca72f2e771b7868b/image.png){width=408 height=74}

![image.png](/uploads/12cc86b05b26bacf44c0b21544f11943/image.png){width=386 height=141}

So the expected behavior is:

* First payment: fail if it exceeds enrollment/device limits
* Recurring payments: may succeed even above enrollment/device limits, as long as they respect the consent limits

Regarding payloads: the difference is whether the payment corresponds to the consent’s `firstPayment` or a recurring execution.

![image.png](/uploads/8331d60a6964069be8b1a190a911f1f9/image.png){width=876 height=323}

We are closing this issue for now based on the spec references shared above. If you believe any additional clarification or adjustments are still needed, feel free to reopen it and we’ll continue from there.

Best regards
