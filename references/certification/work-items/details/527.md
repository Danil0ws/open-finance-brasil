## 1. What Happened and what were you expecting?
I was trying to delete a consent in the mockbank server that had already been deleted. My application already expected the 404 and 422 status codes that indicates that the resource doesn’t exist anymore. However, I got a 400 response with the following payload:
```json
{
    “errors”:[
       {
           “code”: “Consent request already in a rejected state”,“title”:“Consent request already in a rejected state”,
           “detail”: “Consent request already in a rejected state”
       }
    ],
    “meta”: {
        “totalRecords”: 1,
        “totalPages”: 1,
        “requestDateTime”: “2022-12-21T16:57:51Z”
    }
}
```
the [Open-finance Brazil documentation](https://openfinancebrasil.atlassian.net/wiki/spaces/DraftOF/pages/7996030/Informa+es+T+cnicas+-+Consentimento+-+v1.0.3) says that for the 400 response, the reason should be: `if the request was malformed, omitting required fields, either in the body or url`. I think the reason the server responded was very different from what it should be if it really were supposed to respond 400 status code, according to the docs.

Unfortunately, we cannot change this behaviour as it's not explicit in the documentation. We will escalate this with the WG to clarify this, allowing us to both adapt the Mock Bank and reinforce said behaviour on the Conformance Suite.

While this behaviour is not specified in the documentation 400, 404, 410, 422 and other codes can all be considered compliant depending on the interpretation of the user that is implemented.

To give you an example, here we can even go a step further and argue that DELETE should always return 204 if one resource already existed there, as said method is IDEMPOTENT according to https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods

> A request method is considered "idempotent" if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request. Of the request methods defined by this specification, PUT, DELETE, and safe request methods are idempotent.
