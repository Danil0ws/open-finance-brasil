## 📝 Descrição

Hello!

In the **consents_api_negative-extensions_test-module_v3** test, the error message 422 DATA_EXPIRACAO_INVALIDA is expected when the post extends endpoint is created with expirationDateTime D+180 (**Validating post consent extension response expecting error - D+180**). But it looks like the expirationDateTime in this scenario is correct.

Checking what happens in the test, you can see that the current expiration date is **2024-08-17T13:48:26Z**, and the renewal date that should give an error is **2024-08-17T13:48:28Z**, that is, is greater than the current expiration date. Is the test really correct?

**Criado em**: 26/02/2024, 10:29:19

Segundo as especificações da API, a transmissora deve retornar status de erro 422 (`DATA_EXPIRACAO_INVALIDA`) na tentativa de renovação de consentimentos em que o novo expirationDateTime seja:
1 - Menor que a data de requisição (currentDateTime ) do pedido de renovação, ou menor ou igual que a data de expiração atual;
2 - Diferente de prazo indeterminado e maior que 12 meses da data de requisição (currentDateTime);

Além disso, a alteração em uma granularidade menor do que diária, não é um cenário esperado. Dessa forma, o GT entende que o teste deveria ser realizado exatamente com a mesma data (consentimento atual 2024-08-17T13:48:_26_Z e extensão do consentimento 2024-08-17T13:48:_26_Z). Para esse cenário, a resposta esperada deverá ser um 422 DATA_EXPIRACAO_INVALIDA.

Para o cenário com alteração na granularidade de segundos (como o teste está hoje), ambas as respostas podem ser aceitas (422 DATA_EXPIRACAO_INVALIDA e 201).

Hi Hudson! Besides fixing the test, we will send this issue to the WG to discuss, so we can have clearer response on this:

The scenario here is that the conformance suite trying to validate if an extension cannot be execute if done twice for the same expirationDateTime value. What we want to simulate is the case where a user would try to extend the consent twice for the same date. The conformance suite is sending the value of D+180 for two requests in a row, expecting the first one to be accepted and the second one to be denied, since extensions request can only extend the consent.

The problem with this is that, because the conformance suite is sending a value of D+180, and the expirationDateTime also has the time in it, it causes some institutions to accept this second request, since it has 2 seconds of diference, even though they have the same date, as seen below:

**1st Request-** expirationDateTime: 2024-08-17T13:48:\_26_Z

**2nd Request -** expirationDateTime: 2024-08-17T13:48:\_28_Z

In that sense, **the question for the WG is:**

In case an extension is done with only a few seconds of difference, should it be considered a valid extension or not? If not, what would be the limit to consider a valid extension?
