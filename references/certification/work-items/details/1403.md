## 1. What happened and what were you expecting?

During our execution we faced two different problems regarding this test.

**1** - During the test POST automatic-payments/v1/pix/recurring-payments call the provided payload does not have the object riskSignals.

According to the specification, when a SWEPPING recurring consent is created such field is mandatory:

![image](/uploads/24b1c5fa610c3652d03a7f8ec1a6aeb9/image.png)

**Expected behavior:** Since the test creates a SWEEPING recurring consent the payment payload should have a valid riskSignals object set.

**2** - The test apparently expects two webhooks to be received, one regarding the payment transition to ACSC and the other regarding the consent transition to CONSUMED.

The consent that is created sets an amount limit of 600, however the payment that is performed has an amount of 300. A consent should be considered CONSUMED only when all the limit is used, so in this moment the consent is still valid, and that's why the webhook is not sent.

**Expected behavior:** Considering the test description the consent limit should be 300 so in this case after the first payment the consent would be set to CONSUMED and the webhook would be sent.
