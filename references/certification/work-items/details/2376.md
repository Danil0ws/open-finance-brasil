Hi @170791daniel, thanks for the question.

In this case, the invalid data is in the payment request. More specifically, the combination of the payment parameters with the consent type.

The consent is created with **sweeping account fields**, but the test tries to initiate a payment with localInstrument set to AUTO. This setup is not valid for the type of consent that was authorized, which leads to the rejection with DETALHE_PAGAMENTO_INVALIDO.

So, although the individual fields (like amount and date) are syntactically valid, the business validation fails at the POST /recurring-payments step due to an incompatible setup between **payment** and **consent**.

Let us know if you’d like help reviewing that request in the log.
