Hi,

I'll clarify how the expirationDateTime is calculated and applied in these different test conditions.

1. **Regarding Test ID: iDGTVsMFQAhQHoy**: The test executed under this ID was **`consents_api_negative-extensions_test-module_v2`**, which aimed to test the successful creation of a consent and unsuccessfully consent extensions. Here's how the expirationDateTime is determined:
   * When **POST v2/consents** is executed, the **`expirationDateTime`** is set to be +2 hours from the time the consent was created.
   * It is important to note that this timestamp is based on the UTC timezone, which is +3 hours ahead of local time in Brazil. This might seem like it sets **`expirationDateTime`** to +5 hours in the future according to local Brazilian time, but actually, it is +2 hours in UTC. This is why the consent creation is successful, as the **`expirationDateTime`** is correctly set to a future time in UTC.
2. **Regarding Test IDs: C6ETKCdHfFu8x6S and 6HCwfXKhgKiZswM**: This test **`consents_api_negative_test-module_v2`** was designed to ensure a consent cannot be created in different unhappy ciscustances. Here's the summary for these tests:
   * When **POST v2/consents** is executed, the **`expirationDateTime`** is set to be -2 hours relative to the creation time.
   * Again, considering the UTC timezone, which is +3 hours relative to local Brazilian time, this might appear as if the **`expirationDateTime`** is set to +1 hour in the future from Brazil’s local time. However, for the purpose of the test and the API's operation, the relevant timezone is UTC. In this case, the **`expirationDateTime`** is actually set to 2 hours in the past in UTC, leading to an expected **`400 Bad Request`** response because the consent's expiration is incorrectly set in the past.

The Authorization Server is correctly validating the invalid **`expirationDateTime`**, but the response_status_code is not as expected. While it is expected to be a 400, a 422 is provided thus resulting in test execution Failure. Make sure that the response_status_code is as expected so that test module can be run successfully.

Hi,

Thanks for opening the ticket!

The test module execution resulted in failure while conformance suit was executing the following step:

> Creates consent api V2 request for DateTime in the past Expects failure with a 400 Error

In this step, conformance suit made a POST /v2/consents request at "2024-04-10T13:05:56Z" (UTC) ,

sending in it's payload a "expirationDateTime":"2024-04-10T11:05:56Z" (UTC), thus operating according to what is described in the test module summary.

The failure was caused by the response_status_code sent by the authorization server to this request, in which a 422 was sent while a 400 was expected.

To ensure test module can be run successfully, make sure that the response_status_code to a POST /v2/consents with expirationDateTime in the past is a 400.
