## 📝 Descrição


Realizando testes para a API Resources, identificamos que a lógica de pooling desta API mesmo com o retorno 202 não esta implementado no motor. Conforme testes executados, caso a API de recursos retorne 202 o motor falha por esperar o status 200. Sendo assim, questionamos sobre este ponto do tempo de disponibilização da API. No momento em que a requisição é feita para a API de Recursos, o recurso ainda está sendo construído e o motor 2 segundos depois consulta o recurso que ainda está sendo construído.

Hi,

### Problem:

During our testing of the Resources API, we observed that when the API returns an HTTP 202 status code, indicating that the resource is still being processed, CS does not implement the appropriate polling logic. Consequently, CS expects a 200 OK response and, upon receiving a 202, attempts to access the resource prematurely, leading to errors such as:​

![image](/uploads/b8a8af85b27fdb8538006ebd52e1bdff/image.png)

In version 3 of the Resources API, the 202 status code was introduced to signify that the resource is under processing. However, the specification does not clearly define the expected behavior from the initiator's side, such as whether polling should be implemented or what time limits are acceptable for resource availability.

### Request/Suggestion:

To address this issue, it's essential that the [API specification](https://opinbrasil.atlassian.net/wiki/spaces/RDD/pages/3965306/Informa+es+T+cnicas+-+API+Resources+-+v2.5.0) provides clear guidelines on the expected behavior when a 202 status code is returned. This includes defining whether the initiator should implement polling logic, the appropriate intervals between polling attempts, and the maximum duration the data transmitter can remain in this processing state before responding.​

We recommend that the Working Group evaluate this situation to ensure consistent implementation and interoperability across the ecosystem.​

Bom dia,

Na versão 3 da API de Resources, foi introduzido o status 202 para indicar que o recurso está em processamento. No entanto, apesar disso ter sido inserido na especificação, não foi definido qual o comportamento esperado do lado da iniciadora, como a necessidade de implementar uma lógica de polling ou limites de tempo para a disponibilização do recurso.

Recomendamos que o GT avalie a situação, isso inclui definir se a iniciadora deve implementar uma lógica de polling, qual deve ser o intervalo entre as tentativas e qual o tempo máximo que a transmissora pode levar para disponibilizar o recurso.
