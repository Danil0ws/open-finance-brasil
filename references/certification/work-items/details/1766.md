#### Current Behavior:
---
We are receiving an request with an invalid `debtorAccount` (without the mandatory field `debtorAccount.accountType`) **AND** invalid `permissions` and the test expects an error with the `code: PERMISSOES_INVALIDAS`.

#### Expected Behavior:
---
In this case we believe that the test should send a request with only invalid permissions to validate this error code, sending an invalid `debtorAccount` in the same request will fail with another reason because the request was malformed (missing mandatory attribute)

Hi All,

As the new 422 error messages will only be included in the next API version, the conformance suite cannot accept error messages that are not part of the current specification. For now, since there are no specific priorities for error messages, we recommend that the **PERMISSOES_INVALIDAS** error be returned with priority in cases where multiple errors are being sent in the request. In the next version of the conformance suite, we will adjust it to ensure that only one error is returned for this request.

Hi Mauricio! Since there is order defined for error responses, we will add the debtor account field to the test so that's the error is isolated, and there is only one error at the request.

Either way, we would like confimation from the working group for two question:

1. For the POST Enrollments 422 array, we only have two possible options at the enum

* 

![image.png](/uploads/59012642f2ed34c84a93a3c451c0c4fb/image.png){width="850" height="192"}

* But we believe there are other valid error messages in this cases, simliar to Payments V4,as:
  * PARAMETRO_NAO_INFORMADO:  Valida se todos os campos obrigatórios são informados
  * PARAMETRO_INVALIDO: Valida se parâmetros informados obedecem a formatação especificada
  * ERRO_IDEMPOTENCIA: Conteúdo da mensagem (claim data) diverge do conteúdo associado a esta chave de idempotência (x-idempotency-key).
  * NAO_INFORMADO: Não reportado/identificado pela instituição detentora de conta.
* Shouldn't these errors also be added to Enrollments Endpoints, so the message to users and debugging is facilitaed??

2. At the Other Customer Data and Payments APIs, not sending a mandaoty field expectecs 422 - PARAMETRO_NAO_INFORMADO. Here, we understand that there is a unclear behavior, as defined at the swagger:

   **400** - A requisição foi malformada, omitindo atributos obrigatórios, seja no payload ou através de atributos na URL.

   In that sense, when mandatory fields are not sent, should the expected message be a 422, like the other APIs, or 400?
3. At Payments V4, we have defined the order for error validation, as seen below. Shoudn't we have something similar at Enrollments Endpoints? \*
