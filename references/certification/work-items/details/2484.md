Hello @teng.fang. Thanks for sharing the log. From the evidence, this run is from the Conformance Suite (Sandbox), not from FVP (Production).

In your environment, the server is returning 201 Created and issuing a consent even though the request was sent with `businessEntity` (PJ context) together with PERSONAL customer-data permissions.

In practice, it looks like your implementation is ignoring/dropping the `businessEntity` field and still creating the consent, instead of rejecting the request as required by the [Consent API specification](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/219480491/Orienta+es+-+DC+Consentimento) (expected 422 for this combination).

![image.png](/uploads/20ffbb7dd9d5f7be0b1ca4b7c7e07943/image.png){width="397" height="190"}

![image.png](/uploads/a30aa52e614bac17e4bbf4726e02536f/image.png){width="394" height="80"}

![image.png](/uploads/b19110e1de9306321307fceb153cebed/image.png){width="394" height="232"}

Per the test summary, it's expected: _This test makes sure that if businessEntity is sent on the consent creation together with personal customer data permission the server will reject the request._

Regarding the test failure message (Unable to find element $.totalRecords on the OpfPaginationValidator API response): we agree this is not ideal. We will **improve the test** so it fails explicitly at the right point (i.e., if the consent is created when it should be rejected), and to avoid unrelated validations being applied in this scenario.

That said, this **test improvement is not a blocker for your success**. Your implementation should still be adjusted to follow the expected Consent behavior (reject PJ parameters combined with PERSONAL permissions). Once the server behavior is aligned with the spec (422 in this case), the execution should pass regardless of the improvement we’ll apply on our side.

Please feel free to reopen or add new comments in this issue if you need further assistance. We'll keep it open until the improvement is done.

Best regards
