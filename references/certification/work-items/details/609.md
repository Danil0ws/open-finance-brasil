Hi All!
Thanks for the feedback. This is actually the expected behavior as I mentioned earlier.

The error message you are getting is that some fields are being sent where they shouldn't.

On @cassioguizzo case, for example, the 403 response sent at the POST Consents endpoint was:

{"errors":[{"code":"BAD_JTI","title":"BAD_JTI","detail":"Error on jti"}],"meta":{"totalRecords":1,"totalPages":1,"requestDateTime":"2023-01-24T18:37:39Z"}}

Where, by the swagger, the meta field for the 403 POST Consents response should only have the requestDateTime field:

![image](/uploads/433e227912238603b86c273759320715/image.png)

So, the Conformance suite showed that the fields totalPages and totalRecords are not compliant.

In that sense, if you want to want to send any field not specified at the swagger, as totalPages or totalRecords, it must be compliant to [Extensibilidade Specs](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/17377516/Extensibilidade), and follow the regex ^(\[A-Z\]{4})(-)(.\*)$. In that case, RAID-totalRecords, with the four letters being from your unique institution

Hi Everyone! Just giving more context about this error:

We have added a validation for additional properties in the last few days, which has the same root cause for all the failing tests.

This validation checks if any fields that are not on the swagger follow the pattern described at [Extensibilidade Specs](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/17377516/Extensibilidade), which is ^([A-Z]{4})(-)(.*)$

In that sense, any tests with failure indicate that this condition has been triggered by additional fields being sent. This could be either by intended additional fields, typos, or even unintended ones. 

By any means, we are already working on this fix and we will deploy it today, so it's easier for you to provide the necessary corrections. This validation was implemented to avoid any failing certification requests, as it was common during the previous phases.
