## 1. What Happened and what were you expecting?

A few months ago (around Q3 2021), we were instructed that each initiation method should have its specific setup: bank account, CPF, amount and so forth. So DICT has its own setup, INIC has a different setup, and so on.

We've run into a case here where our implementation is not completing this transaction because, apparently, the test information differs from the setup for that specific initiation type.

So we have 2 questions about that, please:

1. Does that information still hold? Should there be one specific setup per initiation type?
2. If that is the case, then how do we match the required amount when the BACEN Pix Tester app generates its own amounts randomly? When we change the payment amount on the non-QRDN test, other tests fail.

Please note that we've passed all tests so far without using a specific setup per initiation type. We've been using the exact same JSON, while simply updating the amounts, qr Codes and dates. Have there been changes in this respect since about one week ago requiring specific setups per initiation type?

Thanks in advance for these clarifications.

About your first comment.

There are two types of tests:
- Tests where the conformance suite uses the full user-provided payload to execute the payment
- Tests where the conformance suite will keep only the debtor account payload when executing the request.

Examples of the second type is the payments-api-test, which will take your provided payload and do a payment, and the payments-api-qrdn-happy test which takes the PIX tester payload provided by you to create the payment. For those tests indeed you must set a correctly valid payload on to be able to pass on it. 

The test you pasted is of the second type: payments-api-proxy-phone-number-proxy-test. So we are updating the request payload with conformance suite defined creditor and payment details. This also means that as long as you are providing a valid debtor account, we should be able to do a valid request for this test, as we provide the localinstrument and the creditor details.

Looking at the log that you pasted, upon taking a look at both the POST Consents and POST Payments I'm unable to spot why it wouldn't be a valid DICT request. Can you point it out to us?
