## 1. What Happened and what were you expecting?
We're done the conformance tests and are actually certified for last Phase 3 Tests (Pix with QRCode), and as we are certified, we've started some bilateral tests with a TPP.

In this tests, we've noticed that we are not implemented an required field in our well-know, and the bilateral tests failed. 

Our well-know does not have the parameter 'registration_endpoint' inside 'mtls_endpoint_aliases' object, and accourding to DCR guide (https://openbanking-brasil.github.io/specs-seguranca/open-banking-brasil-dynamic-client-registration-1_ID2-ptbr.html#name-provisionamentos-do-openid-):
![ASPS](/uploads/98bf22121d7f172e971ec16011926ddc/ASPS.png)

So, we are fixing this issue, but we think the conformance suit should make this validation for the ASPS, to avoid that others players face the same issue.

I have confirmed internally that we don't validate that 'mtls_endpoint_aliases' contains token, registration, and userinfo_endpoint. It will try to get those parameters from the 'mtls_aliases', but if not present it will just pick from the first level of the payload.

This is not validated because this is not expected. Actually you put add enpoints into mtls_endpoints_aliases if you have a setup that requires it (like some clients don’t use mtls and you need to terminate mtls clients on a different TLS concentrator because of that). 

We could do this validation on the Conformance Suite, but this seems like an issue with the translation. Please note how it was written in English:

![image](/uploads/2fb594e17980f264404c11ff920f3096/image.png)


So you must advertise all 4 endpoints, but there's no hierarchical relation between them. This means that the TPP is at fault for doing this not you.
