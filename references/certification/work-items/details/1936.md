#### Current Behavior:

The CS is sending to the endpoint PATCH /pix/recurring-payments/{recurringPaymentId} a CNPJ for identification.

#### Expected Behavior:

It's unclear if this is a configuration issue, but the CS should be sending a CPF to the endpoint.

It's possible that if the businessEntity field had not been filled, the patch would have behaved correctly. However, a validation error occurs before that point because the document sent in the POST pix payment was a CPF, which doesn't match the document on the consent creditors that should be CNPJ.

As discussed along with structure, 

Conformance Suit was updated to expect and throw Warning if a 422 status code on PATCH was received due to document.identification being a CNPJ.  Conformance Suit will use **data.cancellation.cancelledBy.document.identification** as a CNPJ depending on that information being provided during test plan configuration. As conformance suit, by sending a CNPJ on this field, would not be following the pattern defined in the specification, a 422 is expected to be received by the server.

Currently, the failure at PatchRecurringPaymentPixOASValidatorV2 is only triggered if the server is not validating the **data.cancellation.cancelledBy.document.identification** field as defined by the specification. 

The fix in the specification regarding this field will be introduced by the next versions, as of now Conformance Suit is following what was determined.

We will address this discussion to understand if other changes should be made to test behavior.

Hi,

Thanks for the ticket!

We understand your question and we believe it is indeed relevant. After analyzing the provided log, we identified an inconsistency in the specification:

- The field `data.document.identification` sent in the POST recurring-payments request (which refers to the transaction receiver) was recently updated to accept the pattern: `^(?:\d{11}|\d{14})$`. However, the fields inside `data.cancellation.cancelledBy.document` in the PATCH recurring-payments endpoint were not updated accordingly. This discrepancy is problematic, as the documentation states:

  ![image](/uploads/5674ab51a8b9e4d945a48dbda7aa73fc/image.png)

  This implies that cancellations can be initiated by either a CPF or CNPJ entity. Therefore, clarification from the WG is needed regarding whether the following fields should also support both CPF and CNPJ:
  - `data.cancellation.cancelledBy.document.identification`
  - `data.cancellation.cancelledBy.document.rel`

We will need to wait for clarification from the WG on the question above. As for the remaining test execution you mentioned, @ivanzb:

- CS is using a CNPJ for both payment (`data.document.identification` in POST recurring-payments) and cancellation (`data.cancellation.cancelledBy.document.identification` in PATCH recurring-payments) because a business entity is specified in the test configuration and, therefore, is used in the POST recurring-consents request. This means the logged user at the payment initiator institution is interpreted as a CNPJ.

  We recommend not sending the configuration field `businessEntityIdentification` until the WG clarifies what will be decided regarding the field `document` in the PATCH recurring-payments. This will ensure the logged user is going to be interpreted as a CPF, which will then be used in subsequent test calls. As of now, CS is conformant to the specification, and omitting the `businessEntityIdentification` will ensure the test runs smoothly avoiding potential disruptions related to the specification.

Let us know if further clarification is needed. Happy to help!
