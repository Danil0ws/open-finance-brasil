## 📝 Descrição

The current swagger for the payment API specifies that, in both POST Consents and POST Payments Endpoint, the following errors:
- 1.3.2.3 Detalhes do pagamento: Valida se determinado parâmetro informado obedece às regras de negócio (DETALHE_PAGAMENTO_INVALIDO);
- 2.2.2.8 Detalhes do pagamento: Valida se determinado parâmetro informado obedece às regras de negócio (DETALHE_PAGAMENTO_INVALIDO);

In that sense, the specification does not define where each rule should be implemented.

Example of business rules being validated in the POST Consents or POST Payments, depending on the participant:
- Sending a QRES with a QRDN as localInstrument
- Different amounts in the QRCode and the payload
- Different proxy in the QRCode and the payload

On the latest discussion with the Squad it has been defined that.

> As the comparison between the payload and the QRCODE does not involve a check on either the DICT or the SPI there's no requirement for this to be done on a step after the Consents. With this in mind it's ok for the Server to validate on either POST Consents, Post Payments or even GET Payments.
> 
> In line with the DICT validation, Another suggestion here would be to send a proxy key that is invalid - invalid@proxy.key, (can be also on the qres code) and make sure the server only validates it on the POST Payments
