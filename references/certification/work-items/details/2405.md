## 📝 Descrição

Technical information regarding no-redirect payments API makes it clear that the error code "STATUS_VINCULO_INVALIDO" should be used with the HTTP status code 422 (Unprocessable Entity). 

The "**enrollments_api_payments-pre-enrollment_test-module_v2-2**" test demonstrates the correct and expected behavior, while expects http status code 422 (Unprocessable Entity) with error code "STATUS_VINCULO_INVALIDO".

The other tests below are behaving differently than expected:

* "**enrollments_api_payments-pre-account-holder-validation_test-module_v2-2**" expects http status code 401 (Unauthorized) or 403 (Forbidden) with error code "STATUS_VINCULO_INVALIDO" 
* "**enrollments_api_invalid-status-options_test-module_v2-2**" expects http status code 401 (Unauthorized) with error code "STATUS_VINCULO_INVALIDO" 
* "**enrollments_api_rejected-preauthorisation-enrollment_test-module_v2-2**" expects http status code 401 (Unauthorized) with error code "STATUS_VINCULO_INVALIDO" 

Could you please verify this?

#### Current Behavior:

---

HTTP status code 401 (Unauthorized) or 403 (Forbidden) for error code "STATUS_VINCULO_INVALIDO".

#### Expected Behavior:

---

HTTP status code 422 (Unprocessable Entity) for error code "STATUS_VINCULO_INVALIDO".

According to the test summary:

> **Ensure that enrollment-options cannot be created if enrollment status is AWAITING_ACCOUNT_HOLDER_VALIDATION:**\
> • Call the POST enrollments endpoint\
> • Expect a 201 response - Validate the response and check if the status is "AWAITING_RISK_SIGNALS"\
> • Call the POST Risk Signals endpoint sending the appropriate signals\
> • Expect a 204 response\
> • Call the GET enrollments endpoint\
> • Expect a 200 response - Validate the response and check if the status is AWAITING_ACCOUNT_HOLDER_VALIDATION\
> • Call the POST fido-registration-options endpoint with client_credentials token\
> • **Expect 401 - Validate Error response**\
> • Call the GET enrollments endpoint\
> • Expect a 200 response - Validate the response and check if the status is AWAITING_ACCOUNT_HOLDER_VALIDATION

The test explicitly expects a **401 (Unauthorized)** response, but it does **not** mention that it expects the error code “STATUS_VINCULO_INVALIDO.”

In our internal test, the Conformance Suite returns the following response:

![image.png](/uploads/ecdfd9e247e2a91ac1004a78ca243b2c/image.png){width=900 height=246}

You can check here: https://web.conformance.directory.openbankingbrasil.org.br/log-detail.html?log=3aonEX5fGmUyvUu&public=true

[test-log-enrollments_api_invalid-status-options_test-module_v2-2-private_key_jwt-pushed-openbanking_brazil-plain_response-3aonEX5fGmUyvUu.zip](/uploads/0a24923a526e178501ab55b09fa358cd/test-log-enrollments_api_invalid-status-options_test-module_v2-2-private_key_jwt-pushed-openbanking_brazil-plain_response-3aonEX5fGmUyvUu.zip)

This behavior is correct and consistent with the specification, since the endpoint does not accept a `client_credentials` token and should therefore return a **401 Unauthorized** response.
