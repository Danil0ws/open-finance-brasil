## 📝 Descrição

When running the test, the error Value from element code does not match any given enumeration on the Get Recurring Consents Validator V1 API response occurs in the data.rejection.reason.code field. In the test specification we have Expect 201 - Validate Response ... reason.code is REVOGADO_USUARIO but this value is not part of the set [
   "ACCOUNTS_ORIGEM_DESTINO_IGUAIS",
   "REJECTED_USER",
   "UNINFORMED",
   "INSUFFICIENT FUNDS",
   "TIME_EXPIRED_AUTORIZATION",
   "ACCOUNT_NOT_ALLOWS_PAYMENT",
   "FAIL_INFRASTRUCTURE",
   "VALUE_ABOVE_LIMIT"
]

Thanks for opening the ticket:

According to [API Automatic Payments spec](https://openbanking-brasil.github.io/openapi/swagger-apis/automatic-payments/?urls.primaryName=1.0.0-rc.4#/Recurring%20Consents/automaticPaymentsGetRecurringConsentsConsentId): 

![image.png](/uploads/811622722030c39d7c1179f81d9a94df/image.png)![image.png](/uploads/59522fb94e020b02609844782e22c531/image.png)As the consent status was: "status": "REVOKED", the rejection field should not have been sent. As it was sent, according to spec, data.rejection.reason.code may assume the following values:

![image.png](/uploads/2fb585b4a81bd6fbf2f07ac576f5f462/image.png)

As the value provided by the server was: **REVOGADO_USUARIO**

Which is not one of the codes described in the specification, the failure thrown by the conformance suit is expected. Therefore it is operating according to the specification.

Please make sure that if consents "status": "REVOKED", only the revocation fields are sent, this way preventing validations to occur to the rejection reason fields.

Happy to help!
