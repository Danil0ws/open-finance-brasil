Hello,

We reviewed test id **GxHiHZgyTHUulMj** (`consents_api_delete_test-module_v3-3-1`). The failure message about **`consents_access_token`** is misleading. The run actually stops earlier, during **client configuration**, before the consent pre-authorization flow (client credentials and saving the consents access token) runs.

**What the log shows**

1. **`GetConsentV3Endpoint`** — **SUCCESS** (consent base URL is taken from the directory for the selected Authorisation Server).
2. **`GetBusinessIdentificationsV2Endpoint`** — **FAILURE**: _“Unable to locate resource endpoint to continue”_.
3. The **“Deleting consent”** block and **`LoadConsentsAccessToken`** run as part of **cleanup** after the test has already failed. Because pre-authorization never completed, **`consents_access_token`** was never stored, so **`LoadConsentsAccessToken`** fails with _“couldn’t find required object … consents_access_token”_.

**Root cause**

For this module, the FVP validates that the **Participants Directory** exposes both the **Consents v3** endpoint and the **Customers v2** resource used as the protected resource. With **`consent.productType` = `business`**, it expects a **business customers identifications (v2)** discovery URL on the **same Authorisation Server** you selected (in your log: **Seller** / `https://openfinance.risk.test.shopee.com.br`).

The directory payload in the log only lists **consents** and **resources** for that server; it does **not** include the **customers-business / identifications** API the test looks up. The test therefore cannot resolve the resource endpoint and stops during configuration.

**What you should do**

1. **Update in Directory (FVP)** for the Authorisation Server used in this run so it includes the correct **Customers API v2 – Business – identifications** discovery endpoint (and that it matches the implementation you intend to certify), **or**
2. If your certification scope is **natural person (PF)** only, set **`consent.productType`** to **`personal`** in the test configuration **and** ensure the directory registers **Customers v2 – Personal – identifications** for that same Authorisation Server.

After the directory and `consent.productType` align with your actual APIs, re-run the test from the beginning. The **`consents_access_token`** error should disappear once **`GetBusinessIdentificationsV2Endpoint`** (or the personal equivalent) succeeds and the normal pre-authorization flow runs.

If anything is still unclear after updating the directory, send a **full** log from a new run starting at **“Validating Well-Known URI”** through the first failure.
