As defined in:

https://openbanking-brasil.github.io/openapi/swagger-apis/exchanges/?urls.primaryName=1.0.0-rc.6#/Operation%20Details/exchangesGetOperationsOperationId

The 403 message should be used in cases of:

O token tem escopo incorreto ou uma política de segurança foi violada

Which is the case at hand. A 401 should not be expected because the token is a valid one, as it could be used to access information provided by customer business or the customer personal permissions groups, and it also has the correct grant type. But as it is being used to access resources from a API which it should not have access to, it therefore characterizes as a 403 status code case scenario.

Hi,

Thanks for opening the ticket!

Scopes represent what permissions are translated into, when the Token endpoint is called in order to obtain a access token.

When conformance suit executes the following step:

* Call the POST Consents with either the customer business or the customer personal permissions group, depending on whether the brazilCnpj has or not been provided
* Expects a success 200 - Validate response

Those are perfectly acceptable steps, where it is created a consents with a determined set of scopes.

Afterwards when conformance suit executes:

* Call the GET Operations List Endpoint
* Expects a 403 response

Then conformance suit is making a GET request to a endpoint to which it does not have access to. This is only possible because when the Token endpoint was called, the scope (exchanges) that is directly associated with the exchanges permissions, [as defined in consents spec](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/277413962/Informa+es+T+cnicas+-+DC+Consentimento+-+v3.0.0-rc.1), was not sent.

As defined in the security spec:

1\. shall ensure access tokens are issued with sufficient scope necessary for access to data specified in the Permission element of a linked Consent Resource object;

Therefore conformance suit is operating according to expected and to the latests available specification.
