## 📝 Descrição

According to the [wiki](https://gitlab.com/raidiam-conformance/open-finance/certification/-/wikis/Phase-3-Automatic-Payments-Tests?redirected_from=Phase-3-Automatic-Payments-Version-1-Tests#2-retry-test-plan), the auxiliary test plans have to be executed either with the payment date as D+0 or D-1. However, automatic payments shouldn't be allowed to be scheduled before D+2, as enforced by the test _automatic-payments_api_automatic-pix-invalid-dates-sooner_test-module_v2n2_. Keeping validations to check if the payment date is before D+2 prevents the auxiliary retry tests from being executed. Is there a workaround for this?

Hello @JeffersonCarvalh0.

I completely understand your point. It makes perfect sense to have a validation that blocks any POST /pix/recurring-payments with a date earlier than D+2, to prevent the early scheduling of a new automatic payment.

So let me try to clarify my previous answer. In the case of the auxiliary test plan, the context is different: the test does **not** represent the real creation of a new schedule, but rather a simulation of a cycle that has already started (D+0 or D-1).

The key lies in the **referenceStartDate** field.

This field is the anchor of the recurring cycle: when it is configured as D-1 (for extraday) or D+0 (for intraday), it indicates that the consent **already had an active recurrence** starting from that date.

So, when the auxiliary plan performs a POST /pix/recurring-payments with payment.date = D-1 or D+0, it is **re-creating an occurrence that belongs to this already-active cycle**, not scheduling a new one. Therefore, the D+2 restriction does not apply.

In other words:

* The auxiliary plan simulates a context that is already “D+2 ahead” in relation to enrollment. It is not scheduling, it is replicating data from an existing cycle.
* The D+2 rule remains valid for the creation of a new automatic payment schedule.
* That’s exactly why the tests are configured with a referenceStartDate set to D-1 or D+0. This anchor artificially advances the start of the recurrence, allowing the POST at D-1/D+0 to be interpreted as a payment within the cycle, not as a new schedule.

Hello @JeffersonCarvalh0. Thanks for raising this.

You’re correct, according to the business rule, new automatic payments cannot be scheduled before D+2.

However, the auxiliary test plans (as described in the wiki) are not meant to represent new scheduling, as they are data-generation utilities used to **prepare failed payment scenarios for the retry tests**.

That’s why they accept D+0 (intraday) and D-1 (extraday): these configurations let the auxiliary modules create simulated retry payments that belong to an ongoing cycle, so the retry plans can later exercise their validation logic.

This controlled exception only applies in the **sandbox/test environment** to produce valid datasets. It does not override the production rule that forbids scheduling before D+2.

We reinforce that the auxiliary tests are not mandatory to succeed in the retry tests, as described in the same wiki: _"For participants' convenience, these data sets can be created using the auxiliary test plan outlined in the next section. However, participants are free to determine and use the method of their choice for data creation, as long as it meets the required test specifications."_

If you still have doubts or want to share a test log, please feel free to reopen this issue.
