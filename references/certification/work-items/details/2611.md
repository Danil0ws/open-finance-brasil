### Comentário 5
**Autor**: Matheus Mantovani (@matheus-mantovani)
**Criado em**: 09/04/2026, 18:34:11

Hi @erik.dao, thank you for the detailed analysis.

**1. referenceStartDate**

You are right. The referenceStartDate should have been 2026-03-30 (D+1 in UTC-3), not 2026-03-31. Your test ran at 2026-03-30T02:30Z, which is 2026-03-29 23:30 in Sao Paulo. So D+0 = 2026-03-29 and D+1 = 2026-03-30. 

The value 2026-03-31 was incorrectly calculated using UTC instead of UTC-3. We have already identified the root cause and an improvement will be delivered in a future release to fix this. _`Important: this discrepancy does not affect the core validation of the test.`_

**2. "a Payment cannot be executed if done after D+10"**

This means: when calling POST /pix/recurring-payments, if the date field in the request body is more than 10 calendar days after the current date (D+0 in UTC-3), the payment must be rejected with FORA_PRAZO_PERMITIDO. The test sends a second payment with date = D+11 and expects either:

* HTTP 422 with error code FORA_PRAZO_PERMITIDO, or
* HTTP 201, followed by the payment transitioning to RJCT with rejectionReason.code = FORA_PRAZO_PERMITIDO

In your execution: D+0 = 2026-03-29, so the second payment date was 2026-04-09 (D+11), which correctly exceeds the allowed window. This final validation is working as intended.

Thank you again for flagging this.
