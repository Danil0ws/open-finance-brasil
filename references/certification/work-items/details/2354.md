## 📝 Descrição

**Test**: enrollments_api_automatic-payment_enrollment-limits_negative_test-module_v2-2.

The test Module was implemented following the definition in the internal ticket [RAD-227](https://openfinancebrasil.atlassian.net/browse/RAD-227?atlOrigin=eyJpIjoiZDhkODMyMmM1NmRiNGZlNDgzM2Q5ZWFiMjU5OGNhNzMiLCJwIjoiaiJ9).

**Behavior**:

<table>
<tr>
<th>

Ensure that an Automatic Pix recurring payment can be executed if it is above the enrollment limits, provided it respects consent limits

* GET an SSA from the directory and ensure the field software_origin_uris, and extract the first uri from the array
* Execute a full enrollment journey sending the origin extracted above, extract the enrollment ID, and store the refresh_token generated ensuring it has the nrp-consents scope
* Call the GET /enrollments/{enrollment_id}
* Expect a 200 response - Validate the response and check if the status is "AUTHORISED", and retrieve transactionLimit
* Call the POST /recurring-consents endpoint sending product as "AUTOMATIC PAYMENTS", referenceStartDate as D+1, interval as "SEMANAL", automatic.fixedAmount and firstPayment.amount as enrollment transactionLimit + 1.00 BRL, firstPayment.date as D+0
* Expect a 201 response
* Call the POST /recurring-payments endpoint sending payment.amount as transactionLimit  + 1.00 BRL, data.date as D+0
* Expect a 422 response or business rejection - Validate response error.code as "LIMITE_VALOR_TRANSACAO_CONSENTIMENTO_EXCEDIDO"
</th>
</tr>
</table>

**Steps with the identified problem:**

<table>
<tr>
<th>

* Call the POST /recurring-payments endpoint sending, payment.amount as transactionLimit  + 1.00 BRL, data.date as D+0
* Expect a 422 response or business rejection - Validate response error.code as "LIMITE_VALOR_TRANSACAO_CONSENTIMENTO_EXCEDIDO"
</th>
</tr>
</table>

The test summary isn't considering the asynchronous processing, as described in the Automatic Payments API Specification:

<table>
<tr>
<th>

6. **Demais validações executadas durante o processamento assíncrono do pagamento pela detentora, poderão ser consultados pela iniciadora através dos endpoints _GET /pix/recurring-payments/{recurringPaymentId}_ e _GET /pix/recurring-payments_ previstos com retorno HTTP Code 200 - OK com status RJCT (Rejected) e rejectionReason conforme abaixo (detalhamento adicional na documentação técnica da API):**\
   6.1 **Demais validações durante o processamento assíncrono:**\
    6.1.1 - Saldo do usuário: Valida se a conta selecionada possui saldo suficiente para realizar o pagamento (SALDO_INSUFICIENTE);\
    6.1.2 - Limites da transação: Valida se o valor ultrapassa o limite estabelecido \[na instituição (conta ou canal)/no arranjo\] para permitir a realização de transações pelo cliente (VALOR_ACIMA_LIMITE);

   \[...\]
</th>
</tr>
</table>

**Suggestion**:

* Add the asynchronous processing in the test summary/behaviour.

**What needs evaluation from WG:**

* Should we follow up with the proposed suggestion?
