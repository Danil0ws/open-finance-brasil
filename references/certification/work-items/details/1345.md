## 📝 Descrição

The **automatic-payments_api_negative-consents_test-module_v1** does a validation with the x-fapi-interaction-id as '123456' and expects a 422 PARAMETRO_INVALIDO

![image](/uploads/292659fb2b92d2763469e81822040bb1/image.png)

The **payments_api_consents_negative_test-module_v4** does the same validation, but expects 400

![image](/uploads/078d064b31c8077138496e7b16047f14/image.png)


The 400 status should only be when the x-fapi-interaction-id is not sent in the request, no? In this v4 test case, an incorrectly formatted x-fapi-interaction-id is being sent, so the automatic-payments validation makes more sense. Is it expected that a correct x-fapi-interaction-id will be sent in the response if the formatting is wrong in the request, or can it take what was sent and return 422 PARAMETER_INVALID?

Hi Marcelino! By what we understand so far the behavior for the x-fapi-interaction-id is:

* When an invalid x-fapi-interation-id is sent in the header, as "123456", the server should return a 400 or 422 - PARAMETRO_INVALIDO
* When the x-fapi-interaction-id is not sent, the server should respond with 400
* In both cases explained above, the response should contain a valid x-fapi-interaction-id, as an UUID.

As describe [above](https://gitlab.com/raidiam-conformance/open-finance/certification/-/issues/1345#note_1778988778 "payments_api_consents_negative_test-module_v4 is expecting the wrong error message for a invalid x-fapi-interation-id header"), the three scenarios where this is evaluated have already been updated in this [MR](https://gitlab.com/raidiam-conformance/open-finance/certification/-/merge_requests/2351#57e1a5fc545bbd42d129fb30c11f51a2b22c777d "[OCI-3071]:3 testmodules now accept 400 and 422"), and as described at the test summaries. In the test module you sent, the test is falling since the invalid x-fapi header is being sent back, where a valid UUID should be responded - and that why you are receiving the error: "Invalid x-fapi-interaction-id - not a UUID". If you fix this test should continue without any problems.

But as you mentioned, the 422 case is not clear in the documentation. In that sense, we would like **confirmation from the WG for the following question**:

* **Should the server return a valid UUID** as the x-fapi-interaction-id in the event an invalid x-fapi-interaction-id, such as "123456", is provided, **for both error responses 400 and 422 - PARAMETRO_INVALIDO, or is this applicable solely to the 400 error**? If a valid UUID x-fapi-interaction-id should be sent back for both cases, **is there documentation covering the 422 response scenario**?

Hi Marcelino! Thanks for the reply!

The 400 message for the Payments V4 API states that: 

A requisição foi malformada, omitindo atributos obrigatórios, seja no payload ou através de atributos na URL.

With no mention to invalid parameters. At the same time, the message 422 - PARAMETRO_INVALIDO is defined as:

 1.3.1.2 Formatação de parâmetros: Valida se parâmetros informados obedecem a formatação especificada (PARAMETRO_INVALIDO).

in that sense, since the 400 message is specified at the header, we understand that the specs are not clear on this behalf. We will raise this question to the WG and get back to you.
