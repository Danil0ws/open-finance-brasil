Hello @matheus-mantovani, thank you for your reply.

Regarding error 500, we are already aware of it and working to return the correct error; in this case, I believe it is indeed the invalid_scope error.

However, regarding multiple consents in the scope, RFC 6749 §3.3 states the following: "If the value contains multiple space-delimited strings, their order does not matter, and each string adds an additional access range to the requested scope." Based on this, there is no specific order to validate the consents, and we would have to validate all of them until we find the one with the AWAITING_AUTHORISATION status. An example would be if the client sent us a scope containing 100 consents; all of them would have to be validated. Therefore, when we do not identify an optimized journey scenario, we do not allow scopes with more than one consent.

Due to these reasons, we understand that the adjustments necessary to pass this test are unfeasible to implement and release into production.

Hello @felipe.marcolla.

Thank you for the report. Complementing our previous response, we can confirm that the test is sending two consent IDs in the scope of the second PAR request:

`scope: openid payments consent:{consentId1} consent:{consentId2}`

While this is not the ideal behavior and we will be improving it to send only the relevant consent ID, we note that per RFC 6749 §3.3, scope is a space-delimited list of values and the Authorization Server MAY fully or partially ignore scope values based on its policy. In this case, the first consent is already in a final state (CONSUMED), so the AS may be able to identify and process the relevant consent (the one in AWAITING_AUTHORISATION).

We also note that the PAR endpoint accepted the request with a 201 response, meaning the scope was validated and accepted at that stage.

Looking at the logs, the authorization redirect returned `error: 500`, which is not a valid OAuth2 error code per RFC 6749 §4.1.2.1. The expected values would be codes such as `invalid_scope`, `access_denied`, or `server_error`. As a result, the consent was never properly evaluated and eventually expired, leading to a rejection with `TEMPO_EXPIRADO_AUTORIZACAO`.

The expected outcome for this test scenario is a rejection with `VALOR_ACIMA_LIMITE`, since the second consent has an amount of BRL 1,501.00 which exceeds the regulatory Pix Withdraw operational limit. We recommend reviewing both the scope handling and the withdraw limit rejection logic on the AS side.

We will update this issue once the scope improvement is deployed so the test can be re-executed.
