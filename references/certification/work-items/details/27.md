## 📝 Descrição

In Consents api test plan, running the consent-api-test-permission-groups, it's required that the consents API implementation accepts both CUSTOMERS_PERSONAL_IDENTIFICATIONS_READ and CUSTOMERS_BUSINESS_IDENTIFICATIONS_READ with the same test setup.
Our company do not provide business and personal customers APIs in the same brands/authorization servers, so our test fails, given that following the last specification we should return only permissions that we can provide, and removing CUSTOMERS_BUSINESS_IDENTIFICATIONS_READ the only permission left is RESOURCES_READ, wich demands an HTTP 422 error.
Should we ignore the specification to comply with the certification or this issue can be fixed some way?

@talles.fp - this is a valid test. The swagger explicitly does NOT include uniqueItems = true.
https://swagger.io/docs/specification/data-models/data-types/
uniqueItems
You can use uniqueItems: true to specify that all items in the array must be unique:
type: array
items:
  type: integer
uniqueItems: true
# [1, 2, 3] – valid
# [1, 1, 3] – not valid
# [ ] – valid

In the absence of uniqueItems being enforced on the swagger then duplicates are allowed. This principle is no different to scopes on an openid request. scope strings can be duplicated on the authorization request so too logically permission codes can as well.
