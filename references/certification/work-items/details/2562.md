Hi Giovana,

Thank you for the follow-up.

You are correct that the cleanup step uses a client_credentials token. This is aligned with the current Consents specification, which requires client_credentials for consent creation, consultation and revocation, while authorization_code is reserved for consent renewal.  

Regarding the scope set, the conformance suite builds the token request according to the consented permissions and the API family under test. In this test log, the suite initially builds scopes including openid, consents and funds, and later the cleanup token request is also created with grant_type=client_credentials including consents plus additional scopes derived from the testplan context.    

From the suite perspective, the important point for the DELETE consent step is that:

1. the token is obtained via client_credentials; and
2. the token includes the scope required for the endpoint, i.e. consents.

At the moment, the OPF Consents specification states the required grant type for revocation, but it does not define that the token used in this step must contain only a fixed/minimal scope set, nor that additional granted scopes should make the request invalid. The endpoint definition itself requires consents.  

So, the current suite behavior is that it requests a valid service-to-service token containing the necessary scope for the endpoint, even if additional scenario-related scopes are also present. If you enforce a stricter rule such as accepting only an exact scope set for client_credentials in this flow, that would be an implementation-specific restriction rather than something explicitly required by the current Consents API specification.  

This is also consistent with the OAuth RFCs. RFC 6749 defines scope as a space-delimited list in which each value adds an additional access range, and allows the authorization server to determine the effective granted scope. RFC 6750 frames resource access in terms of whether the token has sufficient scope for the requested resource, rather than requiring an exact scope match. In other words, from an OAuth standards perspective, the key validation point is whether the token contains the scope required for the endpoint, not whether it contains only that scope.  

Please feel free to reopen this issue if needed.

Hi,

Thank you for the report and for sharing the test log.

We have analysed the flow and confirmed that the **conformance suite is behaving in accordance with the Open Finance Brasil (OPF) specification** for the consent revocation (DELETE) step.

**What the CS does**

In the cleanup phase, the suite:

1. **Creates a token via the client_credentials grant** (as shown in the log block _"Create a client_credentials token"_ with grant_type=client_credentials and scope including consents).


1. **Calls DELETE /consents/{consentId}** using that token (block _"Deleting consent"_ → CallConsentEndpointWithBearerTokenAnyHttpMethod).

So the token sent on the DELETE request is the **client_credentials** token (service-account), not the authorization_code (user) access token.

**What the specification requires**

According to the API Consents specification:

* For **creation** (POST /consents), **consultation** (GET /consents/{consentId}), and **revocation** (DELETE /consents/{consentId}): a token obtained via **client_credentials** must be used.


* For **renewal** (POST /consents/{consentId}/extends): a token obtained via **authorization_code** must be used.

Quote from the [specification](https://openbanking-brasil.github.io/openapi/swagger-apis/consents/):

\\> _"For the creation, consultation and **revocation** of the consent, a token generated via **client_credentials** must be used. For the consent renewal call, a token generated via authorization_code must be used."_

![image.png](/uploads/6ce0a0ec37f121879ab469d1295dc5df/image.png){width=900 height=41}

So the expectation that the DELETE should be called with the **access_token** (from the authorization_code flow) is **not** what the current OPF specification defines; the spec explicitly requires **client_credentials** for revocation. The conformance suite implements this behaviour.

**Specification references**

* **Guidance – \[DC\] Consent (Open Finance Brasil):**

https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/219480491

* **API Consents – OpenAPI (Swagger):**

https://openbanking-brasil.github.io/openapi/swagger-apis/consents/

If you need more detail on the test flow or the exact steps in the log, we can provide it.
