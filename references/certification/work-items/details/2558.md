## 📝 Descrição

In the conformance test **enrollments_api_payments-unmatching-fields_test-module_v2-2** the expected response is a 422 with PARAMETRO_INVALIDO, but the **fvp-enrollments_api_payments-unmatching-fields_open_test-module_v2-2** expects DETALHE_PAGAMENTO_INVALIDO. 

Since is informed a wrong value in the parameter, makes more sense to use PARAMETRO_INVALIDO. 

So, one of the tests need an adjustment.

Hello @marcelino.junior and @hrezend. Thanks for raising this.

As discussed in the issue #2487 regarding the Automatic Payments similar test module, this is a business-rule restriction, not a technical/formatting issue with the parameter itself.

![image.png](/uploads/63e9f5375074155b6dee40aedd2d6372/image.png){width="900" height="289"}

In the Payments v4.0.1 specification, the API clearly separates:

* Syntactic validations (422) such as:
  * missing mandatory fields (PARAMETRO_NAO_INFORMADO)
  * invalid formatting (PARAMETRO_INVALIDO)
* Semantic/business validations (422) such as:
  * business rules for payment details (DETALHE_PAGAMENTO_INVALIDO)

So in this case, the expected outcome is not tied to “parameter formatting”, but to whether the institution enforces a business rule for this scenario, which is why the DTO **asked the FVP test to accept the following behavior**:

> • Calls the POST Payments Endpoint, using the access token with the nrp-consents, authorisationFlow as HYBRID_FLOW and consentId with the corresponding ConsentID, and amount of 0.5 BRL
>
> • Expects 201 or 422 ~~PARAMETRO_NAO_INFORMADO~~ **DETALHE_PAGAMENTO_INVALIDO** - Validate Error Response

We agree the Conformance Suite test should enforce the same behavior, and we have already shared this adjustment with the DTO team for evaluation.

We'll keep you posted on any updates.

Best regards
