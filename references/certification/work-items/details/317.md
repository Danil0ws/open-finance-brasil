## 📝 Descrição

The summary calls the DELETE consents, then call the token again and expects a 403 or 400 (400 should be included in the summary).
![image](/uploads/49b95dbb6d8e229da4fe962b4e7521bc/image.png)

In the test it doesn't follow this description, it DELETEs the consent, call it back (GET) to ensure it's REJECTED, then calls the customer/personal (3:39:30 PM log). Because it's with the same token (it longs 5 minutes), we receive a 200. 

Following the summary, it should call the token again (after deleting) and get a 400. Then, if call the customer/personal, will receive a 401.

https://web.conformance.directory.openbankingbrasil.org.br/log-detail.html?log=Qimc1DW2xmWa7Tk

Hi Gustavo, Thanks for the Ticket!

The test actually isn't following the summary, thanks for letting us know. Despite that, the behavior that is executed is compliant with the [documentation](https://github.com/OpenBanking-Brasil/specs-seguranca/blob/main/open-banking-brasil-financial-api-1_ID3.md#authorization-server-1), as in:

1. shall only issue access_tokens on presentation of a refresh_token when the consent resource the refresh token is bound to is active and with "AUTHORIZED" status;
2. shall only share access to resources when presented with an access_token linked to an active and valid consent; . In the Invalid Token Receive scenario, status code 401 should be returned.
3. shall revoke refresh tokens and, access tokens where applicable, when the linked Consent Resource is deleted;

Based on that, if the Consent is Rejected by the user, I should not be able to use an access token (even if previously issued) or issue a new access token using a refresh token.

We are going to update the summary and behavior of the test as follows:

Make sure that after consent has been deleted, no more tokens can be used or issued using a refresh token
- Creates consent with all of the existing permissions 
- Redirects the user
- Calls the Token endpoint using the authorization code flow
- Makes sure a valid access token has been created
- Calls the Protected Resource endpoint to make sure a valid access token has been created
- Calls the DELETE Consents API
 Calls the Consents API with the initially authorized Consent 
- Expect a 200 - Make sure Status is set to REJECTED. Make Sure RejectedBy is set to USER. Make sure Reason is set to "CUSTOMER_MANUALLY_REVOKED”
- Call the protected resource with the access token previously issued - expect 401
- Call the token endpoint to issue a new access token using the refresh token - expect 401
