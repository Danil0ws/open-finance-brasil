## 📝 Descrição

In conformance tests, when a payment route is called in no redirect payment flow, dynamic scopes are not being sent. Example: For "/automatic-payments/v2/pix/recurring-payments" route, only the scopes "recurring-payments", "openid", "payments", "nrp-consents" and "enrollment:{enrollmentId}" was sent. **We're missing "recurring-consent:{recurringConsentId} dynamic scope**. The same ocorrs for payment routes (/payments/v4/pix/payments), where we **can't find the "consent:{consentId} dynamic scope**.

Hello @danilodelgado, thanks for raising this point.

We revisited the Payments and Automatic Payments specifications, focusing on the **NonRedirectAuthorizationCode** (no-redirect) flow.

According to the published specs:

* For **no-redirect Payments** (/payments/v4/pix/payments), the required dynamic scope is

  enrollment:{enrollmentId}, together with payments, openid and nrp-consents.
* For **no-redirect Automatic Payments** (/automatic-payments/v2/pix/recurring-payments), the required scopes are

  enrollment:{enrollmentId}, recurring-payments, openid and nrp-consents.

The dynamic scopes consent:{consentId} and recurring-consent:{recurringConsentId} are listed in the specs only for the standard redirect (OAuth2AuthorizationCode) flows, not for the non-redirect flow.

**1) Automatic Payments 2.2.0**

* For the **/pix/recurring-payments** resource, the operation-level security block explicitly separates redirect vs no-redirect:

```
/pix/recurring-payments:
  get:
    security:
      - OAuth2AuthorizationCode:
          - openid
          - 'recurring-consent:recurringConsentId'
          - recurring-payments
      - NonRedirectAuthorizationCode:
          - openid
          - recurring-payments
          - 'enrollment:enrollmentId'
          - nrp-consents
```

**2) Payments 4.0.1**

* For **/pix/payments**, the security block follows exactly this pattern:

```
/pix/payments:
  post:
    security:
      - OAuth2AuthorizationCode:
          - openid
          - 'consent:consentId'
          - payments
      - NonRedirectAuthorizationCode:
          - openid
          - 'enrollment:enrollmentId'
          - payments
          - nrp-consents
```

Based on this, the current behaviour of sending enrollment:{enrollmentId} (instead of consent:{consentId} / recurring-consent:{recurringConsentId}) in the no-redirect payment routes appears to be aligned with the specifications.

We're closing this issue, but please feel free to reopen if you need any additional clarification or find that some adjustment is needed in the documentation and/or conformance test descriptions.

Best regards.
