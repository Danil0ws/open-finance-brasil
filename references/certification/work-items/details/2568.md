Hi @sadraquejsa. Thank you for the report and for sharing the test log.

We have analysed the flow and can confirm that the conformance suite is behaving as expected.

In the cleanup phase, the CS obtains a token via `client_credentials` (as shown in the log block "Create a client_credentials token") and uses it to call `DELETE /consents/{consentId}`. This is aligned with the Consents API specification, which requires `client_credentials` for consent creation, consultation and revocation.

Regarding the scope set present in the token (`consents`, `consent:urn:...`, `variable-incomes`): the suite builds the token request based on the scenario context, ensuring the token contains the scope required by the DELETE endpoint (`consents`). The Consents API specification defines `consents` as the required scope for this endpoint, but does not state that additional scopes granted by the AS should make the request invalid.

The 403 response from your server ("O token tem escopo incorreto ou uma política de segurança foi violada") indicates that your resource server is rejecting a valid `client_credentials` token because it contains scopes beyond `consents`. This would be an implementation-specific restriction on your side, not a requirement of the current Consents API specification.

We have seen this same behavior reported for the `funds` API module (issue #2562). It may be worth checking the scope validation policy applied by your resource server for `DELETE /consents/{consentId}` when the token is issued via `client_credentials`.

Feel free to reopen this issue if needed.
