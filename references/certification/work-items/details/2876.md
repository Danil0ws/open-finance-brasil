## 📝 Descrição

#### Current Behavior:
---
In `credit-portability_api_portability-with_warranty_test-module_v1-1`, after selecting an eligible unsecured contract with a government warranty, the module:

1. Calls `GET /loans/v2/contracts/{contractId}` and extracts `instalmentPeriodicity` from the Loans response (`ExtractInstalmentPeriodicity`).
2. Builds `proposedContract` for `POST /credit-portability/v1/portabilities` using that value (`PreparePortabilityRequestV1n1`).

For contracts whose Loans response returns `instalmentPeriodicity: "OUTROS"` (valid in the Loans API — e.g. FGTS birthday-withdrawal schedules, often with `instalmentPeriodicityAdditionalInfo` such as “Antecipação Saque Aniversário - FGTS”), the suite sends the same value in `data.proposedContract.instalmentPeriodicity`.

The Credit Portability API rejects the request with `422 PARAMETRO_INVALIDO` on `.data.proposed-contract.instalment-periodicity`, because the CPC `proposedContract.instalmentPeriodicity` enum does **not** include `OUTROS`.

Published CPC enum (`proposedContract.instalmentPeriodicity`):
`SEM_PERIODICIDADE_REGULAR | DIARIO | SEMANAL | QUINZENAL | MENSAL | BIMESTRAL | TRIMESTRAL | SEMESTRAL | ANUAL`

Published Loans enum (`EnumContractInstalmentPeriodicity`) **does** include `OUTROS`.

The module prerequisites (unsecured contract + government warranty + `DISPONIVEL` / `isEligible=true`) do not state that `instalmentPeriodicity` must be a specific value, so a contract that satisfies the stated prerequisites can still fail at `POST /portabilities` solely due to this cross-API copy.

#### Expected Behavior:
---
We would like clarification on whether this behaviour is intentional.

As a suggestion, one of the following (or equivalent) would align the suite with the published specs:

- When copying from Loans into `proposedContract`, map `OUTROS` to a CPC-valid value (e.g. `SEM_PERIODICIDADE_REGULAR`), **or**
- Skip / do not select contracts whose Loans `instalmentPeriodicity` is not in the CPC enum, **or**
- Include `OUTROS` in the CPC enum

References:
- Credit Portability swagger (instalmentPeriodicity enum without `OUTROS`): https://github.com/OpenBanking-Brasil/openapi/blob/main/swagger-apis/credit-portability/1.0.0.yml
- Loans swagger (`OUTROS` allowed): https://github.com/OpenBanking-Brasil/openapi/blob/main/swagger-apis/loans/2.5.0.yml
- CPC v1.1.0-rc.1 (if preferred): https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/2030141967/Swagger+-+API+Portabilidade+de+Cr+dito+v1.1.0-rc.1

Hi @wagnerdevocelot 

Thank you for the detailed report.

We have compared CPC v1.1.0-rc.1 and Loans v2.7.0-rc.1 swaggers.

1. We will add an improvement to the test module so it does not select Loans contracts that are incompatible with Credit Portability. Contracts whose Loans `instalmentPeriodicity` is not accepted by the Credit Portability enum (for example `OUTROS`) will be skipped during contract selection, so that value is never sent to `POST /portabilities`.
2. While this implementation is in progress, we suggest that you do not make this type of data available for certification purposes (Loans contracts with `instalmentPeriodicity` set to `OUTROS`), so your runs are not blocked by it.
3. If you would like the specifications to be aligned so that both enums become compatible, we suggest opening a request through the Service Desk addressed to the Credit Portability Working Group, since that is a normative decision under their responsibility.

Best regards.
