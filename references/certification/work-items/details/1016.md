Hi Daniel! Thanks for the ticket!

The error is actually happening at a part of the test where a new consent indeed needed to be used. This is the successful payment that will be executed to consume the consent, which will be reused afterwards. In this specific case, a payment that stayed at RCVD for too long, making the test to fail. As available at the summary, the part of the test in which the test failed is highlighted in bold:

1\. Ensure an error is sent when consent is reused at a failed payment flow\
• Calls POST Consents Endpoint with valid payload, using DICT as the localInstrument\
• Expects 201\
• Call GET Consent\
• Expects 200 - Validate if status is "AWAITING_AUTHORISATION"\
• Redirects the user to authorize the created consent\
• Call GET Consent\
• Expects 200 - Validate if status is "AUTHORISED"\
• Calls the POST Payments Endpoint without the EndtoEndId field\
• Expects 422 PARAMETRO_NAO_INFORMADO \
• Call GET Consent\
• Expects 200 - Validate if status is "CONSUMED"\
• Calls the POST Payments with the EndtoEndId field \
• Expects 422 CONSENTIMENTO_INVALIDO - Validate error message\
2. Ensure an error is sent when consent is reused at a success payment flow\
• Calls POST Consents Endpoint with valid payload, using DICT as the localInstrument\
• Expects 201 - Validate if status is "AWAITING_AUTHORISATION"\
• Redirects the user to authorize the created consent  \
• Call GET Consent\
• Expects 200 - Validate if status is "AUTHORISED"\
• Calls the POST Payments with valid payload\
• Expects 201 - Validate Response  \
• **Poll the Get Payments endpoint with the PaymentID Created while payment status is RCVD, ACCP or ACPD**\
• Call GET Consent\
• Expects 200 - Validate if status is "CONSUMED"\
• Calls the POST Payments with the same consent and payload, but different idempotency key\
• Expects 422 CONSENTIMENTO_INVALIDO - Validate error message

In that sense, if the payment is successful, the test should run without any problems.

We are happy to help with any additional needs!
