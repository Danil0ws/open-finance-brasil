## 📝 Descrição

While executing the `payments_api_consents_rejection-reason_test-module_v3`, we encountered a failure on CS. This failure occurred because CS expects the authorization to be successful when the debtor and creditor are the same. However, our authorization server rejects this scenario, causing the test to stop.

Hi, @mateuscp 

Thanks for providing the test ID. The test failed because it is not conformant to the following test step highlighted in bold:

> Ensure the correct rejectionReason is returned whe the consent is rejected in different scenarios
> 1. Ensure consent is rejected when the same account is sent on creditor and debtor account
> * Call POST consent with the same info on creditorAccount and debtorAccount
> * Call the POST Consents endpoints using token issued via client_credentials grant
> * Expects 422 DETALHE_PAGAMENTO_INVALIDO - Validate Error Message
>
> If no errors are found:
> * Expects 201 - Validate response
> * Redirects the user 
> * **Ensure an error is returned and that the authorization code was not sent back**
> 
> ...

In other words, due to the previous steps where the implementation returns a 201 response to the POST Consents, the user is redirected, and the authorization server is expected to return an error. However, it incorrectly returns a valid response. This implementation error also impacts the subsequent steps because when GET Consents is called later neither the `status` nor the `rejectionReason` meet the expected values.

Therefore, there is no corrections on the CS side. To a successful execution, the implementation needs to be adapted so that it is conformant to the expected behaviour described in the test summary.

Feel free to open another ticket if you get any CS related issue! Happy to help!

**Autor**: Christian Eloysio (@christianraidiam)
**Criado em**: 01/09/2023, 19:34:37

Update on September 1st:

The WG has answered the request, and the test module will be update as below:

Ensure the correct rejectionReason is returned whe the consent is rejected in different scenarios

1. Ensure consent is rejected when the same account is sent on creditor and debtor account

* Call POST consent with the same info on creditorAccount and debtorAccount
* **Expectes 422 DETALHE_PAGAMENTO_INVALIDO - Validate Error Message**

**If no error are found**

* **Expects 201 - Validate response**
* **Redirects the user**
* **Ensure an error is returned and that the authorization code was not sent back**
* Call GET Consent
* Expects 200 - Validate if status is "REJECTED" and rejectionReason is CONTAS_ORIGEM_DESTINO_IGUAIS

2\. Ensure consent is rejected when the user rejects it manually

* Call POST consent **with a valid payload**
* Expects 201 - Validate response
* Redirects the user to reject the consent
* Call GET Consent
* Expects 200 - Validate if status is "REJECTED" and rejectionReason is REJEITADO_USUARIO

3\. Ensure consent is rejected when the authorization time expires. This step will take 5 minutes to run.

* Call POST consent with the expirationDateTime as creationDateTime + 5 minutes
* Expects 201 - Validate response
* Set the conformance suite to wait 5 minutes
* Call GET Consent
* Expects 200 - Validate if status is "REJECTED" and rejectionReason is TEMPO_EXPIRADO_CONSUMO
