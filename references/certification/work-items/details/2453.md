Olá @rodolfo.cruz. Entendemos e agradecemos as considerações.

Do ponto de vista estritamente normativo (Automatic Payments API v2.2.0), a interpretação de 422/PARAMETRO_INVALIDO para esse cenário não se sustenta pelo que a spec define para esse código e para o campo journey:

1. **O que a spec define para journey:**

   O schema Journey é definido como contexto de Jornada Otimizada e "obrigatório quando o usuário manifestar consentimento para compartilhamento de saldo através da Jornada Otimizada em Sweeping”. A spec v2.2.0 não impõe uma restrição técnica que obrigue rejeição síncrona com 422 quando journey é enviado fora do contexto de Sweeping e também não mapeia esse caso para PARAMETRO_INVALIDO no POST.
2. **O que a spec define para 422 / PARAMETRO_INVALIDO:**

   Na seção de 422 do POST /recurring-consents, o uso de PARAMETRO_INVALIDO está descrito para casos de invalidade `sintática` do parâmetro (ex.: formatação/estrutura/valor fora do formato esperado), e não para sinalizar a regra de negócio específica ‘fluxo não suportado’, que a própria spec já trata via GET com REJECTED + rejectionReason. Por isso, para passar a suportar esse fluxo síncrono de forma compatível, seria necessário normatizar esse caso na spec, o que implica potencial novo versionamento.

   ![image.png](/uploads/8e05c89af8e217ef6bc78ec855abe6d1/image.png){width=900 height=392}

Conforme também pontuamos nas mensagens anteriores, o Grupo de Produtos da DTO concorda com o apontamento e já está considerando o ajuste da especificação futuramente para que o fluxo síncrono seja também suportado, como já ocorre em outros cenários do Open Finance. Mas, enquanto a documentação não é ajustada, espera-se que o comportamento adotado seja a validação assíncrona.

Como complemento, fizemos uma validação adicional com a DTO após sua última mensagem. O entendimento é: caso desejem aprofundar a discussão normativa/documental (ex.: permitir validação síncrona no POST antes de uma mudança futura da spec), o caminho mais adequado é abrir um ticket no Service Desk para a Associação Open Finance, especificamente para o GP_Dados do cliente, responsável pela especificação da Jornada Otimizada, e/ou para o GP_Serviços, responsável pela spec da API Pagamentos Automáticos.

De qualquer modo, permanecemos à disposição para auxiliar na análise e para eventualmente ajustar o comportamento do teste, após alinhamento com a estrutura da AOPF.

Olá @matheus-mantovani,
sobre esse tema ainda tenho considerações a fazer para manter o comportamento de validação síncrona  na criação do consentimento de pagamentos automáticos.

Entendemos que a documentação atual do Open Finance não elimina nem proíbe o tratamento síncrono com erro 422 / PARAMETRO_INVALIDO nesse cenário. Ao contrário, ela deixa margem explícita para isso.

1 - [Jornada Otimizada é descrita oficialmente como um fluxo](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1128890377/Jornada+Otimizada#Introdu%C3%A7%C3%A3o)

Conforme a própria documentação oficial:

“A Jornada Otimizada tem como objetivo simplificar a experiência do cliente, permitindo o compartilhamento de dados a partir da jornada de pagamentos, em um fluxo unificado e mais simples.”

Ou seja, Jornada Otimizada não é um produto, mas um fluxo de simplificação aplicado aos produtos existentes.
Quando a especificação e o Swagger indicam que esse fluxo só pode ser aplicado, nesse contexto, a Sweeping, temos uma restrição do contrato de uso do campo.

2 - A própria API prevê 422 / PARAMETRO_INVALIDO para uso incompatível de parâmetros

Em 1.3 - Casos de erro sintáticos e semânticos, consta:
> 1.3.1.2 - Formatação de parâmetros (PARAMETRO_INVALIDO)
> Valida se parâmetros informados obedecem à formatação especificada.

O Swagger, por sua vez, restringe o uso do objeto journey a Sweeping nesse contexto.

Portanto, quando o journey é enviado em um cenário onde ele não se aplica, trata-se de um erro de parâmetro da requisição, e a resposta síncrona 422 / PARAMETRO_INVALIDO está plenamente alinhada com:
- o contrato técnico
- a seção 1.3
- e o modelo de validação de parâmetros definido pela própria API


3 - A validação assíncrona também é possível ,mas a síncrona não é excluída pela documentação

Reconhecemos que a documentação também descreve validações assíncronas com rejeição posterior via GET. Esse comportamento é válido.

O ponto central é que a documentação atual não determina que esse cenário deve ser tratado exclusivamente de forma assíncrona, nem impede a validação síncrona quando a inconsistência decorre do próprio contrato do endpoint.

Ou seja:
- a validação assíncrona é suportada
- mas a validação síncrona com 422 / PARAMETRO_INVALIDO também é suportada pelo modelo da API

E, portanto, ambas deveriam ser consideradas conformes até que a especificação seja revisada para eliminar essa ambiguidade.

4 - Impacto operacional: criar para rejeitar depois gera lixo e custo desnecessário

Há ainda um impacto prático relevante.
Quando a implementação é obrigada a:
1. receber um request que já nasce fora do contrato funcional,
1. criar o consentimento mesmo assim,
1. processá-lo para, só então,
1. rejeitá-lo de forma assíncrona,

isso resulta em:
- criação de registros transacionais que nunca serão utilizados
- maior consumo de armazenamento, mensageria e processamento
- complexidade operacional adicional para as instituições
- poluição dos indicadores regulatórios e operacionais
- custo de infraestrutura desnecessário em todo o ecossistema

Ou seja, gera-se lixo operacional previsível, que poderia ser evitado com um retorno imediato 422, já que a inconsistência é determinística e derivada do contrato técnico.

Esse ponto é particularmente sensível em Open Finance, onde o custo agregado e a escalabilidade impactam o ecossistema como um todo.

5 - Conclusão

Dado que:

1. Jornada Otimizada é definida como um fluxo, não como um produto;
1. O Swagger restringe seu uso em determinados contextos;
1. A seção 1.3 - 422 / PARAMETRO_INVALIDO cobre exatamente violações de regras de uso de parâmetros;
1. E o modelo “cria e rejeita depois” gera custo e lixo operacional evitável;

Entendemos que:

- Retornar 422 / PARAMETRO_INVALIDO na criação do consentimento, quando o fluxo Jornada Otimizada é enviado em um contexto onde ele não se aplica, é um comportamento aderente à especificação vigente.
- A validação assíncrona também é compatível com a documentação, mas não exclui nem invalida a abordagem síncrona.

Até que a documentação seja revisada para definir explicitamente um único comportamento obrigatório, solicitamos que ambas as abordagens sejam consideradas conformes, evitando penalizar implementações que seguiram uma interpretação legítima e técnica do contrato publicado e que, adicionalmente, reduzem custo e complexidade para o ecossistema como um todo.

Seguimos à disposição para colaborar na evolução documental do tema.

Hi @adelino.avelino.

Focusing strictly on what the Automatic Payments API v2.2.0 [spec](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1178042617/Informa+es+T+cnicas+-+SV+Pagamentos+Autom+ticos+-+v2.2.0) defines:

* The rejection reason `FLUXO_NAO_SUPORTADO_PRODUTO` is _explicitly defined in the asynchronous flow_, under “Validações durante o processamento assíncrono do consentimento” (item 2.1.7), to be returned via GET /recurring-consents/{recurringConsentId} with HTTP 200, status=REJECTED and rejectionReason.
* The spec does **not** define any synchronous (POST /recurring-consents) error response for this product flow combination. There is no equivalent synchronous error code for “flow/product not supported” in the POST validation list.

Therefore, in the current version, the expected implementation is exactly what the test validates: create the consent (POST succeeds if the request is valid), then surface the business-rule outcome asynchronously via GET as REJECTED / FLUXO_NAO_SUPORTADO_PRODUTO.

Additionally, this is consistent with how the Optimised Journey [documentation](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1129021472/Transfer+ncias+Inteligentes+-+JO+Jornada+Otimizada+v1.0) frames consent creation. In **“Criação do Consentimento de Transferências Inteligentes”**, it states:

> “O consentimento de Transferências Inteligentes atua como primário e deve ser criado após o consentimento de dados, **obedecendo as mesmas regras da jornada convencional** com a adição do objeto opcional journey no corpo da requisição \[...\]”

Implementing a different behavior (e.g., rejecting this scenario synchronously using an error code not defined for POST) will be **non-compliant with the specification**, because it introduces a response behavior that the spec does not describe for that endpoint/version.

DTO will consider the feedback as a documentation enhancement for a future version, but for now the behavior should remain as specified in v2.2.0.

Hello @luan.ferro, @hudson.ishibashi1, @pedro_alcantara and @gimendes.

We reviewed this issue with the DTO team. Currently, the Automatic Payments API specification **does not have a synchronous validation error code** for this scenario. The validation exists **only asynchronously**, after the corresponding GET request is executed. Because of this, the current flow requires **creating the consent** and then **rejecting it asynchronously**.

At this moment, the Open Finance Structure recommendation is:

* The test behavior is correct.
* The PARAMETRO_INVALIDO error must not be used in this case, as it represents a syntactic error, not a business-rule validation.
* The implementation must handle the asynchronous error.

Additionally, there is already a follow-up to include this validation synchronously in a future version, at which point the behavior and tests may be updated.

Please feel free to reopen this issue if needed, or to share any additional points with the Open Finance Working Groups.
