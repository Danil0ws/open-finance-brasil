Hi @ivanbopus. Thanks for raising this.

The wording in the summary can sound confusing at first glance, because the **POST /authorise** step is expected to return 204. When the summary says “cannot be successfully authorized”, it’s referring to the overall business outcome of the consent (i.e., it must not end up _AUTHORlSED_ for sweeping in this journey), not that the /authorise call itself must fail.

![image.png](/uploads/648ca984421265cbff700e2a26b5b99c/image.png){width="742" height="282"}

In this scenario, the test is checking two different things:

1. **POST /recurring-consents/{id}/authorise**

   The request is valid (token with nrp-consents, valid challenge, valid signature), so the expected result is **204**.

   This step verifies that the authorisation request itself is accepted by the endpoint.
2. **GET /recurring-consents/{id} afterwards**

   For sweeping, which is not supported in this journey, the expected **business outcome** is a rejected consent, with:
   * status = "RJCT"
   * rejection.reason = "FLUXO_NAO_SUPORTADO_PRODUTO"

So the test does not expect the sweeping consent to remain AUTHORISED. It expects a valid POST /authorize call followed by a rejected consent for an unsupported flow.

Regarding 422: in the Automatic Payments specs, **422 is used when the request to the endpoint is invalid** (schema/validation/inconsistent data).

Here, the request is valid, so the rejection is represented on the consent resource (RJCT + reason), not as HTTP 422 on POST /authorise.

If you see it differently, we can raise this with the Open Finance Technical team to align the expected behavior.

Feel free to reopen if you’d like us to proceed with that.
