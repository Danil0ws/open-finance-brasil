## 1. What Happened and what were you expecting?

While running `patch-consents-api-pixscheduling-revoke-authorized`, the test will call the token endpoint several times.

It should then proceed to call the `consents` endpoint using the most recent token obtained, but the test is calling `consents` using the earliest token, which has since been overwritten by later calls to the token endpoint.

Hi Erick, thanks for the prompt reply.

It'd be nice if you could clarify the correct behavior, because this may have implications for the refresh token to consent relation.

Since we disallow refresh token rotation, issuing multiple concurrently valid access tokens using the same refresh token would probably allow a replay attack using the same consent (e.g. if called in rapid succession before the consent changes state).

Refresh token rotation naturally invalidates the previous tokens, given it's a single use code. 

It seems logical to me that we should invalidate the previous access token issued by the same refresh token, but I couldn't find any documentation to back this up officially.

Indeed. We Call the token endpoint three times on this test to make sure that there's no refresh token rotation. We end up using the first issued token, the last 2 calls are just ignored.

Nonetheless for the test behavior to be invalid revoking an access token because you obtained a new access token must be a valid behavior. I couldn't find this defined explicitly on the [Brazilian security standards](https://github.com/OpenBanking-Brasil/specs-seguranca/blob/main/open-banking-brasil-financial-api-1_ID3.md#authorization-server) but it might be related to an OAUTH RFC.

Will check with our FAPI Experts and if the behavior is valid we will update the test. Please feel free to share any documentation that supports that your behavior as valid.
