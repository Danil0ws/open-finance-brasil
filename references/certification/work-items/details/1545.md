## 📝 Descrição

## 1\. What happened and what were you expecting?

While running internal tests,

We could perceive that within the scopes present in the access token used to make the POST recurring-payments call there is:

scope: consent:consentId

It should be

scope: recurring-consent:recurringConsentId

As described in:

https://raw.githubusercontent.com/OpenBanking-Brasil/openapi/main/swagger-apis/automatic-payments/1.0.0-rc.4.yml

for /pix/recurring-payments Post endpoint

Updates on this issue: This has been discussed at the WG, and the following actions will take place:

1. The tests will be adapted. New plans available by next Friday (March 22nd).
2. A new test module will be added, following the specific behavior:
   1. automatic-payments_api_invalid-scope_test-module_v1

      Ensure scope validations are being executed at the POST recurring-payments endpoint, and a payment cannot be created in unhappy requests

      • Call the POST recurring-consents endpoint with sweeping accounts data \
      • Expect 201 - Validate Response and ensure status as AWAITING_AUTHORISATION\
      • Redirect the user to authorize consent, sending the scopes as scope=openid&recurring-payments&consent:{recurringConsentId} \
      • Check if an error is returned at the redirect, and no authorization code is sent back

      If no errors are returned: \
      • Call the GET recurring-consents endpoint \
      • Expect 201 - Validate Response and ensure status is AUTHORISED \
      • Call the POST recurring-payments endpoint using an auth code token with a incorrect scope, as requested at the redirect \
      • Expect 403 - Validate Response

### Comentário 19
**Autor**: Christian Eloysio (@christianraidiam)
**Criado em**: 18/03/2024, 17:03:18

This issue should be **discussed within the Squad Sandbox** to determine how it should be addressed. There are two hypotheses:

1. All institutions have implemented the incorrect scope, and changing the scope will cause all tests to fail at the same point.
2. Institutions are not validating the scope, so changing it will not have any consequences.

Given this situation, we have three possible alternatives:

1. Do nothing and wait for certification to address this issue.
2. Change the scope to the correct one, which will cause a breaking change and require participants to retest.
3. Change the scope to the correct one and add a negative scenario to verify if the correct scope is being validated, which would also result in a breaking change.

Based on this, **which scenario would be the best to pursue?**
