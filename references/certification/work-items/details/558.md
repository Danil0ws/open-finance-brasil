## 📝 Descrição

## 1. What Happened and what were you expecting?
In test payments-api-qrdn-good-proxy-test-v2, when execute second step "Calls the POST Payments Endpoint - Send the CNPJ Initiator provided by the user and Create the E2EID using the CNPJ Initiator", we return error 422 because QCode from QRDN is same used in first step "Calls the POST Payments Endpoint - Send the CNPJ Initiator provided by the user and Create the E2EID using the CNPJ Initiator". So we already return error when call POST with 422 DETALHE_PAGAMENTO_INVALIDO. Field QrCode does not accept. But in test, is expecting success in POST and just return rejection when get payment. Is this correct?

Hi Daniel! Thanks for the ticket!

Indeed, the specification does not specify where the validation should take place, and we will change the test so it accepts the message 422 - PAGAMENTO_RECUSADO_DETENTORA, as specified by the swagger:

" 2.2.2.7 Recusado pela detentora: Valida se pagamento foi recusado pela detentora (PAGAMENTO_RECUSADO_DETENTORA), com a descrição do motivo de recusa (ex. chave Pix inválida, QRCode inválido, conta bloqueada);"
