It looks like you are running an older version of the test module. This test has been updated to **rc.1**, which includes the following changes:

### **Test Steps Overview:**

:one: A **POST** `recurring-consents` request is sent with a random **creditorAccount** number.\
:two: The consent is authorized with that **creditorAccount**.\
:three: A **POST** `recurring-payments` request is sent using the (random) **creditorAccount** number defined in the consent.\
:four: The test expects a **201** response (as the creditor and debtor accounts don't belong to the same account holder institution).\
:five: The test calls the **GET** `recurring-payments/{recurringPaymentId}` endpoint and expects:

* **200 - RJCT**, with `rejectionReason.code` as **TITULARIDADE_INCONSISTENTE** (asynchronous validation).

This update aligns with the **WG definition on Issue** : https://gitlab.com/raidiam-conformance/open-finance/certification/-/issues/2030

### **Key Clarification:**

* As per the WG, **DETALHE_PAGAMENTO_INVALIDO** should only be returned **synchronously** when both the **debtor and creditor accounts belong to the same holder**.
* When they **do not** belong to the same holder, an **asynchronous** validation should return **TITULARIDADE_INCONSISTENTE**, reflecting a failure in the **Payment execution on Pix tester**.

Hello,

Thanks for reaching out!

The expected DETALHE_PAGAMENTO_INVALIDO response occurs due to the validation of the **creditorAccount** details **between** the **recurring consent and the payment request.**

**Rule Behind the Expected Behavior**
The test ensures that a payment cannot be executed if the **creditorAccount** in the payment request does **not match** the one defined in the consent.

**Test Steps Overview**
1️⃣ POST recurring-consents request is sent with a random creditorAccount number.
2️⃣ The consent gets authorized with that creditorAccount.
3️⃣ A POST recurring-payments request is sent using the creditorAccount number defined in the consent.
4️⃣ If the payment request does not match the authorized creditor details, the expected behavior is a 422 DETALHE_PAGAMENTO_INVALIDO error.

Key Validation Rule in the Specification
**According to the specification:**

![image](/uploads/4d0ec3acd342fb27c4bd896b6f38a4b5/image.png)

The first payment is considered as the service membership payment for the payer.
If the creditor and debtor accounts belong to the same institution, the creditor account must belong to the CNPJ provided in /data/creditors/cpfCnpj.
The creditor account used in the first payment must be the same as the one informed in the consent.
If this rule is not followed, the payment must be rejected with DETALHE_PAGAMENTO_INVALIDO, either:
Synchronously with HTTP 422
Asynchronously with HTTP 200 and a subsequent rejection status

**Expected Behavior in the Test Flow**
🔹 If a random account number is used in the consent and the same account number is used in the payment, the system does not assume that the account belongs to the correct creditor.

🔹 This is why the test expects a 422 DETALHE_PAGAMENTO_INVALIDO response, because it ensures that payments can only be executed when the creditor account details are correctly linked to the informed creditor in the consent.
