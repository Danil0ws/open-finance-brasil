## 📝 Descrição

## Summary

Two conformance tests in the Payments v5 suite cover essentially the same scenario — a consent created with `payment.amount` different from the value defined in a Static QR Code (QRES) — but enforce **contradictory expectations** on the `POST /consents` response. It is not possible to satisfy the *primary* expectation of both tests with a single implementation.

## Current Behavior (the inconsistency)

**Test A — `payments_api_qres-wrong-amount-proxy_test-module_v5`** (Reference Error 4.1.3)
- Calls `POST /consents` with a different amount on the QRES vs the payload.
- **Primary expectation: HTTP 422 with `DETALHE_PAGAMENTO_INVALIDO`** (validate error message).
- Fallback: *"If no errors are identified"* → expects 201, redirect, then `GET /consents` with `status = REJECTED` and `rejectionReason = VALOR_INVALIDO`.
- → This test **accepts the synchronous 422** outcome.

**Test B — `payments_api_pix-withdraw-invalid-amount_test-module_v5`**
- Calls `POST /consents` with a Pix Saque QRES and `payment.amount = QR Code value + 1`.
- **Expects HTTP 201** (the test fails if a 422 is returned at consent creation).
- Then redirect, and `GET /consents` with `status = REJECTED` and `rejectionReason = VALOR_INVALIDO`.
- → This test **forbids the synchronous 422** and requires asynchronous rejection only.

For the same underlying business rule (amount must match the QRES value), **Test A accepts a synchronous `422 DETALHE_PAGAMENTO_INVALIDO` while Test B rejects it**. An implementation that returns 422 at consent creation passes Test A but fails Test B; only an asynchronous implementation (201 + later REJECTED/VALOR_INVALIDO) satisfies both.

## Expected Behavior

The two tests should be reconciled so the same scenario has a single, consistent expectation. The specification supports the synchronous validation path for amount divergence:

> **Amount field (POST /consents), Payments v5:** *"For all scenarios where the amount cannot be changed, the amount field must be populated with the value established in the QR Code. If the amount field is populated with a value different from the expected one, an HTTP Status 422 response with code VALOR_INVALIDO must be returned."*

Accordingly, when a Pix Saque consent is submitted with `payment.amount` different from the QR Code amount, returning **HTTP 422 / `VALOR_INVALIDO`** at `POST /consents` (consent not created, authorization flow not initiated) should be a **valid outcome** — consistent with the lenient structure already used by `payments_api_qres-wrong-amount-proxy`.

**Request:** please align `payments_api_pix-withdraw-invalid-amount_test-module_v5` with `payments_api_qres-wrong-amount-proxy_test-module_v5`, accepting the synchronous `422` path (with the appropriate error code) in addition to the asynchronous `201 → REJECTED/VALOR_INVALIDO` path — or clarify which behavior is normative, given that the two tests currently contradict each other.

Hi @martinslm. Thanks for raising this.

After evaluation, the DTO requested a change to payments_api_pix-withdraw-invalid-amount_test-module_v5. It now accepts both outcomes when payment.amount diverges from the QR Code value, aligning it with payments_api_qres-wrong-amount-proxy_test-module_v5:

* Synchronous path: HTTP 422 at POST /consents with error code DETALHE_PAGAMENTO_INVALIDO. The test validates the error and ends there.
* Asynchronous path: HTTP 201 at POST /consents, redirect, then GET /consents returning status REJECTED with rejectionReason VALOR_INVALIDO.

One clarification on the error code: VALOR_INVALIDO is a consent rejectionReason (asynchronous), it is not a valid POST /consents error code. For the synchronous 422 the applicable code is DETALHE_PAGAMENTO_INVALIDO, which is what the module validates.

The change will be included in an upcoming release and we'll keep you posted on the updates here.

Best regards.
