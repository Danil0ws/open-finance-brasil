@lsnoboru , please send the certification request as it is and we will process it ignoring that single failure.



About the test, there's a few failures that we need to qualify here

(1) We should be accepting that indeed you have a transaction that is at least 6 months older as they are -> Wrong Failure here
![image](/uploads/ed3ca9e7a73be0aedcbad95db7c562fd/image.png)

(2) We should be failing you as on the first page there are no transactions that date from less than 6 months.

(3) When we call the specific transactions?fromBookingDate=2021-06-17&toBookingDate=2022-06-17 test is not returning a failure as transactions from other dates are being returned.



To make sure we account for multiple pages my suggestion here is that we change the test scope to be more like

Testing that the server is respecting the BookingDate filter rules
To execute this test a data mass with at least two transactions, one older than 6 months and one 6 months or earlier must be set

- Creates a consent with only ACCOUNTS permissions
- 201 code and successful redirect
- Using the consent created, call the Accounts API
- Call GET Accounts Transactions API, send query parameters fromBookingDate and toBookingDate using 6 months before current date (From D to D-180)
- Expect success, fetch a transaction, get the transactionDate, make sure this transaction is within the range above
- Call GET Accounts Transactions API, send query parameters fromBookingDate and toBookingDate using 6 months older than current date (From D-180 to D-360)
- Expect success, fetch a transaction, get the transactionDate, make sure this transaction is within the range above - Save the date from one of the transactions returned on that API Call - Save it's date
- Call GET Accounts Transactions API, send query parameters fromBookingDate and toBookingDate to be the transactionDate saved on the test below
- Expect success, make sure that the returned transactions is from exactly the date returned above
