## 📝 Descrição

Verificado que no cenário de teste **automatic-payments_api_timezone_test-module_v2**, o motor incrementa no **startDateTime** a data/hora atual(Now) + 1 hour, há algum motivo em incrementar + 1h?, sendo que neste cenário a data/hora de criação do consentimento vai estar sempre posterior ao data/hora da criação do pagamento, resultando na divergência entre o consentimento e pagamento (status code 422).

Segue um exemplo para esclarecimento:

Considerando o Dia e Horário do Teste = 06/03/2025 as 21:00h UTC-3
 
1) Criação do consentimento
 
startDateTime = 07/03/2025 as 01h00 UTC (startDateTime + 1h)
 
2) Post PAGAMENTO
 
date = 06/03/2025 UTC-3 (Data do pagamento)

Data/hora da solicitação do pagamento = 07/03/2025 as 00:00:10 UTC
 
 
Regra de negócio
----------------
 
1) Obter a Data e hora corrente(currentDateTime)
2) CurrentDateTime = 07/03/2025 00:00:10 UTC
3) Obter startDateTime do consentimento
4) startDateTime = 07/03/2025 as 01h00 UTC 
5) Validar regra se currentDateTime >= startDateTime 

CurrentDateTime| 07/03/2025 as 00:00:10 UTC >= startDateTime| 07/03/2025 as 01h00 UTC

O teste neste caso deveria retorna erro de divergência entre pagamento e consentimento, pois o startDateTime  vai ser sempre posterior ao CurrentDateTime(data solicitação do pagamento).

Hi @vitorhas,

Thanks for the response!

During the test module, conformance suit Calls **POST /recurring-consents** sending the following info:

```
    "recurringConfiguration": {
      "sweeping": {
        "startDateTime": "2025-03-11T01:12:38Z",
```

Afterwards it calls **POST** **/pix/recurring-payments** sending in request**:**

```
  "data": {
    "date": "2025-03-10",
```

The server should validate both date field from **POST** **/pix/recurring-payments** startDateTime field from **POST /recurring-consents** in the same TimeZone. By converting the startDateTime provided in the recurring consents to UTC-3 timezone, the server would have: 

```
        "startDateTime": "2025-03-10T11:12:38",
```

Which would then allow the payment which is set to the same date ("2025-03-10") to be executed.

Other timestamps, such as request Time should not be accounted for since the payment request must match the fields that are present on the consent request body.

Hi,

Thanks for creating the issue!

The behavior you described is intentional and aligned with the test's objective of ensuring that payments executed between 9 PM UTC-3 and 11:59 PM UTC-3 are correctly processed and that the system properly handles time zone differences.

As can be seen from the specification:

![image.png](/uploads/cb3b15e93d707922e3f8a8fa9e3e6f8c/image.png)

For a successful execution of this test module you need to convert the different date or dateTime fields to be evaluated in the same timezone. One suggestion would be to convert the startDateTime provided in the recurring consents to UTC-3 timezone.

That would allow the Payment Date to (2025-03-06 UTC-3) , to match the date of the startDateTime (2025-03-07T02:52:19Z UTC, and 2025-03-06T11:52:19Z UTC-3)
