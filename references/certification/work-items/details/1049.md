## 📝 Descrição

Hi, I have a question about this new error code `REFRESH_TOKEN_JWT`. I am having some trouble understanding the expected use case for it. 

I found some documentation for it that reads 

"Consent renewal ( POST /consents/{consentId}/extends) must be possible for consent for which an opaque refresh token was issued. It should not be possible when consent is linked to a JWT refresh token (with a non-extendable term). The transmitter must return error status 422 ( REFRESH_TOKEN_JWT) for requests that do not follow this definition."

Does this mean that on the authorization server side, we are to find the refresh token bound to the provided access token and validate that it is not a JWT? It seems strange and tangential to care about the refresh token when calling the `POST /extends` endpoint.

Also, what does "non-extendable" term mean in this case? Is this referring to a consent that was extended indefinitely, or is this some criterion for the jwt token?

No problems!

And no, these validations on refresh tokens should be executed internally by the account holders. If they hold refresh_tokens as jwts, they should return a 422-REFRESH_TOKEN_JWT error message on the POST Extends.

In the protocol level, Data Receivers should stick to the token with the scope, and be able to process this error message at the POST Extends Endpoint, but no other action needed. Data receivers do not need to make any additional validations on this matter.

### Comentário 4
**Autor**: Christian Eloysio (@christianraidiam)
**Criado em**: 19/10/2023, 14:03:42

Hi Dylan! Thanks for the ticket!

The error should happen if the refresh_token being sent is a JWT, meaning that the consent extension should not be executed. 

The rationale for this lies in the fact that JWTs may contain an optional "exp" claim. [By the specs](https://www.rfc-editor.org/rfc/rfc7519#section-4.1.4), once included, this claim cannot be altered after token issuance. Consequently, even if consent is extended, the client would not be able to access resources if the refresh token expires. Thus, the only viable option in this scenario would be to use opaque refresh tokens.

The upcoming security specification updates will handle this alteration. To ensure compliance with the testing requirements, you must be capable of issuing opaque refresh tokens instead of JWT ones. If your server does not currently support opaque refresh tokens and won't be able to make the necessary adjustments before the certification deadline, we kindly request that you submit a ticket regarding this issue to the Service Desk Platform.

Regarding the checks, it's the responsibility of the Account holder to perform them. This implies that if you're the initiator, you should be able to initiate the calls and handle the processing of the message 422-REFRESH_TOKEN_JWT, if needed. On the account holder's side, any consents tied to a JWT refresh_token should result in this message when extended. Moreover, all institution certifications must demonstrate that they exclusively issue opaque refresh tokens. Consequently, anyone with certification should have the capability to extend consents.

We are happy to help with any additional needs!
