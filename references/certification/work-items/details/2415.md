## 📝 Descrição

**Reference**: SD ticket #124795

---

**Context**: [RFC-6749](https://datatracker.ietf.org/doc/html/rfc6749)

---

**Observed behavior:**

In the test module fvp-credit-portability_api_invalid_grant_type_invalid_x-fapi_invalid_idempodency_test-module_v1, in the scenario _“Calling GET /credit-operations/{contractId}/portability-eligibility using a token with client_credentials grant”_, the FVP currently sends a request with **both** an invalid x-fapi-interaction-id **and** a token obtained via client_credentials, an invalid grant type for this flow. 

Some participants have implemented their APIs so that they validate the header content (including x-fapi-interaction-id) **before** validating the access token. As a result, they are observing failures related to the invalid header in this scenario and are asking for the test to send a valid x-fapi-interaction-id here, arguing that the focus of the scenario is the invalid grant type.

From our point of view (Raidiam), checking header contents before validating the token introduces a potential security risk. RFC 6749 states that _“The resource server validates the access token, and if valid, serves the request.”_ Changing this order can open a window where malicious requests are being partially “served” before the token itself is confirmed as valid.

As a suggestion, we also understand that this topic may be considered technical debt for the ecosystem from a testing perspective. If the structure prefers to focus on testing Credit Portability for now, we can proceed in that direction and change the x-fapi header to be compliant, isolating the access token problem. However, we strongly recommend that, if this is the case, this behaviour be explicitly tested in production when possible, given that it may introduce security risks.

---

**Expected behavior:**

We please request DTO’s analysis and decision on how to proceed with this scenario. Specifically, we would like DTO to confirm whether the current behavior should be **mantained** or **adjusted.**
