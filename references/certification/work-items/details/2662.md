Both are correct validations, should one be prioritized or payments_api_idempotency_test-module_v5 should be updated to accepted PAGAMENTO_NAO_PERMITE_CANCELAMENTO as a valid response?

Hello @joao.oliveira24, thanks for raising this.

We shared this issue with OPF DTO, and the conclusion is that the current test behavior is correct.

Per the Payments API spec, `x-idempotency-key` must be validated **before** any business rule:

* Same key + same payload → return the cached response.
* Same key + **different** payload → HTTP 422 with `code: ERRO_IDEMPOTENCIA`.

A different payload under the same key is a contract violation, not a business error.

**Evidence from the log** (run `JB3RddILgNPHrN5`):

* **12:45:52 UTC** — Payload modified (CPF changed from 01234567890 to 99991111140).
* **12:45:52 UTC** — PATCH /pix/payments/e11b62bc-816a-4302-8717-a8f87e7391d0 **reused** x-idempotency-key: 5353a2bb-0464-4dd8-a614-fb16c6dced34.
* **12:45:53 UTC** — Response: HTTP 422 with code: PAGAMENTO_NAO_PERMITE_CANCELAMENTO.
* **12:45:53 UTC** — Expected: code: ERRO_IDEMPOTENCIA.

The response shows the business rule was evaluated before the idempotency check. Please reorder the validation: idempotency first, business rules after.
