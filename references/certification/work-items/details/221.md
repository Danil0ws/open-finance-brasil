## 1. What Happened and what were you expecting?

The test: account-api-bookingdate-test

Is returning a NPE one the step where it gets a transaction date at random in order to test if the institution is correctly filtering the API response

![image](/uploads/5661c2022091b3e4edc34182006671fc/image.png)

The institution who opened the ticket on the Service Desk also sent the following message to be taken into account when fixing the test:

_From our understanding, the date attributes should not be passed in the headers as pointed out in the Certification Engine, conflicting with the values defined in Swagger as a query where it is passed in the url (param). We suggest checking the error so that we can continue with our validations._

I'm not sure that what has been said relates to the NPE, but indeed the frombookingdate and tobookingdate are set on the swagger to be params to be passed on the query, however we have sent them as headers.

```
    fromBookingDate:
      name: fromBookingDate
      description: 'Data inicial de filtragem. [Restrição] Deve obrigatoriamente ser enviado caso o campo toBookingDate seja informado. Caso não seja informado, deve ser assumido o dia atual.'
      required: false
      in: query
      schema:
        type: string
        maxLength: 10
        format: date
        example: '2021-05-21'
```

When fixing this also make sure we update the summary so it says send query parameters instead of headers.

• Call GET Accounts Transactions API, **send headers** fromBookingDate and toBookingDate using the max period (12 months from exisiting date)
• Call GET Accounts Transactions API, **send headers** fromBookingDate and toBookingDate to be the transactionDate

All good for the header issue, however further investigation around the NPE might be needed.

The transactionId might be an issue then. Looking at the accounts API we have https://openbanking-brasil.github.io/areadesenvolvedor/swagger/swagger_accounts_apis.yaml that:

```
    AccountTransactionsData:
      type: object
      required:
        - completedAuthorisedPaymentType
        - creditDebitType
        - transactionName
        - type
        - amount
        - transactionCurrency
        - transactionDate
        - partieCnpjCpf
        - partiePersonType
        - partieCompeCode
        - partieBranchCode
        - partieNumber
        - partieCheckDigit
      properties:
        transactionId:
          type: string
          description: Código ou identificador único prestado pela instituição que mantém a conta para representar a transação individual.
          maxLength: 100
          pattern: '^[a-zA-Z0-9][a-zA-Z0-9\-]{0,99}$'
          example: TXpRMU9UQTROMWhZV2xSU1FUazJSMDl
```

It's not a required field, so the CS should not be expecting it to be sent.
