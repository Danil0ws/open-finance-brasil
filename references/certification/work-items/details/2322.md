Hi,

We apologise for the incorrect information. The correct term is `{recurringPaymentId}.` 

As per the specification:

![image.png](/uploads/1ddb4710e25275d097a7566c3ddaeed9/image.png)

According to the Pagination documentation, when the method called is `POST`, the self field must point to the resource created. In the case of the `/retry `endpoint, we understand that the resource actually created is the recurring payment itself, and therefore self should point to:

`/pix/recurring-payments/{recurringPaymentId}`

This behaviour is similar to that adopted in other Service endpoints (where POST returns a self GET-able for the created resource) and has also been observed in practice by other participants.

This situation was aligned with the GP responsible for the issue: #2285 

Please, feel free to reach out in case of further questions!

Hi,

We analysed the test log and identified that the test is failing because your server is returning an incorrect selfLink in response to the GET call:

![image.png](/uploads/985cad46c84979aee440aedfa6b9521b/image.png)

`"links": {`

`"self": "https://openfinance-mtls.sandbox.c6bank.com.br/open-banking/automatic-payments/v2/pix/recurring-payments"`

According to the [pagination](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/17377470/Pagina+o) specification, the data.links.self field must contain the same endpoint as the original request. 

![image.png](/uploads/a2d7432218cf81f28ac0228cfe0f2d6d/image.png)

A correct example would be:

`"https://openfinance-mtls.sandbox.c6bank.com.br/open-banking/automatic-payments/v2/pix/recurring-payments/{consentId}"`

In this case, you server must return the `consentId` in selflink.
