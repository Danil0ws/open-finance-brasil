## 📝 Descrição

Hi Master,

We are testing Payments API v5 Dynamic Client Registration, and the FVP DCR request failed because our backend did not receive the client certificate.

#### Endpoint:
POST https://auth.risk.staging.shopee.com.br/oauth/as/register

#### Test case:
payments_api_recurring-payments-daily-core_alphanumeric_cnpj_test-module_v5
Test id: ohPWziFbb0GjsAW

#### Problem:
The FVP HTML log shows `request_mutual_tls` contains `cert`, `key`, and `ca` for the DCR request.

However, in our backend log for the FVP POST request, the `X-Client-Cert` header was missing. Because of that, our server returned:

HTTP 401
error: invalid_client
error_description: Invalid client certificate

We extracted the exact same client certificate, private key, and JSON body from the FVP log, then replayed the same POST request with curl. In that replay:

- TLS server requested client certificate
- curl sent the client certificate
- our backend received `X-Client-Cert`
- the DCR request succeeded with HTTP 201 Created

So the certificate/key/body appear valid, and SGW/backend forwarding also works.

#### Could you please help confirm:
1. Could FVP be reusing an existing TLS connection to the same host that was created without a client certificate?
2. For Dynamic Client Registration, can FVP ensure the request uses a fresh mTLS connection or a connection manager bound to the configured client certificate?
3. Is there any known issue where `request_mutual_tls` is shown in the HTML log, but the actual HTTP client request does not present the certificate during TLS handshake?

#### Evidence:
1. Original FVP DCR request:
- Method: POST
- Path: /oauth/as/register
- User-Agent: Apache-HttpClient/5.5.2 Java/17.0.19
- Content-Length: 34624
- Backend header: `X-Client-Cert` missing
- Result: HTTP 401 invalid_client / Invalid client certificate

2. Replay with exact extracted FVP cert/key/body:
- curl command used the same cert/key/body from the FVP log
- Backend received `X-Client-Cert`
- Result: HTTP 201 Created

3. Another FVP module using mTLS successfully forwarded `X-Client-Cert` to our backend, so this does not look like a general SGW/backend forwarding issue.

Hi @zhidong.tan 

**Q1. Is this "check the CA list before sending the certificate" behaviour new to this plan? Other plans passed with the same config.**

It is not new, and it is not specific to this plan. It is simply how TLS and Java (JSSE) work. During the handshake your server sends a `CertificateRequest` that lists the client certificate CAs it is willing to accept, and our client only presents a certificate whose issuer is on that list. When the issuer is not there, it sends no certificate at all.

We reproduced it live with openssl, on both TLS 1.2 and 1.3, and every path on `auth.risk.staging.shopee.com.br` (register, token, par, resources) advertises only `C=BR, O=SHOPEE, CN=www.shopee.com.br`. The Open Finance `Issuing CA - G2` that signed our test certificate is never advertised. The Directory, on the other hand (`matls-auth.sandbox.directory.openbankingbrasil.org.br`), does advertise a list that includes `Issuing CA - G2` and `Root CA - G2`. That is why, in the same run and with the very same certificate, our mTLS calls to the Directory succeed while DCR to you returns 401.

The reason the other plans pass with this same config is that DCR is the one endpoint where the client certificate is the actual credential. Your token endpoint authenticates with `private_key_jwt`, so a call there goes through without any certificate, and the resource calls ride on the bearer token. Only `/oauth/as/register` has nothing else to fall back on, so when the certificate is missing it answers 401.

If you want to see it on your side:

```
printf 'POST /oauth/as/register HTTP/1.1\r\nHost: auth.risk.staging.shopee.com.br\r\nContent-Length: 2\r\nConnection: close\r\n\r\n{}' \
  | openssl s_client -connect auth.risk.staging.shopee.com.br:443 -servername auth.risk.staging.shopee.com.br -tls1_2 2>/dev/null \
  | grep -A5 "Acceptable client certificate CA names"
```

**Q2. Where do we get the sandbox trust anchors (Issuing CA - G2 and Root CA - G2)?**

Good news first: you already have a certificate issued by our G2. Your organisation's certificates registered in the Directory (org `96748716-9b96-448c-a2b7-2abf9762af8e`, CN=SHOPEE) are signed by `Open Finance sandbox Issuing CA - G2`. So there is nothing to request or re-issue on your side. The only piece missing is trusting that very same G2 chain on your server.

So all you need is this file, published by the Directory keystore (public, no login required): `https://keystore.sandbox.directory.openbankingbrasil.org.br/ca_trusted_list.pem`

It holds exactly the two anchors you are missing:

- `Open Finance sandbox Issuing CA - G2`
- `Open Finance sandbox Root CA - G2`

Add both to the client-auth trust store of `auth.risk.staging.shopee.com.br`, the same store that feeds the `CertificateRequest`. Once G2 is in there, your gateway will advertise it, our client will present the certificate you already hold, and the DCR call will go through. For production the equivalent bundle lives at `https://keystore.directory.openbankingbrasil.org.br/`.

Hi @zhidong.tan

here's exactly what happens, step by step.

Every mTLS request starts with a TLS handshake, and as part of it **your server tells our client which client-certificate CAs it accepts** (the TLS `CertificateRequest`).

On the DCR `POST /oauth/as/register`, that guest list came back with a **single** entry, your own internal CA:

```
C=BR, ST=SP, L=Sao Paulo, O=SHOPEE, CN=www.shopee.com.br
```

The **Open Finance sandbox Issuing CA – G2**, the CA that issued our test client's certificate, was **not** on the list.

Our client is Java/JSSE, which follows the TLS spec strictly: it only presents a certificate whose issuer is on the advertised list. Since our cert is G2-issued and G2 wasn't there, our client concluded "they don't accept my CA" and **sent no certificate at all**. Your gateway then saw an anonymous connection (no `X-Client-Cert`) and returned `401 Invalid client certificate`.

Your curl replay works because OpenSSL/curl ignores that guest list and sends the cert regardless, same cert, different client behavior. So the certificate is valid; the only question is whether the client presents it, and that's driven by what your server advertises.

**if you want to reproduce**:

```bash
H=auth.risk.staging.shopee.com.br
printf 'POST /oauth/as/register HTTP/1.1\r\nHost: %s\r\nContent-Length: 2\r\nConnection: close\r\n\r\n{}' "$H" \
  | openssl s_client -connect $H:443 -servername $H -tls1_2 -enable_pha 2>&1 | grep -A2 "Acceptable client certificate CA names"
```

**Fix:** add the Open Finance sandbox trust anchors (**Issuing CA – G2** and **Root CA – G2**) to the mTLS client-auth trust store on `auth.risk.staging.shopee.com.br`. Once G2 is on the advertised list, our client will present the certificate and the DCR will proceed.

One last note on terminology: both attached logs are standard **Conformance Suite** runs against the **sandbox** directory (`web.conformance…`, `*.sandbox.directory…`), not FVP. FVP is the functional verification run against production, so there's nothing FVP-specific here, this is a sandbox conformance config item on your side.

Feel free to reach us out if needed,
