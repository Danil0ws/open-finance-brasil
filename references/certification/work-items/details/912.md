## 1. What happened and what were you expecting?
The CS set the transaction amount to 9999999999.99 and expect us to reject the consent when the user has insuficient funds or the amount is higher than the current transaction amount limit set by the user. 

However, as stated in the section 2.2.2 of the ["Validações" document](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/164528425/Informa+es+T+cnicas+-+Pagamentos+-+v3.0.0-rc.1), this is a validation that can also be done later in the POST payments step in both synchronous or asynchronous methods. It is not mandatory for it to be verified **only** in the POST Consents step.

In our understanding, the conformance suite should verify first if the consent is `AUTHORISED` or `REJECTED`. If it is `AUTHORISED`, then it should follow the payments_api_nofunds_test-module_v3 test summary.

Hi All! Thanks for the ticket!

This behavior has been changed now for payments V3 so the user journey is enhanced, avoiding the user will consent to a payment that can't be completed. In that sense, all the validations should take place before the POST payments endpoint.

The error messages for these cases are still under 2.2.2 because they can still happen on scheduled payments since the account balance can change until it is executed. In that sense, the behavior for the test is valid, as defined at the WG.

We are happy to help with any further issues.
