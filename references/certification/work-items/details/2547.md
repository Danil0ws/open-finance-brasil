Prezados,

Considerando que este cenário de teste é **especificamente para múltiplas alçadas/autorizadores**, o comportamento esperado do teste está correto e aderente à especificação.

### Sobre o status PARTIALLY_ACCEPTED

Conforme definido na [spec](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1283522692/M+quina+de+Estados+-+v5.0.0-beta.1+-+SV+Pagamentos), o status **PARTIALLY_ACCEPTED** indica que o consentimento:

* Já recebeu **ao menos uma aprovação**
* Ainda **necessita da confirmação de outros autorizadores** para que o processamento da transação possa prosseguir

Neste cenário de múltiplas alçadas:

* Após a criação do consentimento, o status inicial é **AWAITING_AUTHORISATION**
* Com a execução da primeira autorização, o consentimento **deve transitar para PARTIALLY_ACCEPTED**
* O consentimento deve **permanecer em PARTIALLY_ACCEPTED** até que todas as aprovações necessárias sejam realizadas
* Caso as aprovações não ocorram dentro do prazo definido pela spec, o consentimento deve ser movido para **REJECTED**

### Sobre a ausência de pausa no teste

O teste não realiza pausas explícitas para inclusão manual de autorizadores porque:

* O cenário assume que o participante **já possui múltiplos autorizadores configurados**
* As aprovações adicionais devem ser tratadas **automaticamente pelo motor do participante**
* O teste apenas valida a **transição correta de estados**, e não a interação manual com usuários finais

Ou seja, o teste **não espera ações manuais durante a execução**, mas sim que o participante seja capaz de:

* Receber múltiplas autorizações
* Controlar o estado **PARTIALLY_ACCEPTED** até que todas as alçadas sejam satisfeitas

### Evolução esperada do consentimento

No fluxo do teste:

1. Consentimento é criado em **AWAITING_AUTHORISATION**
2. Primeira autorização ocorre → status **PARTIALLY_ACCEPTED**
3. Consentimento permanece em **PARTIALLY_ACCEPTED** enquanto existirem autorizações pendentes
4. Após todas as aprovações, o consentimento transita para **AUTHORISED**
5. O consentimento pode então ser consumido (**CONSUMED**) dentro do prazo definido pela spec

Portanto, no contexto de **múltiplas alçadas/autorizadores**, o teste está correto ao:

* Esperar o status **PARTIALLY_ACCEPTED**
* Não introduzir pausas manuais
* Validar que o participante gerencie internamente as múltiplas autorizações conforme a spec

Caso o consentimento não atinja **PARTIALLY_ACCEPTED**, ou transite diretamente para **AUTHORISED**, isso indica que o participante não está tratando o fluxo de múltiplas alçadas conforme esperado para este cenário de teste.

Permanecemos à disposição para esclarecimentos adicionais.
