## 📝 Descrição

#### Current Behavior:
---
The automatic-payments_api_sweeping-accounts-backward-compatibility_test-module_v2n1 test (contained in plan automatic-payments_test-plan_v2) has behavior that create a payment using version 1, passing a proxy without creditorAccount. After the tested API execute the payment, reading proxy content and store the creditorAccount (connected with informed proxy), the result of GET using version 2 present the creditorAccount information.

The test show an error: The field 'creditorAccount' MUST NOT be present in the GET recurring-payments response. But there no is restriction for return creditorAccount for a payment created in V1 account, accord with documentation the only restriction for creditorAccount is:

"[Restrição]
Caso o pagamento tenha sido criado utilizando versão 2.0.0 ou superior, o retorno desse objeto é obrigatório pela instituição detentora"

#### Expected Behavior:
---
The test should not point this like a error.

Hello, Daniela. This issue is different from issue #2170. The question is that the test require GET v2/recurring-payment (from using a recurring payment Id created with POST v1/recurring-payment) doesn't return creditorAccount object, as test specification: 

Text of Test: Expect 200 - Validate response, ensure status is ACSC, and confirm that creditorAccount field is not included

Error message raised: The field 'creditorAccount' MUST NOT be present in the GET recurring-payments response

But the API's specification doesn't talk about this behavior:

"[Restrição]
Caso o pagamento tenha sido criado utilizando versão 2.0.0 ou superior, o retorno desse objeto é obrigatório pela instituição detentora"

i.e, there is a restriction for creditAccount to be mandatory for payment created using version 2.0.0. Our understanding reading the text is payment created using version 1.0.0, use GET recurring-payments for version 2.0.0 creditAccount object can be returned or not, i.e., return is not a problem.
