## 📝 Descrição

The `resources-api-dcr-happyflow` test is requesting a hardcoded client registration to our authorization server with all scopes from phase 2, but our authorization server does not support all these scopes, so the client is registered with only the scopes we support.

During response validation step, the `CheckScopesFromDynamicRegistrationEndpointContainRequiredScopes` class checks if the registered client has ALL phase 2 scopes, but in my understanding the authorization servers do not need to support all phase 2 scopes.

Error message:

```
'scope' in dynamic registration response does not contain the required scopes as specified in the test configuration.
```

This behavior has been added on this [Merge Request](https://gitlab.com/obb1/certification/-/merge_requests/416), and related to this [issue](https://gitlab.com/obb1/certification/-/issues/119). 


Does this validation really make sense?

test log details: https://web.conformance.directory.openbankingbrasil.org.br/log-detail.html?log=3h5oLApPZKTJpxT

I'm supposing you are talking about https://gitlab.com/obb1/certification/-/issues/119 which says that the bank may return an error if no server supported/usable scopes are requested by the client. 

On this case, the bank indeed returns an error but only because an unusable set is sent. Given that on the test we are asking for the whole set of scopes the bank shouldn't return an error as at least a subset of the scopes must be supported by the server, otherwise, it shouldn't even be participating in this phase.

In case you ask for a scope that the bank does not support (e.g. credit-card-accounts) I believe the bank should not return an error as this just put the burden over the TPP, which would have to check which scopes are supported before doing the DCR. This would be similar to the behavior defined on the consents API: https://openbanking-brasil.github.io/areadesenvolvedor/versions/v1.0.0-rc8.1/swagger/swagger_consents_apis.yaml

>    A transmissora deve retornar, da lista de permissions requisitadas, apenas o subconjunto de permissions por ela suportada, removendo da lista as permissions de produtos não suportados e retornando HTTP Status Code 201. Caso não restem permissões funcionais, a instituição transmissora deve retornar o erro HTTP Code "422 Unprocessable Entity".

>   The server must return, from the list of requested permissions, only the subset of permissions it supports, removing the permissions of unsupported products from the list and returning HTTP Status Code 201. If there are no functional permissions left, the transmitting institution must return the error HTTP Code "422 Unprocessable Entity".

I'm not entirely sure the specs are specific about this. As it's the DCR response it's really https://github.com/OpenBanking-Brasil/specs-seguranca/blob/main/open-banking-brasil-dynamic-client-registration-1_ID2.md that's relevant.

As far as I remember the expected behaviour for DCR in other tests is that server either returns an error or removes the problem scopes, albeit those tests are checking scopes allowed by regulatory roles rather than scopes supported by server.

So I don't think the requested change is the way to go, as it'll probably result in some servers failing the test - returning an error from DCR because we request unsupported scopes preventing the test from continuing.

I think there's a few ways we could go here:

1. reduce the requested scopes to just the ones that server supports by looking at scopes_supported in openid-configuration, checking that at least one phase 1 scope remains

2. get clarity from the specs groups that servers should ignore scopes that are requested but not supported by the server

3. remove `scopes` from the request and allow the server to populate it, probably checking that at least one phase 1 scope remains.


'1' isn't great as it's more complex for clients, so probably '2' or '3' is better.
