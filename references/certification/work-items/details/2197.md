### Comentário 3
**Autor**: Daniela Muller (@danielamllr)

Hi,

Analysing the logs, we identified that the problem occurred at a stage prior to validating the consent status. 

Before the ‘Validate Consent Self Link’, CS tried to make a GET call to the endpoint `recurring-consents/urn:bancodobrasil:4AF80B8307A34ED09AF3B8598AE28056E`. In this call, CS received a ‘Read timed out’ error, indicating that your server took more than 15 seconds to respond.

![image.png](/uploads/9695495b3d675da04c22a78431e3873c/image.png)

Here's what happened: 

*  Conformance Suit tries to validate the selfLink received, which implies making a GET to that URL. At this point, your API timeout occurred. 
* When the **EnsurePaymentConsentStatusWasAuthorised** validator is run, it validates the consent status based on the **last** status information that CS managed to store **successfully**. As the last GET attempt resulted in a timeout, CS used the status it had previously (`AWAITING_AUTHORISATION`) for validation, instead of the `AUTHORISED` that its API intended to return in the call that suffered the timeout.

In short, the test failed due to your API's timeout on the `GET recurring-consents/{consentId}` call. The incorrect status reported (`AWAITING_AUTHORISATION`) is a consequence of this timeout, and not a problem with the final status your API tried to send.

Please review your server's response time for GET recurring-consents/{consentId} calls.

If you still have any doubts, please let us know.
