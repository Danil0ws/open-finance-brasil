Hi @lcoquenao 

Thank you for the detailed report.

For **`consents_api_negative-extensions_test-module_v3-3-1`**, the test module is explicit: after the two negative extension calls (which must return **422** with `DATA_EXPIRACAO_INVALIDA`), the runner issues further **POST** calls to the consent **extension** endpoint with:

* `expirationDateTime` at **D+365** → **201 Created**
* **D+730** → **201**
* a fixed far-future value (**`2300-01-01T00:00:00Z`**) → **201**
* omitting `expirationDateTime` → **201**

So a **422** for the **D+365** (or the later) extension steps is **not** aligned with this module’s expectations, even if you treat a one-year horizon as a **soft** product or operational limit elsewhere.

“Soft” limits in guidelines are often recommendations or risk controls; they do not automatically mean the API must reject the request with **422** in every context. For certification, **v3-3-1** is written to assert that those longer (or indefinite-style) extension payloads are **accepted** with **201**, while **422** is reserved for the **specific invalid sequences** defined in the same flow (e.g. shortening the expiry in a way the spec marks as invalid, and the duplicate **D+180** extension case after a successful **D+180**).

If you believe the published Open Banking Brasil specification for your API version **requires** rejection beyond one year, that would be a **spec vs. test summary** discussion with the GP responsible; as implemented today, **v3-3-1** expects success (**201**) for those steps.
