Hi Reginaldo! Thanks for the response!

We understand that it may be causing issues. At the moment, you AS is creating JWt refreshing tokens with the exp claim by D + 1 year on creation. The problem with this approach is that when the consent is extended to indefinite term, it would stop working after one year, making the consent extension useless.

Understanding that changing to opaque tokens may be a big change that would take time, we will evaluate in the WG tomorrow to already implement https://gitlab.com/raidiam-conformance/open-finance/certification/-/issues/1680, which would allow JWT refresh tokens, as long as they don't have the exp claim for phase 2 tests.

Although this may take some changes, it is already an alternative so you are not blocked at the tests. We are checking with the working groups if there is the case where the exp claim could be send with future values, but this is still under evaluation. But sending the refresh token with an exp claim with D + 1 year is not compliant, since it inherently disables consent extension for more than 1 year.

We are happy to help you with any additional needs, and will post updates at #1680 !

Hi Reginaldo,

Since this may be a problem with the specification, we cannot make any changes to the conformance suite without confirmation from the Working Group. The issue arises because the JWT refresh tokens you are sending include the "exp" claim, as the initial consent does not have infinite duration. Once the consent is extended to infinite, the AS is not allowed to rotate refresh tokens. Consequently, the initiator would have to continue using the same refresh token with an "exp" claim in a consent with an infinite term. This would create an interoperability problem, as the consent would be revoked when the "exp" claim is reached.

Therefore, we need clarification from the Working Group on how the AS should handle consent extensions in cases where the refresh token was issued with an "exp" claim, so that the conformance suite can enforce this behavior correctly. Otherwise, we risk creating an invalid scenario within the ecosystem.

We understand the inconvenience this may cause and will request an accelerated discussion on this topic. Please let us know if you need any additional assistance.

We will keep you updated through the #1659
