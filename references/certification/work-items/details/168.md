1. What Happened and what were you expecting?

The conclusion was that the test expects a token bound to a cert to return a 400. 
We return a 401 which I think is compliant with the spec. The failed test refers to https://datatracker.ietf.org/doc/html/rfc7591#section-3.2.2. There it says:
When a registration error condition occurs, the authorization server returns an HTTP 400 status code (unless otherwise specified)

This case, however, is further specified. See section 3 of the same RFC (https://datatracker.ietf.org/doc/html/rfc7591#section-3) which says:

The client registration endpoint MAY be an OAuth 2.0 [RFC6749] protected resource and it MAY accept an initial access token in the form of an OAuth 2.0 access token…

The method by which the initial access token is verified and validated by the client registration endpoint is out of scope for this specification.

This spec doesn’t say how to validate that access token, but RFC 8705 section 2 does (https://www.rfc-editor.org/rfc/rfc8705.html#section-2): If no certificate is presented, or that which is presented doesn’t match that which is expected for the given client_id, the authorization server returns a normal OAuth 2.0 error response per Section 5.2 of [RFC6749] with the invalid_client error code to indicate failed client authentication

5.2 of RFC 6749 says:
The authorization server responds with an HTTP 400 (Bad Request) status code (unless specified otherwise)

So, this makes it sound like the test is right, but it’s not. The unless specified otherwise is still there and this case is further specified. Remember? RFC 7591 section 3 says the registration endpoint “MAY be an OAuth 2.0 protected resource”. Access control to a protected resource is defined by RFC 6750 section 3.1 (https://datatracker.ietf.org/doc/html/rfc6750#section-3.1):

When a request fails, the resource server responds using the appropriate HTTP status code (typically, 400, 401, 403, or 405) and includes one of the following error codes in the response:
invalid_token The access token provided is expired, revoked, malformed, or invalid for other reasons.  The resource SHOULD respond with the HTTP 401 (Unauthorized) status code.

Therefore, 401 in Curity is correct, and the test is wrong because RFC 6750 says to use the “appropriate” status code. This is set forth in RFC 7235 section 3.1 (https://datatracker.ietf.org/doc/html/rfc7235#section-3.1) which says:
The 401 (Unauthorized) status code indicates that the request has not been applied because it lacks valid authentication credentials for the target resource.
If the request included authentication credentials, then the 401 response indicates that authorization has been refused for those credentials.

With this maze of RFCs, I’m not surprised the test authors got this wrong, but they did

That might be the case, @joseph.heenan , but the conclusion is still correct. The error refers to section 3.2.2 of the RFC7591; in section 3 of the same RFC, it says:

> The client registration endpoint MAY be an OAuth 2.0 [RFC6749] protected resource

Because the registration endpoint that this test is calling accepts an access token, it's certainly a protected resource. RFC 6749 says in 5.2 how to respond to errors that are not specified elsewhere. Section 7 of the same RFC though says that errors accessing protected resources is defined in RFC6750. So, that RFC says that this case is further specified. 

In RFC 6750 section 3.1, it says:

> When a request fails, the resource server responds using the _appropriate_ HTTP status code ... and includes one of the following error codes in the response: invalid_token [when the] access token provided is ... invalid for other reasons. The resource [e.g., the registration endpoint] SHOULD respond with the HTTP 401 (Unauthorized) status code.

Furthermore, RFC 7235 section 3.1 says that the appropriate status code is 401. 

Since 6750 says the resource SHOULD respond with a 401, I suppose 400 is actually correct. But, 401 is certainly correct as well.

For this reason, the test needs to be updated to accept either status code.
