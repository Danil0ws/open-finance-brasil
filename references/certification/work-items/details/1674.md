## 📝 Descrição

The fido-registration-options step on the tests bellow is validating the json response with differences from the swagger specified and the previous builds of the tool. It seems the tool is not resolving the response from the fido-registration-options with the attribute credProps as string as the spec requires, but waiting for a response with boolean.
 

#### Current Behavior:
---
The tool waits the attribute credProps as a boolean not string.

#### Expected Behavior:
---
The tool needs to pass equals the previous releases following the specification, or maybe update the specification on swagger to avoid futures misled.

Hi Hugo,

Thanks for opening this ticket!

The [**Enrollments API specification**](https://openbanking-brasil.github.io/openapi/swagger-apis/enrollments/?urls.primaryName=1.2.0#/V%C3%ADnculo%20de%20dispositivo/enrollmentCreateFidoRegistrationOptions) claims that:

![1.png](https://gitlab.com/-/project/26426113/uploads/174743ded976bf178618ae3480a1a3c3/1.png)**Where “\< \* \>: string”** indicates that any string can be used as a key in this object, and the corresponding value must be a string.

This means that any object contained within the extension element must be of type string.

Altough CredProps are valid extensions for the Authorization Server, as specified in the [Web Authentication (WebAuthn)](https://www.iana.org/assignments/webauthn/webauthn.xhtml) documentation, which determines the possible extensions, we have the following definition for the credProps property:

---

[**10.4. Credential Properties Extension (credProps)**](https://www.w3.org/TR/webauthn-2/#sctn-authenticator-credential-properties-extension:\~:text=10.4.%20Credential%20Properties%20Extension%20(credProps))

**Client extension output**

```
dictionary CredentialPropertiesOutput {
    boolean rk;
};

partial dictionary AuthenticationExtensionsClientOutputs {
    CredentialPropertiesOutput credProps;
};
```

---

The aforementioned extract determines that the credProps field should assume the type boolean when included in the response from the authorization server.

We also have the following definitions for other properties:

---

[**10.6. User Verification Index Extension (uvi)**](https://www.w3.org/TR/2019/REC-webauthn-1-20190304/#sctn-uvi-extension:\~:text=10.6.%20User%20Verification%20Index%20Extension%20(uvi))

**Client extension output**

Returns the authenticator extension output as an ArrayBuffer.

```
partial dictionary AuthenticationExtensionsClientOutputs {
  Coordinates loc;
};
```

---

[**10.7. Location Extension (loc)**](https://www.w3.org/TR/2019/REC-webauthn-1-20190304/#:\~:text=10.7.%20Location-,Extension,-(loc))

**Client extension output**

Returns a JavaScript object that encodes the location information in the authenticator extension output as a [`Coordinates`](https://www.w3.org/TR/geolocation-API/#coordinates_interface) value, as defined by \[Geolocation-API\].

```
partial dictionary AuthenticationExtensionsClientOutputs {
  ArrayBuffer uvi;
};
```

---

[**10.8. User Verification Method Extension (uvm)**](https://www.w3.org/TR/2019/REC-webauthn-1-20190304/#sctn-uvm-extension)

<dl>
<dt>Client extension output</dt>
<dd>Returns a JSON array of 3-element arrays of numbers that encodes the factors in the authenticator extension output.</dd>
</dl>

```
typedef sequence<unsigned long> UvmEntry;
typedef sequence<UvmEntry> UvmEntries;

partial dictionary AuthenticationExtensionsClientOutputs {
  UvmEntries uvm;
};
```

---

While with boolean extension types, the conversion to string may be simple and seamless, these other extension types should assume the format of loc, array or Json Objects as described above.

In cases where all extension types should be turned into strings, transforming extensions like the Location Extension and User Verification Index extension into strings could be detrimental for data processing. If the intent is for this data to be readable by the relying party, transforming these extension types to strings would require significant effort for transformation and interpretation by the other party.

For this reason we will be raising this issue for evaluation of the appropriate Work Group. What we need to understand is:

* Should the Conformance Suite expect that all possible extensions, and their contained elements, types assume a string format, even though this may truncate objects and other data types which would be detrimental for data processing?
