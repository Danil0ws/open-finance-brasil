#### Current Behavior: 

O motor de conformidade está reportando o status de **WARNING** para três testes específicos dentro do plano da API de Pagamentos V5. O motor de validação sinaliza a presença do cabeçalho HTTP customizado `'x-ca-err'` na resposta. Embora o fluxo funcional seja concluído com sucesso, a presença deste campo impede que os testes atinjam o status "PASSED", impactando o marco de 100% de conformidade.

Este cabeçalho é um campo proprietário retornado pelo nosso **Gateway Layer7**, que atua como firewall e porta de entrada dos nossos servidores. Ele é utilizado especificamente para auxílio na identificação de erros e diagnósticos internos durante o processo de autenticação **OAuth2**.

---

Describe the behavior you are currently experiencing. What is happening that you believe is incorrect or unexpected?

#### Expected Behavior: 

A suíte de conformidade deve reportar o status como **PASSED**. De acordo com o princípio de extensibilidade em APIs RESTful, clientes e motores de teste devem ignorar cabeçalhos desconhecidos ou adicionais que não interfiram no payload principal ou na lógica de negócio.

Além disso, nossa instituição já é **certificada no OAuth2** utilizando exatamente esta mesma infraestrutura e configuração de cabeçalhos. Como o comportamento é consistente com padrões de segurança já certificados anteriormente e não impacta a interoperabilidade, ele não deve ser considerado uma falha válida ou motivo de ressalva.

Prezado @rafaelsspaiva, agradecemos o reporte.

O `x-ca-err` não está sendo lido como cabeçalho HTTP. A condição que gera o WARNING (`CheckForUnexpectedParametersInErrorResponseFromAuthorizationEndpoint`) valida apenas os parâmetros do redirect do Authorization Endpoint. Nos três logs, ele aparece no fragment da URL do callback:

`#error=access_denied&error_description=...&x-ca-err=3002124&state=P92vKkYbEk`

Ou seja, o gateway está anexando `x-ca-err` à URL de redirect, e não a um header de resposta de API.

O requisito `OIDCC-3.1.2.6` define um conjunto fechado de parâmetros para a resposta de erro do Authorization Endpoint (`error`, `error_description`, `error_uri`, `state`, `session_state`, `iss`).

O ajuste precisa ser feito no provedor de autorização, removendo o `x-ca-err` da URL de redirect. 

Feito o ajuste, os três testes devem passar sem o WARNING.
