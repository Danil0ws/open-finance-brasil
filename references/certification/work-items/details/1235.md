## 📝 Descrição

## 1\. What happened and what were you expecting?

After the consent status is changed to CONSUMED, the CS is requesting the POST recurring-payments endpoint and expecting a 401 response. We believe this is not the right status code to be used in this situation, as it should be used only for authentication problems such as invalid token or missing/invalid authentication headers as stated in [Códigos de Resposta HTTP](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/17377374/C+digos+de+Resposta+HTTP), which is not the case.

![image](/uploads/e510fa1ffa5c69d169dccf7764df775d/image.png){width=482 height=135}

Trying to create a payment using an already CONSUMED consent is a business rule validation and a 422 response would be the correct status code.

Hi All, thanks for the ticket!

For this specific behavior, according to the s[ecurity specs](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/245760001/EN+Open+Finance+Brasil+Financial-grade+API+Security+Profile+1.0+Implementers+Draft+3#7.2.2.-Authorization-server), the authorization server: 

1. shall only share access to resources when presented access_token linked to an active consent and with the status "AUTHORISED“. For tokens generated with the scope: payments, the status of the consent will not be validated.
   1. In the scenario of receiving an invalid token, status code 401 should be returned.

In this specific case, although we understand that there is a 422 error message at the spec where this behavior would also be applied, since the token is invalid, the API should not even validate the business rule (which is the case for the 422).

In that sense, even though there is the 422  CONSENTIMENTO_INVALIDO error message, ia 401 should be returned since the request should not even have access to the business rules.

We are happy to help with any additional needs!

Hi @caio.tranjan 

I'm reopening this issue, as the problem in question is the expected response status code AFTER the consent has changed to consumed and an attempt to create a payment using it is made.

The attempt to create a payment using an already CONSUMED consent should be blocked by using `422 CONSENTIMENTO_INVALIDO`, a behaviour already defined in the specification (print below). 

As stated before, the 401 status code should only be used for authentication problems such as invalid token or missing/invalid authentication headers. As the tokens are present and valid, this is not the case in this test module.
