## 📝 Descrição

We have identified a problem in the account comparison logic:

In both POST and GET requests of the Automatic Payments API, the account number is sent with the check digit.
However, in the Accounts API when listing accounts, the account number and the check digit are returned separately.
The engine is currently comparing the account (with check digit) returned by the Automatic Payments API against the account without the check digit from the Accounts API list, causing mismatches.


Technical Details

Current Behavior:

- Automatic Payments API:

   - POST /automatic-payments and GET /automatic-payments/{id} → accountNumber includes check digit (e.g., 12345-6).

- Accounts API:

    - GET /accounts → returns accountNumber and checkDigit as separate fields (e.g., accountNumber: 12345, checkDigit: 6).

- Engine compares 12345-6 with 12345, resulting in failed matches.

Expected Behavior:

- Normalize account representation before comparison:

   - Either concatenate accountNumber + checkDigit from Accounts API or split the combined value from Automatic Payments API.

- Ensure consistent format across APIs for validation and matching.

Impact

- Incorrect account matching prevents successful execution of automatic payment workflows.
- May lead to transaction errors and compliance issues.

"debtorAccount": {

"ispb": "00000000",

"issuer": "551",

"number": "0000141534",

In the **POST /automatic-payments/v2/recurring-consents**, the request sent by the Conformance Suite was:

"debtorAccount": {

"ispb": "00000000",

"issuer": "0551",

"number": "00141537",

The Conformance Suite is sending the account number **00141537** in the POST consent request because this value is defined in the configuration form:

`"debtorAccountNumber": "00141537",`

Therefore, the mismatch between the numbers (**00141537** vs. **0000141534**) is not related to the CS comparison logic but rather to the values returned and configured in the config form.
