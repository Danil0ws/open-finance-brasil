## 📝 Descrição

Prezados, boa tarde.

Com a conclusão da issue #2210 foi possível seguirmos com a execução de mais alguns cenários de teste da portabilidade de crédito.

No cenário "credit-portability_api_cancelled-portability_test-module_v1", logo após o pedido de portabilidade de crédito ser realizado, ou seja, portabilityId com status RECEIVED, é realizada a comunicação de cancelamento informando 'rejectedBy' como "PROPONENTE" e o 'reason.type' como "CANCELADO_PELO_CLIENTE", e espera o retorno de sucesso.

![image](/uploads/40a5e9a7291cc95da7b9ea47cb4f03c0/image.png){width=529 height=345}

Porém, segundo a máquina de estados, o cancelamento da portabilidade em status RECEIVED, é uma ação que pode ser realizada somente pelo cliente (apesar de ser atualizada pelas IFs).

![image](/uploads/53c8a329e0d35143847060ee399eaf94/image.png){width=1047 height=650}

O que nos leva ao entendimento de que 'rejectedBy' não poderia ter o valor "PROPONENTE", pois o atributo indica o responsável pela ação de cancelamento e não o responsável pela comunicação dele.

![image](/uploads/5cd5637dfeeb961d7f1fb0ce9b0154f2/image.png){width=927 height=232}

Poderiam verificar se o comportamento do cenário está correto?

Following discussions and alignment of the the behavior os this test module along with the WG, it's behavior will be changed for beta.3 that is being released on the 27th of june!

```
Ensure that a portability request reaches status "CANCELLED".
This test requires the user to have at least one CREDITO_PESSOAL_CLEAN contract with portability-eligibility status as DISPONIVEL and isEligible as 'TRUE'.
This test also requires action from the tester. It will poll for 10 minutes, waiting for the portability status transition to "CANCELLED".
• Call the POST /consents endpoint with 'Credit Operations' permission group(s)
• Expect 201 - Validate Response and ensure status as AWAITING_AUTHORISATION
• Redirect the user to authorize consent
• Call the GET /consents/{consentId} endpoint
• Expect 201 - Validate Response and ensure status is AUTHORISED
• Call the GET Loans Contracts endpoint
• Expect 200 - Validate the response and retrieve all contractIds with productSubType as CREDITO_PESSOAL_SEM_CONSIGNACAO
• Call GET /credit-operations/{contractId}/portability-eligibility for each contractId until one is found with status "DISPONIVEL" and isEligible is 'TRUE' is found
• Call the GET Loans Contracts/{contractId} endpoint
• Expect 200 - Validate the response
• Call the GET Loans Contracts/{contractId}/scheduled-installments endpoint
• Expect 200 - Validate the response and retrieve dueInstalments
• Call the POST /portabilities endpoint with proposedContract totalNumberOfInstalments equal to the original contract dueInstalments
• Expect 202 - Validate the response according to the specification
• Call the PATCH /portabilities/{portabilityId}/cancel endpoint sending rejectedBy as 'USUARIO' and reason.type as 'CANCELADO_PELO_CLIENTE'
• Expect 200 - Validate the response according to the specification
• POLL the GET /portabilities/{portabilityId} for up to 10 minutes while the status is RECEIVED or PENDING
• Expect 200 - Validate the response and ensure the status field is equal to "CANCELLED" and statusReason.reasonType is 'CANCELADO_PELO_CLIENTE'
```
