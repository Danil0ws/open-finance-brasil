### Comentário 2
**Autor**: Erick Domingues (@erick.domingues1)
**Criado em**: 16/12/2022, 15:22:57

Currently, the Conformance Suite will expect the following:

If we break the API contract we will accept:
- 422 with either PARAMETRO_NAO_INFORMADO or PARAMETRO_INVALIDO
- 400 - BAD REQUEST

Here the qrCode field is set as optional so it not breaking an API Contract, meaning we won't accept a 400 return here. However, assuming we were not sending a mandatory field we would accept a 400, which is the case for the E2EID.  as we are still breaking a business rule the 422 would be expected and, on that dimension, the most precise error code as defined by the WG would be PARAMETRO_NAO_INFORMADO

The Conformance Suite team here is merely following the definitions from the WG that defined that the "DETALHE_PAGAMENTO_INVALIDO" should only be used if there is no other code that could be used, which in this case is  "PARAMETRO_NAO_INFORMADO".

If you disagree my suggestion would be to go directly to the WG to have this discussed, as we really don't have any preference on our side.

I strong believe that **mandatory fields** should follow the Swagger specification and the patterns documentation which says that required fields that are not sent in the request must return HTTP 400 as the image below:

![http-400-opb](/uploads/f925d4b2a43ad41aab82f614d6968fbc/http-400-opb.png)

This new rule of returning HTTP 422 for non mandatory fields came out in this v2 release. So far we have been following a pattern for all APIs which is HTTP 400 for non mandatory fields sent over the request.

Besides, this documentation shows a table where the pattern is to use HTTP 400 for mandatory fields.
https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/17377374/C+digos+de+Resposta+HTTP


422 Unprocessable Entity.
Well formed request but business rules where responsible for the error.

400 Bad Request.
Bad formed request leaving out mandatory attributes in the payload or in the URL.

### Comentário 4
**Autor**: Erick Domingues (@erick.domingues1)
**Criado em**: 15/12/2022, 17:48:33

On the latest API we have the following guidelines regarding error code validation:

1.3.1.1 Envio de campos obrigatórios: Valida se todos os campos obrigatórios são informados (PARAMETRO_NAO_INFORMADO);  

1.3.2.3 Detalhes do pagamento: Valida se determinado parâmetro informado obedece às regras de negócio (DETALHE_PAGAMENTO_INVALIDO);  

On the test, we don't send the field qrCode which in this case is a mandatory field. For this reason, we believe PARAMETRO_NAO_INFORMADO is the best error response.

Here the proposal for DETALHE_PAGAMENTO_INVALIDO is use it just when there's no better error codes for it.
