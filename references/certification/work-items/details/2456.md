## 📝 Descrição

Description:

Context: We are running the conformance test script: **HYAa2mXEkL8AU4**. The test scenario validates that a Recurring Consent for Sweeping Accounts cannot be successfully authorized via the Enrollments (No-Redirect) flow.

![image](/uploads/6bd47c7a5f0c7f0ceeaa79824ee2785c/image.png){width=900 height=122}

Current Test Expectation: The test expects the ASPSP to:

Receive the POST .../authorise request.

Return HTTP 204 (No Content).

Asynchronously update the Consent Status to RJCT.

Our Implementation Behavior: Our ASPSP performs synchronous business rule validation. Upon receiving an authorization request for a Sweeping consent through the Enrollment channel, we immediately identify this as an invalid operation. Therefore, we return HTTP 422 (Unprocessable Entity) with the standard error code PARAMETRO_INVALIDO.

Argument for Change: We believe that the test should not impose a specific architectural pattern (i.e., forcing asynchronous validation) on ASPSPs. The handling of business rules—whether synchronous (fail fast) or asynchronous—depends on each institution’s architecture.

Since both approaches effectively prevent the prohibited operation, the test engine should be flexible enough to accept valid architectural choices. Rejecting a request synchronously with HTTP 422 is a standard and secure RESTful practice.

Request: We request that the test script be updated to accept both scenarios:

HTTP 204 (for asynchronous validation).

HTTP 422 (for synchronous validation), provided that the error code is aligned with the rejection reason.

For the 204 scenario, the consent is automatically returned as RJCT after a subsequent GET request, with the rejectReason set to FLUXO_NAO_SUPORTADO_PRODUTO.

For the 422 scenario, the consent remains in AWAITING_AUTHORIZATION, since it will eventually expire and transition to RJCT after a defined period.

This behavior is expected, as there is no linkage between the consent and the enrollment itself; such linkage only exists once authorization is performed.

Hello @gabriel.vasconcelos1 and @pedro_alcantara.

We reviewed this issue with the DTO team. Currently, the Automatic Payments API specification **does not have a synchronous validation error code** for this scenario. The validation exists **only asynchronously**, after the corresponding GET request is executed. Because of this, the current flow requires **creating the consent** and then **rejecting it asynchronously**.

At this moment, the Open Finance Structure recommendation is:

* The test behavior is correct.
* The PARAMETRO_INVALIDO error must not be used in this case, as it represents a syntactic error, not a business-rule validation.
* The implementation must handle the asynchronous error.

Additionally, there is already a follow-up to include this validation synchronously in a future version, at which point the behavior and tests may be updated.

Please feel free to reopen this issue if needed, or to share any additional points with the Open Finance Working Groups.
