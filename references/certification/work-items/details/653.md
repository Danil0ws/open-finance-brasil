## 📝 Descrição

Hi, I am wondering if there could be some clarification for this update to the security profile documentation, specifically when reading these clauses together:

1. should only issue _refresh tokens when linked with an active and valid consent; 
    a. Must not issue refresh_token when consent is in “CONSUMED” status (for phase 3);
    b. It must issue an access_token through a grant_type of type client credentials in status “CONSUMED” (for phase 3).
2. must only share access to resources when presented _access token linked to an active consent and with the status "AUTHORIZED"; 
    a. In the scenario of receiving an invalid token, status code 401 should be returned. 


How should these two points be interpreted when it comes to token issuance from the authorization server. The way I’m reading it is:
```
access tokens should only be issued if the consent is active and valid OR the consent is consumed and a grant_type of client_credentials is used
```
and
```
refresh tokens should only be issued when the consent is active and valid — no exceptions 
```

Am I interpreting these correctly? Point 2 and point 1b seem to conflict with each other, so the only interpretation I can think of is this OR case that I’ve stated.

Hi Dylan! Thanks for the question!

Your interpretation is right. The main issue for the change is that the refresh_token should only be issued or issue a new access token if the consent is not consumed, using the authorization_code flow. Other than that, the requests should all be done using the client_credentials flow, so you assertion is correct, since you can either issue an access token via authorization code when the consent is active, or issue and access token via client_credentials if the consent is already consumed, so you access a GET endpoint, for example.

We are happy to answer any other questions!
