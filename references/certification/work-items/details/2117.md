#### Current Behavior:
---
When performing the PATCH request on the recurring-consents endpoint, the expirationDateTime is updated to D+0. Immediately after, the test attempts to create a payment with the date set to D+2.

#### Expected Behavior:
---
The expirationDateTime must be later than the payment date.

Hi @JoJowam 

As stated in: https://gitlab.com/raidiam-conformance/open-finance/certification/-/issues/2068

The test is working as expected and according to the current v2.0.0-rc.1 that is available in the developer portal.

Therefore there are no changes to be done in this test module until the release of the new stable version of the API

You can find more information about the Changes introduced in the specification of the new version below:

---

The behavior of this test module will only be changed with the new **v2.0.0 stable version** of automatic pix payments.

For this version it was introduced the following braking change in the specification:

> Enforce Rejection of Payments with Scheduled Date after Consent Expiration
>
> **Change:**
>
> A new validation rule is added to ensure that payments are rejected if their scheduled date exceeds the expiration date of the associated consent.
>
> **New Rule:**
>
> * If the payment’s scheduled date is later than the consent expiration date, the request must be rejected.
> * The rejection reason must be **FORA_PRAZO_PERMITIDO**, with a detailed description of the cause in the response.

Therefore, once the **stable** version is released the test module behavior will be changed to:

<table>
<tr>
<td>

Ensure consent edition can be applied to make more restrictive limits

• Call the POST recurring-consents endpoint with automatic pix fields, with referenceStartDate as D+1, not sending the expirationDateTime, interval as SEMANAL, a maximumVariableAmount of 0.50 BRL, and not sending firstPayment information\
• Expect 201 - Validate Response and ensure status as AWAITING_AUTHORISATION\
• Redirect the user to authorize consent\
• Call the GET recurring-consents endpoint\
• Expect 201 - Validate Response and ensure status is AUTHORISED\
• Call the PATCH recurring-consents endpoint with consent edition, sending creditor name as "Openflix" and expirationDateTime as D+0 \
• Expect 201 - Validate Response and ensure status is AUTHORISED\
• Call the GET recurring-consents endpoint\
• Expect 201 - Validate response, ensure status is AUTHORISED and and ensure that fields are as the PATCH Request, and that the field updatedAtDateTime has been updated\
• Call the POST recurring-payments endpoint with amount as 0.50 BRL, date as D+2\
• Expect 422 FORA_PRAZO_PERMITIDO or 201 - Validate Response\
If a 201 is returned:\
• Poll the GET recurring-payments {recurringPaymentId} while the Status is RCVD or ACCP\
• Call the GET recurring-payments {recurringPaymentId}\
• Expect 200 - Validate Response and ensure status is RJCT, ensure that rejectionReason.code is FORA_PRAZO_PERMITIDO
</td>
</tr>
</table>
