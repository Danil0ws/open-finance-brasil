## 📝 Descrição

#### Current Behavior:
---
Right after rejecting an enrollment and verifying that its status has been changed to REJECTED, the CS attempts to make a request using an access token linked to this enrollment to access the POST fido-registration-options. The CS expects a HTTP 422 response.

#### Expected Behavior:
---
Considering that the token is linked to a rejected enrollment, a request to POST fido-registration-options could also result in HTTP 401.

Thanks for opening the issue!

According to securty specification:

> #### 7.2.2. Authorization server
>
> 1. shall only share access to resources when presented access_token linked to an active consent and with the status "AUTHORISED“. For tokens generated with the scope: payments or recurring-payments, the status of the consent will not be validated.
>    1. In the scenario of receiving an invalid token, status code 401 should be returned.

The documentation specifies this behavior in case of a Consent that is not in status "AUTHORISED“. Although this is not the case in this teste module, as there is no consent involved and the enrollment is the one which transitioned from Authorised to Rejected. Therefore the rejection of the enrollment should not invalidade the access token being used.

Also, the security spec introduces the following restriction: "For tokens generated with the scope: payments or recurring-payments, the status of the consent will not be validated." As the enrollment uses the payment scope, this invalid token scenario should not be validated.

With that in mind, Conformance Suit is working as expected waiting for a 422 STATUS_VINCULO_INVALIDO.
