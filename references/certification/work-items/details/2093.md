The expected behavior of this test is to ensure that a payment cannot be scheduled if the creditorAccount used in the payment request does not match the creditor defined in the consent.

Although the recurring-consents endpoint does not explicitly contain a creditorAccount field, it does store creditor information such as:

personType
cpfCnpj
name

These fields provide enough data to verify and match the information provided when creating a payment, even if the firstPayment field was not included in the consent.

Why the Test Fails?
**1️⃣ First Payment Validation:**

The first payment is created using a defined creditorAccount.
This account belongs to the creditor identified in the consent.

**2️⃣ Second Payment Attempt:**

A subsequent payment is attempted using a different creditorAccount number.
The test expects the system to reject this transaction with 422 - PAGAMENTO_DIVERGENTE_CONSENTIMENTO.

**3️⃣ Validation Rule:**

The creditorAccount number must align with the creditor's information stored in the consent.
If a different account is used, it breaks the consistency between the consented entity and the payment execution.

**Summary of the Expected Behavior:**

Payments should only be made to the creditor established in the consent.

If a different creditorAccount is used, the test should fail, either synchronously or asynchronously.

The matching process is based on the creditor’s CPF/CNPJ, name, and personType, ensuring that the account used for payment truly belongs to the authorized creditor.


Let us know if you need further clarification!
