Hi,

Thanks for opening the ticket!

After analyzing the provided test log, we are able to assess that the test module failed during step:

• Call GET Consent\
• Expects 200 - Validate if status is "CONSUMED"\
• Calls the POST Payments with the EndtoEndId field\
**• Expects 422 CONSENTIMENTO_INVALIDO - Validate error message**

During test module execution, the Conformance Suit makes two POST /pix/payments using the consent Linked to the same access token with grant_type Authorization Code.

During the first POST /pix/payments request the payload is created without the EndtoEndId field so that a 422 error is sent on response by the authorization server, ensuring that the consent being used gets consumed.

During the mentioned steps, the Conformance Suit makes a payment request for the second Time, using the consumed consent, and expects a **422** **CONSENTIMENTO_INVALIDO** failures in the response.

As can be seen from the test log, instead of returning a **422** **CONSENTIMENTO_INVALIDO** response for this request, the Authorization Server returned a 201, providing the full 201 payload with links fields.

Given that field self link was provided in the response, conformance suit proceeded to validate it, this is done by calling a GET request to the endpoint contained in this Self Link field.

As this GET request was triggered by a unexpected 201 response containing the Self Link field in the payload, Conformance Suit is working as expected, the error lies in the incorrect 201 response for this request. In the expected case in which a **422** **CONSENTIMENTO_INVALIDO** is returned in the response, as defined by the specification, there are no Links on the 422 response payload, and therefore this GET request would not be created.

Therefore, to ensure test module can be executed successfully, make sure the correct response is sent on response payload when a payment request is made using a token linked to a consumed consent.
