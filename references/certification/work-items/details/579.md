Hi all! Thanks for the replies.

Since this issue had a conflict inside documentation we have taken it to discussion with the Specs Working Group, and the solution was:

"O código a ser usado deverá ser o 403.
 
No header da API, as orientações sobre validações semânticas da API de Pagamentos citadas nos itens 1.2.4.1 e 2.1.4.1 serão revisadas através da inclusão de um item a lista de problemas conhecidos orientando que o código de erro utilizado deverá ser o 403 e não mais o 400."

In that sense, the test will remain expecting 403.

First we need to validate the message's iss and signature, if the message comes with an invalid iss, we will always return 400 as it is one of the first validations to be performed.
According to the [specification](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/24182973/Assinatura+de+Mensagem+vs+Idempot+ncia+-+v2.0.0+-+Pagamentos), validations related to message signatures must precede idempotency validations.

Hi Mauricio! Thanks for the ticket!

The [Idempotency specs for Phase 3v2](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/24182812/Idempot+ncia+-+v2.0.0+-+Pagamentos) specifies that:

3. Ao receber uma requisição com o mesmo x-idempotency-key e com a claim iss não pertencente a organização que possui o software cliente (clientId) a requisição deve ser recusada com o HTTP Status 403;

In that sense, since the specific case where we have the same idempotency key and different iss is explicitly stated in the documentation, the expected response is 403.

Please, feel free to reopen the issue if you disagree! Happy to help with any other issue!
