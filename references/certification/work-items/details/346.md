## 1. What happened and what were you expecting?
According to Open Finance Informa 200, we understand that should not fail a request that has any valid ICP-Brasil chain certificate. So we are not performing a certificate validation over software. 

Regras para autenticação de DCM
 
_Informamos que as regras previstas na autenticação do cliente para sua manutenção (DCM) são as seguintes:

*validar que o certificado apresentado pela aplicação cliente é subordinado às cadeias do ICP-Brasil definidas no Padrão de Certificados do Open Finance Brasil;
*validar a presença e a correspondência do header Bearer Authorization contendo o valor do atributo registration_access_token retornado durante o registro do cliente correspondente.
 
Solicitamos que instituições participantes que estiverem realizando validações adicionais (por exemplo: validação do subject_DN) se adequem à documentação de Segurança._

What has been brought to me by the Squad Sandbox is that your certificate must match the SSA **being present on the request** and not the SSA previously registered. 

Assuming the above is true we would have the following changes:

1) For the GET no SSA is presented so just validating the refresh_token and that the cert is issued from ICP Brasil should be enough. So this step should be a success:

• Attempts 'GET' on client configuration endpoint using MTLS certificate for the second client -> Expects Failure

2) For the PUT we should switch the used SSA so we use the first SSA with the second certificate which then would be a failure. Currently, as it is, it can be assumed as a PASS

 Using the second client with only the DADOS role retrieves from the directory its SSA
• Performs a PUT on the registration endpoint with the configuration from the second client -> Expects a failure

Let me know what you think?
