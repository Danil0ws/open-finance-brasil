#### Current Behavior:

---

Tentamos implementar diferentes formas para passar no dailyLimit_test da JSR. O pagamento está sendo recusado e avaliado corretamente, após isso, o consentimento está sendo avaliado (e é onde estão os problemas de validação).

Por exemplo, atualizando o consentimento para status `CONSUMED`, o teste mostra um `Warning`, mas acaba finalizando com erro indicando que esperava `rejectionReason`, mesmo sem o status ser `REJECTED`.

Nossa solução mais promissora (a que gerou menos erros de validação), foi rejeitar o consentimento também. No entanto, o teste falha com a seguinte mensagem:

```markdown
GetPaymentsConsentValidatorV4
Value from element expirationDateTime is older or younger then the required limit on the Get Payments Initiation Consent V4 API response
```

No entanto, entendemos que o motor está validando o horário de expiração de forma inadequada. Muito provavelmente considerando 5 min antes da autorização, não os 60 minutos válidos após autorização.

#### Expected Behavior:

---

O consentimento realmente deveria ser avaliado? Essa validação da data de expiração (`expirationDateTime`) é realmente necessária? A data limite para o `expirationDateTime` do consentimento considera corretamente 1 hora após a autorização?

Regarding the status, we understand that the Consent should go to CONSUMED as described at the [State Machine](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/347078805/M+quina+de+Estados+-+v4.0.0+-+SV+Pagamentos#CONSUMED):

* O consentimento assume o status CONSUMED após ocorrer o processamento da iniciação do pagamento, seja ele com sucesso (HTTP 201) ou ainda em casos de insucesso (HTTP 422) retornados pela Detentora. Para os demais códigos HTTP não há mudança de status do consentimento, o mesmo permanecerá AUTHORISED, respeitando o tempo máximo de expiração do consentimento (60 minutos).

<span dir="">In that sense, the test module </span>**enrollments_api_excessive-dailyLimit_test-module_v1** should be updated as <span dir="">follows</span>:

Ensure consequent payments cannot be executed if the amount is over the expected dailyLimits\
• GET an SSA from the directory and ensure the field software_origin_uris, and extract the first uri from the array\
• Execute a full enrollment journey sending the origin extracted above, extract the enrollment ID, and store the refresh_token generated ensuring it has the nrp-consents scope\
• Call the GET enrollments endpoint\
• Expect a 200 response - Validate the response and check if the status is "AUTHORISED", and extract the transactionLimit and dailyLimit sent\
• Execute full payments for today using no redirect flows with the transactionLimit sent, until the dailyLimit is exceed\
\
In the last flow, execute the below:\
• Call the POST Payments Consents V4 Endpoint, with the amount as with the transactionLimit sent, with the payment.date for today\
• Expect 201 - Validate Response\
• Call the POST Fido Sign Options Endpoint\
• Expect 204\
• Call the POST Consent Authorise Endpoint\
• Expect 204\
• Call POST Pix Payment Endpoint\
• Expect 201 or 422 VALOR_ACIMA_LIMITE - Validate response\
\
If response is 201:\
• Poll GET Payments Endpoint while status is RCVD, ACCP or ACPD\
• Call Get Pix Payment Endpoint\
• Expect 200 - Validate response and check payment status is RJCT and rejectionReason is VALOR_ACIMA_LIMITE

* **Call the GET Payments Consents Endpoint**
* **Expect 200 - Validate response and ensure status of the consent is CONSUMED**

Hey All! The expirationDateTime is being validate in that way since the because it is still considering the scenario where a consent goes from AWAITING_AUITHORIZATION to REJECTED. As the rules changes, we understand that the expirationDateTime should indeed be at statusUpdateDateTime + 60, as described at the swagger:

Data e hora em que o consentimento da iniciação de pagamento expira. Para consentimentos em status AWAITING_AUTHORISATION, deve ser sempre “creationDateTime + 5 minutos”. Após esse tempo, não sendo aprovado (seja a aprovação única ou primeiro aprovador), o consentimento deve ir para REJECTED. Para consentimentos em status PARTIALLY_ACCEPTED, deve assumir o valor da política de aprovação de cada instituição. **Para consentimentos em status AUTHORISED, devem assumir o valor de “statusUpdateDateTime + 60 minutos”, sendo esse o tempo máximo permitido para o consumo do consentimento.** Caso não seja consumido, deve ser movido para o status REJECTED.
