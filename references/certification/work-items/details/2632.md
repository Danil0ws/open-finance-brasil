Olá @adelino.avelino.

Analisando os logs do teste, identificamos que a causa raiz não está no scope dinâmico, mas sim na criação do consentimento.

O POST Consents retornou **422** com o seguinte erro da sua implementação:

`{ "code": "PARAMETRO_INVALIDO", "title": "Pagamento inválido.", "detail": "Pagamentos do tipo PIX com agendamento devem preencher um cenário válido: single ou recorrente (daily/weekly/monthly/custom)." }`

Como o consentimento não foi criado, o consent ID nunca foi extraído e consequentemente não foi adicionado ao scope da autorização, por isso o erro `invalid_request` no authorization endpoint.

O problema está no `brazilQrdnPaymentConsent` enviado na configuração. O campo `purpose` é obrigatório na spec v5 quando `type = PIX`, mas não está presente no payload configurado:

O que foi enviado:

`"payment": { "type": "PIX", "date": "2026-04-13", "currency": "BRL", "amount": "0.11", "ibgeTownCode": "1234567", "details": { "localInstrument": "QRDN", ... } }`

O que a spec v5 exige — campo `purpose` (\[Restrição\]: _"Campo de envio obrigatório quando o valor do campo /data/payment/type for igual a PIX"_):

`"payment": {`\
`  "type": "PIX",`\
`  "purpose": "IMMEDIATE",`\
`  "currency": "BRL",`\
`  "amount": "0.11",`\
`  "ibgeTownCode": "1234567",`\
`  "details": { "localInstrument": "QRDN", ... }`\
`}`

Para este teste (QRDN happy path, pagamento imediato), o valor correto é `IMMEDIATE`. Adicionando esse campo ao JSON de configuração e executando o teste novamente, o consentimento deverá ser criado com sucesso e o fluxo de autorização seguirá normalmente com o scope dinâmico incluindo o consent ID.

Sinta-se à vontade para reabrir esta issue, se necessário.

Prezados @adelino.avelino 

Analisamos a documentação do [**Financial-grade API Security Profile v2.1.0**](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1334149137/PT+Open+Finance+Brasil+Financial-grade+API+Security+Profile+-+v2.1.0) e não identificamos requisito que determine o uso de escopo dinâmico no authorization request para este cenário.

O conceito de “dinâmico” presente na especificação está relacionado ao **Dynamic Client Registration (DCR)**, onde os scopes podem ser definidos no momento do registro do cliente, e não à obrigatoriedade de uso de escopos dinâmicos durante o fluxo de autorização.

Inclusive, nos logs analisados, o request ao authorization endpoint segue o padrão esperado, utilizando escopos como:

`openid payments` (e eventualmente consent URN)

Dessa forma, não encontramos evidência na especificação que suporte a necessidade de escopo dinâmico para execução desse teste.

Poderiam, por gentileza, compartilhar a referência específica da documentação onde esse requisito é definido?
