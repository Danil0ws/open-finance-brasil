Olá @regis.gregol.

Sim, dá pra validar isso no motor. O equivalente fora do plano FVP é o módulo `enrollments_api_payments-core_test-module_v2-2` no plano Functional Tests for No Redirect Payments API - Based on Swagger version: v2.2.0

Sobre o "1" x "1.00": essa não é uma regra inventada pela FVP. Os campos `transactionLimit` e `dailyLimit` no swagger de enrollments são string monetária com `pattern: ^((\d{1,16}\.\d{2}))$` e `minLength: 4`, ou seja, 2 casas decimais obrigatórias sempre. O valor "1" é inválido por dois motivos: não casa o pattern (falta o `.dd`) e fica abaixo do minLength. A única representação válida de 1 BRL é "1.00".

A diferença entre os dois ambientes é só a mensagem de erro:

* Na FVP, o teste faz uma comparação exata e acusa "Value is incorrect / Expected value 1.00".
  * Para não haver pagamentos altos em produção, a FVP reforça esse tipo de comportamento.
* No motor, o "1" cai apenas na validação de schema do GET enrollments (não casa o pattern / minLength), então o erro aparece como falha de schema, não como "esperava 1.00".

Nos dois casos a correção é a mesma: serializar o valor monetário sempre com 2 casas decimais ("1.00", nunca "1").

Permanecemos à disposição.
