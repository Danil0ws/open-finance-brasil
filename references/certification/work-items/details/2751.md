## 📝 Descrição

Hi Master,

We are testing Mock Bank payment initiation.

#### Participant:
c8f0bf49-4744-4933-8960-7add6e590841

#### Problem:
We observed that Mock Bank returns 500 Internal Server Error for POST /open-banking/payments/v5/pix/payments when the same X-Idempotency-Key is reused, but the later request carries a new consentId.

In our flow, this happened because the previous payment attempt did not move forward as expected, the user re-entered the payment flow, completed FIDO again, and a new payment consent was generated. The later payment request therefore reused the previous payment-level idempotency key, but it was no longer the same authorization context.

The error detail returned by Mock Bank is:

Cannot invoke "Object.equals(Object)" because "inbound" is null

From our code and logs, the direct 500 seems to come from Mock Bank's repeated-request payload comparison logic. At the same time, we would also like to confirm the expected Open Finance / Mock Bank behavior for this scenario: same idempotency key, but a different consent after re-authorization.

#### Could you please confirm:
- If the same X-Idempotency-Key is reused for POST /payments/v5/pix/payments, but the later request has a different consentId, what is the expected behavior?
- Should Mock Bank return a business error such as 409 or 422 in this case, instead of 500?
- Is this treated as an invalid idempotent replay, or as a brand new payment attempt because the authorization context changed after re-FIDO?
- Could you please check whether Mock Bank's repeated-request comparison path is handling nullable fields correctly, such as remittanceInformation or creditorAccount.issuer?
- Is this only a Mock Bank issue, or is the same behavior expected from real participant implementations?

#### Concern:
There seem to be two different concerns mixed together here:

1. Mock Bank currently returns 500 due to an internal null handling issue during payload comparison, which makes the failure look like a server bug instead of a deterministic business outcome.

2. From integration semantics, when a payment request is retried after re-FIDO and a new consentId is generated, it is unclear whether the initiator is still allowed to reuse the original payment-level X-Idempotency-Key, or whether a new key is required because the request is no longer the same payment authorization context.

We want to confirm the expected bank-side behavior so that the initiator can implement the correct retry and state transition handling.

Hi @zhidong.tan 

Thanks for the detailed report.

About the 500: this is a Mock Bank test improvement that we are working right now. 

---

About your questions on expected behavior: 

When the same x-idempotency-key is reused with different payload content (including a different consentId), the expected response is HTTP 422 with code NAO_INFORMADO — not 500. This applies regardless of whether the authorization context changed after re-FIDO.

From the https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/347078709:

▎ (PT) "Ao receber uma requisição com o mesmo x-idempotency-key e com a claim data do JWT com conteúdo diferente do original a requisição deverá ser recusada com o HTTP Status 422 com código NAO_INFORMADO"

▎ (EN) "When receiving a request with the same x-idempotency-key and with the JWT data claim containing content different from the original, the request must be rejected with HTTP Status 422 and code NAO_INFORMADO"

In practice, if you need to initiate a new payment after re-authorization with a new consent, you should use a new idempotency key. The original key is already bound to the first request payload.

---

We will apply a fix so the Mock Bank correctly returns 422 instead of 500 in this scenario.
