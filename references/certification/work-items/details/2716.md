* **SysAid (notas + histórico)** dos 4 tickets confirma a ausência de qualquer ação do usuário `conformance@raidiam.com` (automação) nas datas relevantes dos SRs novos (185860, 185894).

---

**O que a automação faz hoje**

A FVP executa, quando um teste agendado falha:

1. `GET /api/v1/sr?problem_type=Conformidade_..._FVP Manual - Testes Restritos&fields=status,CustomColumn83sr,CustomColumn210sr,CustomColumn178sr`
2. Para cada SR retornado, casa três custom fields:
   * `CustomColumn83sr` (authServerId — UUID da instituição)
   * `CustomColumn210sr` (testGroup)
   * `CustomColumn178sr` (executedSegment — PF/PJ)
3. Se houver ≥1 SR casando, adiciona nota e muda status para ENCAMINHADO N2 ATENDIMENTO em **todos** os SRs da lista.

---

**Hipóteses para a causa raiz**

Consultando hoje, ambos os pares de SRs (antigo + novo) compartilham **a mesma instituição, mesmo testGroup e mesmo testType**. O sintoma observado é compatível com duas hipóteses:

Hipótese A - Truncamento pelo `limit` do SysAid

A query no código não passa `limit` e o SysAid retorna os SRs em **ID ascendente**. Se o servidor aplicasse algum default de limit ≤ 300, o SR novo (ID alto) cairia fora do resultado e só seria visto o ID antigo.

Testado hoje: a mesma query, **sem `limit`**, retorna todos os 417 SRs abertos e inclui tanto 155387 quanto 185860. Com `limit=100/200/300` o 185860 some. Não houve mudança de código da integração da FVP entre 30/04 e hoje, então essa hipótese só se sustenta se o servidor SysAid tivesse um default diferente na época (ou se algum perfil/preferência de servidor tivesse mudado).

Hipótese B - Custom fields não preenchidos no ticket novo

Os tickets antigos (155387, 158843) foram abertos via API pela própria automação (`source = API`), com os 3 custom fields preenchidos na criação. Os tickets novos (185860, 185894) foram abertos via **Administrator Portal** por um usuário. Se um ou mais dos 3 estivesse vazio em 30/04 e 03/05, a automação rejeitaria o SR e devolveria só o antigo.

Hoje os 4 tickets têm os 3 campos populados e idênticos entre antigo e novo. O SysAid não expõe audit log por campo no endpoint público que conseguimos consultar, então não foi possível confirmar o estado dos campos em 30/04 a posteriori.
