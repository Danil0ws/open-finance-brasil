Hi @zhidong.tan ,

Thanks for the detailed report.

**The discovery URL used is not registered in the Open Finance directory.**

The test was configured with: `https://openfinance.risk.staging.shopee.com.br/.well-known/openid-configuration`

This is an internal staging host. it is not one of the authorisation servers registered for SHOPEE in the directory.

The discovery endpoints currently registered for your organisation are:

1. https://openfinance.shppay.app/orgs/shopee/.well-known/openid-configuration
2. https://auth.open.shopee.com.br/.well-known/openid-configuration
3. https://seller-auth.open.shopee.com.br/.well-known/openid-configuration

Please re-run the test using one of these registered, publicly resolvable endpoints instead of the staging host.

---

Answering your specific questions:

1. _Did the FVP environment have any known DNS resolution issue for openfinance.risk.staging.shopee.com.br around 2026-07-07 08:42:45?_

No. The FVP resolver behaved correctly. openfinance.risk.staging.shopee.com.br has no public DNS record, so any resolver on the public internet returns "name not found" (UnknownHostException). This is stable behaviour, not a transient glitch at that timestamp.

2.  _Is there any known intermittent DNS/cache/network issue in the FVP environment that could cause UnknownHostException for the discovery URL while the endpoint remains accessible from other networks?_

No. The reason it works "from your side" is that the host only resolves inside your internal/corporate network. It is not published publicly. The FVP runs from the public internet, so it cannot resolve an internal-only name. UnknownHostException ("Name or service not known") means the name does not exist for the resolver, which is different from an intermittent timeout or a cache miss.

3. _Could you please help confirm whether this should be treated as an FVP-side environment issue, or whether there is any additional requirement on our issuer domain exposure for FVP resolution?_

This is not an FVP-side environment issue. There is a requirement on your side: the discovery/issuer domain used for the test must be publicly resolvable and must match an authorisation server registered in the directory. The test engine fetches exactly the discoveryUrl provided in the test configuration; it does not substitute or resolve it from the directory. So the fix is to configure one of the three registered endpoints above.
