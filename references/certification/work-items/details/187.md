## 1. What Happened and what were you expecting?

The payments-consents-api-pixscheduling-data-scheduled test failed because it expects a 422 error with NAO_INFORMADO code, but we expected success if we returned DETALHE_PGTO_INVALIDO code, with the detail field informing that payment.date or payment.schedule requirements were not fulfilled.

The payments-consents-api-pixscheduling-today-date test failed because it expects a 422 error with AGENDAMENTO_INVALIDO code, but we expected success if we returned NAO_INFORMADO code, with the detail field informing that tehre was an invalid schedule payment date. In the current rc version for scheduled pix (v1.1.0-rc1.0) the AGENDAMENTO_INVALIDO code does not exist (https://openbanking-brasil.github.io/areadesenvolvedor/#tocS_422ResponseErrorCreateConsent), it will be added in the next version?

Hi Norio,

Both the specifications and test are being updated and so you shouldn't consider them as final.

The Conformance Suite is currently being built on a preliminary version of the Specifications, with many points that exist on the Conformance Suite coming from discussions with the WG that might not necessarily end on the final version.

That being said, commenting on your points:

**For your first issue, regarding the error code for bad scheduled data**, we have received the document https://github.com/thbezerra/ob-docs/blob/main/pix-agendamento-proposta-final.md with a few business rules like the AGENDAMENTO_INVALIDO one. Looking again at the comment I can see that they have updated it to be INVALID_SCHEDULE, so we will need to update the C.S but indeed the ERROR codes will have to be added on the [422CreateConsent](https://openbanking-brasil.github.io/areadesenvolvedor/#tocS_422ResponseErrorCreateConsent) 

**For your second issue, about sending data.date and data.schedule.single.date together**, normally we use DETALHE_PGTO_INVALIDO when a non-business rule compliant value is sent on the field, however, however it is not 100% clear on the specs so once again this will have to be addressed by the WorkGroup.
