#### Current Behavior:
---
When running the `payments_api_pix-withdraw-qres_test-module_v5` test against a PSP that complies with the Pix and Open Finance Brasil specifications, the consent is successfully created and the payment is successfully initiated (HTTP 201). However, the payment status remains `RJCT` during polling and never reaches `ACSC`.

The Pix network rejects the payment with:

```json
"status": "RJCT",
"localInstrument": "QRES",
"rejectionReason": {
    "code": "PAGAMENTO_RECUSADO_SPI",
    "detail": "Pagamento rejeitado pelo PSP do recebedor."
}
```

The root cause is that the conformance suite **does not send `transactionIdentification` in the consent/payment payload**, even though the static QR Code provided in the test configuration contains a value in EMV field 62, sub-field 05 (Reference Label / TXID).

Example — the QR Code used during the test contains:
```
62 29 05 25 899f994fca264054921080eec
```
TXID extracted from EMV 62/05: `899f994fca264054921080eec` (25 chars)

The PSP correctly parses the QR Code, identifies the TXID, and forwards the payment to SPI. Because the `transactionIdentification` field is absent (or does not match the QR TXID), SPI rejects the payment as "QR Code data divergent".

The test then fails at the `EnsurePaymentStatusWasAcsc` step with:
```
Expected: ["ACSC"]
Actual: "RJCT"
```

#### Expected Behavior:
---
According to the Open Finance Brasil Payments API specification (v5), when `localInstrument = QRES` and the QR Code payload contains a TXID in EMV field 62/05, the `transactionIdentification` field on the consent and on the payment **must be populated** with that exact value.

> Reference: Open Finance Brasil Payments API v5 — `transactionIdentification` is required when `localInstrument` is `INIC`, `QRDN` or `APDN`, and when `QRES` carries a TXID in the QR payload, the field must match.

The conformance suite should:
1. Extract the TXID from EMV field 62 / sub-field 05 of the configured `qrCode`, and
2. Send it as `transactionIdentification` on the consent and on the payment request.

Without this fix, the test is blocked for any PSP whose SPI validation follows the Open Finance Brasil specification.
