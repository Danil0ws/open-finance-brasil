## 📝 Descrição

#### Current Behavior:

---

The[ Informa 506](https://mailchi.mp/5b61179258b0/open-banking-informa-10106184?e=2eb7798bd9) revokes the exclusive use of opaque refresh tokens in the new profile, allowing the use of JWT refresh tokens within the ecosystem. This change is due to the modification of item 24,[ section 5.2.2 of the security profile](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/245760001/EN+Open+Finance+Brasil+Financial-grade+API+Security+Profile+1.0+Implementers+Draft+3#5.2.2.-Authorization-server), which states that the authorization server:

24. _shall issue refresh_tokens (JWT or opaque) **without an expiration period in scenarios where it is necessary.**_

This means that authorization servers can issue JWT refresh tokens, as long as they do not contain the "exp" optional claim for long-lived consents. The issue with this approach is that, according to the new security profile, the authorization server ([item 15](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/245760001/EN+Open+Finance+Brasil+Financial-grade+API+Security+Profile+1.0+Implementers+Draft+3#5.2.2.-Authorization-server)):

15. shall not allow refresh token rotation;

This scenario could lead to a situation **where an authorization server issues a refresh token with an exp claim when the consent has an expiration date. If the consent is extended and refresh token rotation is not allowed, the token would become useless after the exp date is reached, unintentionally revoking the consent.**

We believe there might be an issue with the security specification, as it does not accommodate consent extension when the refresh token is initially issued with an exp claim. Therefore, we seek **confirmation from the Security working group on the following question:**

1. How should an authorization server handle the consent extension once the first refresh token is issued as a JWT with the "exp" claim?

Hi Ranieri,

Thanks for the response! However, there are cases where the participant sets the `exp` claim to match the consent expiration time. For example, we issued a one-day consent, which generated a refresh token with a one-day expiration. Later in the test, this consent was extended, but since the refresh token is a JWT, it retained the same expiration value.

According to [RFC 7519, section 4.1.4](https://datatracker.ietf.org/doc/html/rfc7519#section-4.1.4):

> The "exp" (expiration time) claim identifies the expiration time on or after which the JWT **MUST NOT** be accepted for processing.

If we remove the JWT validation from the test without implementing another validation, this would mean the participant would go to production with this implementation. Therefore, we would be requiring participants to ignore the `exp` claim in the token, which is against the RFC.

Therefore, a suggestion would be:

- The authorization server should not issue JWT refresh tokens with the `exp` claim, since this claim is optional.
- Alternatively, set a predefined date like D+100 years as the minimum value for this claim.

This approach ensures interoperability and avoids security issues where participants have to ignore JWT claims.

Hi Ranieri! Still, I believe we may not have been entirely clear about the issue here:

What the Security specs claim is that:

24. _shall issue refresh_tokens (JWT or opaque) **without an expiration period in scenarios where it is necessary.**_

This means that the AS could issue a refresh_token with an exp claim that is after the current consent end date but does not guarantee that the exp claim will be after any extensions after expected at the consent.

For example, we have seen a test in which a participant had the following behavior:

* The Conformance Suite creates a consent for D+1
* The User authorizes the consent
* The AS issues a JWT Refresh Token with the exp as D+1
* The Conformance Suite extends the consent to long-term (No expiration)
* The Server accepts the request, but the refresh token is kept the same since refresh_token rotation is not allowed

In the case above mentioned, the AS issuing the refresh token with an exp claim as D+1 is compliant to the security spec since this was not considered "necessary" in the first consent creation. But once the extension is executed, even though "in theory" the server executed the extension for the long term, it kept the same refresh token, which became useless after D+1. In that sense, we believe there is a gap in the security specification since It's not clearly defined "where it is necessary" to not issue a jwt refresh token without an expiration period, since all consents can be extended to long term, and therefore, may be necessary.

In that sense, the question is, when a refresh token jwt is issued:

* Which validations should the conformance suite execute against the exp claim/consent expiration?
* In case the exp claim is kept, what date is considered to be "unreachable"?
* Are the answers for the questions above clearly stated in the current security profile?

Prezados, segue resposta do GT Segurança.

A existência ou não do atributo exp é uma particularidade da implementação do AS da instituição financeira. Algumas, na emissão de refresh_tokens de longa duração optam por não definir um valor para este atributo, outras definem este atributo com um valor inalcançável, por exemplo, 2300-01-01.

Em ambas situações, a renovação é permitida pois o limite do tempo de vida do consentimento é seu prazo em si e não o prazo do refresh_token, pois um refresh_token com prazo inalcançável acaba tendo o mesmo comportamento de um refresh_token sem prazo (sem o atributo exp).

Dessa forma, entendemos não existir problema na utilização de tokens JWT(com ou sem atributo exp) ou opacos para essa situação, desde que mantidas as premissas do perfil de segurança.
