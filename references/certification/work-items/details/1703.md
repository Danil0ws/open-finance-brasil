The test module execution failed due to the rejection of DCR by the Authorization Server, the reason thrown regards the use of **response_types<span dir=""> </span>'code' and not 'code id_token'.**

According to what is described in [RFC 7591](https://datatracker.ietf.org/doc/html/rfc7591):

> [**2.1**](https://datatracker.ietf.org/doc/html/rfc7591#section-2.1)**. Relationship between Grant Types and Response Types**
>
> The "grant_types" available to a client influence the "response_types" that the client is allowed to use, and vice versa. For instance, a "grant_types" value that includes "authorization_code" implies a "response_types" value that includes "code", as both values are defined as part of the OAuth 2.0 authorization code grant. As such, a server supporting these fields SHOULD take steps to ensure that a client cannot register itself into an inconsistent state, for example, by returning an "invalid_client_metadata" error response to an inconsistent registration request. The correlation between the two fields is listed in the table below.
>
> | grant_types value includes: | response_types value includes: |
> |-----------------------------|--------------------------------|
> | authorization_code | code |
> | implicit | token |
>

As seen above, the response_types: "code id_token" are linked to the grant type, with the implicit grant type including the response type id_token and the authorization_code including the code.

When, on server configuration, fapi_response_mode is set to jarm, the test doesn't add the grant type implicit. This is because:

When using JARM, the id_token is not exposed directly during redirect, while when using plain response, the id_token is exposed in the redirect URL. As JARM encapsulates the response in a JWT (JSON Web Token), It therefore removes the id_token as a direct response possibility. Therefore, the only possible response type is code.

Therefore Conformance Suit is operating as expected when sending response_types: "code" as fapi_response_mode=jarm is set on test configuration. To execute the test module successfully two paths can be followed:

* Execute test module using fapi_response_mode=plain_response
* Make sure that Authorization server supports Jarm and expects response_types on client's meta_data according to expected.

Additionally, this test will be updated so that it is updated to the new Fapi Profile, therefore fapi_response_mode=plain_response will be set by default during test execution.
