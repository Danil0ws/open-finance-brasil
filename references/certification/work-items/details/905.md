## 📝 Descrição

## 1. What happened and what were you expecting?

Following this documentation: https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/164528425/Informa+es+T+cnicas+-+Pagamentos+-+v3.0.0-rc.1 on **5.1.9**:

 > 5.1.9 - Valor inválido: O valor enviado não é válido para o QR Code informado (VALOR_INVALIDO);

The consent can be rejected by the reason VALOR_INVALIDO in the proccess of authorising the consent, and the test only expects this behavior on the payment initiation (POST Payments Endpoint step) proccess. But when we reject the consent in the proccess of authorisation, we can't start the payment.

Hi,

This issue was recently taken to discussion at the WG and following their September 1st decision the test module will be updated as described below:

Ensure that **consent** fails when the amount sent on the Static QR Code differs from the payload (**Reference Error 4.1.3**)

* Call POST Consent with different amount values on QRES and the payload
* Expects 422 - DETALHE_PAGAMENTO_INVALIDO
* Validate Error message

If no errors are identified:

* Expects 201 - Validate response
* **Redirects the user**
* **Ensure an error is returned and that the authorization code was not sent back**
* **Call GET Consent**
* **Expects 200 - Validate if status is "REJECTED" and rejectionReason is  VALOR_INVALIDO**
