Hello @hrezend.

On the new points you raised:

* **“There’s no PATCH endpoint to update these fields”**

  Correct. And that’s exactly why the webhook exists here. This test is validating a "Detentora" update, and the DATA_CHANGED webhook is the mechanism to notify the ITP that the already-authorised enrollment data has changed. It’s not meant to be an ITP-driven update via API.
* **“These fields are defined during AWAITING_ACCOUNT_HOLDER_VALIDATION via UX”**

  Yes, that’s one moment where they can be set. But the test is intentionally covering a _different_ scenario: a change after the enrollment is already AUTHORISED, to ensure your implementation can signal and expose updated enrollment parameters post-authorisation.
* **“Why would the user change what they already defined?” / “Doesn’t that seem wrong?”**

  It’s a valid scenario: limits/expiry can be changed after authorisation. The goal is to ensure the ITP isn’t left with stale data when that happens.
* **“Is it meant to cache and only persist after AUTHORISED?”**

  No, the expectation is not about delaying persistence. The expectation is simply that after AUTHORISED, if any of these fields changes in your system, you send DATA_CHANGED and the subsequent GET reflects the new values.

So the flow is: AUTHORISED baseline → change happens → webhook → GET shows delta.

Please feel free to reopen the issue if further information is needed.

Hi @lheperez. Thanks for the clarification.

This test is specifically validating a **post-AUTHORISATION edit** on an **AUTHORISED** enrollment. Because of that, the “old values” used for comparison are **not** the ones from the earlier GET when the enrollment was `AWAITING_ACCOUNT_HOLDER_VALIDATION`.

Instead, the baseline the test uses is the most recent stored enrollment representation right before the DATA_CHANGED webhook is expected, like the values returned by the GET /enrollments/{enrollmentId} step that confirms the enrollment is `AUTHORISED`.

So in your current flow:

* The limits are already being changed during the authorisation process / intermediate statuses.
* By the time the test reaches the GET that confirms `AUTHORISED`, it already stores the new values as the baseline.
* Then you send a DATA_CHANGED webhook, but no further effective change happens _after_ that baseline was stored.
* Therefore, the final GET returns the same “new values” again, and the comparison fails.

To pass this test, the change must happen **after** the enrollment is already `AUTHORISED`, and the webhook must reflect that change, as described by the test summary. Concretely:

1. Ensure the enrollment reaches `AUTHORISED`.
2. Only then modify at least one of: transactionLimit, dailyLimit, expirationDateTime.
3. Ensure the updated value is returned by GET /enrollments/{enrollmentId}.
4. Send the webhook with eventType = DATA_CHANGED after the change is effective.

If the values are only modified during the authorisation journey (before the test stores the `AUTHORISED` baseline), the test will keep failing as observed.

Please feel free to reopen this issue if needed.

Hi,

Based on our analysis, it appears that none of the fields **transactionLimit**, **dailyLimit**, or **expirationDateTime** were actually changed.

According to the test definition, once the enrollment reaches **AUTHORISED** status, the expectation is not only to send a webhook with `eventType = DATA_CHANGED`, but also to ensure that **at least one** of these fields is effectively updated in the detentora server **before** the webhook is sent.

After receiving the `DATA_CHANGED` webhook, the CS calls `GET /enrollments/{enrollmentId}` and validates that at least one of those fields differs from the previously stored values. In this case, the GET response still returns the same values as before, which causes the test to fail.

To pass this test:

* First, update one of the following fields in the detentora system: `transactionLimit`, `dailyLimit`, or `expirationDateTime`;
* Ensure that the updated value is reflected in the `GET /enrollments/{enrollmentId}` response;
* Only then send the webhook with `eventType = DATA_CHANGED`.

If the webhook is sent before any effective change (or if the GET still returns the original values), the test will fail as observed.
