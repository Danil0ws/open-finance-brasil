## 📝 Descrição

## 1. Motivation

Certificates for Open Banking can be issued by multiple certificate authorities, which means that there's a risk that two certificates issued for the same software statement might not have exactly the same DN. 

This means that when Clients start replacing their certificates, be it because they are expired or because they are now using a new type of CA, all servers should be able to correctly handle the DCM and the newly updated certificate.

This only applies to servers that authenticate the token using the tls_client_auth method

## 2. Test Behavior

This behavior only applies to the current security specifications - If any change comes from point 3 test behavior must be updated accordingly


- Set two hardcoded certificates (Cert A and B) with different DNS pointing at the same software statement on the Sandbox Directory
- Perform a DCR with Cert A - Make sure a client_id is correctly generated
- Generate a token for the created client_id using Cert A (Creating a consent might be a good approach here too)
- Perform a PUT to DCM with the subject_dn of Cert B using cert for Cert A
- Verify a GET to DCM using cert for Cert B succeeds
- Make sure that you can correctly use Cert B with the client_id by calling the token endpoint (Once again it can go a step further and create a consent)
- Make sure that you can no longer use Cert A to create tokens with the existing client_id (**Assumption 2**)
- Perform a PUT to DCM with the subject_dn of Cert A using Cert A (**Assumption 1**)
- Make sure that you can now use Cert A to create tokens with the existing client_id

## 3. Assumptions

Looking at the existing security specifications we need the Security WG to evaluate if the assumption below is valid.

[Current OBB DCR specifications](https://openbanking-brasil.github.io/specs-seguranca/open-banking-brasil-dynamic-client-registration-1_ID2.html) say “shall require and validate that all client authentication mechanisms adhere to the requirements defined in RFC7591 and RFC7592, validating the registration_access_token and using a secure connection, protected by certificate Issued from chain of certificates linked to ICP-Brasil"

**Assumption 1**: Any valid ICP Brasil certificate issued can be used to update the DCR, even if the certificate dn is different from the registered subject_dn



[OAuth 2.0 Mutual TLS Client Authentication and Certificate-Bound Access Tokens says on item 2.1](https://tools.ietf.org/id/draft-ietf-oauth-mtls-14.html#pki_method)" The client is successfully authenticated if the subject information in the certificate matches the single expected subject configured or registered for that particular client "

**Assumption 2**: Once a new subject is registered the certificate used by the client must have a corresponding registered dn in order for it to authenticate and obtain an access tokens.

## 4. Potential Risks/ Upgrades on Security Specifications

When drafting this ticket Raidiam has spotted an issue with the existing security specifications for DCR for the Open Banking.

The item that talks about [Client Maintenance](https://github.com/OpenBanking-Brasil/specs-seguranca/blob/main/open-banking-brasil-dynamic-client-registration-1_ID2.md#client-maintenance---get-register---put-register---delete-register) does not require any type of binding between the SSId/OrgId of the certificate used and the client_id. 

> Client Maintenance - GET /register - PUT /register - DELETE /register
> - validate that the certificate presented by the client application is subordinate to the ICP-Brasil chains defined in the Open Banking Brasil Certificates Standard;
> - Validate the presence and matching of the Bearer header Authorization containing the value of the registration_access_token attribute returned during registration of the corresponding client.

This means that if organisation A, registered on the directory, gets the cliend_id and the registration_access_token from organisation B on the directory, they would be able to hijack this client as per specs.
