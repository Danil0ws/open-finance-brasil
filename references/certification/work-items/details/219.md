## 1. What Happened and what were you expecting?

We recently received a client registration request with a rather large redirect_uris field.

We then went after the specs and found that there are no limits established anywhere(?)

The software statement swagger does not limit this field: https://github.com/OpenBanking-Brasil/specs-seguranca/blob/main/dcr_review/dcr-dcm-swagger.yaml

On the British Open Banking specs, there is a 256 array size limit: https://github.com/OpenBankingUK/client-registration-api-specs/releases (assuming max URI length for each entry to 256, this would establish a hard limit of 256 * 256 bytes)

We were unable to find any conclusive spec for the Brazilian standard.

Would you be able to point us in the right direction? Is there a formal specification somewhere that establishes the maximum size for redirect_uris during DCR?

Thank you very much in advance.

Hi Jose, 

We took this discussion internally and we believe that the IETF/OIDF do not define anything at all about the length of nearly anything, which indeed can cause interoperability issues.

Currently, the directory will limit the RedirectURI to be registered on a software statement to be of 255 characters, so it wouldn't be possible to have anything longer than that on a SSA. The directory array size is also 255 characters

The RedirectUri on the directory swagger


>        RedirectUri:
>           description: The Software Statement redirect compliant URI
>           items:
>             format: uri
>             pattern: ^(http:\/\/|https:\/\/).*
>             type: string
>             maxLength: 255
>             x-pattern-message: RedirectUri must be in a URI format https://... or
>               http://...
>           maxLength: 255
>           type: array

Thinking about updating the security specs, our opinion is that nobody should be sending a redirect URL over 128 characters, and everyone should be accepting redirect URLs of at least 1024, however we are not in charge of updating this documentation and this would need to be sent to the Security WG for discussion.
