## 📝 Descrição

Hi there!

It's been quite challenging to pass payments certification, mainly because proxy, qrCode and transactionIdentification validations rules.

Current API Payment Initiation OAS says:

* qrCode must be present for QRES and QRDN localInstruments
* proxy must be present for INIC, DICT, QRDN and QRES localInstruments; and must be absent for MANU localInstrument
* transactionIdentification must be present for INIC localInstrument; and must be absent for MANU and DICT localInstrument

We must provide initial payloads with all properties listed above, and tester will change these payloads according to each test case scenario.

For now, I’m focusing on qrCode.

Test case `payments-consents-api-manu-fail-test` description explicitly says “Payments Consents API test module ensuring a qr code must be absent when the local instrument is MANU” which is clearly different from OAS, same for `payments-consents-api-dict-test` which description says “Payments Consents API test module ensuring a qr code must be absent when the local instrument is DICT” again against OAS.

So, our test run with OAS rules had these two test cases failing (http://web.conformance.directory.openbankingbrasil.org.br/plan-detail.html?plan=lnM24JmAszg4S).

If we change qrCode validation rules to: `must be present for QRES and QRDN localInstruments; and must be absent for MANU and DICT localInstruments` and rerun all tests we pass `payments-consents-api-manu-fail-test` and `payments-consents-api-dict-test`, but got a `payments-consents-api-proxy-email-proxy-test` and `payments-consents-api-proxy-phone-number-proxy-test failure`. Both are sending qrCode for DICT instrument and expect a success 201, which is clearly against our fictional new rule. (http://web.conformance.directory.openbankingbrasil.org.br/plan-detail.html?plan=HbNAQM4psY1cL)

Could you please help us with this paradox?

Thanks
