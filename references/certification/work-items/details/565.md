### Comentário 3
**Autor**: Christian Eloysio (@christianraidiam)

We generally add these issues to the functional tests when there's something specific to the context that is not being tested at the OIDF tests. Here, since we had definitions that were published at Informa 218 which wouldn't be tested at the OIDF tests, they were added to the functional ones.

Regarding the 4th point, we are sending both "openid" and "payments" scopes at a client_credentials grant. Since [openid should not be sent at the client_credentials grant](https://mailchi.mp/18107e66cfae/open-banking-informa-9162397?e=9b9743fbe2), it is expected that the server will issue the access token without this scope. Since the scope is changed from the request, it is expected that the server response will only have the scope "payments". In a nutshell:

**Request**: scopes "openid" and "payments" using client_credentials grant

**Response**: scope "payments" on the response since openid cannot be issued using client_credentials

Happy to help with any other issue!

Hi Rajesh! Thanks for the ticket!

Regarding your questions:

1. The RFC 6749 is related to the OAuth 2.0 Authorization Framework, not the OpenID Connect. The Financial Grade API (FAPI) spec is a layer on top of the OAuth 2.0. Therefore, as the functional flow for the test runs inevitably through the FAPI/OAuth specificities, we have to use this documentation to support the tests. The openid scopes are also attached to the tests since the payment flow needs authentication, which is supported by the ID_Tokens made available through the openid scopes.
2. Although the focus for the functional tests is on the functional flow, the security side is deeply attached to it, and sometimes will be included in the tests.
3. Although we have some bugs on the test, which is expected during the beta testing, we already have at least 10 institutions passing the module. The intention here is to fix all the bugs needed to make it available for certification on January 13th. Besides that, all test modules have also been approved by the working group before development.
4. The main guideline is that, if the issued access token scope is different from the one requested by the client, the authorization server MUST include the "scope" response parameter to inform the client of the actual scope granted, as stated at the [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749#section-3.3). If you feel the table is needed to make the implementation easier, we kindly ask you to open a ticket at the SysAid Service Desk to address it to the Working Group.

I hope this helps you, and we are happy to help with any other issue!

Best Regards
