## 📝 Descrição

When authorizing the consent, if there is an invalid enrollment status, an error occurs with code 422 and the status 'STATUS_VINCULO_INVALIDO'. However, when retrieving the consent, why does the status should return as 'NAO_INFORMADO' instead of 'STATUS_VINCULO_INVALIDO'?

#### Current Behavior:
---
After an error of STATUS_VINCULO_INVALIDO when we retrieving the consent the status is NAO_INFORMADO
#### Expected Behavior:
---
Shouldn't the status be STATUS_VINCULO_INVALIDO

Hi @dogue100,

Thanks for opening the ticket!

While the consent authorization on the no redirect journey flow uses following endpoint:

**POST enrollments/v1/consents/{consentId}/authorise**

Which is defined in the [API Enrollments for Payment Initiation specificaiton](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/405995741/Informa+es+T+cnicas+-+SV+V+nculo+de+dispositivo+-+v1.3.1)

For the GET request, no redirect journey shares the same endpoint used for Payments V3:

**GET payments/v3/consents/{consentId}**

Which is defined in the [API Payment Initiation spec](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/180061271/Informa+es+T+cnicas+-+SV+Pagamentos+-+v3.0.0)

As can be seen from the defined payload for the response of this GET request, STATUS_VINCULO_INVALIDO is not a valid rejectionReason for the consent, therefore NAO_INFORMADO is expected.
