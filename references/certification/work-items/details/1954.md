### Comentário 6
**Autor**: Caio Tranjan (@caio.tranjan)
**Criado em**: 08/01/2025, 18:34:15

Hi,

Thanks for opening the issue! During this test execution, the main objective is to assert that a payment cannot be scheduled the creditorAccount Information used to create the payment is not the same as the creditor informed during consent. Therefore it executes:

- Call the POST recurring-consents endpoint with automatic pix fields, with referenceStartDateTime as D+1, interval as SEMANAL, minimumVariableAmount of 0.5 BRL, maximumVariableAmount as 0.8 BRL and sending firstPayment information with amount as 1 BRL, date as D+0

Sending:

```
    "creditorAccount": {
        "ispb": "12345678",
        "issuer": "1775",
        "number": "1234567891",
        "accountType": "CACC"
      }
```

Then:

- Call the POST recurring-payments endpoint with the information defined firstPayment payload
- Expect 201 - Validate Response

Sending:

```
      "creditorAccount": {
        "ispb": "12345678",
        "issuer": "1775",
        "number": "1234567891",
        "accountType": "CACC"
      }
```

And at last:

- Call the POST recurring-payments endpoint with an amount of 0.50 BRL, and date as D+4, and creditorAccount number as a random number
- Expect 422 PAGAMENTO_DIVERGENTE_CONSENTIMENTO or 201 - Validate Response

Sending:

```jsx
"creditorAccount": {
      "ispb": "12345678",
      "accountType": "CACC",
      "issuer": "1775",
      "number": "8799"
```

If you notice, in this last call, the number being sent is random and not equal to the one consented, therefore Conformance suit expects either a synchronous or assyncronous failure.

Feel free to add comments and reopen issue in case further assistance is required.
