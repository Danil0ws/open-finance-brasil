Olá @fo946493. Analisando o log, podemos verificar o seguinte:

* O teste faz a chamada: POST api.openbanking.uatbi.com.br/open-banking/enrollments/v2/enrollments
* E recebe uma resposta 201 CREATED, contendo um JWT com:

```
{
  "alg": "PS256",
  "kid": "Hh9TY1dd....",
  "typ": "JWT"
}
```

* É esse kid que o motor utiliza, na sequência, para validar o self link enviado, procurando um JWKS, com base no que sua org disponibiliza em:
  * https://keystore.sandbox.directory.openbankingbrasil.org.br/31ee4f72-8769-5136-83e4-03f2dd4c935e/application.jwks

Aqui o ponto chave é que esse kid não existe no JWKS publicado atualmente (no JWKS retornado, os kid são outros, como jltUZMc0…, 4Vb0aON…, JXBn8zI…, etc.).

Como o Motor valida a assinatura buscando no JWKS uma chave que corresponda ao kid do header, a validação falha por não encontrar uma key correspondente.

Um ponto importante: o motor expõe exatamente o dado enviado por sua implementação, não há um cache/manipulação da resposta apresentada.

Assim, recomendamos identificar qual componente da sua implementação está efetivamente assinando esse JWT, verificando onde está configurada a chave privada que gera o kid inativo = Hh9TY1dd \[…\]. Em seguida, alinhar a rotação para que o serviço assine com uma chave cujo kid esteja publicado nos certificados do Diretório, garantindo que o kid emitido no header do JWT seja exatamente um dos kid disponíveis no JWKS.

Estamos encerrando esta issue, mas sinta-se à vontade, por favor, para reabrir caso necessário.
