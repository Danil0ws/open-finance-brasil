Hi,

Thank you for the report and the evidence you shared.

After reviewing it, the **conformance suite is behaving in line with the Open Finance Brasil (OPF) specification** for the consent revocation endpoint.

According to the API Consents specification, the required token type is:

* **Creation** (POST /consents), **consultation** (GET /consents/{consentId}), and **revocation** (DELETE /consents/{consentId}): a **token obtained via client_credentials** must be used.


* **Renewal** (POST /consents/{consentId}/extends): a **token obtained via authorization_code** must be used.

Quoting the specification:

\\> _"For the creation, consultation and **revocation** of the consent, a token generated via **client_credentials** must be used. For the consent renewal call, a token generated via authorization_code must be used."_

So in the final step of the test (cleanup), the conformance suite **obtains a token via the client_credentials grant** and uses that token for **DELETE /consents/{consentId}**, as required by the spec. Using an **authorization_code** (user access_token) for revocation is **not** specified; the spec requires **client_credentials** for the DELETE.

**Specification references:**

* **Guidance – \[DC\] Consent (Open Finance Brasil):**

https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/219480491

* **API Consents – OpenAPI (Swagger):**

https://openbanking-brasil.github.io/openapi/swagger-apis/consents/

(The API description states that client_credentials is used for creation, consultation, and revocation.)

If you need more technical detail on the test flow, we can provide it.
