## 📝 Descrição

## Current Behavior

The test step `EnsureTransactionBillForecastDateNextMonth` validates that installment transactions follow a consecutive monthly sequence based on `billForecastDate`.

Currently, the CS:

* Groups transactions implicitly by `identificationNumber`
* Assumes a single installment flow per card
* Validates `billForecastDate` sequence across all returned transactions

In scenarios where multiple valid installments exist simultaneously (e.g. annuity + invoice installment), the API may legitimately return multiple transactions for the same month. However, the CS evaluates them as a single sequence, resulting in failures such as:

> "The installment's bill forecast date is not the next consecutive month from the previous"

---

## Specification Alignment

The spec defines that:

* `identificationNumber` represents the card identifier, not an installment identifier, meaning it cannot be used to uniquely group installment flows
* `transactionId` is the unique and immutable identifier of each transaction, so each record must be treated as an independent financial event
* In installment purchases, `transactionDateTime` must be the same for all installments of a purchase, while `billForecastDate` indicates the billing month/year for each installment

From this, it follows that:

* Multiple transactions can legitimately share the same `billForecastDate`
* Different installment flows (e.g. annuity vs invoice installment) can coexist in the same month
* There is no rule in the specification enforcing a single transaction per month per card

---

## Expected Behavior

The validation should not assume a single installment flow per `identificationNumber`.

Instead, the CS should:

* Group transactions by logical installment flow (e.g. based on consistent `transactionDateTime` or other grouping attributes)
* Validate the sequence of `billForecastDate` **within each group independently**

For each group:

* `billForecastDate` should follow consecutive months
* Multiple transactions with the same `billForecastDate` should be accepted if they belong to different flows

Prezados, complementando a resposta do ticket #184133:

O teste foi atualizado em 24/04/2026, justamente para tratar o cenário de múltiplos parcelamentos simultâneos para o mesmo identificationNumber.

A nova lógica:

\-Agrupa as parcelas pelo campo transactionDateTime, não por identificationNumber. -Cada parcelamento (anuidade, parcelamento de fatura, etc.) ocorre em um momento específico e, portanto, terá um transactionDateTime distinto, formando um grupo independente. A validação de meses consecutivos é feita dentro de cada grupo, isoladamente. 

Assim, o cenário descrito, identificationNumber=8910 com dois parcelamentos legítimos e simultâneos (5 TARIFA + 5 PAGAMENTO), passa no teste atual, desde que cada contrato traga seu próprio transactionDateTime.

O log apresentado no ticket refere-se a uma execução de 13/04/2026, anterior à atualização. A mensagem de erro citada ("The installment's bill forecast date is not the next consecutive month from the previous") foi removida nessa atualização.

Pedimos que executem novamente o teste contra a versão atual do conformance suite (a partir de 24/04/2026). Caso o erro persista, por favor anexem o novo log para análise.
