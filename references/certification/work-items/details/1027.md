Hi All!

The issue has already been fixed and it's using the authorization code grant token to perform the POST Consents Extends Call. if a new test plan is created, there should be no issues on this matter.

Regarding the questions raised, currently, the POST Consents Extends Endpoint has the exactly same security schema as the others Resources Endpoints, as Accounts, Credit Cards, and other products. Therefore, both the access token retrieved from the authorization code exchange at the Authorization Server, and the token issue with a refresh_token, should be accepted at this endpoint.

From a functional perspective, this should allow th user to extend the consent at any time:

1. A recently created consent can be immediately extended, prior to the access token expiry.
2. If the access token expires, the extension can be executed at any time as long as the consent is still authorized, using the refresh_token to get a new access token, in the same way that the resource endpoints are accessed.

In that sense, there is no issue with the specifications or the conformance suite on this matter, since the security schema from this endpoint is the same as the resource endpoints:

Hi @benisson, for me the test seems to be incorrect. If it aims to test the extent of a consent with an invalid status, the consent status should be `REJECTED` to validate the 422 error code (`ESTADO_CONSENTIMENTO_INVALIDO`). According to the proposal, there is no way to attempt to extend a consent in an `AWAITING_AUTHORISATION` status because the endpoint won't accept the client_credentials token (the only token that can be generated before the consent authorization).

The other option is if the regulation specifies that this endpoint will be hybrid (accepting either client_credentials or authorization_code/refresh_token). In that case, the test would be accurate, and our token scope validation should be adjusted accordingly. However, as far as I am aware, this proposal was approved, and this endpoint should only accept tokens of the authorization_code/refresh_token type (those with the scopes `openid` and `consent:consentId`).
