## 📝 Descrição

#### Current Behavior: 

---

Atualmente, estamos enfrentando um problema na validação da resposta de erro ao processar um pedido de extensão para um consentimento que já foi rejeitado. O teste espera que, ao retornar um erro 401 (não autorizado), seja incluído um campo "errors" no corpo da resposta, contendo uma lista de erros. No entanto, como o erro 401 está sendo gerado pelo Servidor de Autorização e não pela API de negócio (Consentimento), esse campo "errors" não é aplicável e, portanto, não está sendo retornado. Isso está causando a falha no teste de conformidade.

Foi aberto o ticket #60693 no Service Desk do Open Finance onde esta situação foi questionada. O retorno foi que o motor de conformidade realiza validações baseando-se na especificação vigente e sugere a abertura desse ticket via GitLab para discussão e esclarecimento de GT responsável.

#### Expected Behavior: 

---

Esperamos que a validação considere a natureza do erro 401, que é um erro de segurança, e não exija a presença do campo "errors" no corpo da resposta. Acreditamos que a validação deveria apenas checar o código de retorno 401 sem exigir o campo "errors", conforme era feito na certificação anterior (3.0.0).

Thanks for creating the ticket!

Error messages 401 or 403 come as as an output for failures during validations on the Security Layer. 

For this types of error the Conformance Suit validates the payload as defined in the Open Finance specification for the consent api, which can be found via the link:

https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/714440780/Informa+es+T+cnicas+-+DC+Consent+-+v3.2. 

Which defines that the following pattern should be followed:

```
{
  "errors": [
    {
      "code": "string",
      "title": "string",
      "detail": "string"
    }
  ],
  "meta": {
    "requestDateTime": "2021-05-21T08:30:00Z"
  }
}
```

The Observed Failure is a result of the following payload sent by the server for a 401 error code:

```
{"error":"invalid_token","error_description":"Grant request is invalid"}
```

Since the Conformance Suit performs its validations based on the current specification and swagger, we understand that it is operating as expected in this scenario as the schema on the received payload does not follow what is described on the specification.

Therefore we understand that this Issue regards Doubt or a request for change in the specification and therefore on test module behavior. As mentioned on the issue description, what the participant wants evaluation from the Appropriate WorkGroup is:

"Esperamos que a validação considere a natureza do erro 401, que é um erro de segurança, e não exija a presença do campo "errors" no corpo da resposta. Acreditamos que a validação deveria apenas checar o código de retorno 401 sem exigir o campo "errors", conforme era feito na certificação anterior (3.0.0)."
