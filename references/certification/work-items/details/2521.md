## 📝 Descrição

The test payments_api_consent-bulk-cancel_negative_timezone_test-module_v5 creates 5 payments scheduled for D+1 (• Call POST /consents with schedule.daily.startDate as D+1 and schedule.daily.quantity as 5). It expects the error PAGAMENTO_NAO_PERMITE_CANCELAMENTO (• Expects 422 – PAGAMENTO_NAO_PERMITE_CANCELAMENTO) to be returned when attempting to cancel all payments linked to the consent after 10:00 pm (22:00 (UTC-3)).

In the “Pagamentos API” V5.0.0 documentation we have the following descriptions:

* “O cancelamento de pagamentos agendados (SCHD) pode ser enviado até 22:00 (Horário de Brasília) do dia anterior à data de efetivação do pagamento. Todos os pagamentos vinculados a esse consentimento e previstos para ocorrer a partir do dia seguinte serão cancelados, em até 60 minutos.”
* “Se não restar nenhum pagamento (ocorrência) que poderá ser cancelado, a requisição PATCH retorna HTTP Status 422 com o code PAGAMENTO_NAO_PERMITE_CANCELAMENTO.”

So, the expected response when consuming the endpoint to cancel all payments of a consent (Call PATCH /consents/{consentId}/pix/payments (bulk cancel)) should be 2xx, since there are 4 payments that can be canceled, those with a schedule later than D+1.

My question is as follows: Should I block the cancellation of all payments related to the consent if even one of them cannot be canceled, and return HTTP Status 422 with the code PAGAMENTO_NAO_PERMITE_CANCELAMENTO? Or, should I cancel all payments that can be canceled and keep only the D+1 payment with SCHD status, returning 2xx?

Hi @arthurkaizer 

For the purpose of **conformance with the test payments_api_consent-bulk-cancel_negative_timezone_test-module_v5**, it is important to clarify that the expected behavior validated by the Conformance Suite is that the **bulk cancel operation must be handled atomically** when executed **after 22:00 (UTC-3)**.

Therefore, when consuming the endpoint **PATCH /consents/{consentId}/pix/payments** in this time window:

* If **at least one scheduled payment linked to the consent is no longer eligible for cancellation** due to the time restriction,
* The bulk cancellation request **must be rejected as a whole**,
* **No payment** associated with the consent should have its status changed to **CANC**,
* And the API must return **HTTP 422** with the error code **PAGAMENTO_NAO_PERMITE_CANCELAMENTO**.

This is the exact behavior explicitly validated by the test scenario, regardless of the existence of other future occurrences that, if evaluated individually, could still be cancellable.

To proceed and successfully complete the test, you should **block the cancellation of all payments** and **return HTTP 422 with the code `PAGAMENTO_NAO_PERMITE_CANCELAMENTO`**.

For the **bulk cancel endpoint** (`PATCH /consents/{consentId}/pix/payments`), the operation is treated as **atomic**. If **any payment linked to the consent is not eligible for cancellation** (for example, due to the cancellation time window having been exceeded), the request **must be rejected as a whole**. 

![image.png](/uploads/a88cb76893c952ecfbdc1d8e427705be/image.png){width=900 height=142}

In this case:

* No payments should be cancelled (no status should change to `CANC`);
* The API must return **HTTP 422 – `PAGAMENTO_NAO_PERMITE_CANCELAMENTO`**.

Please let us know if you need any additional clarification.
