Hi,

Thanks for the ticket!

The test indeed uses an incorrect token on GET Payments. However, it's essential to clarify that this is an alternative step that occurs because the test never meets its requirement of getting a 422 response to the POST Payments request, which is described as expected in the summary last steps, shown below:

> * Calls the POST Payments Endpoint with a different city on the qrcode
> * Expects 422 PAGAMENTO_DIVERGENTE_CONSENTIMENTO
> * Validate Error message

This error at POST Payments is in accordance to swagger [API Payment Initiation 3.0.0.0-beta.1](https://raw.githubusercontent.com/OpenBanking-Brasil/openapi/main/swagger-apis/payments/3.0.0-beta.1.yml) (Reference Error 2.2.2.6).

As the implementation incorrectly returns a 201, CS proceeds to validate its self link, as it does for all 201 responses. But in this case with the wrong token associated with it.

**Therefore, it's important to state that CS should indeed spot a failure on your test execution and the incorrect implementation behaviour needs to be be adjusted to align with the swagger/test summary.** I do understand the engine token failure at the alternative test step can be confusing and we will enhance that. However, it's crucial to emphasize that this enhancement does not obstruct your path to a successful execution in any way, once it is the implementation (not CS) that does not let the test reach its expected state.

Happy to help!
