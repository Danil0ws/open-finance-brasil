## 📝 Descrição

## 1. Specification and Motivations

This request concerns the claim sub of the id_token which is mentioned on the following specifications


[OIDC core](https://openid.net/specs/openid-connect-core-1_0.html#toc)

```
sub
REQUIRED. Subject Identifier. 
A locally unique and never reassigned identifier within the Issuer for the End-User, which is intended to be consumed by the Client, e.g., 24400320 or AItOawmwtWwcT0k51BayewNvutrJUqsvl6qs7A4. 
It MUST NOT exceed 255 ASCII characters in length. The sub value is a case-sensitive string.


```
```
8.  Subject Identifier Types
A Subject Identifier is a locally unique and never reassigned identifier within the Issuer for the End-User, which is intended to be consumed by the Client. Two Subject Identifier types are defined by this specification:

public
This provides the same sub (subject) value to all Clients. It is the default if the provider has no subject_types_supported element in its discovery document.
pairwise
This provides a different sub value to each Client, so as not to enable Clients to correlate the End-User's activities without permission.
The OpenID Provider's Discovery document SHOULD list its supported Subject Identifier types in the subject_types_supported element. If there is more than one type listed in the array, the Client MAY elect to provide its preferred identifier type using the subject_type parameter during Registration.
```




[Brazilian Security Specifications](https://github.com/OpenBanking-Brasil/specs-seguranca/blob/main/open-banking-brasil-financial-api-1_ID3.md#id-token-as-detached-signature)

```
Personally, Identifiable Information may include, but is not limited to,
Claim sub if you use information that makes it possible to identify the natural person;
```

The latest talk regarding this field on the security WG is that the sub is unique for every single CPF that exists within the institutions, in this case, the End-User. This means that when two different consents are authorized for the same CPF on the same Authorisation Server, they should have the exact same sub.

The issue that has been spotted on multiple test is that many times we have orgs sending the dynamic consentid on this field, which is not unique for every end-user within an institution. 


## 2. Request for evaluation

Does the OIDF Agree with that interpretation regarding the sub-claim, or additional documentation would be required for the interpretation above to be drafted?

## 3. Request for test

Assuming the request is valid, the group is also requesting a test to be implemented on either the FAPI - Brazil test plan or Brazilian Functional Test Plan.

The test should be something along the lines of:

The test will generate two consents for the same user using ~~two different applications~~ the same application and will make sure that the id_token returned on the OIDC Authorization code flow for both authorized consents have the same sub claim.

The first discussion has shown that Brazil does not mandate pairwise not public which allows the subject identifier to have two potential formats. 

Public - This provides the same sub (subject) value to all Clients. 

Pairwise - This provides a different sub-value to each client.

Also according to the documentation, we have that "When a sector_identifier_uri is provided, the host component of that URL is used as the Sector Identifier for the pairwise identifier calculation"

As the sector_identifier_uri that the SSA provides always has the host set to be the directory Keystore, this leads to a potential interpretation that the provider will always support the same sub.

Given the definition brought with the points above test has been updated to:

The test will generate two consents for the same user using ~~two different applications~~ the same application and will make sure that the id_token returned on the OIDC Authorization code flow for both authorized consents have the same sub claim.
