## 📝 Descrição

## 1\. What happened and what were you expecting?

When running ANY TEST MODULE IN THE COMPLIANCE ENGINE we expect product URLs to be fetched from the sandbox directory and not written based on the consents URL. This has greatly hindered our testing process as our format between consent and product URLs is different. There was already a ticket in progress, which was closed saying that the problem had been resolved and when we tested it we observed that the problem remains. We request that for this test and for future ones, Radiam can build the engine already considering the search for URLs from the sandbox environment to avoid work for houses that use different URL formats between consent and product APIs.

Example: Card URLs do not have "itau-itau" in their formatting, but we are modifying them exclusively for engine testing and need to remove these adjustments to go into production.

Hi,

After reviewing the Test ID you provided, it's essential to clarify a key aspect,  each authorization server must have a distinct Well-Known URL. Unfortunately, having multiple authorization servers with the same Well-Known URL is not supported, which is likely the root of the issue you're experiencing.

To ensure a successful execution of your tests, please adapt your implementation, so that is follows one of these two possibilities:
1. **Unique Well-Known URL:** Ensure that there is only one Well-Known URL for each Authorization Server. This means that each server must be distinctly identifiable and cannot share its URL with others.
2. **Resource URL Registration:** Register the same Resource URL across all of the Authorization Servers. This will help in maintaining consistency and avoiding conflicts during the testing process.

If you encounter any further issues or have additional questions, please do not hesitate to open another ticket.

### Comentário 14
**Autor**: Christian Eloysio (@christianraidiam)
**Criado em**: 25/10/2023, 17:02:06
**Atualizado em**: 25/10/2023, 17:04:15

We have investigated the issue, and we would like to provide more visibility on what's happening:

- The engine is trying to look up the URL in the directory based on the Org Id and Well Known sent in the configuration. In your case, you have two auth servers for the org ID with the same Well Known, but only one of them has the API Family Type "credit-cards-accounts" registered. In this case, the engine is checking the first auth server it finds, and since it doesn't have the credit card URL, it constructs it from consents.

In that sense, the correction made is working as expected. We will make the change so that it checks all the auth servers within the org ID with the specified well-known, however, if you  register the credit card APIs in Sandbox on all your Auth Servers that have the same well-known or keep only one auth server per well-known, you will be able to run the test without further issues.

In that sense, we will develop this as soon as possible, but we are currently prioritizing other issues opened to be fixed.

We will keep you updated here. We are happy to help with any additional needs!
