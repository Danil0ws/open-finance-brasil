### Comentário 10
**Autor**: Matheus Mantovani (@matheus-mantovani)
**Criado em**: 16/10/2025, 09:52:02

Hello @rafael.cassalichio.

In the test enrollments_api_max-challenges_test-module_v2-2, after the third call to POST /enrollments/{enrollmentId}/fido-registration-options with a different x-idempotency-key, the expected behavior is to return 422 MAXIMO_CHALLENGES_ATINGIDO and **keep the enrollment in AWAITING_ENROLLMENT.**

The 422 payload your API returned on the 3rd call is exactly the condition this scenario expects (a new challenge cannot be created because one is already active):

```
"errors": [
    {
      "code": "MAXIMO_CHALLENGES_ATINGIDO",
      "title": "Parâmetros de assinatura FIDO já foram gerados para o enrollmentId especificado",
      "detail": "Já existe um challenge ativo para este enrollment."
    }
  ],
```

Here, the 422 is a **request-level** error indicating that no additional challenge can be created. It must not change the enrollment state.

The REJEITADO_MAXIMO_CHALLENGES_ATINGIDO value under cancellation.reason.rejectionReason applies **only when the enrollment is actually moved to REJECTED**, which is **not** the flow validated by this test.

From the logs, your endpoint is marking the enrollment as REJECTED after returning 422, which leads to the test failure. You should adjust the behavior to keep the enrollment in AWAITING_ENROLLMENT. With this adjustment, the scenario should pass.

Please feel free to reopen this issue if needed.

Best regards.
