## 📝 Descrição

Prezados, boa tarde.

Ao executar os testes `automatic-payments_api_automatic-pix-extraday-retry-unaccepted_test-module_v2-2` foi identificado uma inconsistência no step `PostRecurringPaymentPixRetryOASValidatorV2n2` onde é validado um código (`PAGAMENTO_DIVERGENTE_CONSENTIMENTO`) inexistente no schema `422ResponseErrorCreateRetryPixRecurringPayment`, portanto, retornando um erro de assert.

Foi informado através de uma [issue](https://gitlab.com/raidiam-conformance/open-finance/certification/-/issues/2309#note_2731142998) que o teste será alterado para agora esperar o código `LIMITE_TENTATIVAS_EXCEDIDO`.

Entendemos que o erro é ocasionado pelo consent ter o campo `isRetryAccepted` valorado com `false`. Ficamos em dúvida se o código proposto (`LIMITE_TENTATIVAS_EXCEDIDO`) é o mais aderente ao motivo do erro, dado que o mesmo não deixa explícito que o motivo foi uma configuração do consentimento.

Desta forma, gostaríamos de sugerir a criação de um novo código mais assertivo para este cenário, e.g. `CONSENTIMENTO_NAO_PERMITE_RENTENTATIVA` .

Desde já, grato!

Boa tarde prezado,

Entendemos o seu ponto de vista de que um código de erro mais explícito sobre a configuração do consentimento seria ideal. No entanto, a escolha do código `LIMITE_TENTATIVAS_EXCEDIDO` foi definida pela estrutura do Open Finance e está alinhada com a interpretação atual da especificação para este tipo de cenário.

Conforme a documentação de erros para o HTTP Code `422 - Unprocessable Entity`, o código:

* **`LIMITE_TENTATIVAS_EXCEDIDO` (4.2.2.16)**: É utilizado quando se **valida se todas as tentativas de liquidação permitidas já foram realizadas**.

Embora o seu erro seja causado por `isRetryAccepted: false`, o resultado prático para o fluxo de pagamento é o mesmo: **o limite de retentativas foi atingido/esgotado**, pois a única tentativa (ou a primeira) é negada permanentemente pela regra de negócio do consentimento. De uma perspectiva de fluxo de retentativa, o consentimento não aceita mais nenhuma.
