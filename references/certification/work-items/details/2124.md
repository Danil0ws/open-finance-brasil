Thanks for creating the issue!

Breaking down the steps executed during test module:

• Call the POST recurring-consents endpoint with automatic pix fields, with referenceStartDate as D+1, interval as SEMANAL, minimumVariableAmount of 0.5 BRL, maximumVariableAmount as 0.8 BRL and sending firstPayment information with amount as 1 BRL, date as D+0 

> Note that the creditor information provided during consent creation is specific to the first payment, as shown below:
>
> ```
> recurringConfiguration.automatic.firstPayment.creditorAccount
> ```
>
> However,  there is no creditor information provided for recurring payments at this stage, meaning the recurring payments could be directed to a different creditor account.

• Call the POST recurring-payments endpoint with the information defined firstPayment payload\
• Expect 201 - Validate Response

> The Conformance Suite processes the first payment by using the creditor information provided in the consent, which is valid.

• Call the POST recurring-payments endpoint with an amount of 0.50 BRL, and date as D+4, and sending ispb as defined by the Central Bank and creditorAccount number as a random number\
• Expect 201 - Validate Response

> The Conformance Suite schedules the recurrent payment after the first payment. However, it is important to note that the server cannot verify the creditor information between recurring-consent and the recurring-payments at this stage, as the creditor information provided in recurring-consents was specific to firstPayment. The error will occur only during the actual payment execution on the scheduled date, as the account does not exist, and the SPI will return a failure during payment liquidation.

The behavior of this test module has been validated with the WG,

Could you please provide the specific business rule that you understand is being violated?
