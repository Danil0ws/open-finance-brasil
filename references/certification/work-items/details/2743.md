Hi Master,

We are testing Open Finance Brazil Enrollments v2 / Payments v5 payment initiation against the Mock Bank / Raidiambank environment.

#### Participant:
c8f0bf49-4744-4933-8960-7add6e590841

#### Problem:
We observed that an enrollment was successfully created and later returned as AUTHORISED, but after some time it changed to REJECTED without the user explicitly unlinking it.

As a result, the subsequent payment flow failed at the FIDO sign step.

#### Observed behavior:

1. POST /open-banking/enrollments/v2/enrollments succeeded and returned:
- HTTP 201
- enrollmentId: urn:raidiambank:enrollment:9a172131-6b65-4448-8b35-e35c2c6fec8e
- status: AWAITING_RISK_SIGNALS
- expirationDateTime: 2026-06-01T04:08:15Z

2. POST /open-banking/enrollments/v2/enrollments/{enrollmentId}/fido-registration-options succeeded.

3. On 2026-06-02, GET enrollment returned HTTP 200 with:
- status: AUTHORISED

4. On 2026-06-03, POST /open-banking/enrollments/v2/enrollments/{enrollmentId}/fido-sign-options failed with HTTP 422:
```json
{
  "errors": [
    {
      "code": "STATUS_VINCULO_INVALIDO",
      "title": "STATUS_VINCULO_INVALIDO",
      "detail": "Vinculo inválido"
    }
  ],
  "meta": {
    "requestDateTime": "2026-06-03T07:39:13Z",
    "totalPages": 1,
    "totalRecords": 1
  }
}
```
Immediately after that, GET enrollment returned HTTP 200 with:
status: REJECTED

This makes us unsure whether Mock Bank is applying a time-based invalidation rule to an AUTHORISED enrollment, or whether this is only mock behavior and not expected in live banks.

We also noticed that the enrollment creation response contained:

expirationDateTime: 2026-06-01T04:08:15Z
However, the same enrollment was still returned as AUTHORISED on 2026-06-02, and only later became REJECTED on 2026-06-03.

So we would like to confirm how expirationDateTime should be interpreted, and whether a later automatic transition from AUTHORISED to REJECTED is expected.

#### Could you please help us confirm:
1. Why did this enrollment change from AUTHORISED to REJECTED?

2. Is this behavior specific to Mock Bank, or should we expect the same behavior from live banks as well?

3. Does the bank apply any time limit / expiration policy to an already AUTHORISED enrollment after registration is completed?

4. If yes, what is the exact invalidation rule?

5. How should expirationDateTime in the enrollment response be interpreted?Is it only for the initial enrollment journey, or is it also related to later enrollment invalidation?

6. If an enrollment becomes invalid after being AUTHORISED, should Mock Bank / bank send an enrollment webhook to notify the client side in advance?

#### Concern:
If an enrollment can later become invalid / REJECTED without explicit unlink action from the user, the user may not be aware of it and may continue trying to pay.

In that case, payment initiation will fail unexpectedly, and the user may not proactively unlink and relink the bank account.

This creates a risk for the payment flow unless the invalidation is clearly notified or predictable.

Hi @zhidong.tan, thanks for reaching out with such a detailed report!

:white_check_mark: Your enrollment was successfully created on June 1 and reached AUTHORISED status.

:white_check_mark: On June 2, you completed two successful payments using this enrollment (at 07:12 and 07:44 UTC) - everything was working fine up to that point.

:warning: However, at 2026-06-02 08:38:40 UTC, your application made a call that caused the rejection:

`POST /consents/urn:raidiambank:payment-consent:6af88da8-d13f-4d27-aa99-c6956e960f76/authorise`

`x-fapi-interaction-id: 8e0f1aa8-dcf8-4a28-849e-52457dcdec95`

The FIDO assertion in this request contained credential ID `BBlPEPmyemo...` (hex: `04194f10f9b27a6a...`), but **no matching public key was found for this credential + enrollment combination**. The error returned was: `RISCO: could not find registered public key`

As per spec behavior, a failed FIDO assertion is treated as a security risk, **so the Mock Bank permanently rejected the enrollment and the associated consent.**

The STATUS_VINCULO_INVALIDO errors you observed on June 3 were a consequence of this earlier rejection.

---

Regarding expirationDateTime — it only applies to the initial enrollment journey (AWAITING_RISK_SIGNALS → AWAITING_ENROLLMENT transitions). Once an enrollment reaches AUTHORISED, it is not subject to time-based expiration.

Hope this clarifies things! Let us know if you have any further questions.
