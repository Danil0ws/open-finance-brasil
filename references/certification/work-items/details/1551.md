Thanks for opening the ticket!

When conformance suit checks if statusUpdateDateTime is after the request time it is validating the statusUpdateDateTime provided in the response for the PATCH payments/consents/{consentId}, following information:

```
  "data": [
    {
      "paymentId": "e39c1a8f-c995-4e42-8c7c-810fa771517a",
      "statusUpdateDateTime": "2024-03-21T13:13:40Z"
    },
    {
      "paymentId": "8cd6726f-605f-4990-b3d8-688cd359c78c",
      "statusUpdateDateTime": "2024-03-21T13:13:42Z"
    },
    {
      "paymentId": "4ce2721b-0c68-4a82-bccc-4531a276fd85",
      "statusUpdateDateTime": "2024-03-21T13:13:44Z"
    },
    {
      "paymentId": "8c7f3634-a010-411f-b358-39929e0b1533",
      "statusUpdateDateTime": "2024-03-21T13:13:45Z"
    }
  ],
```

Against the requestDateTime field that is also present on the response for the PATCH endpoint:

```
 "meta": {
    "requestDateTime": "2024-03-21T13:13:46Z"
  },
```

As you can see, all of the 4 payments have their statusUpdateDateTime be grater then requestDateTime returned on the response.

The “10:13:38” timestamp that you sent is just a clock on timezone (utc-3) that is displayed for log generation reasons, not being validated by the conformance suit, given that the timestamps sent on request and response respect the timezone (utc) as determined by the specification.

Therefore, in order to assure the test module can be successfully executed, please make sure that filed “requestDateTime” is being sent correctly.

Feel free to open a new issue or reopen this one if you have any additional questions,

Happy to help!
