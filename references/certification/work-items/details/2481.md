## 📝 Descrição

Dear Support Team,

During the execution of the JSR certification tests (FIDO/Enrollment), we identified incorrect behavior in the Compliance Engine regarding the manipulation of the userHandle field between the creation and authentication steps.

The Engine is erroneously interpreting a valid Base64Url string as plain text and applying a new encoding layer (Double Encoding) before sending it back to the ASPSP. This alters the value of the opaque identifier and causes the transaction to be rejected by the FIDO server with the error USER_HANDLE_NOT_MATCHED.

Scenario Details
Test Case: Ensure payment reaches an accepted state when a payment without redirect is executed...

Creation Step: POST /fido-registration-options 
(Server Response)
....
"user": {
      "id": "hx6p3O2xF7SQjc4nr5BFafqCtq5wYa9l3X2n-L37O6g",
      "name": "string",
      "displayName": "string"
    }
....

Failure Step: POST /consents/{id}/authorise 
(Radiam Request)

.....
"userHandle": "aHg2cDNPMnhGN1NRamM0bnI1QkZhZnFDdHE1d1lhOWwzWDJuLUwzN082Zw"
.....

Technical Evidence (Payload Analysis)
Below, we demonstrate the inconsistency found in the execution logs:

1. Value sent by the Server (Response from Options endpoint): In the data.user.id field, we sent the following value, correctly encoded in Base64Url (RFC 4648):

JSON

"id": "hx6p3O2xF7SQjc4nr5BFafqCtq5wYa9l3X2n-L37O6g"
Note: Please observe the presence of the hyphen character (-), which is typical of the Base64Url alphabet.

2. Value returned by the Engine (Request to Authorise endpoint): In the data.fidoAssertion.response.userHandle field, the Engine returned:

JSON

"userHandle": "aHg2cDNPMnhGN1NRamM0bnI1QkZhZnFDdHE1d1lhOWwzWDJuLUwzN082Zw"
3. Proof of Double Encoding: By performing a standard Base64 decode on the value returned by the engine (aHg...), the result obtained is the literal string of the original value:

Decode("aHg2cDNPMnhGN1NRamM0bnI1QkZhZnFDdHE1d1lhOWwzWDJuLUwzN082Zw") Result: "hx6p3O2xF7SQjc4nr5BFafqCtq5wYa9l3X2n-L37O6g"

Conclusion and Request
The analysis indicates that the Test Engine parser failed to recognize the Base64Url format (likely due to the presence of - or _ characters), treated the identifier as a common string, and re-encoded it.

According to Open Finance documentation and FIDO Alliance specifications, the userHandle (User ID) is an opaque identifier (byte array) that must be preserved integrally by the Client (in this case, the Engine) and returned to the ASPSP without any alterations or additional re-encoding.

We request an urgent fix in the Engine to ensure the value is treated as pass-through, respecting the original Base64Url encoding provided by the institution.

Hi @gabriel.vasconcelos1. Thanks for the detailed report, we agree with your analysis.

We recently introduced a change to encode this field because one of our tests was correctly sending a mock userHandle data, but incorrectly formatted as plain text. However, that change ended up affecting scenarios where the value is already coming from the POST /fido-registration-options response (already Base64Url encoded), causing the double-encoding behavior you observed.

We’ll address this with a new fix so that values coming from the fido-registration-options response are preserved and passed through correctly.
