Boa tarde @danielamllr , espero que esteja bem. Considerando que, especialmente a respeito da lógica padrão recomendada não se trata de uma obrigação, mas sim uma sugestão, e que a implementação que foi feita desde o início do Open Finance Brasil foi diferente da recomendação (em que pese não prejudicar de nenhuma forma sua segurança, imprimindo inclusive maior eficiência no tratamento das requisições e respostas), pedimos gentilmente que reconsiderem a análise à luz dos seguintes argumentos complementares.

É crucial entender a divisão de papéis: o Servidor de Autorização (AS) é responsável pela autenticação do usuário (e também pela validação do grant_type no momento da emissão do token).
 
O Servidor de Recursos (RS), por sua vez, não é responsável pela autenticação. Seu papel principal é validar a autorização contida no token para conceder ou negar acesso ao recurso que ele protege, garantindo que o grant_type utilizado é apropriado para o recurso que está sendo acessado (como /portabilities).
 
Em nossa implementação do servidor de recursos, realizamos as validações de escopo antes da validação do grant type.
 
No cenário em questão, onde um token é enviado com o grant_type client_credentials (quando authorization_code é esperado) e não possui os escopos esperados para acesso ao recurso, nossa implementação, ao seguir essa ordem, levará à rejeição da requisição.
 
Ressaltamos que as especificações do OAuth 2.0 (RFC 6749, RFC 6750) e as do FAPI não ditam uma ordem rigorosa para as mensagens de erro que devem ser retornadas ao cliente quando múltiplas condições de falha são identificadas pelo Servidor de Recursos.
 
A prioridade de validação (escopos antes do grant_type) é uma escolha arquitetural válida para nossa implementação.

Agradecemos o seu retorno e pedimos desculpas pela confusão anterior. 

A expectativa do motor de conformidade para o `401 Unauthorized` neste cenário baseia-se nas melhores práticas de segurança e nas especificações que regem o OAuth 2.0 e os Perfis FAPI, onde a **autenticação do token (verificar se o token é válido em si)** precede a **autorização (verificar se o token tem as permissões para o recurso/ação)**.

As documentações técnicas que embasam essa ordem são:

1. **RFC 6750 – OAuth 2.0 Bearer Token Usage, Seção 3.1: "Error Responses"**:
   * Esta RFC é clara ao estipular que, se o `access_token` enviado em uma requisição for **inválido, ausente ou expirado**, o Servidor de Recurso (a sua API) **DEVE** retornar um `HTTP Status Code 401 Unauthorized`.
     2. **RFC 7235 – Hypertext Transfer Protocol (HTTP/1.1): Authentication, Seção 3.1: "401 Unauthorized"**:
     * Define que o status `401 Unauthorized` indica que a requisição não foi aplicada porque exige autenticação. É a resposta apropriada quando as credenciais de autenticação são insuficientes ou inválidas.
     * Diferencia-se do `403 Forbidden`, que ocorre quando o servidor entende a requisição, mas se recusa a autorizá-la (mesmo com autenticação válida).
     3. **Perfis FAPI (Financial-grade API) e as Diretrizes do Open Finance Brasil**:
     * As especificações FAPI e as diretrizes de segurança do Open Finance Brasil são construídas sobre os fundamentos do OAuth 2.0 e HTTP, com um foco ainda maior na segurança e na distinção clara de falhas.
     * A lógica padrão e recomendada é que, ao receber uma requisição, o Servidor de Recurso deve primeiro:
       1. **Validar o `access_token` em si (Autenticação):** Isso inclui verificar formato, assinatura, expiração (do JWT), e se o emissor (Issuer) é o esperado.
       2. **Verificar a Autorização (Escopos/Permissões/Consentimento):** Somente após a validação bem-sucedida do token, o servidor deve então verificar se o token possui os escopos necessários, se o consentimento associado está ativo (se aplicável), e se o cliente tem permissão para acessar aquele recurso específico com base nas regras de negócio.

   Sua implementação retorna `403 Scopes Not Granted`. Isso indica que você está realizando a validação dos escopos _antes_ de determinar se o tipo de token (`client_credentials`) é apropriado para autenticar a requisição para o recurso `/portabilities`.

Boa tarde prezados,

Após análise pelo Grupo de Trabalho (GT), gostaríamos de reforçar a distinção entre um erro de autenticação (que resultaria em 401 Unauthorized) e um erro de autorização (que resulta em 403 Forbidden).

**RFCs e Perfis FAPI que corroboram a distinção:**

* **RFC 6750 – OAuth 2.0 Bearer Token Usage:** Esta especificação detalha como o token deve ser transportado e validado. Ela reforça que, se o token estiver ausente, inválido (sintaticamente ou por formato) ou expirado (no sentido técnico de validade do próprio token), o recurso protegido deve retornar um <strong>401 Unauthorized</strong>.
* **RFC 7235 – Hypertext Transfer Protocol (HTTP/1.1): Authentication:** Esta RFC define os significados dos status de autenticação no HTTP. Ela diferencia o <strong>401 (quando a autenticação falha ou está ausente)</strong> do <strong>403 (quando a autenticação foi bem-sucedida, mas o acesso ao recurso está proibido)</strong>. Essa distinção ajuda a reforçar a ideia de separar claramente os mecanismos de autenticação (token inválido/ausente) e autorização (escopo/consentimento insuficiente).
* **Perfis FAPI (Financial-grade API):** As especificações FAPI, desenvolvidas para ambientes financeiros, adotam essa mesma separação. De acordo com as boas práticas descritas nesses perfis, o access token deve ser validado primeiro (autenticação) e, estando válido, a verificação dos escopos ou consentimentos deve ocorrer (autorização). Assim, um token inválido gera <strong>401</strong>, enquanto um token válido semanticamente (mas sem os escopos ou permissões necessárias) resulta em <strong>403</strong>.

**Reforçando o cenário específico do teste "expired-consent":**

Compreendemos o seu argumento sobre a revogação de tokens quando o consentimento expira, levando a uma requisição com token inválido e, consequentemente, a um 401. No entanto, é fundamental diferenciar o cenário de um "token inválido" (em sua estrutura ou validade técnica) do cenário específico que este teste visa validar: <strong>a tentativa de usar um access token associado a um consentimento que está expirado (ou seja, não mais ativo/autorizado).</strong>

O sumário do teste `credit-portability_api_expired-consent_test-module_v1` claramente define:

* "Call the POST /portabilities endpoint using token associated to the expired consent"
* "Expect **403** - Validate the response ensure"

A mesma seção da especificação que você citou (`PT Open Finance Brasil Financial-grade API Security Profile 1.0`) também afirma que o Servidor de Autorização:

* "só deve compartilhar o acesso aos recursos quando apresentado `access_token` vinculado a um consentimento ativo e com o status "AUTHORIZED"."

Neste cenário de teste específico, o access token pode ser <strong>sintaticamente válido</strong> e ter sua validade técnica (expiração do JWT) ainda ativa, mas ele está intrinsecamente vinculado a um consentimento que não está mais <strong>ativo</strong> ou <strong>AUTHORIZED</strong> devido à sua expiração. Portanto, o acesso ao recurso (`/portabilities`) deve ser negado com base na <strong>autorização</strong>.

A especificação prevê o <strong>403 Forbidden</strong> em situações onde:

* O cliente não tem as permissões necessárias para acessar o recurso.
* O recurso é acessado com um token válido (autenticado), mas o contexto (como o consentimento subjacente estar expirado ou inativo) não permite a operação.

A distinção é que <strong>401 Unauthorized</strong> é para quando o token em si está inválido ou ausente (falha de <strong>autenticação</strong>), enquanto <strong>403 Forbidden</strong> é para quando o cliente está autenticado, mas <strong>não autorizado</strong> a realizar a ação específica no recurso (falha de <strong>autorização</strong>).

No caso de um consentimento expirado, o sistema entende que o token (que representa a permissão concedida pelo consentimento) não confere mais a autorização para acessar o recurso.

Portanto, a resposta **403 Forbidden** é considerada correta e em conformidade com a especificação para este cenário de uso de um token associado a um consentimento expirado, uma vez que o token não confere mais a permissão de acesso ao recurso da API de Portabilidade, e não necessariamente porque o token é sintaticamente inválido.

Esperamos que esta explicação detalhada esclareça o comportamento esperado do teste.

“If the protected resource determines that the access token is insufficient to access the resource, the resource server SHOULD respond with the HTTP 403 (Forbidden) status code.”

No cenário relatado, o token é válido e o cliente está autenticado, mas não possui os escopos ou o grant type apropriado para o recurso. Isso caracteriza uma falha de autorização, não de autenticação, o que justifica o uso do 403.

Naquela ocasião, o encaminhamento final foi de flexibilizar as regras do motor de testes para aceitar tanto o retorno 401 quanto o 403, reconhecendo que ambas as respostas são tecnicamente aceitáveis e que diferentes implementações podem adotar abordagens distintas sem comprometer a segurança ou a conformidade.
Diante disso, reforçamos o pedido para que o motor de testes seja ajustado de forma a aceitar ambos os códigos de status (401 e 403) nesse tipo de cenário, promovendo maior interoperabilidade e respeitando a diversidade de implementações legítimas dentro do ecossistema.

Boa tarde @fredmvj 

Sua dúvida foi encaminhada e avaliada pelo Grupo de Trabalho (GT):

De acordo com o posicionamento do GT e as diretrizes do Open Finance Brasil, que adota o modelo REST para a construção de APIs conforme sua documentação de [princípios](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/17377303/Princ+pios), bem como as melhores práticas para a implementação de APIs RESTful, a ordem correta para validação e retorno dos códigos de status `401 Unauthorized` e `403 Forbidden` é sempre **priorizar a validação do `401` antes do `403`**.

Este princípio segue uma lógica de segurança fundamental:

1. **Autenticação (`401 Unauthorized`):** Primeiro, o servidor deve verificar se a identidade do cliente é válida. Isso inclui a verificação da validade estrutural do token, sua assinatura, expiração e se ele corresponde a um cliente autenticado. Se o token for inválido, ausente, ou se a autenticação falhar de alguma forma, o retorno esperado é `401 Unauthorized`.
2. **Autorização (`403 Forbidden`):** Somente após o cliente ser autenticado (ou seja, ter um token válido, mas não necessariamente com as permissões corretas para o recurso em questão), o servidor deve verificar se ele possui as permissões (escopos) necessárias para acessar o recurso específico ou realizar a ação solicitada. Se o cliente for autenticado, mas não tiver autorização para a ação, o retorno esperado é `403 Forbidden`.

No cenário do teste, ao tentar acessar o endpoint `POST /portabilities` com um `access_token` obtido via `client_credentials`, o token pode ser considerado "válido" do ponto de vista de autenticação (o servidor consegue processá-lo e identificar o cliente), mas o **grant type `client_credentials` não confere a autorização (escopos) necessária** para operar em recursos de portabilidade que exigem consentimento do usuário (via `authorization_code` grant).

Portanto, a expectativa é que, ao identificar que o tipo de concessão do token não é o adequado para o recurso que está sendo acessado, a validação de autenticação (relacionada ao _tipo_ de token que _pode_ acessar aquele recurso) falhe antes da validação mais granular de escopos, resultando em um `401 Unauthorized`. A resposta `403 Forbidden` indica que o servidor reconheceu o cliente, mas negou a permissão para a ação, o que sugere que a validação de autorização (escopos) ocorreu antes ou em paralelo à validação da adequação do tipo de credencial.

Conforme a recomendação do GT, a sua implementação deve priorizar a verificação da adequação do `grant type` para o recurso, retornando `401` quando o tipo de token não é o esperado para o recurso (mesmo que o token em si seja tecnicamente "válido" em sua forma e assinatura).
