## 📝 Descrição

## 1. Issue

On the  `patch-consents-api-pixscheduling-revoke-authorized`, the test will create consent and call the token endpoint three times in a row to confirm that the refresh token has not been rotated.

When the test had been deployed it was using the first created token to call the PATCH Consents API, which made one user experience issues as their server was not persisting the access token, responding with a 401 when the first token was used - [Discussed on this ticket](https://gitlab.com/obb1/certification/-/issues/213).

We have since updated the test to use the last issued token as the objective of the test was not to validate the token persistence.

Nonetheless, the question continues. Is an authorization server allowed to “revoke” a previously requested access token or should it accept all the created access tokens?

Discussing the matter internally we understand that in the scope of RC6749 it seems to be entirely left unsaid what happens if you refresh an access token before the end of it’s lifetime. We also believe that, given the current specifications we should have something like 

- 1 <= number of active access tokens permitted by AS per grant < infinity

1 might not be an ideal number, but “infinity” is clearly not practical for /some/ authorization servers.


## 2. Request

Define rules of Access token persistence and update the Brazilian Security Standards

O GT Segurança informa que este comportamento não foi normalizado no perfil de segurança do Open Finance, sendo as duas alternativas, revogação ou não de access_token anteriores, um comportamento válido.

Para que o teste tenha sucesso em qualquer situação, recomendamos que o teste sempre utilize o último access_token emitido.
