Hi @joao.oliveira24 

We have analyzed your report, and we have identified a difference in the interpretation of the execution flow.

In the FVP webhook test, the conformance suit is responsible for **making a call to your endpoint**, not the other way around. In the PAR request (or DCR request), the FVP sends the base webhook URI, and it is your server's responsibility to build the complete URI to receive the notifications. 

The client (your server) only provides the base URI, such as `https://web.fvp.directory.openbankingbrasil.org.br/test-mtls/fvp/w`, and the server must assemble the full URL, like `https://<host>/test-mtls/fvp/w/open-banking/webhook/v1/payments/v4/consents/{consentId}`, as specified in https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/200736835/Registro+do+Webhook+-+Webhook+-+v1.2.0.

The webhook test expects the following flow:

* The FVP makes the first webhook call to your endpoint.
* Your server must **return a `529` response** to this first call, signaling that the notification should be retried.
* After the first call with `529`, it expects your server to make a second call (retry) to the same route, to which it must return a `202`.

Your evidence, the `curl` command, shows a request that was made from **you to our webhook endpoint**, and the `200 OK` response you received confirms that our endpoint is available to receive the notification. However, this does not reflect the behavior of your server during the test, which should be to receive the call and return the initial `529`.

We suggest that you check your server's logs to confirm if the webhook calls from the FVP are being received correctly and, more importantly, if your server is configured to **respond with an HTTP status of `529` on the first interaction**, as required by the test.

Please perform this verification and run the test again. If the problem persists, please provide us with your logs so we can investigate further.
