**Autor**: Leandro José de Bortoli (@leandrobortoli)
**Criado em**: 15/05/2023, 19:32:55

Hi @erick.domingues1 , @ian.costa

The specifications do indicate that the PATCH method only supports client credentials. However, a known error BCLOG-F03-V02-010 states that authorization codes will be accepted in the PATCH endpoint to avoid abruptly breaking the integration until further notice. The same applies to the GET method with error BCLOG-FO3-V2-009.

Therefore, it is unclear whether we should remove access to authorization code tokens in the GET and PATCH methods in this change or in future iterations since I'm not sure the payment initiators were notified to make that change.

For more information, you can refer to the following link: [Link to Known Issues - v2.0.0](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/31162369/v2.0.0+Problemas+conhecidos)

### Comentário 26
**Autor**: Erick Domingues (@erick.domingues1)
**Criado em**: 15/05/2023, 14:22:30
**Atualizado em**: 15/05/2023, 16:21:45

Considering the **GET Payments method**, we have received the following reading around the current documentation.

[The version 2.0.0 of the Payments API defined that](https://openbanking-brasil.github.io/openapi/swagger-apis/payments/2.0.0.yml)

The GET Payments support both client credentials as well as authorization codes as token types

```
 '/pix/payments/{paymentId}':
    get:
      security:
        - OAuth2AuthorizationCode:
            - openid
            - payments
        - OAuth2ClientCredentials:
            - payments

```

The same cannot be said for the PATCH Payments, which support only client credentials

```
    patch:
      tags:
      security:
        - OAuth2ClientCredentials:
            - payments
```

However, we must take into consideration that the [security documentation](https://github.com/OpenBanking-Brasil/specs-seguranca/blob/main/open-banking-brasil-financial-api-1_ID3.md#authorization-server-1) also defines that: 

```
2. shall only share access to resources when presented with an access_token linked to an active and valid consent;
   In the Invalid Token Receive scenario, status code 401 should be returned.

```

This brings us to the conclusion that:
- Tokens issued via Authorization_Code will cannot be used after the POST Payments method has been called, as this will move the underlying Consent to a "CONSUMED" state
- PATCH and GET Payments methods should always be called using tokens issued via client_credentials after the POST Payments is called 

As Next Steps:
**On our side we must update all the tests that haven't been correctly updated so that we always use tokens issued via client_credentials to POLL the GET Payments endpoint - This is being treated as top priority.**

My understanding is that it is no longer possible to use the refresh token to generate new authorization_code access tokens once the consent has been consumed. However, it's important to note that these changes do not invalidate the access tokens that have already been generated.

In light of this, I believe that the method GET payment should continue to function properly with the authorization_code access tokens that are already valid. Despite the limitation on generating new access tokens, the existing tokens should still be recognized.
