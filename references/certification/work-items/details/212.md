## 📝 Descrição

## 1. Context

- Multiple issues regarding servers taking too long to a client request have been raised by participans on  the interoperability tickets
- Currently the CS will wait 60 seconds before it assumes the Server was unable to respond
- At the same time, according to the dev portal, High priority APIs should respond within 1000ms for 95% of the time. Medium priority is 1500ms 
  *  This can be found on https://openbanking-brasil.github.io/areadesenvolvedor/#nivel-de-desempenho and should be only used as a reference to what we should aim to reach, not exactly the value

## 2. Definitions so we can update the CS

- Define what should the max time that the Conformance Suite should wait for a server to respond
- Define if this behavior should be different for any other APIs or if any waiting time should be done between the consent creating and calling another API

### Comentário 2
**Autor**: Jose Fonseca (@zefonseca)
**Criado em**: 01/04/2022, 15:01:46

Hi Erick, please note that there are two different wait periods:

1. The time for the server to respond to a single request
2. The total time for an async request to be approved, rejected, etc

Number 1 is easy to enforce, as per your initial post. But #2 is a bit more convoluted.

Currently, the test is rejecting an async payment when it is not rejected after a certain number seconds of polling: 

https://web.conformance.directory.openbankingbrasil.org.br/log-detail.html?log=3WmGmJQTdBF6zc6&public=true

I'm not sure this is actually enforceable.

For example, in production, an institution can legally withold a PIX payment for several hours if fraud is suspected. Also, there's an SLA which accommodates a certain error margin, so if the tests begin to enforce the time limits, the SLA's and various legal requirements will need to be taken in consideration as well (e.g. it'd be OK for an institution to not respond to an async PIX payment for up to 72 hours or so).
