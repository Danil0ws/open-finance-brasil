## 📝 Descrição

## 1. What happened and what were you expecting?

Boa tarde,

Como complemento a issue #1454, gostariamos que fosse avaliado/revisado o diagrama de sequência da API de pagamentos v4: https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/347078729/Diagrama+de+Sequ+ncia+-+v4.0.0+-+SV+Pagamentos

Nele é indicado que o token/refresh_token de authorisation code deve ser emitido somente após o consentimento assumir o status de AUTHORISED, o que não acontece nos testes de conformidade de múltipla alçada (pagamentos v4 e pagamentos automáticos v1).

![image](/uploads/e4d10766f3439717a35515f3aabf1c18/image.png)

Nesses testes, é esperado que após a primeira autorização do consentimento de múltipla alçada, já seja disponibilizada a uri de callback, que permite a troca do token de authorisation code para um consentimento com status de PARTIALLY_ACCEPTED, o que não condiz com a documentação apontada acima.

Ainda sobre este item, reforçamos a redução de segurança deste fluxo, uma vez que estariamos viabilizando um authorization code, de uso restrito para a iniciação de pagamento a um consentimento ainda não autorizado. Entendemos que apenas para fim de retorno de callback para a iniciadora, não deveriamos utilizá-lo, dando brechas para uma possível exposição dos recursos, uma vez que o consentimento ainda não está apto para realizar uma iniciação de pagamento, evitando assim fazer validações da camada de segurança na camada de negócio.

Hi Rafael! Thanks for the ticket!

In our understanding, if the authorization code is not returned at the redirect, then there is no way that the initiator could get this information after the approval from the second authorizer.

Besides that, following what is defined in the security specs:

* You should only share access to resources when presented access_token linked to active consent and with the status "AUTHORISED".

In that sense, although the initiator would have the authorization code, it should not grant access to resources that are not authorized, since the consent status would be "PARTIALLY_ACCEPTED" and, therefore, the access to the resources would not happen.

Besides that, the [RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749#section-1.3.1) explicitly states that the authorization code should be returned after the redirect, as in:

* the client directs the resource owner to an authorization server (via its user-agent as defined in \[[RFC2616](https://datatracker.ietf.org/doc/html/rfc2616)\]), which in turn directs the resource owner back to the client with the authorization code.

If an authorization code is not returned from the user redirection, then there is no way to get a valid auth code token and, therefore, the message 422 - CONSENTIMENTO_PENDENTE_AUTORIZACAO would never be used, since a response 401 or 403 would be returned at this case, as I would only have a client credentials token, or an auth code from another payment, which would not have the correct scope.

Regarding the fact that the conformance suite does a token request before the consent is "AUTHORISED", we understand that the flow suggests that this step will be executed after the second approver, but no place prohibits this from being executed before.

By any means, we will send this question for the working group to evaluate. **What we need answer is**:

1. Given the additional information provided, **in the situation of a Multiple Consents Account**, should an **authorization code be returned after the authorization from the first approver**?
   1. If the answer is no:
      1. How the authorization code would be retrieved after the second authorizer approval?
      2. In which case the error message 422 - CONSENTIMENTO_PENDENTE_AUTORIZACAO would be used?
2. In case a**n authorization code can be retrieved but the token endpoint should not be called**, which error should be returned in this case? Is there anywhere in the specification where this behavior is defined?
