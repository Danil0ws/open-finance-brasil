## 📝 Descrição

## 1. What happened and what were you expecting?
Prezados,
Estamos enfrentando um problema no teste "payments_api_idempotency_test-module_v4", onde é testado o seguinte cenário:
É criado um consentimento e alterado o seu status para "AUTHORISED", em seguida, o teste realiza a troca do authorisation_code pelo access_token e refresh_token.
Com esse access_token é realizada uma chamada no endpoin POST /pix/payments e tem um retorno de sucesso onde o consentimento é transitado para o status de "CONSUMED".
Em seguida há duas novas tentativas de uso do access token, sendo que uma delas espera que seja validada a chave de idempotência, também no endpoint POST /pix/payments
Entendemos que é errado utilizar o mesmo access token e esperar ter a permissão de acesso válida, uma vez que a documentação de segurança diz o seguinte:
"Servidor de autorização
1. Além dos requisitos descritos nas disposições de segurança do Open Finance Brasil, o Servidor de Autorização deve apenas emitir refresh_tokens quando vinculados a um consentimento ativo e válido;
a.Não deve emitir refresh_token quando o consentimento estiver no status "CONSUMED" (para fase 3);
b.Deve emitir um access_token por meio de um grant_type do tipo client credentials no status "CONSUMED" (para fase 3).

2. Só deve compartilhar o acesso aos recursos quando apresentado access_token vinculado a um consentimento ativo e com o status "AUTHORIZED";
a. No cenário de recebimento de token inválido, deve ser retornado status code 401."
O item 1.b é muito claro em dizer que se deve emitir access token com grant_type "client_credentials" quando o consentimento estiver em status "CONSUMED".
E o item 2 reforça que só deve ter acesso aos recursos, que no caso das APIs de pagamentos o recurso é a iniciação de pagamentos por meio do endpoint POST /pix/payments, quando o access_token estiver vinculado a um consentimento "ATIVO" e com status "AUTHORISED", ou seja, se o status do consentimento for "CONSUMED" o access_token não permitirá acesso ao recurso e, de acordo com o item 2.a, devemos retornar o status 401.

Outro ponto importante é que de acordo com a RFC 6749 o access token gerado a partir da troca do authorisation_code é vinculado ao refresh token, logo, não é possível afirmar que a citação do GT de segurança referente ao grant_type "refresh_token" não impacte sobre a gestão deste access_token.

Gostaríamos que fosse revisado o cenário do teste considerando a documentação de segurança do Open Finance e/ou que o GT esclarecesse como deve ser o comportamento das soluções para estes cenários.

Hi, according to what is described in security spec v1 in \[en\]: https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/240649123/EN+Open+Finance+Brasil+Financial-grade+API+Security+Profile+1.0#7.2.-Authorisation-Life-Cycle,

### 7.2.2. Authorization server

In addition to the requirements outlined in Open Finance Brasil security provisions the Authorization Server

2. shall only share access to resources when presented access_token linked to an active consent and with the status "AUTHORISED“. **For tokens generated with the scope: payments,** the status of the consent will not be validated.

This enables scenarios where idempotency is required. 

This is also being stated in the security specs v2: https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/245694465/PT+Open+Finance+Brasil+Financial-grade+API+Security+Profile+1.0+Implementers+Draft+3#7.2.2.-Servidor-de-autorização,

We understand that the security spec v1 in \[pt\] does not explicit this exception which we believe is a mistake. Therefore we will be raising this matter to the appropriate WG.

So what needs orientation from the WG:

* Although this is not described in the \[pt\] version, should this determination described on the \[en\] version of the security spec be followed: **tokens generated with the scope: payments,** the status of the consent will not be validated?
