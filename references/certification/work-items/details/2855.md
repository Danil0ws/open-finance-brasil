## 📝 Descrição

**Context**

* The Orientações Gerais - \[JO\] Jornada Otimizada v1.0 page sets, as a prerequisite for the data holder, that the authorisation server must have the DADOS and CONTAS roles enabled
  * https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1129250817
* In the JO flow the data consent is created before the primary consent and carries no reference to it. The data.isLinked field is the only Optimised Journey context indicator the data holder receives on POST /consents.
* In the consents 3.3.1 API the field is declared under CreateConsent, with the restriction that it is mandatory for every consent initiated from the optimised journey, regardless of the consent status. 
  * https://github.com/OpenBanking-Brasil/openapi/blob/main/swagger-apis/consents/3.3.1.yml#L597-L601
* The same guidance restricts JO permissions to balances and limits, and requires a 422 response with code COMBINACAO_PERMISSOES_INCORRETA if any other permission is requested.
* The standard does not cover the case of a data holder receiving data.isLinked equal to true without meeting the role prerequisite. That is the subject of this issue.

---

**Observed behavior**

* On 22/08/2026, an authorisation server with the DADOS role active, the CONTA role inactive and no payments API family declared in the Directory received a POST /consents with data.isLinked = true and permissions outside the balances and limits set, including EXCHANGES_READ.
* The response was HTTP 201, with x-v equal to 3.3.1 and the consent created in AWAITING_AUTHORISATION.
* The position stated by the institution is that the Optimised Journey does not apply to it, since it does not meet the role prerequisite, and that the request was handled as a conventional data consent, whose permission combination is valid.
* The consent created cannot be linked to any primary consent, as the institution is not able to hold one. In the JO the validity of the data consent is tied to the validity of the primary consent.
* The journey object exists only in ResponseConsentRead, used by the GET. The 201 of the POST references ResponseConsent, which does not contain the object, so there is no way to signal or to verify at creation time whether the link was recognised.
  * https://github.com/OpenBanking-Brasil/openapi/blob/main/swagger-apis/consents/3.3.1.yml#L1018-L1040
* The 422 error code enum has seven values and none of them describes an unsupported journey.
  * https://github.com/OpenBanking-Brasil/openapi/blob/main/swagger-apis/consents/3.3.1.yml#L1197-L1215
* Directory survey in production: 32 of the 199 active authorisation servers offering the consents v3 API belong to organisations without an active CONTA role, and can therefore be in the same situation.

---

**Expected behavior**

We ask AOPF for a position on the points below.

1. Must a data holder that does not meet the DADOS and CONTAS prerequisite interpret data.isLinked equal to true, or may it ignore the field and handle the request as a conventional data consent?
2. If it must interpret the field and reject the request when the permissions fall outside the balances and limits set, which 422 code applies? COMBINACAO_PERMISSOES_INCORRETA, ERRO_NAO_MAPEADO, or is a new code needed for an unsupported journey?
3. If it may ignore the field, what is the expected handling of the consent that was created, which has no primary consent to be linked to? Does it remain valid as a conventional data consent, is the initiator expected to revoke it, or is another outcome foreseen?
4. On GET /consents/{consentId}, a consent must be created with data.isLinked equal to true return data.journey.isLinked equal to true while still in AWAITING_AUTHORISATION, as stated in the field restriction, or only after the user has given consent, as stated in the journey object restriction?

The answer determines whether the fvp-optimised-journey_invalid-permissions_test-module-v1 module remains applicable in the automated FVP to authorisation servers that do not meet the role prerequisite, and whether the current 201 response is to be treated as conformant.

---

**Our reading, submitted for validation**

* The role prerequisite governs who may offer the journey to the customer, that is, present the unified authorisation screen, hold the primary consent and link both consents. In our reading it does not authorise discarding a field that belongs to the API version the institution declares.
* Because the data consent is created first and carries no linkId, data.isLinked is the only context signal available at creation time. If it can be ignored, the field has no function on POST /consents.
* On that reading, a data holder that receives data.isLinked equal to true and cannot create the JO link should reject the request rather than create a consent that can never be linked to a primary consent. None of the available 422 codes currently describes this case.
