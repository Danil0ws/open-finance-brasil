## 1. What Happened and what were you expecting?

The step "Making PIX request with the same payload but different idempotency key" expects a 201 as response, but its trying to create a new payment using a consent already consumed. In my understanting, as the second request is using a different idempotency-key, the expected result should be 422 - CONSENTIMENTO_INVALIDO.

This specific case is described at [general information for Idempotency](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/24182812/Idempot+ncia+-+v2.0.0+-+Pagamentos):

3. Ao receber uma requisição com o mesmo x-idempotency-key e com a claim iss não pertencente a organização que possui o software cliente (clientId) a requisição deve ser recusada com o HTTP Status 403;

In that sense, since its more specific, the expected state should be 403.

Hi All! Thanks for the ticket!

This is unexpected behavior and we will adapt the test to the following behavior:


Ensure Error when payment request is sent with reused invalid iss and idempotency key

- Calls POST Consents Endpoint
- Expects 201 - Validate Response
- Redirects the user to authorize the created consent 
- Call GET Consent, with the same idempotency id used at POST Consent
- Expects 200 - Validate if status is "AUTHORISED" 
- Call the POST Payments with an invalid iss
- Expect 403 - Validate Error Message
- Calls the POST Payments, with the same idempotency key used at POST Consent
- Expects 201 - Validate Response
- Call the POST Payments with the same idempotency key but a different payload
- Expect 422 ERRO_IDEMPOTENCIA - Validate Error Message
- Call the POST Payments, with the same payload as the previous request but a different idempotency id
- Expects 422 - CONSENTIMENTO_INVALIDO


Please let us know if you find any issue
