Hi @rodrigo.machado1

After analyzing the logs, we found out that your test is failing in the **first** call.

So, according with the test summary, CS calls POST 3 times:

In the last flow, execute the below:\
**• Call the POST Payments Consents V4 Endpoint, with the amount as with the transactionLimit sent, with the payment.date for today\
• Expect 201 - Validate Response**\
• Call the POST Fido Sign Options Endpoint\
• Expect 204\
• Call the POST Consent Authorise Endpoint\
• Expect 204\
• Call POST Pix Payment Endpoint\
• Expect 201 or 422 VALOR_ACIMA_LIMITE - Validate response

Your server is returning the 422 VALOR_ACIMA_LIMITE in the first call, in this step:

• Call the POST Payments Consents V4 Endpoint, with the amount as with the transactionLimit sent, with the payment.date for today\
• Expect 201 - Validate Response

CS should expect a 201 or 422, but only on the call that **exceeds** the limit. The first call is made with a value equal to the transactionLimit, and a 201 is expected.

In your test, the `transactionLimit` is **0.93** and the `dailyLimit` is **1.86**. So, the first call was made with `amount: 0.93`

![image.png](/uploads/2ea681d61a95946997eed2c239904646/image.png)

And your server returned:

![image.png](/uploads/ea6baeea93d18d525490b617acb9c508/image.png)

In this step, your server should return a 201 response.

But in the last call: **Call POST Pix Payment Endpoint, you can return a 201 or 422 response.**

Here you can verify a sucsessful test, where CS calls the pix/payments endpoint 3 times:

https://web.conformance.directory.openbankingbrasil.org.br/log-detail.html?log=rOoOFDgkcJ3UV7J&public=true

Hi @rodrigo.machado1

Thank you for reaching out!

The test was designed to validate compliance with the `dailyLimit`, which is the daily payment limit.

The test retrieves a `transactionLimit` of `0.93` and a `dailyLimit` of `1.86`. 

The expected behavior is that your API processes the first transaction of `0.93` successfully, as it is within the `dailyLimit` of `1.86`. 

The `VALOR_ACIMA_LIMITE` error should only be returned on a subsequent payment attempt, when the `dailyLimit` has actually been exceeded (for example, on the third payment attempt). The test failed because your application rejected the **first transaction**, even though the amount of `0.93` was well below the `dailyLimit` of `1.86`. 

![image.png](/uploads/6b62ea0802dafdcb860aaae77b5cac4f/image.png)

This indicates that the problem is not with the timing of the validation but with the logic for applying the limits, which is preventing even valid initial payments from being processed. 

To resolve this issue, it is necessary investigate why the first transaction is being rejected, ensuring that the daily limit validation logic is correctly applied to future transactions.
