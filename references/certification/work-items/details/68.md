### Comentário 10
**Autor**: Joseph Heenan (@joseph.heenan)
**Criado em**: 28/10/2021, 07:27:04

I tend to agree with @ptheys interpretation of the specs as currently written (I wasn't previously aware of that text in the spec).

https://datatracker.ietf.org/doc/html/draft-idempotency-header (which is a draft, expired and not directly referenced by the Brazil standards as far as I know) is the most detailed writing I'm aware of on an idempotency header. It defines the header to be a transport level (i.e. HTTP) level behaviour, not an application level one. i.e. the expectation is that retries by the client are dealt with by the http client, and hence the request does not change between retries.

i.e. software is expected to first check the idempotency key, and if the key is the same and the request the same, the previous response should be provided with no action performed by the application.

This would, technically, potentially leave a 'replay attack' open. However the 'replay attack' can at most be used to retrieve the exact response previously given - as the idempotency header is the same and the required behaviour is to NOT initiate a payment on a repeated request with the same body / idempotency. Hence I am not sure if replay is really an issue - the number of real world attacks where the attacker has access to the request but not the original response must be small, and (even assuming they did not originally have access to the response), it's unclear how accessing the previous response could in some way advantage the attacker.

The issue of what to do with requests with **different** idempotency keys but the same jti is a completely separate issue, and one that is above the http layer - but as per `payments-consents-api-jti-reuse-test` the expectation is that replay of the jti is detected and rejected there.

In my understand there are two different validations. 

The first one, is to reject reply attacks and for that the jti should always be different, even for messages that have the same idempotency key. If the jti is reused thats an error.

The second validation is the idempotency to ensure that for the same operation only one resource is created. For that is used the header x-idempotency-key. Messages with the same idempotency key must have the same data inside the payload (the “data” attribute  only, not the other attributes of the jwt).

So if a payment initiator lost the response of consent or payment creation (e.g. timeout), it should get the same data, the same x-idepotency-key and sign it using a new jti. This will generate a new payload that ensures that it isn’t a reply attack and is idempotent.
