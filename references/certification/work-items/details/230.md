## 1. What Happened and what were you expecting?

Dear Raidiam, could you please clarify if the client_name must be unique for a given TPP? 

Or may a single entity register several equal client_name's with different client_id's?

This issue came up in production tests, so we did some research into the subject and found only 2 products which mention client_name explicitly as a primary key when client_id is absent: WSO2 [0] and OneWelcome [1]. 

[0] https://medium.com/identity-beyond-borders/trying-out-openid-connect-dynamic-client-registration-in-wso2-identity-server-c0666cd14f0d

[1] https://developer.onewelcome.com/v1.0/dynamic-client-registration-api--dcr-/ref

Most other implementations we studied don't mention the subject explicitly.

Thanks in advance for your assistance.

There is nothing in any specification that I'm aware of that mandates an authorisation server to require unique client names. My reading of this is the opposite is true. The AS must support multiple software records with the same client_name.

RFC7591 The base specification suggests that client_name can be omitted which means Authorisation Servers shouldn't be relying on this as a unique key (or any sort of key).

   client_name
      Human-readable string name of the client to be presented to the
      end-user during authorization.  If omitted, the authorization
      server MAY display the raw "client_id" value to the end-user
      instead.  It is RECOMMENDED that clients always send this field.
      The value of this field MAY be internationalized, as described in
      Section 2.2.

From OIDC Registration

client_name
OPTIONAL. Name of the Client to be presented to the End-User. If desired, representation of this Claim in different languages and scripts is represented as described in Section 2.1.

Personally i believe it is definitely made optional and non unique in RFC7591 under the description of software_id.

**software_id**
      A unique identifier string (e.g., a Universally Unique Identifier
      (UUID)) assigned by the client developer or software publisher
      used by registration endpoints to identify the client software to
      be dynamically registered.  Unlike "client_id", which is issued by
      the authorization server and SHOULD vary between instances, the
      "software_id" SHOULD remain the same for all instances of the
      client software.  The "software_id" SHOULD remain the same across

      multiple updates or versions of the same piece of software.  The
      value of this field is not intended to be human readable and is
      usually opaque to the client and authorization server.

Assuming that the software name doesn't change but the version does an authorisation server would be required to support multiple clients with the same software_id and if it is the same software it is only logical that the name of the software should be duplicated across multiple clients as well. Note that cilent_name is not explicitly marked as unique in any way.

Based on the above i would say that the vendor implementations that you have identified are non compliant.
