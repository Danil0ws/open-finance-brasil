## 📝 Descrição

The test enrollments_api_automatic-payments_automatic-pix-scheduling_1-2_test-module_v2-2 performs a check via EnsureTokenEndpointResponseContainsNrpConsentsScope on the response body of a refresh_token grant call to the token endpoint (POST /v1/oauth2/token). The check fails because the scope field is absent from the response body.

We believe this is not a valid failure.

Per FAPI 1.0 Financial-grade API Security Profile 1.0 — Part 1, §5.2.2, the authorization server ( https://openid.net/specs/openid-financial-api-part-1-1_0.html):

```
*"shall return the list of granted scopes with the issued access token **if the request was passed in the front channel and was not 
integrity protected**"*
```

In Open Finance Brasil, this token request does not go through the front channel — it uses the PAR (Pushed Authorization Request) flow, and the request object is integrity-protected by a signed JWT. Therefore, returning the scope field in the token endpoint response body is not mandatory for this flow.

The scopes are already verifiable from the issued access_token JWT claims itself.

Test log: https://web.fvp.directory.openbankingbrasil.org.br/log-detail.html?public=true&log=WO8zCyTUUpPRgp6

Affected condition: `AbstractEnsureTokenEndpointResponseContainsScope.java`

Could this check be downgraded to WARNING for PAR+JWT flows, or clarified whether there is a Brazil Open Finance regulatory requirement that overrides the FAPI spec optionality?

#### Current Behavior:

---

The test enrollments_api_automatic-payments_automatic-pix-scheduling_1-2_test-module_v2-2 fails with a FAILURE result on the EnsureTokenEndpointResponseContainsNrpConsentsScope check. The check reads the scope field from the refresh_token grant response body of the token endpoint (POST /v1/oauth2/token) and fails if the field is absent.

We believe this is not a valid failure. Per FAPI 1.0 Part 1 §5.2.2, the authorization server "shall return the list of granted scopes with the issued access token if the request was passed in the front channel and was not integrity protected." In Open Finance Brasil, this request goes through the PAR flow and the request object is integrity-protected by a signed JWT — therefore returning scope in the token response body is optional, not mandatory.

Test log: https://web.fvp.directory.openbankingbrasil.org.br/log-detail.html?public=true&log=WO8zCyTUUpPRgp6

#### Expected Behavior:

---

The check should either be removed or downgraded to WARNING for token requests made through the PAR flow with JWT-signed request objects, since the FAPI 1.0 spec only mandates returning scope in the token response when the request was passed through the front channel without integrity protection — which is not the case here.

* E.g. 1: **From**: "...store the refresh_token generated ensuring it has the nrp-consents scope". **To**: "...store the refresh_token generated; if the token response returns a scope field, it must contain nrp-consents (an omitted scope is accepted as unchanged, per RFC 6749 §5.1)".

Hello @marcos.tavares1. Thank you for raising this. It's a valid concern and our analysis confirmed some points to bring out.

You are correct that RFC 6749 §5.1 makes the `scope` field optional when the granted scope is identical to the requested scope, and that FAPI 1.0 Advanced §5.2.2-15 further relaxes this requirement when the authorization request is integrity-protected. It's always the case in Open Finance Brasil, given the mandatory PAR + signed JWT requirement.

Beyond that, looking at the test module summary, the intent is to verify that when the token endpoint is called with a refresh_token grant, the resulting token carries the `nrp-consents` scope. The issue we identified is that the current check is actually reading the `scope` field from the optional HTTP response body rather than inspecting the scope claims inside the access token JWT itself. Since RFC 6749 makes that response body field optional, the check ends up failing on a valid implementation that simply chose not to duplicate scope information in the response body.

We'll keep you updated on the outcome.
