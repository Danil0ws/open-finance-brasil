## 1. What happened and what were you expecting?
Some tests for sweeping-accounts are emitting the error: `GetRecurringConsentsValidatorV1: Unable to find element ibgeTownCode on the Get Recurring Consents Validator V1 API response`

There should not be a validation of it since it is mandatory only for automatic and for for Sweeping Account as mentioned in the schema:

> [Restrições]
> 
> Campo obrigatório que deverá ser retornado quando o consentimento estiver ou passar pelo status AUTHORISED;
> Campo obrigatório quando o oneOf utilizado do recurringConfiguration for “automatic”.

Hi, tanks for opening the ticket!

It seems that the failure was thrown when test module was executing the following steps:

* Call the GET recurring-consents endpoint
* Expect 201 - Validate Response and ensure status is AUTHORISED

While Checking the created consent it is possible to find that indeed its status was as AUTHORISED.

As defined in the [automatic payments specification](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/289243438/Informa+es+T+cnicas+-+SV+Pagamentos+Autom+ticos+-+v1.0.0-rc.2) as mentioned:

> **\[Restrições\]**
>
> **Campo obrigatório que deverá ser retornado quando o consentimento estiver ou passar pelo status AUTHORISED**
>
> **Campo obrigatório quando o oneOf utilizado do recurringConfiguration for “automatic”.**

Given that the consent had the AUTHORISED status, the conformance suit correctly validated for the presence of the ibgeTownCode element in the response body. As conformance suit is operating according to expected and defined in the specifications, please make sure to make the aforementioned adjustments to ensure the test module can be run successfully.
