Olá @JeffAzeveSantos, obrigado pelas novas evidências.

Não houve alteração no Mock Bank relacionada ao tema. A concatenação aparenta ser montada na aplicação de vocês.

Os elementos que mostram isso:

* O print que você enviou é o método `createUrlReturnAndParams(consentId, savedContact)` do front de vocês. Ele monta a URL a partir de `window.location.origin` mais `URL_RETURN` e concatena `consent`, `token`, `brandId`, `tecnologia`, `segmento`, `txId`, `remittanceInformation`, `qrCode`, `callbackURL`, `savedContact` e `version`, gravando em localStorage na chave RETURN-URL. O `consent` vem do `consentId` que a aplicação já tem, e os demais de `createdIParamsPix`, estado interno de vocês.
* A URL de exemplo não foi gerada pelo Mock Bank. O `id_token` dela tem `iss` igual a `https://api.tu.prebanco.com.br/bradesco/pf/open-banking` e `iat` 1697828239, ou seja 20/10/2023, emitido pelo autorizador de vocês no ambiente TU. No fluxo desta issue o `iss` é `https://auth.mockbank.openbankingbrasil.org.br` e o `iat` é 1786717236, 14/08/2026.
* O `consent` naquela URL é `urn:bradesco:a39f8cbf-...`, um consentId do Bradesco, não do Mock Bank.
* Nenhum desses campos é parâmetro OAuth 2.0 ou OIDC. O redirecionamento acrescenta apenas `code`, `id_token` e `state` ao `redirect_uri` registrado, conforme OpenID Connect Core 1.0, seção 3.3.2.5.

Sugerimos validar com o time interno responsável por esse front e pelo serviço que responde o `create-consent-payment`, verificando se `consentId` e `createdIParamsPix` estão chegando preenchidos no momento em que a URL de retorno é montada. A resposta que você enviou traz apenas `uriRedirect`, `consentId` e `savedContact`, sem os demais campos usados na concatenação.

Para correlacionar o retorno com a jornada, use o `state`, que vocês já enviam.

Ficamos à disposição.

Olá @JeffAzeveSantos,

A URL de retorno está correta e completa para o fluxo utilizado (`response_type=code id_token`). 

A resposta do redirecionamento traz o `code`, o `id_token` e o `state`, no fragmento da URL (a parte após o `#`). É o que aparece no retorno enviado no seu exemplo:

```
https://pf.api.bradesco.com/bradesco/open-banking/redirect/#code=...&id_token=...&state=...
```

Isso é o que a especificação [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html) define para esse fluxo (seção 3.3.2.5, "Successful Authentication Response"):

- `code`: "Authorization Code. This is always returned when using the Hybrid Flow."
- `id_token`: "ID Token. This is returned when the response_type value used is code id_token or code id_token token."
- `state`: "OAuth 2.0 state value. REQUIRED if the state parameter is present in the Authorization Request."

Ou seja, não é esperado um campo `consent` nessa resposta de autorização. 

O `consentId` não é entregue no redirect: ele é retornado no corpo da resposta do `POST /consents`e trafega na jornada de autorização dentro do `scope`, no formato `consent:<consentId>`.

Fluxo esperado a partir daqui: usar o `code` retornado para obtê-lo no `/token` e, com o `consentId` que já possuem, consultar o `GET /consents/{consentId}`.

Ficamos à disposição caso tenha mais dúvidas.
