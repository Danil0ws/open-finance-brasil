## 📝 Descrição

## 1\. What happened and what were you expecting?

The recurring-consent is created setting the transactionLimit as `0.00`. Afterwards, the test module call the POST recurring-payments endpoint with the amount as `300.00` and expect the payment to be successfully created..

The transactionLimit field is defined as the "maximum amount allowed for each transaction" and "the payment should be rejected if the payment amount is above said limit", therefore, as the payment amount is bigger than the transactionLimit, we are blocking the payment attempt, causing the test module to fail.

![image.png](/uploads/b75c0efbe525ce0f5043be7f799de382/image.png){width="223" height="103"}

The transactionLimit field is an optional field and if the objective is to not use it in this test module, it should be removed from the consent creation.

![image](/uploads/fb550af8845b6bd70a92df78723d564b/image.png){width=286 height=73}

After analyzing the mentioned test id, it was possible to notice that the field transactionLimit is not being sent on the POST recurring-consents request:

![image.png](/uploads/e5945349bc258e8809883919f096803a/image.png)

While it is being included on the response:

![image.png](/uploads/bd02586f7d77db6406f267dbc8a5fc04/image.png)

As correctly mentioned the transactionLimit field is optional, so to ensure the test module can be executed successfully, make sure not to include this field on the response for POST recurring-consents.
