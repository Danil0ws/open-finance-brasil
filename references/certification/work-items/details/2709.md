## 📝 Descrição

Olá,

Segundo a especificação:

`Apenas pagamentos iniciados por usuários com plenos poderes de aprovação (que não necessitam de outras aprovações para autorização do consentimento) são permitidos. Pagamentos dependentes de múltiplas alçadas aprovadoras devem ter o consentimento rejeitado, após a autorização do primeiro aprovador, com o motivo PERMISSAO_INSUFICIENTE.`

`5.1.13 - Permissão insuficiente: A solicitação de Saque ou Troco foi realizada por um usuário sem plenos poderes de aprovação (PERMISSAO_INSUFICIENTE).`

Gostaríamos de entender o porque que o teste `payments_api_pix-consents-multi-authorization-permission_test-module_v5` não executa o fluxo de autorização do consentimento. Dado que a especificação define que o motivo de rejeição `PERMISSAO_INSUFICIENTE` deve ser após a autorização do primeiro aprovador.

Pessoal,

Conforme mencionado, a issue foi debatida pelo GT Serviços em 26/05/26 e ficou definido que o comportamento a ser testado é o seguinte:

- This test requires a static QR code generated by Pix Tester, which MUST contain an FSS and a value, and may or may not contain a txId.
- This test module validates that the consent is rejected with PERMISSAO_INSUFICIENTE when an account that requires full approval powers for consent authorization is used. This teste requires a multi-authorization debtor account
- Validates if the user has provided the field 'Payment consent - Logged User CPF - Multiple Consents Test' or 'Payment consent - Business Entity CNPJ - Multiple Consents Test'. If neither field is provided the whole test scenario must be SKIPPED
- Set the payload loggedUser/businessEntity using the provided multiple consents CPF/CNPJ
- Call POST /consents with purpose = WITHDRAW
- Expects 201
- Redirects the user to authorize the created consent
- Poll the Get Consents endpoint with the ConsentID Created while status is **"PARTIALLY_ACCEPTED" or** **"REJECTED"**
- Expects 200
- Check the status is REJECTED with rejectionReason.code "PERMISSAO_INSUFICIENTE" and validate the response

Entendeu-se que a interpretação é que deve-se sim permitir a autorização pelo operador, conforme previsto na versão atual da especificação. A alteração realizada no sumário inclui a possibilidade de já obter REJECTED na consulta ao consentimento, mas não prevendo a ida direto de AWAITING_AUTHORISATION para REJECTED, mas sim prevendo a passagem muito rápida por PARTIALLY_ACCEPTED, possibilitando já obter o estado REJECTED na consulta.

Concordo com @adelino.avelino, o teste deveria aceitar os dois comportamentos, pois mesmo que seja permitido transitar para um estado não significa que deve-se transitar para ele.

![image](/uploads/1dac3e23050622eb3139ee42d5f66d48/image.png){width=900 height=226}

Acho que tudo depende da interpretação do que seria após autorização, vejo três cenários:
 
1. Após o **fluxo** de autorização -> falha pois não tem permissão, consentimento transita para rejeitado.
2. Após o **fluxo** de autorização -> sucesso, porém aprovador não tem permissão, consentimento transita para rejeitado.
3. Após o **consentimento** autorizado -> sucesso, consentimento transita para parciamente aceito e depois para rejeitado por falta de permissão.

Em nenhum dos cenários acima o teste estaria correto, pois mesmo no terceiro caso que o consentimento ficaria parcialmente aceito, a transição para rejeitado poderia ser imediata e portanto o GET do teste estaria verificando um estado passado.

Ou seja, o **após**, pode ser no momento seguinte, o teste está forçando um tempo determinado para o **após**.
