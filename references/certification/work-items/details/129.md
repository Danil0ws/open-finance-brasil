1. What happens?
When POST /payments/consent is invoked with the attribute person_type = "INVALID", the test expects the follwing error code response, "DETALHE_PGTO_INVALIDO". 
Not long ago the same test was expecting "NAO_INFORMADO" for the same test case. 


2. Test Id
payments-api-consent-invalid-person-type

3. Comments
Looking at the Swagger specification and also looking at the Schemas for payload objects, the attribute personType is not within de "details" object on the request payload. For that reason the most appropriate error code would be "NAO_INFORMADO".


https://openbanking-brasil.github.io/areadesenvolvedor/#tocS_422ResponseErrorCreateConsent
https://openbanking-brasil.github.io/areadesenvolvedor/#criar-consentimento-para-iniciacao-de-pagamento

Looking at the merge requests this has been updated on: https://gitlab.com/obb1/certification/-/merge_requests/415, however, I can confirm that we were manually checking this step when doing conformance. At first glance, the term "details of the payment" are very broad and I'm not sure it only refers to the payments/details on the swagger. For example, if this were true the amount field wouldn't be considered a detail of the payment. 

Moreover, I understand that it's way better for the TPP to receive the following error when they send a wrong person type

"errors": [
    {
      "code": "DETALHE_PGTO_INVALIDO",
      "title": "Detalhe do pagamento invalido.",
      "detail": "O campo PersonType não atende os requisitos de preenchimento."
    }

instead of

"errors": [
    {
      "code": "NAO_INFORMADO",
      "detail": "Não reportado/identificado pela instituição detentora de conta.",
      "title": "Não informado."
    }

To change this behavior to accept either error codes would need a formal request from either the Sandbox Squad or the Specifications WG
