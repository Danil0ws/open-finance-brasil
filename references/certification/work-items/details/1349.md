Hi Caio, and everyone,

The extension flow is permitted only for a consents who had in AUTHORISED state. So, in this case, the receptor have a valid refresh_token to emit an access_token from the authorization_code flow. That's why the alias to the security schema is OAuth2AuthorizationCode, to specify that an access_token from the authorization_code flow is expected to the endpoint.

When an access_token from client_credentials flow is used, then the security policy will be incorrect, but the access_token is a valid one, our software is able to found it. That way, the error status code will be 403, because the server received a valid access_token, but the security policy is invalid.

Please, can we accept too the status 403, rather than only the status 401 in this cenario?

Hi,

After a more thorough evaluation o the test log provided, we were able to identify that the test module is working as expected.

This test module has the objective of validating a consent extension through a post extends done without user redirect. In this scenario (in which there is no user redirection), there is not a token with authorization code as it is not needed, therefore a token with client_credentials is used (which is the only token that can be obtained in this scenario). As the Post extends is being called with a token which has client_credentials grant_type, the conformance suit is correctly expecting a responde_status_code 401, which as described in the available spec:

401 Cabeçalho de autenticação ausente/inválido ou token inválido.

Therefore conformance suit is operating as expected and according to the specification to validate this specific scenario.
