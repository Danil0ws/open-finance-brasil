I will begin with the conclusion and the provide a more detailed run trough the test module to explain it's behavior!

**The test Summary states the following:**

> This test will simulate an failed intraday retry after 12PM, with a previous intraday tentative. **`To achieve this, the test requires a pre-created and approved Consent ID, which should be configured in the "Intraday ConsentId - Two Payments" field, with two Failed Payment ID, which will be retrieved during the test.`** The test will also need a refresh token linked to the client and user specified in the configuration. `An access token derived from this refresh token will be used to make the payment, configured in the "Intraday Refresh Token - Two Payments" field.` The pre-set consent must have isRetryAccepted set to false, and no firstPayment should be included.

### Conclusion:

The information being used by conformance suit is correct and according to what is described in the test plan Summary.

* Field intradayTwoPaymentsConsentId (1df4ba47-c1e6-4c25-bffa-2104e41ac02d) provided in Test Plan Configuration is being used to call GET recurring-consents
* "recurringPaymentId": "3a9e2de2-41e1-4004-af14-dc438fac1696" being used is being provided by the server in GET recurring-consents (1df4ba47-c1e6-4c25-bffa-2104e41ac02d)
* POST openid-connect/token is being called using refreshToken provided in intradayTwoPaymentsRefreshToken in test plan configuration

Therefore, the test module is using the intended information, which is being provided in test plan configuration and by the server trough GET endpoint responses.

You can access a Guide on executing Retry test modules trough the following link: [Link to guide](https://gitlab.com/raidiam-conformance/open-finance/certification/-/wikis/Phase-3-Automatic-Payments-Tests?redirected_from=Phase-3-Automatic-Payments-Version-1-Tests#automatic-payments-retry-tests:~:text=the%20Sandbox%20Environment.-,Automatic%20Payments%20Retry%20Tests,-The%C2%A0Automatic)

### Test Steps Run trough

**-\> Calling GET recurring-consents**

> • Call the GET recurring-consents {recurringConsentId} endpoint, using the Intraday ConsentId with Two Payments specified in the Config and a client_credentials token\
> • Expect a 200 response - Validate the response, ensure the status is "Authorised", isRetryAccepted is false, no firstPayment information is present

Conformance Suit Calls:

```
 GET recurring-consents/urn:rendimento:1df4ba47-c1e6-4c25-bffa-2104e41ac02d
```

Which points correctly to the field **intradayTwoPaymentsConsentId** **provided in Test Plan Configuration**.

**-\> Calling GET Recurring-payments**

Test module then proceeds to call the GET recurring-payments endpoint to check all payments:

```
GET /pix/recurring-payments?recurringConsentId=urn:rendimento:1df4ba47-c1e6-4c25-bffa-2104e41ac02d
```

Which contains the **intradayTwoPaymentsConsentId** **provided in Test Plan Configuration,** It receives from server the following information in response:

```
"recurringPaymentId": "3a9e2de2-41e1-4004-af14-dc438fac1696",
"recurringPaymentId": "94f9d2ee-8b3f-4bb9-9485-435f80932b69",

Both wich are associated to:
 "recurringConsentId": "urn:rendimento:1df4ba47-c1e6-4c25-bffa-2104e41ac02d",
```

**-\> Calling GET Recurring-payments {recurringPaymentId} endpoint**

Test module proceeds to call the GET recurring-payments {recurringPaymentId} endpoint to **to fetch the original payment data:**

```
GET /automatic-payments/v2/pix/recurring-payments/3a9e2de2-41e1-4004-af14-dc438fac1696
```

It receives from server the following information in response:

```
 "recurringPaymentId": "3a9e2de2-41e1-4004-af14-dc438fac1696",
```

**-\> Calling POST recurring-payments endpoint**

Later on the test module, the following step is executed:

> • Call the POST recurring-payments endpoint, using an access token derived from the refresh token in the configuration. Send a new E2EID, date as D+0, and the other fields with the same information as the previous payment, and include the paymentId in originalRecurringPaymentId

Conformance Suit calls token endpoint:

```
POST openid-connect/token
```

Sending the **intradayTwoPaymentsRefreshToken provided in the test plan configuration** correctly.

After that the following request is made:

```
POST automatic-payments/v2/pix/recurring-payments
```

Witch contains in it's payload:

```
  "recurringConsentId": "urn:rendimento:1df4ba47-c1e6-4c25-bffa-2104e41ac02d",
  "originalRecurringPaymentId": "3a9e2de2-41e1-4004-af14-dc438fac1696"
```
