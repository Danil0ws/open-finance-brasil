## 📝 Descrição

Hi, I was running this new conformance test (`consents_api_extension-jwt-module_v2`) and came across this error:

![image](/uploads/ca2d350c5222a99268cd900fc7db85a1/image.png)

This raised a question for me: what about implementations that only support refresh tokens in opaque format? This particular test would be irrelevant for them as they are incapable of issuing refresh tokens in jwt format. Should the test behavior be modified in order to account for this? I think it would be counterproductive to ask these institutions to implement support for jwt refresh tokens just to turn around and deny it for this use case. 

If there were some documentation stating we should be supporting jwt refresh tokens then that is another story. However, I have not found any and there have been no formal tests barring implementations lacking this capability from becoming certified. Do you know what the official stance is on this?

Hi Dylan! Thanks for the ticket!

There are two certifications in place for the Simplified Consent Renewal:

* One for institution that support opaque refresh tokens, which should execute the test plan `Functional Tests for Consents Extensions API`
* One for institutions that only support refresh_token jwt, which should execute the test plan `Functional Tests for Consents Extensions API with JWT,`  which is only to validate if the endpoint and the error message has been implemented

No institutions are required to certify at both test, which would be indeed nonsense. Each institution only have to certify at one of the test plans above mentioned, as stated at Informa 476, available at https://mailchi.mp/d61a94d14876/open-banking-informa-9417136?e=2eb7798bd9.

We are happy to help with any additional needs!
