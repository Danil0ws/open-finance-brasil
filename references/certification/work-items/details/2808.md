#### Current Behavior:

---

Ao executar o módulo `resources_api_unavailable_test-module_v3-1`, o motor identifica corretamente o resource `ACCOUNT` no status `UNAVAILABLE` e, conforme o comportamento esperado do módulo, chama `GET /accounts/v2/accounts` para validar que o resource indisponível não aparece na listagem. Essa chamada retorna `403` com um corpo fora do padrão de erro do Open Finance (um fault de gateway, no formato SOAP), pois a API de Accounts não é implementada — a B3 não oferece esse produto. O teste falha em seguida com `NullPointerException` ao tentar processar o campo `data`, que vem nulo.

Consultamos as Orientações oficiais da API Recursos (Área do Desenvolvedor) e identificamos que, quando o participante não possui recursos daquele tipo de produto, o comportamento esperado é retornar HTTP 200 com lista vazia — não uma obrigatoriedade de ter sempre pelo menos 1 resource cadastrado.

Diante disso, gostaríamos de confirmar:

1. Para um participante que não oferece nenhum produto de Fase 2 (Contas, Cartão de Crédito, Operações de Crédito) — apenas dados cadastrais — é aceitável que a API Recursos retorne uma lista vazia, mesmo que isso signifique nunca atingir o estado `UNAVAILABLE`/`TEMPORARILY_UNAVAILABLE` para nenhum resource?
2. Nesse cenário, o módulo `resources_api_unavailable_test-module_v3-1` é aplicável a esse perfil de participante, ou existe alguma configuração/test plan alternativo previsto para participantes sem recursos de produto?
3. Caso não haja alternativa, qual é a orientação oficial para satisfazer esse módulo sem cadastrar um resource "artificial" que não tenha uma API de produto real por trás?

#### Expected Behavior:

---

Esperávamos um dos seguintes comportamentos: (a) que a API Recursos pudesse retornar lista vazia para um participante sem recursos de produto de Fase 2, sem que isso seja tratado como bloqueio de certificação; (b) que o módulo `resources_api_unavailable_test-module_v3-1` não fosse obrigatório para um perfil de participante que não possui nenhum resource de Contas/Cartão/Contrato para testar indisponibilidade; ou (c) caso um resource precise ser cadastrado de todo modo, uma orientação clara sobre como sua API de produto correspondente deveria se comportar (ex: um stub mínimo compatível com o spec) para não gerar essa falha.

Olá, @tayssa.silva

Obrigado pelo detalhamento.

O que é anunciado no Diretório precisa corresponder ao que a instituição entrega. Se uma família de API está publicada como Active ali, o motor a testa e espera uma resposta conforme.

Sua API Recursos publica um recurso ACCOUNT com status UNAVAILABLE. O módulo então chama o endpoint do produto correspondente (GET /accounts/v2/accounts) para confirmar que o recurso indisponível não aparece na listagem, esperando HTTP 200. O gateway de vocês respondeu 403 Forbidden com um corpo fora do padrão Open Finance (SOAP Fault MessageBlocked), pois a API de Accounts não está implementada, e por isso o teste falha.

A raiz é a incoerência entre o que é anunciado e o que é entregue: a família "accounts" está publicada como Active no Diretório e há um recurso ACCOUNT na API Recursos, mas o /accounts/v2/accounts não responde de forma conforme.

Dois caminhos para escolher como corrigir:

- Se a B3 oferece Contas: o /accounts/v2/accounts precisa responder 200 (ainda que lista vazia, sem o recurso indisponível), sem bloqueio de gateway.
- Se a B3 não oferece Contas: não anunciar o recurso ACCOUNT na API Recursos e retirar a família accounts do escopo/Diretório. Cadastrar um recurso "artificial" sem API por trás é o que gera a falha.

Respostas às perguntas

1. Lista vazia é aceitável?
   * Sim, uma API Recursos vazia (nunca atingindo UNAVAILABLE) é estado válido; não há obrigatoriedade de manter recursos cadastrados.
2. O módulo é aplicável?
   * Ele roda porque o escopo inclui a API que o exige. Para perfil só de dados cadastrais, o escopo não deve incluir APIs de produto de Fase 2, aí o módulo sai do plano.
3. Como satisfazer sem recurso artificial?
   * Não é preciso. Ou o produto existe (API responde 200) ou não existe (recurso não é anunciado e a API fica fora do escopo). Não há requisito de "stub".

Ficamos à disposição caso queira tirar mais dúvidas.
