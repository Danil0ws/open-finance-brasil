## 📝 Descrição

In the test **enrollments_api_excessive-dailyLimit_test-module_v2-2**, when the Pix Payment Endpoint returns 422 (VALOR_ACIMA_LIMITE) after exceeding the dailyLimit, the behavior is correct.

However, the engine continues the flow expecting a 201, does not treat the 422 as an expected result, and the test fails.

Expected: when receiving 422 (VALOR_ACIMA_LIMITE), the test should finish successfully.

Could you please confirm whether the engine should stop the flow in this case, or if any adjustment is needed in the test to handle 422 as a valid final response?

Hi @bellebernieri23. After further analysis, we found that your implementation is rejecting the **first** POST /payments request, even though the enrollment limits have **not** been exceeded.

The Conformance Suite sent a GET request to https://mtls.openbanking-h.ebanx.com/open-banking/enrollments/v2/enrollments/urn:ebanx:3130b600-f0ed-444b-b3a3-24ea472bee23 and received as response:

![image.png](/uploads/2cf33e31dc3dc9d7563348c5402194b2/image.png){width="426" height="146"}

Then, the first POST /payments request is sent with an amount that is **equal to** the configured limits. The limits are **not surpassed**.

![image.png](/uploads/ce84876a921178b50daaff1d0b47e558/image.png){width="535" height="150"}

However, the request is still rejected with **422 UNPROCESSABLE_ENTITY**:

![image.png](/uploads/3e0d0f2c425ae79fabd806fce4db9f60/image.png){width="452" height="153"}

Based on this, we recommend reviewing the validation rule to ensure the request is only blocked when the payment amount exceeds the configured limits, not when it is **equal to** them.

Please feel free to reopen the issue if you need any further support.
