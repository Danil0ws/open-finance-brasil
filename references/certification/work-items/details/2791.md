Hi @danielamllr ,

There is an inconsistency in the available documentation, since the regex for the **endToEndId** field allows the use for alphanumeric digits in the positions related to the ISPB (which, by the way, is an alphanumeric field):
`pattern: ^([E])([0-9A-Z]{8})([0-9]{4})(0[1-9]|1[0-2])(0[1-9]|[1-2][0-9]|3[0-1])(2[0-3]|[01][0-9])([0-5][0-9])([a-zA-Z0-9]{11})$`

Also, according to official documentation regarding the pacs.008 fields from _Banco Central_, this positions can be set with the first 8 digits of the cnpjInitiator field, allowing for the use of alphanumeric digits.

> Deve ser preenchido no formato padrão ExxxxxxxxyyyyMMddHHmmkkkkkkkkkkk
> - xxxxxxxx:  identificação do agente que gerou o idFimAFim (<EndToEndId>), podendo ser: o ISPB do participante direto, o ISPB do participante indireto ou os 8 primeiros dígitos do CNPJ do iniciador de pagamento  (8 caracteres alfanuméricos [0-9A-Z]{8});

Hi,

Thanks for reporting this. After reviewing the test log (ID R3v8Nwyl0RltQZ3) and the current test module implementation, this is the expected behavior of the conformance suite. Please note the following:

1. **`cnpjInitiator` and the `endToEndId` ISPB are independent fields with different semantics.**
   * `data.cnpjInitiator` identifies the payment initiator (ITP) as defined by the Open Finance Brasil Automatic Payments API specification.
   * The 8-digit segment embedded in the `endToEndId` is the **ISPB of the payer's PSP**, as defined by the Bacen Pix standard (Manual de Padrões do Pix): `"E" + ISPB (8 numeric digits) + yyyyMMddHHmm + 11 alphanumeric characters`.
   * There is no rule in either specification requiring the ISPB in the `endToEndId` to be derived from `cnpjInitiator`.
2. **The `endToEndId` ISPB segment must be strictly 8 numeric digits.** An alphanumeric CNPJ (in this test, `MNHWSA6K000160`) cannot be used in that position — it would produce a non-compliant `endToEndId` under the Pix standard. For this reason, the test module uses a valid numeric ISPB (`44471172`) so that the generated `endToEndId` stays spec-compliant, while still sending the alphanumeric CNPJ in `data.cnpjInitiator`, which is what the test is designed to validate.
3. **What the test actually validates** (per its summary) is that `data.cnpjInitiator` and the creditor/debtor documents contain letters and numbers — which is being done correctly. The test summary does not require any relationship between `cnpjInitiator` and the `endToEndId` ISPB.

In short, the observed behavior is intentional and consistent with both the Pix standard and the Open Finance Brasil specification. No change is required on the conformance suite side.

If you have any further questions, please let us know.
