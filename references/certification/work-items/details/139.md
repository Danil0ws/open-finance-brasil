## 📝 Descrição

While testing locally, the Customer-Personal-api-wrong-permissions-test was
failing because it first tests for a successful call and later it tests for
the missing scope, which should return 403 FORBIDDEN. But in the first
case, the 'customers' scope was not being added, causing the response
status to be 403 and the test to fail.

Adding this line to CustomerPersonalWrongPermissionsTestModule.java solved
the issue and the entire test completed successfully, although I'm not sure
this is the correct solution.

```
@Override
protected void prepareCorrectConsents() {
    callAndStopOnFailure(PrepareAllCustomerPersonalRelatedConsentsForHappyPathTest.class);
    callAndStopOnFailure(PrepareToGetPersonalQualifications.class);
    {+ callAndStopOnFailure(AddScopesForCustomerApi.class); +}
}
```

Looking at your comment I think it's worth looking at the security specifications:

https://github.com/OpenBanking-Brasil/specs-seguranca/blob/main/open-banking-brasil-dynamic-client-registration-1_ID2.md#regulatory-roles-to-openid-and-oauth-20-mappings

> The following table describes the regulatory roles for Open Banking and the related OAuth 2.0 scopes mapping. If the scopes are omitted during the DCR process, the authorization server shall grant the complete set of potential scopes based on the registering bank's regulatory roles, as described in the Server Defaults section.


https://github.com/OpenBanking-Brasil/specs-seguranca/blob/main/open-banking-brasil-financial-api-1_ID3.md#authorization-server-1

> - 4. Shall ensure Access Tokens are issued with sufficient scope necessary for access to data specified in the Permissions element of a linked Consent Resource object;
> - 5. Shall not reject an authorization request requesting more scope than is necessary to access data specified in the Permissions element of a linked Consent Resource object;
> - 6. May reduce requested scope to a level sufficient to enable access to data resources specified in the Permissions element of a linked Consent Resource object;

This means that you could be granting the remaining scopes for this client as it's a DADOS client.

This would be different if the permissions were not included, as this would necessarily mean the access should not be granted, which is exactly what the test is trying to check.

Nonetheless, as the purpose of the test is to evaluate the permissions we can accept the change as proposed by you. Given that you have already updated this on your copy of the conformance we would be glad you could propose the P.R. Either way we will update this week.
