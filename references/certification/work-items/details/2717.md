## 📝 Descrição

#### Current Behavior:
---

So, in the configuration for the test module **payments-withdraw-qres_test-plan_v5** we need to inform a valid Withdraw QRCode that is generated from Pix Tester tool, which will be used for the test **payments_api_pix-withdraw-qres_test-module_v5**.

However, on test **payments_api_pix-withdraw-invalid-amount_test-module_v5**, Conformance Suit generates the consent and the payment using another QRCode in order to test and validate the expected behavior of the present test. When we try to run this test, we are rejecting the consent because this new QRCode points to a different proxy from the one informed in the test configuration.

Proxy from configuration: 4004901d-bd85-4769-8e52-cb4c42c506dc
This proxy is generated from Pix Tester tool and is linked to the QRCode used on the configuration.

Proxy linked to the QRCode generated from Conformance Suit for this test: cliente-a00001@pix.bcb.gov.br


#### Expected Behavior:
---
Conformance Suit should also change the proxy field on the consent creation during this test, not only the QRCode used.

#### Evidence:
---
[Test logs](https://web.conformance.directory.openbankingbrasil.org.br/log-detail.html?log=0FUT4OpNVokEhgw&public=true)

The rejection was made prior to the authorization process, so it is not shown in the test logs. But we refused when validating the QRCode:

`00020126510014BR.GOV.BCB.PIX0129cliente-a00001@pix.bcb.gov.br52040000530398654071500.005802BR5910Joao Silva6014BELO HORIZONTE62070503***6304A431`

`Chave PIX informada no consentimento (4004901d-bd85-4769-8e52-cb4c42c506dc) difere da chave PIX do QR Code (cliente-a00001@pix.bcb.gov.br). ConsentId: urn:bergs:de42fed0-b113-4513-8a36-67572970a7ce.`

Also, the QRCode generated by Conformance Suit doesn't have the FSS field, so despite sending purpose=WITHDRAW in the consent creation, the QRCode is not for "Pix Saque".

**Boa tarde!**

Colaborando com @abellinaso , identificamos um problema adicional: o objeto `creditorAccount` também está sendo alterado entre a criação do **consentimento** e a criação do **pagamento**.

**Consentimento** _(enviado através da configuração)_:

<figure>

JSON

`"creditorAccount": { "accountType": "CACC", "number": "00660945", "ispb": "60701190", "issuer": "2500" }`

</figure>**Pagamento** (gerado pela Conformance Suite):

<figure>

JSON

`"creditorAccount": { "accountType": "CACC", "number": "12345678", "ispb": "99999004", "issuer": "0001" }`

</figure>Assim como ocorre com o campo \`proxy\`, a Conformance Suite parece estar substituindo os dados do \`creditorAccount\` por valores próprios ao gerar o pagamento, sem respeitar as informações definidas na configuração do consentimento. Isso resulta em uma inconsistência entre os dois objetos, podendo causar rejeições indevidas no fluxo de pagamento.
