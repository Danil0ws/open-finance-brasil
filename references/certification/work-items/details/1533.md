## 1. What happened and what were you expecting?
   As mentioned in the issue [1500](https://gitlab.com/raidiam-conformance/open-finance/certification/-/issues/1500), the test try to create new payment using same **access token** and a **CONSUMED** consent.
   The problem in this execution step is that after consent is **CONSUMED**, the **access token is invalidated** and **cannot be reused**, where we return error **401 instead of 422**.
   
  Below is the part of documentation that explain access token time to live for **AUTHORISED** consent and links this logic for **CONSUMED** consent.

   [Official link](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/305594517/M+quina+de+Estados+-+v4.0.0-rc.2+-+SV+Pagamentos)

Hi Rodrigo! Thanks for the ticket!

This topic has evolved a lot in versions V3 and V4, with changes in the Security Spec to cover this case. This case has been better explained and discussed recently at https://gitlab.com/raidiam-conformance/open-finance/certification/-/issues/1489#note_1810278247. In a nutshell, a token is valid as long as the expiration time for it is also valid. this does not mean that the user will have access to the resources since it should also validate the consent status the security spec.

We are happy to help with any additional needs!

Thanks for opening the ticket! As stated in the [API Payment Initiation spec](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/305594722/Informa+es+T+cnicas+-+SV+Pagamentos+-+v4.0.0-rc.2):

```
2.0 Validações na criação do pagamento - Síncrono (POST /payments)
 2.2 Casos de erro sintáticos e semânticos, previstos com retorno HTTP Code 422 - Unprocessable Entity (detalhamento adicional na documentação técnica da API):
  2.2.2 Semânticos
   2.2.2.5 Status Consentimento: Valida se o consentimento encontra-se em um dos estados finais “CONSUMED” ou “REJECTED" (CONSENTIMENTO_INVALIDO);
```

Therefore conformance suit is operating as expected and determined by the specification.
