## 📝 Descrição

### Description

Several conformance test modules send `x-bcb-nfc: true` on the `POST /enrollments/v2/consents/{consentId}/authorise` request regardless of the payment consent's `localInstrument`. This is compliant with the Payments API v4 spec, but inconsistent with the Payments API v5, which explicitly distinguishes NFC-initiated flows from non-NFC ones at the `localInstrument` level.

---

### Reference

Per `EnumLocalInstrument` in `payments-5.0.0`:

| `localInstrument` | Description | NFC |
|-------------------|-------------|-----|
| MANU | Inserção manual de dados da conta transacional | No |
| DICT | Inserção manual de chave Pix | No |
| APDN | Leitura de QR code dinâmico via NFC | **Yes** |
| QRDN | Leitura QR code dinâmico (exceto NFC) | No |
| APES | Leitura de QR code estático via NFC | **Yes** |
| QRES | Leitura de QR code estático (exceto NFC) | No |
| INIC | Iniciador de pagamentos | No |

The Enrollments swagger defines `x-bcb-nfc` as: _"O campo representa uma transação iniciada via NFC"_. Sending `x-bcb-nfc: true` together with a non-NFC `localInstrument` (anything other than `APDN`/`APES`) is therefore semantically inconsistent.

---

### AOPF request

The header `x-bcb-nfc` must reflect the actual `localInstrument` of the payment consent:

* `localInstrument` ∈ {`APDN`, `APES`} → `x-bcb-nfc: true`
* `localInstrument` ∈ {`MANU`, `DICT`, `QRDN`, `QRES`, `INIC`} → `x-bcb-nfc: false`

This adjustment must be applied to both the test implementations and the corresponding test summaries that document the header value.
