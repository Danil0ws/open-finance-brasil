## 1. What happened and what were you expecting?

Hello, I'm running the test `automatic-payments_api_expirationDateTime_test-module_v1`, but it is failing to return 401 to a payment request where its consent is already consumed.
I want to understand better what is the expected behaviour, given the security spec does not orient to revoke tokens in that situation and there's a 422 error that includes situations where the consent is not `authorised`. Should it be a valid response to this situation?

References:

1. API:
`Status Consentimento: Valida se status de consentimento é diferente de “AUTHORISED” (CONSENTIMENTO_INVALIDO);`
Section 4.2
https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/320144040/Informa+es+T+cnicas+-+SV+Pagamentos+Autom+ticos+-+v1.0.0-rc.4

2. Security spec:
```
shall only issue refresh_tokens when linked to an active and valid consent;

Must not issue refresh_token when consent status is "CONSUMED" (for phase 3);

Must issue an access_token through the grant_type client credentials when consent status is "CONSUMED"(for phase 3).

shall only share access to resources when presented access_token linked to an active consent and with the status "AUTHORISED“. For tokens generated with the scope: payments, the status of the consent will not be validated.

In the scenario of receiving an invalid token, status code 401 should be returned.

shall revoke refresh tokens and, access tokens where aplicable, when the linked Consent Resource is deleted;
```
Section 7.2.2
https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/240649123/EN+Open+Finance+Brasil+Financial-grade+API+Security+Profile+1.0#7.2.2.-Authorization-server

Hi @jaquelineduque 

It is our understanding that in:

1. shall only share access to resources when presented access_token linked to an active consent and with the status "AUTHORISED“. For tokens generated with the scope: payments, the status of the consent will not be validated
   1. In the scenario of receiving an invalid token, status code 401 should be returned.

As the point “a” Is nested within 2, the invalid token mentioned regards a token linked to a consent which is not in status AUTHORISED.

As for Section 4.2, point 4.2.2.4 in the [Automatic Payments spec](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/320144040/Informa+es+T+cnicas+-+SV+Pagamentos+Autom+ticos+-+v1.0.0-rc.4), we do not see a scenario on which a 422 status code for validating if consent is in status different then “AUTHORISED” would be applicable.

The way we see, the security spec does indeed leave margin for interpretation, therefore we will be raising this point to the appropriate WG.

What we need evaluation for WG is:

1. \[[Security Profile 1.0 - 7.2.2. Authorization server, Topic 2, subtopic “a”](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/240649123/EN+Open+Finance+Brasil+Financial-grade+API+Security+Profile+1.0#7.2.2.-Authorization-server)\]: Does the “invalid token” referred to on point “a” refers to a token linked to a consent with status different that “AUTHORISED” as described on Topic 2? If affirmative, should a 401 be the correct response code when an attempt is made to access resources using a access_token linked to a consent with the status different then "AUTHORISED“?
2. **\[**[Automatic Payments - 4. **Validações na criação do pagamento - Síncrono (_POST /pix/recurring-payments_)**, Topic 4.2.2.4](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/320144040/Informa+es+T+cnicas+-+SV+Pagamentos+Autom+ticos+-+v1.0.0-rc.4)\]:

   4.2 **Casos de erro sintáticos e semânticos, previstos com retorno HTTP Code 422 - Unprocessable Entity**

   4.2.2.4 Status Consentimento: Valida se status de consentimento é diferente de “AUTHORISED” (CONSENTIMENTO_INVALIDO);

   When should the error message CONSENTIMENTO_INVALIDO along with status code 422 be sent?
3. \[[Issue #1454](https://gitlab.com/raidiam-conformance/open-finance/certification/-/issues/1454)\]: It is being discussed in this issue the inclusion of error.code "CONSENTIMENTO_PENDENTE_AUTORIZACAO” with status code 422 to be returned when a POST recurring-payments is made using a token linked to a consent in status “PARTIALLY_ACCEPTED”. As this status is in fact different then "AUTHORISED“, taking the Security profile specification into consideration, should this scenario actually return a 401, or would the Automatic Payments specificaiton prevail in this case, thus returning a 422?

Hi, thanks for the ticket!

For this specific behavior, as correctly pointed according to the s[ecurity specs](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/245760001/EN+Open+Finance+Brasil+Financial-grade+API+Security+Profile+1.0+Implementers+Draft+3#7.2.2.-Authorization-server), the authorization server:

1. shall only share access to resources when presented access_token linked to an active consent and with the status "AUTHORISED“. For tokens generated with the scope: payments, the status of the consent will not be validated.
   1. In the scenario of receiving an invalid token, status code 401 should be returned.

In this specific case, although we understand that there is a 422 error message at the spec where this behavior would also be applied, the API should not even validate the business rule (which is the case for the 422).

In that sense, even though there is the 422 CONSENTIMENTO_INVALIDO error message, a 401 should be returned since it regards errors that happen on the security layer, which preceeds any business rules validations.

We are happy to help with any additional needs!
