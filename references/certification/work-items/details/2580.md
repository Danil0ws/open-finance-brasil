## 📝 Descrição

## 1. What happened and what were you expecting?

Hello, I'm running the test `payments_api_consumed-consent_test-module_v5`, but it is failing because the conformance suite expects a **422 Unprocessable Entity** response when the consent is in status `CONSUMED`.

In our implementation, once the consent becomes `CONSUMED`, the Authorization Server revokes the tokens linked to that consent, so any subsequent request using that token is rejected earlier by the security layer with **401 Unauthorized**, as the token is no longer valid.

Given this, I would like to better understand what the expected behavior of the test should be. The security profile explicitly states that:

> 1. shall only issue refresh_tokens when linked to an active and valid consent;
>    1. Must not issue refresh_token when consent status is "CONSUMED" (for phase 3);
>    2. Must issue an access_token through the grant_type client credentials when consent status is "CONSUMED"(for phase 3).
> 2. shall only share access to resources when presented access_token linked to an active consent and with the status "AUTHORISED“. For tokens generated with the scope: payments, the status of the consent will not be validated.
>    1. In the scenario of receiving an invalid token, status code 401 should be returned.
> 3. shall revoke _refresh tokens_ and, _access tokens_ where aplicable, when the linked Consent Resource is deleted;

In this scenario, when a request is made with a token linked to a `CONSUMED` consent, the token is invalid and a **401** response seems compliant with the security profile. On the other hand, the API spec defines a **422** error for situations where the consent is not in `AUTHORISED` status.

Because of this overlap, my understanding is that the test could accept either **401** (invalid token because the consent has been consumed and the token revoked) or **422** (business validation on consent status), even though in our specific implementation the 422 path will never be reached due to the earlier security validation.

Could you confirm whether the test can be updated to assert that either **401** or **422** is acceptable in this scenario?

Hello @laerson.guimaraes 

Thank you for raising this question.

Regarding the security argument, the Open Finance Brasil Security Profile is explicit on this point: "for tokens generated with the scope payments or recurring-payments, **the status of the consent will not be validated**."

Because of that, the fact that the consent is in status CONSUMED does not, by itself, justify treating the token as invalid at the security layer and returning 401 Unauthorized.

In other words, the argument presented mixes consent lifecycle with token validity. The Security Profile does not establish that a consent in status CONSUMED automatically makes an already issued payment token invalid. Therefore, this point does not support changing the expected behavior of the test to accept 401 as equivalent to the business validation expected for this scenario.

Please feel free to reopen this issue if needed.

Best regards
