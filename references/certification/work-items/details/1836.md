## 📝 Descrição

**Description:**

According to the User Experience Guide ([link](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/17378535/Guia+de+Experi+ncia+do+Usu+rio)), on page 209, it mentions the possibility of the user providing the debtor account information to the initiator during the device enrollment process, which is then sent by the initiator in the POST Enrollment Request.

However, the guide instructs that when this data is not valid, it should only not be used, accepting the request and allowing the user to modify the information, as shown below:

![image.png](/uploads/a1c127ef889e15dace84c2b487c290e6/image.png){width="610" height="653"}

On the other hand, the FAQ for Enrollment ([link](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/591102972/FAQ+-+JSR+-+v2.0.0-rc.1+-+SV+V+nculo+de+dispositivo)) states in an example that if the ISPB is not valid, the request should be rejected with a 422 - CONTA_INVALIDA response, as seen below:

**Q: Posso rejeitar uma tentativa de vínculo de maneira síncrona?**\
A: Sim. É possível retornar qualquer um dos erros presentes na especificação, atentando-se sempre em ser coerente entre as razões e os códigos. Para o código HTTP 422, recomendamos o uso com cautela do motivo "CONTA_INVALIDA", uma vez que esta pode ser alterada pelo usuário durante o processo de autorização, recomendamos seu uso para casos mais extremos, como ISPB não pertencente a instituição, por exemplo.

Based on this, there seems to be an inconsistency regarding this case. We would like confirmation from the working group:

1. In the case where an invalid debtor account is sent by the initiator in the POST Enrollments request, what is the expected behavior?\
   a. The request is accepted, and the user is prompted to change the debtor account during the redirection.\
   b. The request is denied, and the message "422 - CONTA_INVALIDA" is sent.\
   c. The request is denied, and the message "422 - PARAMETRO_INVALIDO" is returned.
2. Is the behavior the same for all fields within the debtorAccount (e.g., ISPB, issuer, number, or accountType), or does it vary depending on which field is sent?

### Comentário 2
**Autor**: GT Especificações (@GT_Servicos_ChicagoAdvisory)
**Criado em**: 17/10/2024, 14:47:06

O Squad JSR entende que a definição de conta válida é uma decisão da instituição detentora de contas e é um critério da detentora realizar a validação nesse ponto da jornada, ou seja, os comportamentos A e B são possíveis. O Cenário C é uma validação do ponto de vista sintático baseado nas regras colocadas no Swagger e deverão ser verificadas antes de qualquer regra relacionada ao caso B. Por exemplo: o ITP envia o ISPB com nove caracteres, o detentor DEVERÁ ser enviado o erro “422 – PARAMETRO_INVALIDO”. Outro cenário: o ITP envia o ISPB com oito caracteres porém este ISPB não existe, o detentor PODERÁ seguir com o cenário A ou B. Este mesmo tratamento serve não só para o campo ISPB, mas também para os campos issuer, number e accountType.
