Hi @jaquelineduque 

Thanks for bringing this to our attention,

According to the [API Automatic Payments specification](https://openbanking-brasil.github.io/openapi/swagger-apis/automatic-payments/?urls.primaryName=1.0.0#/Recurring%20Consents/automaticPaymentsPostRecurringConsents) for POST recurring-consents:

**debtorAccount:**

Object containing the identification of the payer's source account. Information about the payer's source account can be brought in the consent to the holder if the initiator has collected this information from the customer. Otherwise, it will be collected from the holder and brought to the initiator as a response to the creation of the payment.

Therefore conformance suit will be adjusted so that debtorAccount information is not filled during the POST recurring-consents call, thus preventing this failure from happening since it will need to be provided by the holder.

Hi,

As can be seen below, the test module is using the debtorAccount in the POST /recurring-consents exactly as provided in the test config:

![1.png](/uploads/d33dde99bf20b19bc7dc2d4b1f6af9ab/1.png)

The main objective of this test module is to ensure a payment using sweeping account can be successfully executed when the creditors are all from the same company, for that it uses a BCB provided CNPJ Pix key to be used as a proxy for the creation of payments. As described on the test summary:

“This test will always use the following CNPJ 98380199000125 as proxy and businessEntityIdentification when creating the payment, and not considering what is informed on this field on the config, although if this field is not informed the test will be skipped. Therefore the 98380199000125 should be registered in the ASPSP for a successful test run.”

Taking that into consideration, it seems that the implementation returned a 422 due to 98380199000125 not being registered in the ASPSP

Feel free to reopen this issue or open a new one if you have any other questions,
