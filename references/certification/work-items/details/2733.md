## 📝 Descrição

**Contexto**

Entendemos que o comportamento atualmente validado pelo teste **payments_api_pix-consents-multi-authorization-permission_test-module_v5** até pode estar aderente à interpretação atual da especificação, exigindo:

autorização inicial do primeiro aprovador;
transição do consentimento para PARTIALLY_ACCEPTED;
posterior rejeição com motivo PERMISSAO_INSUFICIENTE.

No entanto, gostaríamos de propor uma flexibilização do teste e da interpretação da especificação para também aceitar rejeição síncrona durante o fluxo de autorização.

**Motivação Técnica**

Se a instituição financeira já possui, durante o processo de autenticação/autorização, a informação de que o usuário autenticado não possui poderes de aprovação suficientes para aquela operação, obrigar o fluxo a prosseguir até PARTIALLY_ACCEPTED gera:

processamento desnecessário;
manutenção de estados intermediários sem possibilidade real de conclusão;
maior consumo de recursos computacionais;
aumento de complexidade operacional no motor de Open Finance.

Do ponto de vista de engenharia de software, o comportamento mais eficiente seria rejeitar a operação assim que a insuficiência de permissão for detectada.

**Experiência do Usuário (UX)**

O fluxo atual induz o usuário a concluir:

autenticação;
redirecionamento;
biometria/senha;
confirmação da operação;

para apenas depois receber um erro de PERMISSAO_INSUFICIENTE.

Isso cria uma falsa expectativa de sucesso e aumenta o atrito na jornada do usuário.

Uma rejeição imediata durante o fluxo de autorização é mais transparente e alinhada às boas práticas de UX em serviços financeiros.

**Coerência entre Cenários de Erro**

Foi citado na issue https://gitlab.com/raidiam-conformance/open-finance/certification/-/work_items/2709

Se cenários de “limite excedido” podem possuir tratamento mais imediato ou comportamento distinto, entendemos que o cenário de “permissão insuficiente” também poderia admitir rejeição antecipada.

Manter fluxos técnicos radicalmente diferentes para erros de negócio semelhantes aumenta a complexidade de implementação para as instituições participantes.

**Ambiguidade Semântica da “Autorização”**

A especificação menciona que o erro deve ocorrer “após a autorização do primeiro aprovador”.

Entendemos que o termo “autorização” pode ser interpretado como:

o ato técnico de tentativa de autorização/autenticação;
e não necessariamente a conclusão bem-sucedida do consentimento em PARTIALLY_ACCEPTED.

Nesse entendimento, a instituição estaria aderente à regra ao:

AWAITING_AUTHORISATION -> REJECTED (PERMISSAO_INSUFICIENTE)

desde que o erro seja consequência direta da tentativa de autorização do usuário.

Assim, a transição por PARTIALLY_ACCEPTED poderia ser **opcional** e não **mandatória**.

**Integridade Semântica do Estado PARTIALLY_ACCEPTED**

O status PARTIALLY_ACCEPTED aparenta ter sido concebido para **fluxos legítimos de múltiplas alçadas** ainda passíveis de conclusão.

Utilizá-lo em cenários onde o sistema já sabe previamente que a operação nunca poderá ser concluída distorce:

o significado funcional do estado;
indicadores estatísticos;
métricas operacionais derivadas do diretório central.

Na prática, o consentimento já nasce inviável.

**Sugestão**

Solicitamos avaliar a flexibilização do teste para aceitar ambos os comportamentos:

Fluxo assíncrono atual

AWAITING_AUTHORISATION -> PARTIALLY_ACCEPTED -> REJECTED

Fluxo síncrono alternativo

AWAITING_AUTHORISATION -> REJECTED

desde que:

o motivo seja PERMISSAO_INSUFICIENTE;
a rejeição ocorra como resultado direto da tentativa de autorização;
e os requisitos de segurança/autenticação permaneçam preservados.

Entendemos que essa flexibilização manteria aderência funcional à especificação ao mesmo tempo em que permitiria implementações mais eficientes e melhores experiências para o usuário final.

Prezado,

A issue foi debatida pelo GT Serviços em 26/05/26 e ficou definido que o comportamento a ser testado é o seguinte:

- This test requires a static QR code generated by Pix Tester, which MUST contain an FSS and a value, and may or may not contain a txId.
- This test module validates that the consent is rejected with PERMISSAO_INSUFICIENTE when an account that requires full approval powers for consent authorization is used. This teste requires a multi-authorization debtor account
- Validates if the user has provided the field 'Payment consent - Logged User CPF - Multiple Consents Test' or 'Payment consent - Business Entity CNPJ - Multiple Consents Test'. If neither field is provided the whole test scenario must be SKIPPED
- Set the payload loggedUser/businessEntity using the provided multiple consents CPF/CNPJ
- Call POST /consents with purpose = WITHDRAW
- Expects 201
- Redirects the user to authorize the created consent
- Poll the Get Consents endpoint with the ConsentID Created while status is **"PARTIALLY_ACCEPTED" or** **"REJECTED"**
- Expects 200
- Check the status is REJECTED with rejectionReason.code "PERMISSAO_INSUFICIENTE" and validate the response

Entendeu-se que a interpretação é que deve-se sim permitir a autorização pelo operador, conforme previsto na versão atual da especificação. A alteração realizada no sumário inclui a possibilidade de já obter REJECTED na consulta ao consentimento, mas não prevendo a ida direto de AWAITING_AUTHORISATION para REJECTED, mas sim prevendo a passagem muito rápida por PARTIALLY_ACCEPTED, possibilitando já obter o estado REJECTED na consulta.
