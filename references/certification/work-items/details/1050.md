## 📝 Descrição

1. What happened and what were you expecting?

Our authorisation server has the following phase 1 and phase 3 family types registered on Central Directory:
[
  "payments-consents",
  "channels",
  "payments-pix",
  "discovery",
  "admin",
  "products-services"
]

And our well-known endpoint is responding correctly with phase 3 scopes:
    "scopes_supported": [
        "openid",
        "payments"
    ], 

But somehow, FVP is expecting different scopes to be returned in the response. This test module is validating scope for the API family type channels, which is a public API and would not require a token (scope) Given that we are exposing only phase 1 and phase 3 endpoints, shouldn't these 2 scopes be enough?

Hi Rodrigo,

The idea of this step of the test is to validate if the scopes supported from the well-known configuration, correspond to the API family types published in the directory, and also the other way around.

From the image, it is possible to see that scopes from the well-known are accounts, consents, credit-card-accounts... However, the apis published in the directory are only the four from the image [payents-consents, payments-pix, discovery, admin]. The error message is also not clear and we are now working to improve it, but the scope field in there should correspond to all scopes for which there is not a respective api published.

The next step of the test would check if the ROLEs in the directory correspond to the APIs published, according to the table in https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/82215063/PT+Open+Finance+Brasil+Financial-grade+API+Dynamic+Client+Registration+1.0+Implementers+Draft+3#7.2.-Fun%C3%A7%C3%B5es-regulat%C3%B3rias-para-mapeamentos-OpenID-e-OAuth-2.0. Here, you should verify if the organization has the correct ROLEs created, depending on the api published for the authorisation server.
