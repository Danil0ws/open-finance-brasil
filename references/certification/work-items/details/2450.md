Hello @ranieri85.

You are right that this is not a transient issue. After reviewing logs from the FVP and from the PCM reporting, we were able to reconstruct what is happening on your test plan.

**1. What actually happens when the test runs**

From the FVP logs and PCM events we can see that, when you run the portability tests for the AS `d0a262b8-e097-4e53-b5c1-7c26d064afbd`, the FVP **does** send a DCR request:

```
{
  "timestamp": "2025-12-07T01:11:26.017Z",
  "statusCode": 403,
  "httpMethod": "POST",
  "endpointUriPrefix": "mtls-api-proxy.crefisa.com.br",
  "endpoint": "/orgs/crefisa/reg",
  "clientSSId": "d52c9049-a67b-432f-bdde-fe613099f83b",
  "clientOrgId": "b2a8233c-eda6-4c46-8263-813d71508f1b",
  "serverOrgId": "9294c0e8-ab01-5614-942d-97f261fe3454",
  "role": "CLIENT"
}
```

* **Result:** HTTP 403 FORBIDDEN

So, contrary to what the FVP error message suggests, the request is reaching your infrastructure and is being rejected with 403 by the endpoint mtls-api-proxy.crefisa.com.br/orgs/crefisa/reg.

**2. Why the FVP shows “Unknown endpoint” and a Java stacktrace**

In the FVP logs we also see the following line:

```
DCR client registration failed for client at
https://mtls-api-proxy.crefisa.com.br/orgs/crefisa/reg
with status 403 FORBIDDEN and message <HTML><HEAD>
```

This tells us two important things:

1. Your registration endpoint is returning HTTP 403, and
2. The response body starts with \<HTML\>\<HEAD\>, i.e. it is an HTML error page (probably from a proxy/WAF), not a JSON body.

The FVP DCR handler, however, currently assumes that the response body from the registration endpoint will always be a JSON object (for both success and error cases), as per the DCR/OAuth/OpenID expectations. It tries to parse the body as JSON and ends up throwing:

```
{
  "cause": "java.lang.IllegalStateException: Expected BEGIN_OBJECT but was STRING at line 1 column 1 path $",
  "message": "java.lang.IllegalStateException: Expected BEGIN_OBJECT but was STRING at line 1 column 1 path $",
  "exceptionType": "com.google.gson.JsonSyntaxException"
}
```

This is a Java stacktrace from the FVP itself (not from your implementation). Because this exception happens after the HTTP call, in an internal translation layer, the error report shows this message above with statusCode 500. That is why you see “Unknown endpoint” and Java details.

**3. Successful execution and stability of the tooling**

From our side we could also confirm that:

* At least one DCR execution for your institution completed successfully on the previous day, using the same FVP portability test plan `("2025-12-05T14:31:54.611+00:00")`
* There were no changes or deployments to the FVP or to the Directory configuration in the interval between the successful and failing executions.
* The same portability test modules are running successfully against other Authorisation Servers in the ecosystem, using the same FVP version.

This indicates that the overall FVP/Directory setup and the test modules themselves are stable, and that the current behavior is specific to how the AS (or the proxy in front of it) is handling and responding to the DCR requests.

**4. Recommended next steps**

We recommend reviewing the configuration of mtls-api-proxy.crefisa.com.br/orgs/crefisa/reg (including any WAF/proxy in front of it) so that DCR errors are returned as JSON with Content-Type: application/json, following the usual OAuth/DCR error format.

In parallel, we will raise an improvement for the FVP so that, when it receives a non-JSON response from a registration endpoint, it shows a clearer message (including HTTP status and URL) instead of the low-level JsonSyntaxException.

---

Once the behavior of the endpoint has been adjusted, you can rerun the portability tests on the same FVP plan and they should progress past the DCR step.

If you still see any unexpected behavior after that, please feel free to reopen this issue and share the new error report. We’ll be happy to review them together.
