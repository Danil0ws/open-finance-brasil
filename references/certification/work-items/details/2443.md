#### Current Behavior:
---
O teste fvp_dcr_automatic-payments_api_negative-consents_test-module_v2 do plano de testes dcr-fvp_test-plan  está esperando um retorno 400 (EnsureConsentResponseCodeWas400) quando não envia o parâmetro x-fapi-interaction-id para **endpoints negociais** "recurring-consents".
As validações são as seguintes: 

  - Call the POST recurring-consents endpoint without the x-fapi-interaction-id               
     Expect 400 - Validate Error Message and check if a x-fapi-interaction-id has been sent back
  - Call the POST recurring-consents endpoint with the x-fapi-interaction-id as '123456'                 
     Expect 400 - Validate Error Message and check if a x-fapi-interaction-id has been sent back 


#### Expected Behavior:
---
O comportamento correto **para endpoints negociais** deveria considerar a documentação do endpoint, não a definição geral do FAPI (que é válida para os endpoints de segurança [/token,/register,etc.]). 
A documentação do endpoint "recurring-consents" prevê o seguinte comportamento: 
> 4.2 Casos de erro sintáticos e semânticos, previstos com retorno HTTP Code 422 - Unprocessable Entity (detalhamento adicional na documentação técnica da API):<BR/>
> 4.2.1 Sintáticos <BR/>
> 4.2.1.1 Envio de campos obrigatórios: Valida se todos os campos obrigatórios são informados (PARAMETRO_NAO_INFORMADO);<BR/>
> 4.2.1.2 Formatação de parâmetros: Valida se parâmetros informados obedecem a formatação especificada (PARAMETRO_INVALIDO).

Hello @cruzcunha. 

We escalated the question to the Open Finance DTO team, and they confirmed that, for the scenarios where the issue is related to the `x-fapi-interaction-id` header, the **expected behavior is HTTP 400 (Bad Request)**.

The rationale is that missing or malformed HTTP headers are treated as a request-format problem, while HTTP 422 (“parameter not informed”) is reserved for validation errors in the JWS/body. Since the `x-fapi-interaction-id` is not part of the JWS, it falls into the 400 errors.

For that reason, the current conformance test modules were designed, in agreement with DTO, to expect **400** in these flows.

If, in the future, the Working Group/DTO decides to change this pattern, we will align and update the test plans accordingly. But at this moment, the behavior of the tests matches the guidance we received.

Please feel free to reopen this issue if needed.

Conceptually, we understand that the absence of a mandatory header fits better as a malformed request (**400**) than as a validation error (**422**), which is why this test plan was designed this way. The same logic is applied to other product test modules. 

From the conformance engine perspective, the behaviour is consistent with the test plan agreed with the Open Finance Structure, which is why we believe it's important to have DTO/Working group analysis to move on.
