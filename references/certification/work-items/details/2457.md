Hi,

The test explicitly defines the following step:

**“Call POST Consents Authorize with a mocked payload on the FIDO assertion.”**

In order to send a valid authorization request (including the **challenge** and other required data inside `POST /consents/{consentId}/authorise`), the participant must previously call:

**POST /fido-sign-options**

This endpoint is responsible for generating the challenge used in the authorization request.

However, **POST /fido-sign-options can only be called after the consent has already been authorised**.\
If the consent were authorised, it would no longer be in the **AWAITING_ENROLLMENT** status, which would make it impossible to reproduce the scenario required by the test (calling `/authorise` while the enrollment status is AWAITING_ENROLLMENT).

For this reason, the test correctly uses a **mocked FIDO payload** and validates that the ASPSP returns **HTTP 422 – STATUS_VINCULO_INVALIDO** when `/authorise` is called in this state.

Therefore, the behavior expected by the test is correct and aligned with the specification.\
If there is still disagreement with this approach, the case can be forwarded to the product working group for evaluation of a possible change in behavior.
