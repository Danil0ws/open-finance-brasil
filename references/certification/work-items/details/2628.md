## 📝 Descrição

## Current Behavior

When sending authorization requests to the `/par` endpoint, the scope parameter contains **duplicate consent scopes**:

`scope=openid customers consent:urn:bancodobrasil:1B127DF0B5B741889B51C4700A0873DA consent:urn:bancodobrasil:1B127DF0B5B741889B51C4700A0873DA ↑ DUPLICATED ↑`

**Observed in test logs:**

* Scope `consent:urn:bancodobrasil:1B127DF0B5B741889B51C4700A0873DA` appears **twice** in the same request
* This pattern is consistent across test executions in all three affected modules

## Affected Modules

* `customers-personal_api_wrong-permissions_test-module_v2-3`
* `customers-business_api_wrong-permissions_test-module_v2-3`
* `customers-business_api_operational-limits_test-module_v2-3`

### Comentário 5
**Autor**: Matheus Mantovani (@matheus-mantovani)
**Criado em**: 15/04/2026, 10:17:34

We reviewed the applicable specifications and repeating the same `scope-token` within the `scope` value does not constitute a protocol violation:

* **RFC 6749 §3.3** defines `scope` as a space-delimited list (`scope = scope-token *( SP scope-token )`), with no uniqueness requirement. The "parameter MUST NOT be included more than once" rule in §3.1/§3.2 applies to the parameter itself, not to tokens within its value.
* **FAPI 1.0 Advanced §5.2.3** only requires duplication of `response_type`, `client_id` and `scope` across the request object and query parameters when JAR is used without PAR. It does not address token repetition within the `scope` value.
* **OFB FAPI Security Profile v2.2.0 §7.1** defines the dynamic consent scope as `consent:{ConsentID}` and sets constraints on the ConsentID, but does not mandate uniqueness of tokens within the `scope` string.

That said, the current behaviour is still worth addressing: repeating the same `consent:{id}` inflates the `scope` claim on issued access tokens, adds noise to the logs, and may produce divergent outcomes across strict and lenient AS implementations. 

For these reasons, we classified this as an **improvement** (deduplicating `scope-token`s before building the PAR request), rather than a conformance bug.

Sources:

* [RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749)
* [FAPI 1.0 Advanced](https://openid.net/specs/openid-financial-api-part-2-1_0.html)
* [OFB FAPI Security Profile v2.2.0](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1675395089/PT+Open+Finance+Brasil+Financial-grade+API+Security+Profile+-+v2.2.0)
