## 1. What Happened and what were you expecting?

For all of the negative proxy tests that have been created the Sandbox Squad has requested us to also expect an additional failure scenario which should happen on the authorization flow/redirect. 

Those negative scenarios are based on issues on the payload sent on the payment request that can only be observed when the organization compares this against the Central Bank PIX APIs. For example, a proxy key that doesn't have the correct CPF or even a QRCode on an used state.

The negative proxy scenarios that we currently have are the following:

- payments-api-qres-wrong-amount-proxy-test
- payments-api-qres-mismatched-proxy-test
- payments-api-qrdn-with-qres-code-test
- payments-api-qrdn-good-proxy-test
- payments-api-proxy-fake-email-proxy-test
- payments-api-proxy-real-email-invalid-credior-proxy-test
- payments-api-proxy-test-incorrect-cpf


One org that is currently failing on the redirect can be seen here: https://web.conformance.directory.openbankingbrasil.org.br/log-detail.html?log=C7uKWAGqPbTGLfo&public=true

We are currently discussing what should be the expected error. Our initial assumption here is that it could be "access_denied" as specified by [rfc6749](https://datatracker.ietf.org/doc/html/rfc6749#section-4.1.2.1). We should also request an appropriate error message, that must be discussed with the specifications WG. 

We must also get OIDF opinion here if they agree with this error if we should use another or even if we should create a Brazilian-specific error code here.

I'm not sure I actually qualify as an official OIDF opinion, but here's my take:

`access_denied` is probably okay. There's potentially an argument that `invalid_request` is applicable. Ecosystems don't generally seem to define their own errors here, though I'm not sure why not (perhaps not all authorization servers allow flexibility in the returned errors, or perhaps given the availability of the error_description parameter it was felt unnecessary).

Note that it's probably implicit that if an error can be returned from the authorization endpoint, the test should also be updated to allow it to be returned from the pushed authorization endpoint request if the user has selected to run the test with PAR. (As generally servers supporting PAR are permitted to perform verification at the PAR endpoint, or to delay verification until the authorization endpoint.)

There should be examples of allowing both types of optional failure in the OIDF suite already, the general pattern can probably be reused in functional: 

 * FAPI1AdvancedFinalEnsureRequestObjectWithoutExpFails shows allowing potential rejection at the PAR endpoint 
 * FAPI1AdvancedFinalEnsureDifferentNonceInsideAndOutsideRequestObject shows allowing potential rejection from authorization endpoint

The final complication is that some servers may choose not to redirect back in the case of an error at the authorization endpoint, implying the test needs to accept a screenshot show the displayed error - FAPI1AdvancedFinalEnsureDifferentNonceInsideAndOutsideRequestObject also handles that).

If instead redirecting back is required in this case (and a screenshot isn't acceptable), the squad should make that clear.
