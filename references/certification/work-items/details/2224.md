Bom dia Eri,

Conforme retorno do GT:

* **O Cenário "Consentimento Expirado" é um Problema de Autorização:**
  * No teste "credit-portability_api_expired-consent_test-module_v1", o token em uso pode, de fato, ser sintaticamente válido e não estar "expirado" em termos de sua própria validade JWT naquele exato momento da chamada. No entanto, o **consentimento subjacente ao qual esse token está associado expirou**.
  * A especificação é clara ao afirmar que o Servidor de Autorização "só deve compartilhar o acesso aos recursos quando apresentado `access_token` vinculado a um **consentimento ativo e com o status "AUTHORIZED"**".
  * Quando o consentimento expira, a permissão para acessar os dados ou recursos através daquele token é revogada semanticamente. O token, embora possivelmente válido em sua forma, **não confere mais a autorização** necessária para a ação de portabilidade. Portanto, a negação de acesso é por falta de autorização para o recurso, não por uma falha na autenticação do token em si.
* **RFCs e FAPI Reforçam a Distinção Contextual:**
  * A **RFC 6750 (OAuth 2.0 Bearer Token Usage)** e a **RFC 7235 (HTTP/1.1: Authentication)** são os fundamentos para essa separação. O 401 é para falha de autenticação (o _quem_ você é ou a validade intrínseca do seu _crachá_). O 403 é para falha de autorização (o _que_ você pode fazer com o seu crachá, mesmo que ele seja válido, ou seja, se você tem permissão para entrar _nesta_ sala específica).
  * Os **Perfis FAPI** seguem essa diretriz rigorosamente. Eles determinam que a validação do `access_token` (autenticação) é a primeira etapa. Se o token é válido, a próxima etapa é a verificação de **autorização** (escopos, consentimento ativo, etc.). Uma falha nesta segunda etapa deve resultar em **403 Forbidden**.

  Portanto, a expectativa do teste de conformidade para um `403 Forbidden` está alinhada com as melhores práticas de segurança FAPI e com a semântica de autenticação vs. autorização no HTTP, mesmo considerando a revogação lógica dos tokens associados a um consentimento expirado.

Boa tarde prezados,

Após análise pelo Grupo de Trabalho (GT), gostaríamos de reforçar a distinção entre um erro de autenticação (que resultaria em 401 Unauthorized) e um erro de autorização (que resulta em 403 Forbidden).

**RFCs e Perfis FAPI que corroboram a distinção:**

* **RFC 6750 – OAuth 2.0 Bearer Token Usage:** Esta especificação detalha como o token deve ser transportado e validado. Ela reforça que, se o token estiver ausente, inválido (sintaticamente ou por formato) ou expirado (no sentido técnico de validade do próprio token), o recurso protegido deve retornar um **401 Unauthorized**.
* **RFC 7235 – Hypertext Transfer Protocol (HTTP/1.1): Authentication:** Esta RFC define os significados dos status de autenticação no HTTP. Ela diferencia o **401 (quando a autenticação falha ou está ausente)** do **403 (quando a autenticação foi bem-sucedida, mas o acesso ao recurso está proibido)**. Essa distinção ajuda a reforçar a ideia de separar claramente os mecanismos de autenticação (token inválido/ausente) e autorização (escopo/consentimento insuficiente).
* **Perfis FAPI (Financial-grade API):** As especificações FAPI, desenvolvidas para ambientes financeiros, adotam essa mesma separação. De acordo com as boas práticas descritas nesses perfis, o access token deve ser validado primeiro (autenticação) e, estando válido, a verificação dos escopos ou consentimentos deve ocorrer (autorização). Assim, um token inválido gera **401**, enquanto um token válido semanticamente (mas sem os escopos ou permissões necessárias) resulta em **403**.

**Reforçando o cenário específico do teste "expired-consent":**

Compreendemos o seu argumento sobre a revogação de tokens quando o consentimento expira, levando a uma requisição com token inválido e, consequentemente, a um 401. No entanto, é fundamental diferenciar o cenário de um "token inválido" (em sua estrutura ou validade técnica) do cenário específico que este teste visa validar: **a tentativa de usar um access token associado a um consentimento que está expirado (ou seja, não mais ativo/autorizado).**

O sumário do teste `credit-portability_api_expired-consent_test-module_v1` claramente define:

* "Call the POST /portabilities endpoint using token associated to the expired consent"
* "Expect **403** - Validate the response ensure"

A mesma seção da especificação que você citou (`PT Open Finance Brasil Financial-grade API Security Profile 1.0`) também afirma que o Servidor de Autorização:

* "só deve compartilhar o acesso aos recursos quando apresentado `access_token` vinculado a um consentimento ativo e com o status "AUTHORIZED"."

Neste cenário de teste específico, o access token pode ser **sintaticamente válido** e ter sua validade técnica (expiração do JWT) ainda ativa, mas ele está intrinsecamente vinculado a um consentimento que não está mais **ativo** ou **AUTHORIZED** devido à sua expiração. Portanto, o acesso ao recurso (`/portabilities`) deve ser negado com base na **autorização**.

A especificação prevê o **403 Forbidden** em situações onde:

* O cliente não tem as permissões necessárias para acessar o recurso.
* O recurso é acessado com um token válido (autenticado), mas o contexto (como o consentimento subjacente estar expirado ou inativo) não permite a operação.

A distinção é que **401 Unauthorized** é para quando o token em si está inválido ou ausente (falha de **autenticação**), enquanto **403 Forbidden** é para quando o cliente está autenticado, mas **não autorizado** a realizar a ação específica no recurso (falha de **autorização**).

No caso de um consentimento expirado, o sistema entende que o token (que representa a permissão concedida pelo consentimento) não confere mais a autorização para acessar o recurso.

Portanto, a resposta **403 Forbidden** é considerada correta e em conformidade com a especificação para este cenário de uso de um token associado a um consentimento expirado, uma vez que o token não confere mais a permissão de acesso ao recurso da API de Portabilidade, e não necessariamente porque o token é sintaticamente inválido.

Esperamos que esta explicação detalhada esclareça o comportamento esperado do teste.

Hi,

We understand your point, however there is a difference between the scenario of an "invalid token" from the specific scenario this test aims to validate: **the attempt to use an access token associated with a consent that is `expired`**.

The summary of the `credit-portability_api_expired-consent_test-module_v1` test clearly defines:

* `Call the POST /portabilities endpoint using token associated to the expired consent`
* `Expect 403 - Validate the response ensure`

The same section of the specification you cited also states that the Authorization Server:

* "**só deve compartilhar o acesso aos recursos quando apresentado access_token vinculado a um consentimento ativo e com o status "AUTHORIZED"**."

In this specific test scenario, the access token might be _syntactically valid_, but it is intrinsically linked to a consent that is no longer `active` or `AUTHORIZED` due to its expiration. Therefore, access to the resource (`/portabilities`) must be denied.

The specification provides for `403 Forbidden` in situations where:

* The client does not have the necessary permissions to access the resource.
* The resource is accessed with a valid token, but the context (such as the underlying consent being expired or inactive) does not allow the operation.

The distinction is that `401 Unauthorized` is for when the token itself is invalid or missing (authentication failure), while `403 Forbidden` is for when the client is authenticated but not _authorized_ to perform the specific action on the resource (authorization failure).

For tokens generated with the scope: `payments` or `recurring-payments`, "o status do consentimento não será validado". However, for other scopes like credit portability, the consent status **is** validated.

The specification also mentions other cases where `403 Forbidden` is expected, for example, "Em caso de reutilização \[de jti\], deverá ser retornado o código de erro HTTP 403". This reinforces that `403` is used for various authorization-related denials beyond just an invalid token format.

In the case of an expired consent, the system understands that the token (which represents the permission granted by the consent) no longer confers the authorization to access the resource.

Therefore, the `403 Forbidden` response is correct and in compliance with the specification for this scenario of using a token associated with an expired consent, as the token no longer confers the _permission_ to access the Portability API resource, and not necessarily because the token is _syntactically invalid_.
