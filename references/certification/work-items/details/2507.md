## 📝 Descrição

#### Current Behavior:

In the test resources_api_operational-limits_test-module_v3-1, my API returns a 202 response with no body and no Content-Type header. However, the test fails with the message:

```
"Resource endpoint did not declare a content type."
```

#### Expected Behavior:

According to the [specification](https://openbanking-brasil.github.io/openapi/swagger-apis/resources/3.1.0.yml), the 202ResponseResource does not state that a JSON body must be returned. Therefore, I expected a response with no body and no Content-Type header to be accepted.

Do I need to change my response, or should the test accept a response with no body and no Content-Type header?

Hi @moacir.queiroz, thanks for raising this.

You are right that, in the Resources API Specs, the 202 response does not explicitly define a response body Content-type. So returning no body and no Content-type is acceptable from that perspective.

However, the Open Finance Brasil [HTTP Headers guideline](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/17377351/Cabe+alhos+HTTP) states that **Content-Type is mandatory in response headers**, and should be application/json unless another format is explicitly supported/negotiated via Accept. Because of that requirement, the conformance test expects the Content-Type header to be present even for a 202 response.

![image.png](/uploads/c19ed57eede36b892451525a61ec9b60/image.png){width=872 height=266}

**Recommendation:** keep returning 202 with an empty body, but include:

* Content-Type: application/json

This should satisfy the test expectation and align with the OFB headers guidance.

Hi,

Thank you for reporting this behavior and for providing the detailed evidence.

We acknowledge that, according to the specification, the **202 Accepted** response for the Resources API does not explicitly require a response body nor the declaration of a `Content-Type` header when no payload is returned. We are currently reviewing the test validation logic to assess whether it is enforcing requirements beyond what is defined in the specification.

In parallel, and as a **temporary workaround to avoid blocking your conformance execution**, we recommend returning an **HTTP 200 OK** response for this endpoint, which is fully supported by the specification and accepted by the test without triggering this validation.

We will follow up once the analysis is completed and confirm whether an adjustment to the test behavior is required.
