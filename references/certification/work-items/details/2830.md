## 📝 Descrição

  O motor de certificação passou a reprovar respostas JSON de erro cujo Content-Type é application/json sem a declaração explícita de charset, mesmo quando o payload está codificado em UTF-8.

  Gostaríamos de confirmar se essa validação é realmente necessária e se deve ser aplicada globalmente a todas as respostas HTTP com status >= 400.

  #### Current Behavior:

  1. A API retorna o status esperado pelo cenário, por exemplo 403 Forbidden.
  2. A resposta contém um payload JSON válido e o header:

     Content-Type: application/json

  3. A validação de formato reconhece corretamente a resposta como JSON.
  4. Em seguida, o OpenApiValidator reprova a resposta com:

     Response content type did not declare a charset

  5. A implementação atual realiza essa validação para todas as respostas JSON com status >= 400, exigindo:

     Content-Type: application/json; charset=UTF-8

  #### Expected Behavior:

  1. Respostas com Content-Type: application/json, corretamente codificadas em UTF-8, poderiam ser aceitas sem a declaração explícita de charset.

  2. A documentação geral de cabeçalhos do Open Finance também orienta que o Content-Type da resposta seja application/json, sem mencionar a obrigatoriedade do parâmetro charset:
     https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/17377351

  4. Caso a declaração explícita seja realmente obrigatória devido às especificações OpenAPI, poderiam confirmar:
      - A validação deve ser aplicada a todas as respostas 4xx e 5xx?
      - É intencional que respostas 2xx aceitem application/json sem charset, enquanto respostas de erro não?

  #### Evidence:

  Módulo em que evidenciamos o erro:

  - accounts_api_permissions-restriction_test-module_v2-5-1

Olá, @pedro-beltrao

Essa exigência do `charset=utf-8` é normativa e vem de duas fontes que se reforçam:

* A primeira é o documento de [**Cabeçalhos HTTP**](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/17377351/Cabe+alhos+HTTP) do Open Finance Brasil (que você mesmo citou), que define o Content-Type padrão como `application/json;charset=UTF-8` e coloca o suporte a esse padrão como obrigatório.
* A segunda, e bem mais direta pro seu caso, é o próprio **Swagger da API de Contas v2.5.1**, que declara explicitamente o media type `application/json; charset=utf-8` nas respostas de erro (400, 401 e nos demais status acima de 400).

Enquanto o Swagger declarar o charset nesses status, omitir esse valor é não-conformidade, independentemente do teste.

Sobre o argumento de que o motor conseguiu decodificar o JSON e que isso "confirmaria" o UTF-8: o fato de um cliente específico ter conseguido decodificar não torna a declaração dispensável. O Open Finance é um ecossistema com vários participantes, e a receptora precisa conseguir interpretar o payload de forma inequívoca, sem depender de auto-detecção ou de heurística de cada implementação. A declaração do charset no Content-Type é o que garante essa interoperabilidade.

No ecossistema, alguma receptora pode assumir um encoding diferente e acabar corrompendo caracteres acentuados (ç, ã, é...), que são super comuns nos campos `title` e `detail` de erro em português. Por isso a validação faz sentido e deve ser mantida.

Sobre as perguntas finais:

* Sim, a validação vale pra qualquer resposta em que o Swagger declare o `charset=utf-8`, e no caso da API de Contas isso cobre os status de erro (400, 401, 403 e os demais 4xx/5xx descritos na spec com esse media type). 
* Sobre a diferença entre 2xx e erro: Se no Swagger as respostas de sucesso estão como `application/json` e as de erro como `application/json; charset=utf-8`, o teste cobra exatamente isso em cada status, sem adicionar nem remover requisito.

Ficamos à disposição.
