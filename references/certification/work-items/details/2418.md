## 📝 Descrição

### Observed behavior:

* FVP integration with PCM for Credit Portability (CPC) was developed following published PCM specifications: [PCM-v310.openapi.yaml](/uploads/8281fb9aafb9e92089b88ba9f6eff747/PCM-v310.openapi.yaml)
* The mandatory fields were implemented as per the image below.
* After first reports, PCM responded with the following error message:

  ```
  [{\"reportId\":\"266672d4-f902-42cc-be03-5b644f11ee63\",\"correlationId\":\"\",\"status\":\"DISCARDED\",\"message\":\"creationDateTime should not be empty, clientOrgId '1dbfe32a-5f1e-4841-a30c-9f1b5f24ad36' is invalid to role 'CLIENT'., Requester id mismatch with clientOrgId\"}]
  ```
* After alignment with DTO regarding issue https://gitlab.com/raidiam-conformance/open-finance/certification/-/issues/2397, all three points were fixed. However, reports sent to **/account-data** and **/cancel** endpoints were still being marked **DISCARDED** because PCM expected **`creationDateTime`** even when the Credit Portability specification did not require it. So, we suggested updating PCM’s validation to reflect the specification.

  ![image.png](/uploads/3ab2cb8dd5f36ce621a8b99769122064/image.png){width="193" height="330"}
* Until **12 November**, when PCM released a hotfix, FVP reports for Credit Portability had no further adjustments pending to be **ACCEPTED**. After this hotfix, FVP reports started being **DISCARDED** for other reasons, as described in this document: [PCM report investigation.pdf](/uploads/ef492245cee2b9b4c612f871a4ea0ed0/PCM_report_investigation.pdf)

### Expected behavior:

* Following the PCM hotfix and a new alignment with DTO/PCM teams, we concluded that:
  * `timestamp` pattern needs adjustment to follow PCM specs
  * `creationDateTime` needs a new fix to appear in reports, even if not required by PCM. Previous fix did not work as expected
  * `portabilityId` and `creditPortabilityStatus` should also be sent by FVP, even if not mandatory in PCM specs
  * "Requester id mismatch" issue needs further investigation
