Hi @gabvcampaner ,

Could you, please, provide us with some evidence to help us better understand the cited situation?

From our analyses, the test shows that at POST Consents, your implementation returned status 201. Therefore, the test follows the flow highlighted in bold below:

> Ensure that payment fails when the amount sent on the Static QR Code differs from the payload (Reference Error 2.2.2.3)
>
> * **Call POST Consent with different amount values on QRES and the payload**
> * Expects 422 - DETALHE_PAGAMENTO_INVALIDO
> * Validate Error message
> 
> If no errors are identified:
> * **Expects 201 - Validate Reponse**
> * **Redirects the user to authorize the created consent**
> * **Call GET Consent**
> * **Expects 200 - Validate if status is "AUTHORISED"**
> * **Calls the POST Payments Endpoint**
> * **Expects 422 - VALOR_INVALIDO**
> * **Validate Error message**
> 
> (...)

Finally, at POST Payments, CS receives from your implementation a 422 response with code `DETALHE_PAGAMENTO_INVALIDO` and not 422 `VALOR_INVALIDO`, which is what the test expects at this point. It follows evidence below:

Hi,

Thanks for the ticket and your patience! 

The test failed because the implementation wrongly sends the code `DETALHE_PAGAMENTO_INVALIDO` where it is expected the code `VALOR_INVALIDO`. Note that the code `DETALHE_PAGAMENTO_INVALIDO` is expected to be returned at the initial POST Consents call. In case it does not happen and the test succeeds with a 201 response at the initial POST Consents call, then the test is expected to fail at POST Payments call with the 422 code `VALOR_INVALIDO`.

Therefore, there is no corrections on the CS side. To a successful execution, the implementation needs to be adapted so that it is conformant to the specifications and therefore with the test summary.

Feel free to open another ticket if you get any other issue! Happy to help!
