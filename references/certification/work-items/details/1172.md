## 📝 Descrição


Hello, we are facing an issue and believe it to be a problem with understanding the specification.

During a test, we encountered the following error:

The response from the token endpoint does not have a scope field.

However, upon checking the specification, the following excerpt is noted:

> The authorization server MAY fully or partially ignore the scope requested by the client, based on the authorization server policy or the resource owner's instructions. **If the issued access token scope is different from the one requested by the client, the authorization server MUST include the "scope" response parameter to inform the client of the actual scope granted.**

https://datatracker.ietf.org/doc/html/rfc6749#section-3.3

We would like to understand if the scope field is mandatory in the response, or only in the mentioned case.

Hi Jorge!

Here is the complete response to the question you mentioned:

For the payments, the client credentials token should only have the "payments" scope, as described in the spec:

![image.png](/uploads/09324c4aa285c1d87951b4f189d097ad/image.png)

Besides that, following what is defined at [Open ID Connect](https://openid.net/specs/openid-connect-core-1_0.html#TokenRequest), the token request for an id_token, in which the scope openid is defined:

`A Client makes a Token Request by presenting its Authorization Grant (in the form of an Authorization Code) to the Token Endpoint using the grant_type value authorization_code`

In that sense, the openId scope is unknown fhere both because the scope being presented is "payments", but also that this is a client_credentials grant.

Additionally, as discussed at [Informa 218](https://mailchi.mp/18107e66cfae/open-banking-informa-9162397?e=9b9743fbe2), which was released when this test was released, it is stated that the unknown scopes should be ignored, as its the case here.

In that sense, on the test above mentioned, what is being tested is that when a token endpoint is called with additional scope, as "openid" in this case, it will:

1. Adjust the scope to what is expected for the request, ignoring the scope "openid" in this case
2. Return the "scope" parameter, since it was changed from the request (openid scope ignored)
   1. Reference [RFC](https://datatracker.ietf.org/doc/html/rfc6749#section-3.3): "If the issued access token scope is different from the one requested by the client, **the authorization server MUST include the "scope" response parameter to inform the client of the actual scope granted"**

This test was developed based on a request from the Security WG and has been validated since Payments V2, and the item mentioned should be applied both to the Payments and Customer Data Consents.

Other discussion on this topic can be found here: https://gitlab.com/raidiam-conformance/open-finance/certification/-/issues/548#note_1227035903

So, to address the question you initially asked:

**Q**: We would like to understand if the scope field is mandatory in the response, or only in the mentioned case.

**A:** The scope parameter should be sent every time the token issue has a scope different from the one requested.

We will close this issue, but feel free to reopen if the question remains.

We are happy to help with any additional needs!

hi,
I have two issues with the item mentioned. 
1. The item clearly mentions the consents resources, and thus should only be applied to the consents resources. The payments consent doesn't even have the permission object.
2. Even if it does also apply to the payment consent, the phrasing "shall ensure" should not be understood as "shall return" (as seen in item 8). Since it does not specify what should be returned, the understanding from https://datatracker.ietf.org/doc/html/rfc6749#section-3.3 should still hold.

Hi Jorge! Thanks for the ticket!

As available at the [security specs](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/245760001/EN+Open+Finance+Brasil+Financial-grade+API+Security+Profile+1.0+Implementers+Draft+3#7.2.2.-Authorization-server),  the authorization servers:

4. shall ensure access tokens are issued with sufficient scope necessary for access to data specified in the Permission element of a linked Consent Resource object;

In that sense, for Open Finance Brazil, the scope should always be present at the response.
