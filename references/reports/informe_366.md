# [Open Finance] Informa #366

*Go live* das APIs de Dados Abertos – fase 4A 1ª onda (investimentos, câmbio e credenciamento)            O ***go live* das APIs de Dados Abertos – fase 4A 1ª onda (investimentos, câmbio e credenciamento) será em 30/04/2023,** seguindo o cronograma da IN 357 divulgado no Informa #331 [“Importante: datas para sucesso nos testes beta do motor de conformidade de dados abertos (APIs de Investimentos, Câmbio e Credenciamento)”, enviado em 02/03/2023].     Essas APIs terão **certificação automatizada** no Diretório, ou seja, os testes serão executados automaticamente **no momento da publicação da API**. Caso a API esteja conforme, a publicação será feita com sucesso. Caso algum problema seja encontrado, este será notificado e a publicação não será efetivada. Portanto, não será necessária a submissão de pedidos de certificação através de tickets no service desk. Maiores informações estão no Guia Operacional do Diretório (páginas 75 a 80).     O Diretório de Sandbox já possui essa funcionalidade e as instituições podem utilizá-lo para testes. Por sua vez, a atualização dessa **funcionalidade estará disponível no Diretório de Produção até 28/04/2023 e as instituições terão até o 30/04/2023 para publicar as devidas APIs**. |

 Cronograma das APIs de Capitalização, Previdência e Seguros Pessoais da fase 4A (dados abertos)        O cronograma dos marcos de sucesso para as APIs de Capitalização, Previdência e Seguros Pessoais da fase 4A (dados abertos), aprovado na 156ª reunião do Conselho Deliberativo, é:  - **Marco de 25% de sucesso: 02/05/2023** - **Marco de 50% de sucesso: 18/05/2023** - **Marco de 75% de sucesso: 30/05/2023** - **Marco de 100% de sucesso: 14/06/2023** - **Publicação no Diretório: 14 a 16/02/2023** - **Go live: 16/06/2023**  A certificação das APIs de dados abertos será realizada de maneira automatizada no momento da publicação no diretório, conforme Guia Operacional do Diretório (páginas 75 a 80). Para a realização dos testes, poderá ser utilizado tanto o motor de conformidade quanto o Diretório de Sandbox.     O cálculo da porcentagem está sendo feito baseado no total de endpoints que a instituição disponibilizará para a primeira onda da fase 4A e os respectivos sucessos, arredondando para baixo. |

 ¹ Para os casos em que a quantidade de endpoints esperada para o marco for zero, é esperado que a instituição esteja executando os testes, mesmo sem ter obtido sucesso ainda.     Problemas ou inconsistências identificadas devem ser notificadas através do repositório no GitLab no link abaixo. Tickets abertos através da plataforma do Service Desk continuarão sendo tratados. |

 Consulta ao ecossistema sobre sugestões de melhoria para o tema Qualidade de Dados        O Squad Qualidade de Dados solicita o apoio das instituições para a identificação de problemas de qualidade de dados para APIs de Fase 2 (dados do cliente). Para tanto, será disponibilizado um período de 7 dias de consulta ao ecossistema para que as casas identifiquem problemas e enviem sugestões de melhoria. Tais contribuições devem ter ênfase na Fase 2.  O período de coleta de sugestões de melhorias iniciar-se-á em 25/04/2023 e encerrar-se-á em 02/05/2023, de modo que sugestões encaminhadas fora desse período não serão consideradas.     Recomendamos que a consulta seja encaminhada para desenvolvedores e analistas de dados.    Toda solicitação de melhoria deve ser registrada no [Service Desk](https://servicedesk.openbankingbrasil.org.br) via abertura de um ticket, por meio da opção Solicitações de melhorias > APIs.  Na abertura do ticket, o título deve ser registrado como “Squad Qualidade de Dados - Consulta” e na descrição devem ser citados, respectivamente, API, endpoint, campo e indicação do problema, para que o ticket possa ser considerado. Para casos nos quais já houver ticket bilateral com o problema relatado, solicita-se que o número do ticket seja informado.     Exemplo de problema da fase 2:  - Recorrência de envio de valores dummy para campos obrigatórios     API: financings  Endpoint: contracts  Campo: contractDate  Recorrência de envio de valores dummy (0000-01-01) para atributos obrigatórios, como data de contratação (contractDate) de uma operação de financiamento, que sempre deveria existir.     Os problemas devem ser classificados de acordo com a lista abaixo:​  - Uso de domínios incorretos​ - Ordem de grandeza inconsistente (precisão)​ - Campo com conteúdo não passível de interpretação​ - Tempestividade de dados em não conformidade com requisitos - Categorização incorreta de tipo de transação​ - Ausência de informação​ - Valor do preenchimento correto, porém não permitido pela expressão regular - Valor do preenchimento incorreto, frente a pela expressão regular - Nome incorreto do atributo e/ou atributo inexistente - Envio de objetos duplicados - Outros |
