# [Open Banking] Informa #114

Fase 3 – Tratativa de erros de validação do QR Code em cenários assíncronos Em retificação e complemento ao Informe #94 esclarecemos a respeito da Tratativa de erros de validação do QR Code em cenários assíncrono     Para a iniciação de pagamentos no arranjo PIX (Escopo Fase 3), detalha-se a seguir o comportamento da validação do QR Code do arranjo:   - A validação do QR Code no Arranjo PIX pela detentora de conta é obrigatória quando o *localInstrument*for igual a QRDN ou QRES. No entanto, ela possui flexibilidade para escolher em que momento a validação deverá ser executada:    1. Um dos cenários possíveis é que a **validação** ocorra **anteriormente a autorização do consentimento pelo usuário.** Neste caso, o comportamento esperado é:   - Caso a validação seja aplicada de forma **síncrona** na API DE POST/CONSENTS       - A API deverá retornar o erro HTTP 422, código retornado DETALHE\_PGTO\_INVALIDO.     - Observamos que neste caso o consentimento não é criado.     - Observamos que neste caso o pagamento não é criado.   - Caso a validação seja aplicada de forma **assíncrona** e ocorra durante a jornada de autenticação e autorização no ambiente da detentora de conta prévio a autorização do consentimento (Fluxo FAPI).      - Caso a detentora observe que o QR Code apresente algum erro (QR Code inválido, QR Code expirado, entre outros) durante esta jornada, observamos que o consentimento associado ao pagamento deverá ter seu status alterado para REJECTED e a jornada interrompida com a correta notificação ao usuário e retorno ao ambiente da iniciadora.     - Observamos que neste caso o pagamento não é criado.   2. Outro cenário possível é que a **validação** ocorra **posteriormente a autorização do consentimento pelo usuário.** Neste caso, o comportamento esperado é:   - Caso a validação seja aplicada de forma **síncrona** na API DE POST/PAYMENTS.       - A API deverá retornar o erro HTTP 422, código retornado COBRANCA\_INVALIDA.                Observamos que neste caso o consentimento associado ao pagamento irá para o status CONSUMED e o pagamento não será criado.   - Caso a validação seja aplicada de forma assíncrona o comportamento espero é que:      - A API POST/PAYMENTS deverá seguir seu fluxo padrão retornando HTTP 201     - A API DE GET/PAYMENTS (após eventual validação e erro no QRCode) deve prever o erro de validação                A API deverá retornar HTTP 200, informando o Status RJCT e o rejectionReason ELEMENT\_CONTENT\_FORMALLY\_INCORRECT - Elemento da mensagem incorreto (CH16). observamos que o consentimento associado ao pagamento deverá ser mantido como CONSUMED, pois este erro caracteriza um pagamento mal sucedido como qualquer outro erro encontrado nesta etapa do processo.  - Comportamento do motor de teste:        Observação: O motor de conformidade está sendo ajustado para atender ao comportamento descrito e será notificado as instituições assim que o mesmo estiver disponível. As instituições que já estão certificadas não serão afetadas e as certificações emitidas continuarão válidas.        Tempo de *pooling:* 30 segundos com tempo máximo de 5 minutos   Além disso, o tema será **incluído na planilha de problemas conhecidos Fase 3, com o código** **BCLOG-FO3-012****.** |
