# [Open Finance] Informa #273

Atualização das planilhas de problemas conhecidos das versões 1.x das fases 2 e 3  Com a publicação da IN n° 306 do DENOR/DEINF em 19/09/2022 e a definição de novo limite global para requisições simultâneas por segundo (TPS), o Banco Central reforçou a necessidade de adequação das APIs v1.x de Dados Cadastrais e Transacionais, de Iniciação de Pagamentos, bem como das APIs de Dados Abertos para a correta contabilização de acordo com as regras definidas.    De acordo com a orientação do DENOR/DEINF, não haverá contabilização de limites operacionais e os erros de TPM serão contabilizados conforme a IN nº 130 para as APIs que se encontram na versão citada no parágrafo acima.    **Para sincronizar a entrada em produção dos limites TPS entre as intuições do ecossistema e reduzir ao máximo impactos, a data de implementação deverá ser no dia 15/12/2022 às 00:00h para as instituições transmissoras/detentoras e receptoras/ITPs.**    Os Grupos Técnicos de Especificações Dados do cliente, Serviços e Dados abertos comunicam que foram incluídos itens às planilhas de problemas conhecidos das fases 2 e 3, conforme segue:   - **Planilha de problemas conhecidos da fase 2, versão 1.x**   - **BCLOG-F02-224**   - **API/Sessão:** Todas da fase 2   - **Endpoints:** Todos da fase 2   - **Campo:** Não se aplica, pois a alteração foi realizada no HTTP status code   - **Qual o problema:** A IN 306 orienta a contabilização global de limites de TPS pela transmissora. Atualmente o status code 429 pode ser utilizado tanto para identificar estouro de TPM quanto TPS, inviabilizando a diferenciação de estouro de TPS para contabilização global   - **Como deveria ser:** Deveríamos ter status code diferentes para mapear estouro de TPS e TPM   - **Orientação:** Utilização do status code 529 pela transmissora para identificação de estouro de TPS e utilização exclusiva do status code 429 para estouro de TPM - **Planilha de problemas conhecidos da fase 3, versão 1.x**   - **BCLOG-F03-018**   - **API/Sessão:** API Payments   - **Endpoints:** Todos   - **Campos:** Não se aplica, pois a alteração foi realizada no HTTP status code   - **Qual o problema:** A IN 306 orienta a contabilização global de limites de TPS pela transmissora. Atualmente o status code 429 pode ser utilizado tanto para identificar estouro de TPM quanto TPS, inviabilizando a diferenciação de estouro de TPS para contabilização global   - **Como deveria ser:** Deveríamos ter status code diferentes para mapear estouro de TPS e TPM   - **Orientação:** Utilização do status code 529 pelas detentoras de conta para identificação do estouro de TPS e utilização exclusiva do status code 429 para estouro de TPM |
