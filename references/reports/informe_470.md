# [Open Finance] Informa #470

Publicação da v3.0.0 da API de Pagamentos Comunicamos que as instituições detentoras de conta deverão realizar o *deploy* e publicar a v3.0.0 da API de Pagamentos no Diretório até às 23h59 de 13/10/2023 – **data** **do *go-live***, informando o link da sua certificação.     A v2.0.0 deverá continuar disponível até o término do período de convivência, 15/12/2023 às 23h59. Informações sobre a retrocompatibilidade entre as versões 2.0.0 e 3.0.0 da API de Pagamentos podem ser consultadas no informa #445.     As instituições iniciadoras de pagamento deverão realizar os ajustes necessários para utilizar a v3.0.0 da API de Pagamentos até o final do período de convivência, em 19/11/2023. Recomendamos que essa transição seja realizada o mais breve possível.     O cronograma completo foi divulgado na IN 403 e também pode ser conferido no Informa #464 “Atualização do cronograma da API de Pagamentos – v3.0.0”. |

 PCM: novos endpoints da API Pagamentos v3 Informamos que a PCM já está apta a receber reportes relativos à versão 3 das APIs de Pagamento conforme a documentação do endpoint de reporte em <[Tabela de endpoints](https://bra01.safelinks.protection.outlook.com/?url=https%3A%2F%2Fopenfinancebrasil.atlassian.net%2Fwiki%2Fdownload%2Fattachments%2F37879861%2FTabela%2520additionalInfo%2520%25E2%2580%2593%2520campos%2520contexto%2520e%2520obrigatoriedade%2520(cliente%2520server)v12__20231004134608.xlsx%3Fapi%3Dv2&data=05%7C01%7Csecretariado%40openfinancebrasil.org.br%7C9001e181da0d4997364508dbca7edca9%7C7531e8b3c928494b9b897ee3d353272d%7C0%7C0%7C638326418443377345%7CUnknown%7CTWFpbGZsb3d8eyJWIjoiMC4wLjAwMDAiLCJQIjoiV2luMzIiLCJBTiI6Ik1haWwiLCJXVCI6Mn0%3D%7C3000%7C%7C%7C&sdata=Du7epo04Fkb%2FEcKq0Eh2VGsaXYV35noeYx2mMIsng58%3D&reserved=0)>.    Alertamos que o acionamento da v3, além do novo enum de endpoints, demandará mudanças no preenchimento do campo additionalInfo do reporte:   1. Inclusão dos subcampos “rejectionReasonCode” e “rejectionReasonDetail” que deverão ser preenchidos com as mesmas strings obtidas em ".data.rejectionReason.code“ e ".data.rejectionReason.detail“ do response 2. Inclusão do subcampo “webhookInteractionId”, que deverá ser preenchido com este id caso o GET esteja sendo feito devido a um estímulo do webhook 3. Inclusão do subcampo “authorisationFlow” deve ser preenchido com a mesma string obtida no ".data.authorisationFlow“ no response do POST /open-banking/payments/v3/pix/payments.” |

 Atualização recente na documentação de Dynamic Client Registration (DCR) Informamos que foi adicionada nova condição à documentação de Dynamic Client Registration (DCR) para atender ao novo perfil único FAPI:    *"7. não deve rotacionar o registration\_access\_token"*    Ademais, foram incluídos novos escopos permitidos na tabela da seção 7.2 para adequar a documentação às especificações da API de Pagamentos automáticos e API de Investimentos. Esta alteração não impacta o novo perfil único FAPI 1.0. |
