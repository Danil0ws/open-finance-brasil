# [Open Finance] Informa #467

Lançamento da versão beta.2 das especificações de renovação de consentimento simplificada     Informamos que, em 06/10/2023, foi publicada a versão beta.2 das especificações de renovação de consentimento simplificada, as quais estão disponíveis na Área do Desenvolvedor em:   - Especificações de APIs > Dados Cadastrais e Transacionais > API Consentimento > v2.2.0-beta.2 – Consentimento > Informações Técnicas – Consentimento – v2.2.0-beta.2.    As alterações realizadas da versão beta.1 para beta.2 foram:  - Ajustes nas definições de segurança dos novos *endpoints* para renovação de consentimentos autorizados sem redirecionamento; - Ajustes no media type do status code 422; - Inclusão dos novos *endpoints* para renovação de consentimentos na página de Informações Gerais; - Inclusão de orientações importantes para esclarecer as regras para renovação de consentimentos autorizados sem redirecionamento; - Inclusão de nova situação de erro padrão status code 422 para os novos *endpoints*.    Além disso, destacamos que:  - As alterações citadas acima não impactam nos 6 módulos de testes disponibilizados pelo Squad Sandbox na data de hoje (06/10/2023); - Esse lançamento não se aplica à criação de novos consentimentos com prazo indeterminado e aos consentimentos de múltiplas alçadas.   As informações necessárias para a abertura de tickets com dúvidas ou sugestões de melhorias mantém-se as mesmas das divulgadas anteriormente através do Informa #456 (“Divulgação cronograma de renovação simplificada de consentimento e revisão do cronograma minor da fase 2”, publicado em 19/09/2023). |

 Requisitos para o *go-live* de novos produtos        Gostaríamos de elucidar alguns requisitos necessários para um go live de sucesso de novos produtos.     Além da obtenção da certificação funcional e a publicação da API com a declaração dos endpoints e a sua disponibilização para o ecossistema, algumas ações adicionais são necessárias para garantir o correto funcionamento do ecossistema e evitar problemas de interoperabilidade. Para cada papel, as instituições devem:     **Transmissor/Detentor de conta**   - Alterar Authorization Server para reconhecer os escopos do novo produto; - Alterar conteúdo da url de well-known para indicar os novos escopos; - Cadastrar novas famílias de APIs e seus endpoints no Diretório  **Receptores/Iniciadores de pagamento:**  - Registro do Software Cliente (clientId):           - Realizar o processo de DCM com as instituições transmissoras atualizando a lista de escopos incluindo os definidos para o novo produto; |
